# Questions for SumUp before we build the card-reader integration (2026-09-08)

**Status: SENT to SumUp 2026-09-08; awaiting reply.** The card-reader build (Track H) does not start until the answers land — question 4 (does the reader work offline once paired) is design-invalidating.

Context to give SumUp: we are building a restaurant point-of-sale for Spain. We want to drive a
SumUp card reader (Solo, or whichever model you recommend for a counter) from our own software using
the Cloud API for reader checkouts. The venue must be able to keep taking card payments when the
internet is down. The four questions below decide the design, so we need answers before we start.
Our own notes on what is verified and what is not are in
`docs/superpowers/specs/2026-07-30-sumup-card-present-provider-design.md` §7.

## 1. Does the reader still work on its own after it is paired to the Cloud API?

Once a reader is paired to a merchant's Cloud API integration, can staff still take a payment
directly on the reader, without our software and without an internet connection, using the reader's
own standalone mode? Or does pairing disable standalone use, the way some other vendors do?

Why we ask: our outage plan is "if the internet drops, take the card on the reader directly and
record it in the till as a manual card payment". If pairing turns standalone mode off, that plan does
not work and we need a different reader for the fallback.

## 2. Can we supply our own transaction reference when we start a checkout?

When our software starts a reader checkout through the API, can we send our own reference (the
`client_transaction_id`), so that if our request times out and we retry, SumUp recognises the
retry as the same payment rather than charging the customer twice? Or is that id only generated by
SumUp and returned to us?

Why we ask: a till on a flaky network will retry. We need retries to be safe by design, not by luck.

## 3. Are reader-checkout webhooks signed the same way as online-payment webhooks?

Your online-payments documentation describes HMAC-SHA-256 signed webhooks with retries. The
terminal-payments webhook page is not available. Do reader (in-person) checkout events arrive as
signed webhooks with the same signature scheme, retry policy and event shape? If they are not
signed, what is the recommended way to verify they came from SumUp?

Why we ask: we refuse any webhook we cannot verify. If reader events are unsigned we will poll
instead, which changes how quickly the till learns a payment succeeded.

## 4. How do we cancel or reverse a reader payment?

If a reader payment completes but the sale is then cancelled at the till, what is the correct API
call: a void, a refund against the transaction, or something specific to reader checkouts? Is a
same-day reversal treated differently from a later refund, in fees or in what the customer sees?

Why we ask: our design currently maps "void" onto the refund endpoint, which we have not been able
to confirm.

## Two smaller questions, if easy to answer

- Which reader model do you recommend for a fixed counter position with a receipt printer nearby,
  and which for a waiter carrying it to tables? Do both support the Cloud API the same way?
- Does SumUp support Bizum in-person payments on the reader (tap or QR)? Our reading of the public
  documentation is that it does not.

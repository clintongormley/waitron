# SumUp Solo experiments — answering the four questions with the reader in hand

**Date written:** 2026-09-10. **Runs from:** 2026-09-11.
**Status:** IN PROGRESS (2026-09-11). Setup 0.2–0.6 are run and recorded below: the Solo is paired
(`rdr_19F1G0V4JF98NBRQDARRW2293X`) and the healthy path works end to end. Experiment 1 onwards —
starting with the design-invalidating standalone question — is still empty. Each experiment has a _Result_ block to
fill in as it is run.

The four questions in [2026-09-08-sumup-questions.md](2026-09-08-sumup-questions.md) went to SumUp on
2026-09-08 and have had no reply. The owner now has a SumUp Solo, so the gate on the card-reader
build (backlog Track H item 4) changes from "wait for the answers" to "run these experiments and
record what happened". Three of the four questions are settled by the device; the fourth is settled
well enough to design against.

The house rule applies harder here than anywhere: **state the experiment, not the conclusion**
(CLAUDE.md §1). Every experiment below says what the FAILING case prints _before_ it is run, so a
result that looks the same either way is recognised as measuring nothing. When you write the
_Result_, copy the actual output; do not paraphrase it into the answer you hoped for.

What goes back into the code afterwards: the provider spec's §7 list
([2026-07-30-sumup-card-present-provider-design.md](../superpowers/specs/2026-07-30-sumup-card-present-provider-design.md))
gets one dated line per item, quoting the _Result_ here. The spec is not rewritten; it records what
was true when written, and this file is the receipt.

**What changed in SumUp's documentation since the spec was written (2026-07-30 → 2026-09-10).**
Preparing this runbook meant re-reading the docs, and SumUp's published OpenAPI file (see
Provenance) describes more than the web pages do. Four differences matter to the experiments:

- The refund endpoint is now `POST /v1.0/merchants/{merchant_code}/payments/{transaction_id}/refunds`;
  the spec's `/v0.1/me/refund/{txn_id}` is the old path. `GET /v0.1/me` is likewise gone from the
  OpenAPI file; the merchant code comes from `GET /v0.1/memberships`.
- A reader now has a **status endpoint** (`GET …/readers/{reader_id}/status`) reporting `ONLINE` /
  `OFFLINE`, the screen state (`IDLE`, `WAITING_FOR_CARD`, …) and the **connection type**
  (`Wi-Fi`, `lte`, `umts`, `gprs`, …). That is an objective probe for the standalone experiments.
- A reader checkout can be **read back by id** (`GET …/readers/{reader_id}/checkout/{checkout_id}`)
  with a `status` of `pending` / `successful` / `failed` / `cancelled`, so the adapter has two
  polling routes, not one.
- The reader-checkout webhook payload is documented: `event_type` `solo.transaction.updated`,
  `payload.client_transaction_id`, `payload.merchant_code`, `payload.status` (`successful` /
  `failed`). Three retry policies are now in print — nine with backoff (the July read), four fixed
  intervals (the webhooks page today), "up to 5 times with exponential backoff" (the OpenAPI
  callback) — and none of the three sources describes a signature. Experiment 3 measures it.

## 0. Setup (once, ~20 minutes)

### 0.1 What you need

- The SumUp merchant login used to buy the Solo.
- The Solo, charged, on the same Wi-Fi as your laptop for the healthy-path runs. Its firmware
  version matters: SumUp's OpenAPI file requires 3.3.24.3 or later for checkouts, 3.3.28.0 for
  terminate and 3.3.39.0 for the status endpoint. Let it update before starting (Settings on the
  reader) and write the version down; 0.5's `rstatus` helper reports it too.
- A card of your own. Every successful payment is real money and costs the real fee. Budget six
  payments of €1 (SumUp's minimum is €1 in Spain; confirm on the first attempt) and expect all but
  one to be refunded by the end.
- `curl`, `jq`, and a tunnel tool for the webhook experiment. `cloudflared` gives a throwaway public
  HTTPS URL with no account: `brew install cloudflared`.

### 0.2 Credentials — keep them out of the repo

Create an API key in the SumUp dashboard: **Settings → For Developers → Toolkit → API Keys →
Create**. SumUp shows the key once and does not store it. Put it in a file OUTSIDE the repo:

```bash
mkdir -p ~/.sumup-experiments
cat > ~/.sumup-experiments/env <<'EOF'
export SUMUP_API_KEY='...paste...'
export SUMUP_MERCHANT_CODE='...'   # filled in by 0.3
export SUMUP_API=https://api.sumup.com
EOF
chmod 600 ~/.sumup-experiments/env
source ~/.sumup-experiments/env
```

An API key "grants broad access to the merchant account" (SumUp's words). Revoke it in the same
dashboard page when the experiments are done; the provider build will mint its own and seal it
through the credentials CLI.

While you are in the developer portal, also create an **affiliate key** (the portal's _Affiliate
Keys_ page; the OpenAPI file says the `app_id` and `key` "should be generated by the integrator"
there). Experiment 2 needs both values. Add them to the env file as `SUMUP_AFFILIATE_APP_ID` and
`SUMUP_AFFILIATE_KEY`. If the page does not exist or the key cannot be created, record that in 2a's
result; it is itself an answer.

### 0.3 Find the merchant code

```bash
curl -s "$SUMUP_API/v0.1/memberships" -H "Authorization: Bearer $SUMUP_API_KEY" \
  | jq '.items[] | {merchant_code: .resource_id, type, name: .resource.name, roles}'
```

The `merchant_code` is the `resource_id` of the merchant membership (example shape in the docs:
`M2DDT39A`). It is also printed in the SumUp dashboard under the account details, which is a
useful cross-check. Paste it into the env file and re-source it. If this call returns `401`, the
key is wrong and nothing below will work; stop here.

**Result (0.3, run 2026-09-11):** `HTTP 200`. One membership:
`{"merchant_code":"MY2NPHDW","type":"merchant","name":"Test restaurant","roles":["role_admin","role_owner"]}`.

Two baselines taken before pairing, both with the key from 0.2:

- `GET /v0.1/merchants/MY2NPHDW/readers` → `HTTP 200 {"items":[]}`. No reader is paired to this
  account, so 0.4 starts from nothing and the post-pairing list must hold exactly one item.
- `GET /v2.1/merchants/MY2NPHDW/transactions/history?limit=1` → `HTTP 200 {"items":[]}`. The account
  has taken no payments, so the first `SUCCESSFUL` row anywhere in 4c's report is 0.6's.

**Does the key carry reader scope?** Worth settling before the five-minute pairing window is
running. Reader ids are exactly 30 characters and the endpoint validates that BEFORE it
authorizes, so the first two attempts measured nothing: `rdr_BOGUS` and a 32-character id both
returned `HTTP 400 request validation failed` (`minLength: got 9, want 30`, then
`maxLength: got 32, want 30`) — the same 400 an unauthorized key would have produced. With an
exactly-30-character absent id the answer separates, and a wrong-key control proves the two
outcomes differ:

```
good key, absent reader  HTTP 404  {"detail":"Reader not found"}
bad  key, absent reader  HTTP 401  {"detail":"Unauthorized."}
```

### 0.5 Helpers used below

```bash
# Start a €1 checkout on the paired reader. Extra JSON fields are merged in from $1.
checkout() {
  local extra="$1"; [ -z "$extra" ] && extra='{}'
  curl -s -w '\nHTTP %{http_code}\n' -X POST \
    "$SUMUP_API/v0.1/merchants/$SUMUP_MERCHANT_CODE/readers/$SUMUP_READER_ID/checkout" \
    -H "Authorization: Bearer $SUMUP_API_KEY" -H "Content-Type: application/json" \
    -d "$(jq -n --argjson extra "$extra" '{total_amount:{currency:"EUR",minor_unit:2,value:100},description:"waitron experiment"} + $extra')"
}
# Look a transaction up by whichever key you have: tx client_transaction_id=… | foreign_transaction_id=… | id=…
tx() {
  curl -s "$SUMUP_API/v2.1/merchants/$SUMUP_MERCHANT_CODE/transactions?$1" \
    -H "Authorization: Bearer $SUMUP_API_KEY" | jq '{id, transaction_code, status, amount, timestamp, events}'
}
# Read a checkout back by its checkout_id (the second polling route).
ck() {
  curl -s "$SUMUP_API/v0.1/merchants/$SUMUP_MERCHANT_CODE/readers/$SUMUP_READER_ID/checkout/$1" \
    -H "Authorization: Bearer $SUMUP_API_KEY" | jq '.data | {status, payment_status, payment_failure_reason, client_transaction_id, valid_until, updated_at}'
}
# The reader's own view of itself: online?, on what connection?, what screen?, firmware.
rstatus() {
  curl -s "$SUMUP_API/v0.1/merchants/$SUMUP_MERCHANT_CODE/readers/$SUMUP_READER_ID/status" \
    -H "Authorization: Bearer $SUMUP_API_KEY" | jq .data
}
```

Every `checkout` call prints the HTTP status on its last line. Keep the whole output; the response
body's `data` carries `checkout_id` and `client_transaction_id`, which the later steps need.

Run `rstatus` once now and paste it below. It is the baseline every later `rstatus` is compared to
(expected: `status: ONLINE`, `connection_type: Wi-Fi`, `state: IDLE`, and the firmware version).

## 1. Does standalone use survive pairing? (the design-invalidating question)

This decides whether the deli's outage plan is real: "internet down → take the card on the reader
directly → record a manual card tender in the till"
([deli hardware design §5](../superpowers/specs/2026-07-30-deli-hardware-design.md)). Two things
could break it. Pairing might disable the reader's own payment screen. Or logging back in as the
merchant, which standalone use needs, might undo the pairing. Each is one sub-experiment.

### 1a. Can the merchant log back in, and does the pairing survive?

On the reader, log in with the merchant account. Then:

```bash
curl -s "$SUMUP_API/v0.1/merchants/$SUMUP_MERCHANT_CODE/readers/$SUMUP_READER_ID" \
  -H "Authorization: Bearer $SUMUP_API_KEY" | jq .status
rstatus
checkout
```

**Failing case looks like:** the reader refuses the login while paired, or the pairing status flips
from `paired` to `expired`/`unknown`, or `rstatus` reports `OFFLINE`, or the checkout returns a
non-2xx status or never reaches the screen. Any of those means pairing and standalone use are
mutually exclusive on this firmware.

Cancel the checkout on the reader's screen rather than paying (keep the money for the later runs).

**Result (1a, run 2026-09-11): pairing and standalone use are MUTUALLY EXCLUSIVE on firmware
3.3.42.2.** The experiment could not even be run as written, because the login it starts with is not
offered:

- **There is no log-in option anywhere on the reader while it is paired.** The failing case this
  experiment predicted was "the reader refuses the login"; what actually happens is that the reader
  never offers one.
- **The paired home screen shows only the SumUp logo.** No amount entry, no charge screen — so the
  device cannot take a payment of its own while paired, independently of the login question. This is
  the observation that settles the design question; "no login" alone would not have.
- **The cloud side stays healthy throughout.** Immediately after the failed attempt the reader still
  read `status: "paired"` and `ONLINE / IDLE / Wi-Fi`, so nothing about this is a fault or a dropped
  pairing.
- **It is recoverable, but only by unpairing.** The device offers
  **Connections → Cloud API → Disconnect**. SumUp documents the full undo as two steps — delete the
  reader through the Readers API, then disconnect manually on the Solo — so a reader is either an
  API terminal or a standalone terminal, switched by hand at the counter, never both at once.

**Owner decision, 2026-09-11: accepted, and the outage design changes rather than the reader.** The
bar keeps a separate standalone POS machine for the internet-down case instead of switching the
paired Solo back and forth. The deli-hardware outage path is updated accordingly
([deli hardware design §5](../superpowers/specs/2026-07-30-deli-hardware-design.md)); 1b and 1c below
are no longer gating anything, though 1c is still worth running for a different reason (it tells us
whether the reader needs the venue's Wi-Fi at all, or can live on its own SIM).

Not measured, and worth stating so nobody assumes it: whether re-pairing after a disconnect issues a
NEW reader id. If it does, every switch invalidates the `WAITRON_TILL_SUMUP_READER_ID` stamped into
the till, which is an argument for the pairing UI rather than an env var.

## 2. Can we supply our own reference, and does SumUp deduplicate on it?

SumUp's create-checkout body has no `client_transaction_id` field; that id is returned, not
supplied. What it does accept is `affiliate.foreign_transaction_id` — "a unique identifier for the
transaction. It can be used later to fetch the transaction details via the Transactions API" — and
the retrieve endpoint looks transactions up by it. The `affiliate` block requires `app_id` and
`key` from the developer portal (0.2). So the question splits in two.

### 2a. Does our own key let us find the transaction before we ever stored SumUp's id?

This closes the crash window in the provider spec §7 item 1: if we can look up by OUR key, the
adapter never has to persist SumUp's id before it can poll.

```bash
KEY=$(uuidgen | tr A-F a-f)
checkout "{\"affiliate\":{\"app_id\":\"$SUMUP_AFFILIATE_APP_ID\",\"key\":\"$SUMUP_AFFILIATE_KEY\",\"foreign_transaction_id\":\"$KEY\"}}"
tx foreign_transaction_id=$KEY          # BEFORE tapping: does the PENDING row exist under our key?
```

Then tap, and run the same `tx` again.

**Failing case looks like:** the create call rejects the `affiliate` block (record the exact error
body), or the lookup returns nothing until after the payment completes. A rejection because the
affiliate key is wrong is a setup problem, not a finding; fix 0.2 and rerun.

**Result (2a):**

```
(paste: create HTTP status + error if any; tx output before tap; tx output after tap)
```

### 2b. Is a second checkout with the same key refused?

Immediately after 2a's payment has completed:

```bash
checkout "{\"affiliate\":{\"app_id\":\"$SUMUP_AFFILIATE_APP_ID\",\"key\":\"$SUMUP_AFFILIATE_KEY\",\"foreign_transaction_id\":\"$KEY\"}}"
```

**Failing case for "idempotent at the vendor" looks like:** `HTTP 201` with a NEW `checkout_id`,
and the reader waking for a second €1.00. That is the likely outcome (the OpenAPI file describes
`affiliate` as metadata "to track the source of the transaction", not as an idempotency key), and
it means retries are made safe by our own `payment_ref` anchor and `resolvePending`, not by SumUp.
A `409` or similar refusal is the passing case.

Cancel on the reader; do not pay a second time. Afterwards, run `tx foreign_transaction_id=$KEY`
once more: with two checkouts under one key, does the lookup return the paid one, the cancelled one,
or an error? The adapter's sweep needs to know which.

## 3. Are reader webhooks signed, and how do they retry?

Three retry policies are in print and no source describes a signature for reader events (see the
note at the top). The device settles it.

### 3a. Capture one delivery

Terminal 1 — a listener that dumps every request verbatim:

```bash
mkdir -p ~/.sumup-experiments/hooks && cd ~/.sumup-experiments/hooks

from http.server import BaseHTTPRequestHandler, HTTPServer
```

## 4. Cancelling a completed reader payment

The spec mapped "void" onto the refund endpoint and could not confirm it. Two facts to establish:
whether an immediate refund of a fresh reader payment is accepted, and what the customer and the
fee report see afterwards. The endpoint is
`POST /v1.0/merchants/{merchant_code}/payments/{transaction_id}/refunds`, which "refunds an
identified transaction either in full or partially", with an optional `amount` (in major units in
the documented example: `{"amount": 5}`) and a full refund when it is omitted.

### 4a. Immediate full refund of the payment from 0.6

```bash
TXN=<id from 0.6's tx output>
curl -s -w '\nHTTP %{http_code}\n' -X POST \
  "$SUMUP_API/v1.0/merchants/$SUMUP_MERCHANT_CODE/payments/$TXN/refunds" \
  -H "Authorization: Bearer $SUMUP_API_KEY" -H "Content-Type: application/json" -d '{}'
tx id=$TXN
```

**Failing case looks like:** `409` "not refundable in its current state" — which would mean a
same-day reversal needs a delay or a different call, and the adapter's `void` must be an
asynchronous job rather than an inline call. Passing: `200 {}` and `status: REFUNDED` with a
`REFUND` event.

**Result (4a, run 2026-09-11): a FULL refund works on this route, but the top-level status does NOT
flip.** `POST /v1.0/merchants/MY2NPHDW/payments/f37572ac-…/refunds` with body `{}` → **`HTTP 201`**
(the runbook predicted 200; record: 201), body `{}`. Reading the transaction back:

```json
{ "status": "SUCCESSFUL", "amount": 1.0, "refunded_amount": null,
  "events": [ {"type":"PAYOUT","status":"SCHEDULED","amount":0.98},
              {"type":"REFUND","status":"REFUNDED","amount":1.0} ] }
```

A refund is a FIRST-CLASS separate transaction, not just a field change. It surfaces in TWO places:
(1) as its own `type: REFUND` row in the transactions history (`id 11233372107` here), linked to the
original payment by its `transaction_code` (`TAAA6BYAS7B`) — this is what the SumUp DASHBOARD lists as
a *Rimborso*, confirmed by the owner's screenshot; and (2) as a `REFUND` event inside the original
payment's `events[]`. What does NOT change is the original payment's top-level `status` — it stays
`SUCCESSFUL` even on a full refund, and `refunded_amount` stays null. So a reconciler reads "refunded?"
from the separate REFUND transactions (or the original's events), NEVER from the original's `status`.
The adapter's own `refund()` only reads the HTTP code of the refund POST, so none of this breaks it;
it is guidance for the reconciler. (An earlier draft of this note called the event the "only" trace —
wrong: the separate refund transaction is the primary one.)

### 4b. Partial refund of the payment from 2a

```bash
TXN=<id from 2a>
curl -s -w '\nHTTP %{http_code}\n' -X POST \
  "$SUMUP_API/v1.0/merchants/$SUMUP_MERCHANT_CODE/payments/$TXN/refunds" \
  -H "Authorization: Bearer $SUMUP_API_KEY" -H "Content-Type: application/json" -d '{"amount":0.40}'
tx id=$TXN
```

**Failing case looks like:** rejection for a partial amount (then `capabilities.partialRefund` is
false for reader payments), or the amount being read in the wrong unit (a `0.40` that refunds
€0.004 or errors would show the units are minor; record the body). Record what `status` reads after
a PARTIAL refund; the spec's status handling assumes `REFUNDED` means all the money came back, and a
partial refund may leave the status at `SUCCESSFUL` with a `REFUND` event, which the sweep would
then have to read from the events, not the status.

**Result (4b, run 2026-09-11): the adapter's PARTIAL-refund route SILENTLY NO-OPS — a shipped bug.**
`POST /v1.0/merchants/MY2NPHDW/payments/e0b4869c-…/refunds` with `{"amount":0.40}` (euros, exactly
what the adapter sends — `toMajorUnits(0.40) = 0.40`, `packages/payments-sumup/src/client.ts:66`)
returned **`HTTP 201 {}`** and refunded NOTHING: no `REFUND` event, `refunded_amount` null, and the
transaction's advertised refund link still read `max_amount: 1.0` a minute later. Confirmed absent in
the SumUp dashboard by the owner. A second `{"amount":0.80}` on the same route also returned `201` and
also did nothing — so nothing over-refunded (the €1.20 of attempts were all no-ops), but only because
the route ignores the amount body.

**The partial DID work on the route the transaction advertises in its own `links`:**
`POST /v0.2/refund/e0b4869c-…?merchant_code=MY2NPHDW` with `{"amount":0.40}` → **`HTTP 204`**, a
`REFUND` event of `0.40`, and `max_amount` dropped `1.0 → 0.60`. So partial refunds ARE supported on
the Solo; the `/v1.0/.../payments/{id}/refunds` path honours a full refund (empty body) but silently
discards an `amount`.

**Consequence for shipped code (#309):** `SumUpClient.refund` posts `{amount}` to the `/v1.0` path
and reports `accepted` on any non-4xx (`sumup-client.ts:112-118`), so `reverseViaSumUp`'s PARTIAL
path records a refund that never happened. Full reversals are fine. Fix is an endpoint/route change
on the partial path, plus a regression test that asserts the balance actually moved (reading the
`REFUND` event or `max_amount`, not the HTTP code). Logged to the backlog SumUp debt.

# A947 3c: pinned follow-mode measurement

**Stop at the measurement gate.** On 14 November 2026, Litestream 0.5.18 followed a
normal data insert through its applied transaction position, but its complete output
bytes differed from a direct restore of the same frozen generation. Do not build the
planned runtime follower from this result without returning this limitation to the watcher.
No fiscal code, runtime API, alert, screen or promotion path changed.

## What you can reproduce

The throwaway probe ran at `bench/sqlite-failover/src/probes/follow-mode.ts`; it is
not part of the shipped repository. Its source is retained in the local receipt
`measurement/follow-mode.ts` under the receipt root below. It uses the existing
bench's Litestream configuration/version lookup and polling sleep. It starts one owned
versitygw 1.8.0 process on loopback and a small SQLite database on Node v26.13.0.
Follow and one-shot restore use the same configuration, generation and SSE-C key settings.
Versitygw ignores encryption: this measures follow mechanics, not encryption at rest or
production stream-key verification. No production guard is called or bypassed.

Run from the feature worktree with a **new, empty receipt directory**:

```sh
cp /Users/clintongormley/waitron-campaign-h/receipts/a947-3c/measurement/follow-mode.ts bench/sqlite-failover/src/probes/follow-mode.ts
```

## The control distinguishes upload from application

Before starting a follower, the probe restores a baseline, commits a second row and
uploads it. The unchanged baseline does not acquire an applied-position sidecar.
The assertion expecting uploaded transaction ID (TXID) `0000000000000002` fails:

```text
newly uploaded TXID must be applied
+ 'no-applied-position'
- '0000000000000002'
```

Starting real `restore -f -follow-interval 100ms` into a separate fresh output makes
the same assertion pass. Run 4 reached its initial TXID in 53.029 ms. This is one local,
16,384-byte startup observation, not a large-venue startup estimate.

Run 4 is the normal data-growth representative. Its next insert stores an 86,016-character payload, standing in for image data, and
grows the source from 4 to 26 pages. Immediately after its synchronous commit returns, the probe
starts monotonic timing, uploads once, confirms the store's level-0 TXID, and watches
the native follower sidecar. Upload confirmation took 52.084 ms; applied TXID
`0000000000000003` was observed after 129.035 ms. Observation polls are 25 ms apart;
the follower polls every 100 ms. These are observed bounds from one run, not a latency guarantee.
The follower log separately records `follow: applied updates` from TXID 2 to 3.

No SQLite connection opens the follower output while follow writes it. Live observation
reads only `<output>-txid`; complete bytes are read after the follower exits.

## Exact bytes fail after ordinary database growth

No more source writes occur after the final insert. Its upload exits 0, the follower
reaches TXID 3, SIGTERM stops it with exit 0, and direct restore of `generation-a`
exits 0. Neither output is opened through SQLite, vacuumed or rewritten before comparison.
Both files contain **106,496 bytes**:

| Output | SHA-256 |
| --- | --- |
| Followed | `ebc5cd80c20cc67cc172f168a7236a793738dda03f93188f50fddc011da61a27` |
| Direct restore | `c0d4e7eefe9f9776053fc1d1fb7b9d3cd13e672e36bfc479f185e904cc96c0a0` |

Exactly six offsets differ: **18, 19, 24, 25, 26, 27**. The first two contain `1` in
the followed file and `2` in the direct file. Run 2's small insert, which did not grow
the database, produced equal 16,384-byte outputs; that control would miss this case.
Run 3's schema write also produced these six differing offsets. No row-equivalence or
integrity-check result is claimed for any output.

physical generation restart, signed-generation switching, clean stop/restart, sustained
progress reliability, and production startup on a representative venue remain unmeasured.

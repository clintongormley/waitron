B3 — how should you unlock a headless box when its security chip refuses?

The installer design is approved with your changes. This is the only remaining choice; the
six-slice plan is written. No setup code is made or requested, and every later recovery sheet
repeats the disk key. Building still needs its own go-ahead.

Recommendation A: use a cable for recovery, plus the box’s own Waitron screen when available.
A headless box normally on Wi-Fi needs a cable to the router for this rare recovery step.

All choices use an encrypted recovery page at the box-specific address on its sheet, for
example https://unlock-a1b2.waitron.local. A separate recovery certificate is signed while the
normal system is unlocked; the normal server key and signing key remain encrypted. A device
already trusting the box’s local certificate authority is the intended easy path. On a new
device, compare the public authority certificate’s full fingerprint with the sheet before
installing trust; never bypass an unexplained warning. If that device cannot do the check,
use an already-trusting device or the local Waitron screen. Real phone/Linux qualification
is still required. A genuinely expired or unreadable recovery certificate requires the local screen until the
unlocked box can repair it; a headless box then needs a display and input device plugged in.
An already-trusting device cannot make an expired certificate valid. A different correctly
dated/trusting device helps only a client clock or trust problem. Never use an unencrypted key form.

The startup image is unsigned: encryption of the connection cannot prove that the startup
program has not been replaced. The screen warns when startup files differ or cannot be checked.
After opening, the box checks against its encrypted record before resealing. Keeping the disk
key inside the encrypted disk permits later sheets, at the cost that a privileged running-host
compromise can obtain it. Reinstall produces a new key and sheet; same-box configuration cutover
keeps the existing pair.

A (recommended) — Cable or local screen. No recovery Wi-Fi credential in startup files and no
recovery hotspot. Example: after a firmware change Marta connects the box to the router, opens
the sheet’s address on her already-trusting phone or laptop, checks the disk UUID and enters
the matching disk key. She needs a cable if the box normally uses Wi-Fi.

B — A plus a separately configured recovery Wi-Fi network. Example: at a wireless-only site
Marta has already provided a separate restricted recovery SSID. The box joins it before unlock;
she still checks the encrypted connection. Its Wi-Fi credential is readable from the startup
disk. It must never be the venue’s normal Wi-Fi password and needs separate setup/rotation.

C — A plus the box’s temporary unlock-only Wi-Fi hotspot, with its own connection secret on
the recovery sheet. Example: Marta joins that box-specific network, checks the encrypted
connection and enters the disk key. The hotspot forwards nothing and closes after unlock or
cancel. It adds a second paper secret and radio/discovery qualification; it is separate from
the installer’s open hotspot and never runs alongside an unlocked venue.

For all three, one verifier serves the local screen and every network client. Wrong keys
impose shared waits of 2, 4, 8, 16, 32, then 60 seconds, capped at 60 until success or reboot.
Three wrong keys mean 2, 4 and 8 seconds. Someone on the network can see that recovery is
waiting and delay you with wrong keys, but gets no admin, setup or network-change authority.
A reboot clears this memory-only delay; it does not limit offline attacks on a stolen disk.

Choose A, B or C, or describe a change. Only unlock-specific execution waits for this answer.

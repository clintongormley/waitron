# A790: shared browser choices agreed; remembering after reopening

H is agreed: on the dashboard without a device profile, printer choices belong to this
browser and are shared by everyone who signs in. Receipt and Invoice stay separate for
each sale venue. Ana prints Harbour’s Receipt on Patio and the server accepts; Luis next
signs in, with Bar and Patio both still eligible. Patio is selected for Luis. Memory
never grants access to an otherwise inaccessible printer. Sign-in never prints.

I is the sole next question, proposed only: should accepted choices survive closing all
browser windows and reopening (recommended), or be forgotten on browser close? Recommend
retaining so returning to this workstation restores its last accepted destination.
The alternative asks you to choose again, under the still-proposed several-printer
fallback. Both options keep H’s sharing between logins and a final named print confirmation.

The I example assumes the same normal browser with its site data retained. Ana’s Patio
request was accepted before closing; when Luis returns, both Bar and Patio remain eligible,
so G’s sole-printer rule cannot hide the difference. Logout alone is not browser close.
Technical storage, unusual/private browser lifecycles, expiry/reset and errors require a
later builder proposal. No persistence guarantee is implied after clearing site data.
Concurrent/late requests, account transitions, device Invoice memory, portable receipt
holding, multiple/zero fallback and complete design/plan/build stay open. Phone Equipment
remains A796’s one setting. All A–H answers retain their precise scope.

Eight PNG/SVG pairs cover English/Spanish, light/dark and 390/1280 px. Each PNG was rendered
in headless Chromium and visually inspected; native SVG text boxes were checked inside
the drawing. These are static discussion drawings, with no runtime, accessibility,
physical-paper or legal evidence. Example-only buttons label the illustration, not a
proposed product action. Earlier conflicting boards remain history.

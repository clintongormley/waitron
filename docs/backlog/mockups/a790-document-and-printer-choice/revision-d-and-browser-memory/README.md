# A790: Receipt directly and dashboard memory

D is approved: simplified-sale Print/reprint opens Receipt directly. The worked device
example keeps `S/318`, €14.50, Spanish and one guest, with an inline, foldable printer
selector and a final named print press. It adds no full-invoice issuance, conversion or email.
The copy label applies when the server designates a copy.

E is the sole next owner question. Should a dashboard without a device profile remember
its last-used Receipt and Invoice printers separately per sale venue (recommended), or
share one remembered printer between the document choices within each venue?

For Harbour's `F/1042`, first print Receipt on Bar receipt, then Invoice on Office · A4.
Reopening Receipt preselects Bar in the separate proposal, Office in the shared proposal,
provided it is still active at Harbour. Both proposals keep Harbour and Hillside memory
apart; that memory scope is a proposal, not part of B's already approved browser scope.
B continues to offer every active printer at the sale's venue, including A4 and portable
printers. Paper does not convert the recorded invoice. Neither proposal changes a phone's
Equipment setting.

Storage, update timing, expiry, first-use/unavailable fallback, portable receipt-holder
enforcement and the complete design/plan/build still require agreement or design work.
A796's decided phone Equipment save handling is retained; A790 integration still needs
verification. No general single/zero-printer or automatic-print approval follows from D.

The eight PNG/SVG pairs show D and both E proposals, in English/Spanish, light/dark, at
390/1280 px. These are static discussion drawings, with no runtime, accessibility, hardware
or legal evidence. Existing boards remain historical where superseded. The final action
illustrations in E say “Example only” because they compare remembered choices, not new
product actions.

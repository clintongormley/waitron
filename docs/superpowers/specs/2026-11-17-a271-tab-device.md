**Reproduction:** at #3677 merge224a631150, two real Chromium tabs shared a browser context. After the chooser request failed and B enrolled, A's device API and visible login heading changed to B. The stable-A assertion failed; explicit original-A dev-id control returned A. Local receipts: `~/waitron-campaign-f/receipts/a271-20261117/`. This proves dev chooser fallback, not non-dev Demo pairing.

**Dev first:** select the existing seeded device explicitly, keeping dev's existing id override. Every tab-auth request carries its marker even before a device is selected. A missing/invalid credential never borrows another tab's cookie. New-device enrollment can use the real existing-format device proof. No adopt route, secret rotation or enrollment-permission change.

**Sign-in:** retain each tab's session token in memory and the existing person header. Reload locks again, as today. Persist its device proof in sessionStorage, with memory fallback if storage is blocked. Closing a tab does not delete rows or revoke sessions. Duplicated/restored tabs may remain the same device, unsigned-in; no tab registry or coordination.

**Boundary:** accept tab proofs only in dev or Demo; refuse their headers elsewhere. Reuse existing hash checks, revocation, device/session binding, origin checks and approved enrollment. Secrets leave only explicit tab join/login responses, marked no-store, never logs or URLs. Normal appliances keep cookies.

**Demo step:** after the owner answers, enable automatic or explicit per-tab use in non-dev Demo through the same transport. Qualify two tabs using real dashboard pairing approval. That part remains unavailable until decided and built.

# A1484: Delete hardware and add it again

**Proposal for owner approval; build nothing yet.** The owner asked “it is much more intuitive to just delete and readd” and “so we'd remove the status filter as well  for those”. Full request: `~/waitron-campaign-shared/desk/done/20261110-1859-delete-and-readd.md`. Separate Sol high draft, checked by the driver; one Claude read, corrections incorporated. Neither review nor the desk's recommendation approves this design.

**What you would see.** Receipt/kitchen printers, A4 printers, devices/tills/kitchen screens, card readers and print agents offer Delete and their normal Add flow. Remove Active switches, Disable/Enable, active/disabled columns and status filters. Deleted hardware disappears; connection, unpaired and job status stay visible where relevant. Products use Archive (`apps/dashboard/src/widgets/product-list.ts:1243`) and stay outside this change, as does fiscal node identity.

**Recommendation: keep identity and equipment settings, clear live assignments.** Delete keeps history, name and calibration; devices keep their profile and local configuration, subject to a replacement if that profile has retired. Printer/reader Delete clears their live routing, device/profile choices and defaults using today's impact-confirmed removal (`printer-delete.ts:172`; `card-reader-delete.ts:292`). Device Delete ends sign-ins and releases holds; preserve its browser proof for the authorised returning-device Add flow rather than clearing it (`device-delete.ts:221`). Adding hardware again does not restore cleared assignments or ended print/invoice work. This avoids an invisible deleted printer remaining responsible for kitchen tickets. Alternative: keep assignments too, with “Deleted” shown in every referring picker; that saves setup but leaves service pointing at unavailable hardware, so it is not recommended.

**Identity on Add.** Discovery AND manual receipt-printer Add must restore the most recent matching hidden registration: USB/Bluetooth transport and local key, network host/port, or cloud-poll identifier. Manual Add currently always inserts (`packages/printing/src/printers.ts:54`), so this needs changing, not merely relabelling. Device return uses its proven cookie and manager acceptance. A4 Add matches host/port/resource path and refreshes capabilities, as `registerPagePrinter` does (`apps/server/src/page-printers.ts:69`). No match creates a new registration; old historical references remain attached to their original rows.

**Readers and agents.** Keep reader Delete's current provider unpair and payment-in-progress refusal (`apps/server/src/card-reader-delete.ts:93`); keep its explicit provider-disconnected confirmation. Unpair remains available and leaves the reader listed as unpaired. Provider-verified adoption can restore a retained provider/reference match; pairing with a newly issued provider reference creates a new id, as today (`payments-api.ts:879`). For agents, Add offers previously removed trusted agents using the existing Allow operation, including this box's agent (`print-api.ts:863`); a fresh remote pairing creates a new id and its A4 printers must be found again to bind to it. Agent Delete stops transport, keeps printers listed as unavailable, and its confirmation explains this. Queued work may resume only when the original agent is added back. Automatic self-enrolment never reverses Delete.

**Deletion is separate from a system switch-off.** Use existing `deletedAt` for printers/devices/readers; `active=false` without deletion stays listed, including Bluetooth unpair and reader Unpair (`print-api.ts:709`; `card-reader-delete.ts:244`). A4 printers and agents have no automatic switch-off in the paths inspected; their explicit Delete can reuse their inactive flag. Inspect every writer before build. Matching deleted rows is a deliberate change to today's rule, including retained rows already present; no special legacy restoration path is proposed before go-live. Historical print-job, invoice-delivery, payment and fiscal device references are neither removed nor reassigned (`packages/db/src/schema/print-jobs.ts:38`, `invoice-deliveries.ts:65`, `packages/payments/src/schema/payments.ts:110`, `packages/fiscal-verifactu/src/schema/registros.ts:36`).

**Proposed CLAUDE.md §3 replacement, with matching conventions-ui.md update:**

> Hardware offers Delete and Add, with no Disable/Enable or active/disabled filter. Delete hides the registration and preserves historical references; its confirmation names assignments and work it removes. A system switch-off is not Delete and stays listed. Add restores a retained identity only through its matching transport endpoint, proven device cookie, provider-verified reference or explicit trusted-agent choice; fresh provider references and fresh agent pairing create new identities. Adding again never restores cleared routing or ended work.

**EN / ES words.** Delete / Eliminar; Add / Añadir. Printer confirmation: “Delete {name}? History and printer settings are kept. Assignments are removed. Add it again to use it.” / “¿Eliminar {name}? Se conservan el historial y los ajustes de impresión. Se eliminan las asignaciones. Para usarla, añádela de nuevo.” Device, reader and agent confirmations name their own effects above; keep their existing safe Stop choice. A4 guidance: “To add it again, use Add a printer.” / “Para volver a añadirla, usa Añadir impresora.” Update existing hardware help and `apps/server/src/guide/{en,es}/printers.md` with shared heading ids.

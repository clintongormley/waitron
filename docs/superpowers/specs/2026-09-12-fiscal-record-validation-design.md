# Checking a fiscal record before it is written — design

**Date:** 2026-09-12
**Status:** approved (owner, 2026-09-12)

## 1. What this fixes

`packages/verifactu/src/validate.ts` checks a Veri\*Factu record against AEAT's rules — the issuer's
tax identifier length, the invoice number's length and character set, the date and hash formats, XML
control characters in the free-text fields, the amount formats, the VAT breakdown's line count, the
500-character cap on the operation description, and two arithmetic cross-checks (25 distinct
reporting points when this was written). `validate` is exported from the package barrel. **No
production file calls it.**

Established by experiment rather than by searching. `validate` was made to throw on its first line,
and two suites were run. `@waitron/fiscal-verifactu` passed whole — 343 tests across 39 files,
including the end-to-end write path, the correction and canje paths, the drain, and the real
PostgreSQL replication fidelity cases — so nothing in the package that writes and submits records
calls it. The control in the other direction: `@waitron/verifactu`'s own tests fail under the same
sabotage, so the sabotage was reachable and detectable. The file was restored afterwards.

What that costs, proved end to end in the same session. With a venue's invoice series code set to
`Serie A`, `recordSale` resolved normally and wrote `num_serie_factura = "Serie A/1"` into
`registros_facturacion` — the append-only, hash-chained table. Running the validator on that same
string returns `NUMSERIE_CHARSET`: AEAT would reject every record carrying it. Nothing between the
wizard's text box and that table checks anything; `asString` (`apps/server/src/setup-api.ts`) requires
only a non-empty string.

The fields at risk are the ones an operator types and nothing else re-checks: the invoice series
codes, the legal name, the operation description. The tax identifier is already covered by the
country pack's own validator, which the browser and the server each run
(`validateSpanishNif`, `packages/country-es/src/spain.ts`).

## 2. The rule

> A record AEAT could not accept is refused before it is written. A record AEAT would accept, but
> whose numbers disagree with themselves, is written, filed, and flagged.

That line is not arbitrary — it is what `validate`'s own severity split already means. Everything it
reports at error severity makes a record AEAT cannot accept; its two warnings are the arithmetic
cross-checks, and the file records why they are only warnings (`validate.ts`, above
`CUOTA_TOTAL_MISMATCH`): AEAT applies a ±10.00 euro tolerance and treats a breach as an admissible
error, so refusing locally would block records AEAT would have accepted.

Refusing on the errors is safe to do at a till, but the reason needs stating precisely rather than
broadly. The error checks divide in two. Those driven by OPERATOR INPUT — the series code's character
set and length, control characters in the legal name, the operation description's cap, the tax
identifier's length — read venue configuration that is fixed at setup and identical for every sale, so
a failure there surfaces on the venue's first sale and cannot begin at sale 500 mid-service. The rest
— the date and hash formats, the amount formats, the VAT breakdown's line count — are generated by our
own code from the basket, so one of those failing IS possible mid-service and would mean a bug in us.
Refusing is still right in that case: a record that AEAT will reject is worse written than refused,
because the table it would be written to cannot be edited afterwards.

## 3. Layer 1 — refuse at the chain seam

One place covers all four record types. In `packages/fiscal-verifactu/src/chain.ts`, `attemptAppend`
builds the record (`buildAltaRecord` / `buildAnulacionRecord`) and inserts it eight lines later. The
check goes between the two.

Three reasons this is the seam and not the four call sites in `backend.ts`:

- It is the first moment the COMPLETE record exists. The chain pointer and the hash are filled in
  here, so this validates the record that will actually be stored, not an approximation of it.
- It is inside the nested `tx.transaction()` savepoint, so a throw discards the attempt without
  destroying the sale already written in the enclosing transaction.
- It sits inside the retry loop but outside its `isUniqueViolation` filter, so a validation failure
  propagates immediately instead of being retried to exhaustion.

On any error-severity issue, throw `fiscal.record_invalid` carrying the offending field name and the
issue's own code — **never the field's value**. That restriction is not stylistic: the shared error
boundary writes an `AppError`'s params into `waitron.log`, which the unauthenticated recovery page
renders to anyone on the venue's LAN (CLAUDE.md §3), so params never carry operator data.

`fiscal.record_invalid` is a new code registered in `packages/fiscal-verifactu/src/errors.ts`. It is
English, not Spanish, because it names our own local refusal rather than an AEAT wire state — the
distinction its siblings already draw (`fiscal.sale_not_recorded` beside `fiscal.registro_rechazado`).

Warnings do not throw. They are handled in §6.

## 4. Layer 2 — refuse at the setup boundary

A record refused at the chain seam is refused at the till, which is the worst place to learn that a
series code has a space in it. The operator must be stopped where they typed it.

**The constraint.** The server cannot import the validator. `@waitron/verifactu` is a regime package,
and `scripts/module-seams.test.ts` pins the `apps/server/src` allowlist as EMPTY — a list that may
shrink and never grow.

**The way through, which already exists.** `FiscalContribution.provisioningSecret`
(`packages/fiscal/src/contribution.ts`) exists for exactly this shape: the host holds an opaque value
and does not know the regime's rules, so it reaches them through a seat. Its `validate` seat even
carries this design's own rationale in its comment — refuse a malformed value "BEFORE `provisionVenue`
mints the unrepairable SIF/hash chain (CLAUDE.md §5) so a malformed secret is refused with nothing
stamped or minted."

So: a sibling seat on `FiscalContribution` that checks the venue's fiscal text fields. It takes the
venue request's own fields, throws `setup.request_invalid` naming the offending field, and writes
nothing. `fiscal-verifactu` implements it from the same rules the record validator applies;
`fiscal-none` does not offer it, and a venue under a regime that files nothing is not checked.
`apps/server/src/setup-api.ts` reaches it through the descriptor, alongside the country pack's
existing tax-identifier and postal-code checks, and adds no regime import.

The seat's name is the plan's to choose, against its siblings on `FiscalContribution`; this design
fixes its shape (takes the venue fields, throws naming a field, writes nothing) and not its spelling.

The fields it covers: the two invoice series codes (character set, the length of `<code>/<counter>`,
and the 38-character base budget that `MAX_BASE_CODE_LENGTH` reserves for a restore's installation
suffix), the legal name (control characters), and the operation description (control characters and
the 500-character cap).

## 5. Layer 3 — the wizard marks the field

The plumbing is already there. `setup.request_invalid` carries `params.field`, and the wizard's API
client deliberately preserves `params` alongside `code` so the wizard can drive per-field inline
validation off it (`apps/setup/src/api/client.ts`, whose comment says so).

What is missing is the routing. `#mapProvisionError` (`apps/setup/src/setup-app.ts`) sends
`setup.request_invalid` to the REVIEW screen with the raw field path in a banner — "The box rejected
the details (field: venue.seriesCode)" — because its comment assumes "the field's own screen already
validates the same rule". For these fields that assumption is false, which is the whole reason this
design exists.

So: map the venue field paths this seat can reject back to the venue screen, mark that field invalid
inline, and give it a sentence saying what is wrong with it. That is the same shape as the per-field
error work already in the backlog for this screen, and it is deliberately narrow here — only the
paths this seat produces.

**Not built: a browser-side check as the operator types.** The venue screen contacts no server at
all; the first request is the provision POST from the review screen. Checking a series code while it
is typed would need the regime's rules in the browser, which the seams forbid unless they travel as a
browser-safe preset, and a preset for this would have to be built. The country packs are not the
place — a character set chosen for the Veri\*Factu QR is a property of the filing regime, not of
Spain. So the operator learns at provision time and is returned to the field. §9 records the
alternative.

## 6. Warnings raise an incident

The two arithmetic warnings mean our own totals disagree with our own VAT lines by more than 10 euros
— a bug in the money, while the venue keeps selling. A log line is too quiet for that. `recordIncident`
(`packages/core/src/incidents.ts`) already takes a structured error, a till, a sale id and a severity
of `warning` or `error`, and is what the fiscal drain and the payments reconcilers already use.

So a warning-severity issue raises a `warning` incident against that sale and does not block it.

**Stated plainly, because it would otherwise read as a promise this design does not keep: nothing
displays incidents today.** `openIncidents` is the only function that reads the table and has no
caller anywhere; no dashboard screen, till screen or report mentions incidents (whole-repo text
search outside tests). `apps/server/src/pass.ts` names the intended audience as "an operator grepping
`drain.complete` (or the `incidents` table directly)" — and a real venue's operator has no terminal,
so neither of those is a surface.

That gap is wider than this design and is not fixed here. Four producers already raise invisible
incidents: the fiscal drain when AEAT rejects a record, the payments reconciler on drift, the Stripe
device provider, and the card provider pool. An operator surface serves all of them, and one shaped
around two arithmetic warnings would be the wrong shape. It gets its own branch (owner decision,
2026-09-12); the backlog carries it.

## 7. Testing

- **The refusal, proven by deletion.** Remove the `validate` call from `attemptAppend` and the test
  must go red. A negative control confirms it fails for the stated reason.
- **End to end through `recordSale`**, which is the property that matters: an invalid series code is
  refused AND nothing was written — no row in `registros_facturacion`, no chain head advance, and the
  sale itself absent. PGlite is the right target: this is neither a privileges nor a contention test,
  and §4 asks for the lighter one with a reason.
- **Every record type**, since the seam serves four: sale, void, correction, substitution.
- **A warning does not block**: a record breaching the 10.00 tolerance is written, and an incident
  row exists against that sale.
- **The boundary seat**: a bad series code is refused with `setup.request_invalid` naming the field,
  with nothing provisioned; a `fiscal-none` venue with the same input provisions normally.
- **The seam guard stays green** — `scripts/module-seams.test.ts`, which is what proves layer 2 did
  not reach for the regime directly.
- **The wizard** marks the named field and returns to the venue screen.

## 8. Not in scope

The drain does not validate before sending. With layer 1 in place a chained record is always valid,
so the check would be dead code, and pre-production records need no covering — no
backwards-compatibility work until a real venue is live (CLAUDE.md §3).

Also untouched, each its own backlog item: the venue screen's single generic error sentence, the
series-code defaults, whether the wizard should ask for a till at all, and the operation
description's wording.

## 9. Open points

- **A browser-side series-code check** would need a browser-safe fiscal preset (§5). Worth revisiting
  if a second regime ever needs the same thing; not worth inventing for one.
- **A guard that this stays wired.** The behavioural test proven by deletion is the real guard. A
  root text-walking guard could also assert that `validate` has a caller, which is the shape
  `scripts/errors-reachable.test.ts` already uses for a related problem. Decide during the plan
  whether that earns its place or merely duplicates the deletion test.
- **`fiscal-none`** offers no seat, so its venues are unchecked at the boundary. That is correct —
  there is no filing format to violate — but it means the wizard's behaviour differs by regime, and
  the plan should confirm no shared code assumes the seat exists.

# A1111: sign in to a mirror as yourself

**Status, 2026-10-26:** proposed full design for owner approval. Design only. No approval, implementation plan, implementation, tests run, or release qualification is implied. Source references describe a reading of base `71bb5126c364e546298b14f23f2c3a3ae553d704`; proposed behaviour below is not present behaviour.

## Why this changes

When you open a mirror today, Waitron gives you an administrator session without asking who you are. That lets you download another person's whole personal-data file. Being read-only prevents changes; it does not establish who may read private information.

The owner's intent is settled: you identify yourself with your own venue account, each read checks your own permissions, and the ambient mirror administrator goes away. Everything about the mechanism, limits and unavailable methods in this document is a **proposal**, not an owner-approved decision.

The recommended first release uses the email and password already in the venue copy, plus your authenticator code when your account requires it. It holds its own sessions in memory, outside the venue database. It stops protected access when it cannot establish that its copy of account authority is at most fifteen minutes old. This deliberately trades long disconnected access for a bounded window in which an unseen revocation could still permit a read.

## 1. Goals and boundaries

You should get the same permission decision on the mirror as the source routes would give your account against the same account snapshot. The mirror adds its read-only restriction. It never substitutes a more privileged person, treats reachability as authority, or accepts a primary's copied dashboard or till session as mirror sign-in.

The design covers dashboard sign-in and logout, protected reads and downloads, fresh permission checks, live events, session isolation, and mode changes. It preserves each route's permission and subject restrictions. A person's own download remains their own; another person's download needs `personal_data.export`, currently held only by Admin.

It does not add remote Cloud identity, a new identity provider, a new dashboard PIN method, new custom roles, a replicator, a recovery mechanism, sales on a mirror, or credential editing on a mirror. It does not change protected fiscal writers, hash inputs, invoice allocation, append-only records, `registerSif` or `restoreFiscal`. Existing independently authenticated promotion and retirement operations keep their own authority and fiscal requirements.

The first release is one server process per mirror. Multiple processes would need shared session and rate-limit storage and are outside this proposal. No new database, migration, `node.db`, local table or persistent session file is required.

## 3. Chosen authentication methods

### First release: password, preserving the enrolled factor

`checkManagerPassword` can read a copied `persons` row and verify its password without opening a write transaction (`packages/identity/src/manager-login.ts:23-68`). It uses the folded, normalized email lookup shared with the uniqueness index. Reuse that lookup and password-verification discipline, including the dummy derivation for unknown, inactive and passwordless accounts. Do not call the existing `loginManager` to complete mirror login: its completion starts a database session and can consume a recovery code (`packages/identity/src/manager-login.ts:105-127`).

Proposed mirror completion re-reads the account after password derivation, checks the same snapshot generation and credential fingerprint, verifies an enrolled authenticator code, and then creates a local session. The fingerprint is a process-keyed digest of the account ID, login email, password hash, encrypted authenticator secret and Google link; it is not a new stored verifier and never leaves memory. Store no password, code or raw account secret in the session. Status and permissions are always read again, not frozen in that fingerprint.

If the account has an authenticator, the password alone never signs it in. Ask for its code only after the password is accepted, following the existing two-step form. TOTP, a time-based authenticator code, can be verified locally if the copied ciphertext can be opened and the mirror clock is qualified for that check. The existing secret reader uses AES-GCM and returns null for an unreadable secret (`packages/identity/src/mfa.ts:19-63`). The explicit account key is transferred at adoption (`apps/server/src/adopt.ts:144-150`) and derives the TOTP purpose key at boot (`apps/server/src/account-key.ts:7-25`; `apps/server/src/boot.ts:1461-1465`). Do not assume an arbitrary copied venue folder includes this key: if explicit adopted key provenance or code-clock readiness is absent, factor login is unavailable, with no password-only fallback. Clock uncertainty blocks factor completion; it does not change fiscal clock rules.

For this proposal, code-clock readiness means an authenticated source-time observation accompanying the current freshness receipt establishes a difference of at most thirty seconds, including its uncertainty. It lasts no longer than that fifteen-minute receipt. A wall-clock jump exceeding one second relative to elapsed monotonic time clears readiness until another observation. Reuse `verifyTotp`'s existing code window (`packages/identity/src/totp.ts:5-19`); do not widen it. These numerical readiness limits are proposed defaults, not a new fiscal clock authority. Key replacement/loss or lost readiness invalidates existing factor-authenticated mirror sessions as well as preventing completion.

The account key opens encrypted TOTP material; it is not a universal key for all node-local seals. Google client secrets in this tree come from configuration, while `node_sealed_state` is an encrypted backup archive read through recovery (`apps/server/src/sealed-state.ts:25-35`, `:51-58`). Neither copying that archive nor having the TOTP key proves that Google can operate on the mirror. No source secret is copied or unsealed just to enable an unavailable method.

**Passkey reservation:** RP means relying party, the identity against which the passkey is checked. The server currently supplies both `managementRpId` and exact `managementOrigin` (`apps/server/src/boot.ts:2006-2007`). A different mirror hostname or origin may not accept an existing primary passkey. That is a repository-grounded design inference, pending real browser/address qualification, not a tested universal browser claim. A later passkey design must settle allowed RP/origins, counter coordination, one-time local ceremonies, snapshot rollback and restart. It may not turn off the existing checks to make a mirror work.

## 4. Where sign-in and sessions live

Create one process-owned mirror-auth store at the trading boot boundary. Bind it to the configured mirror node ID, venue identity/environment, canonical served management origin including port, and a new random process epoch. An epoch is a random identifier for this particular running instance. The store contains only token hashes, person IDs, credential fingerprints, session timing, accepted snapshot identifiers, limits and rate-limit state. Its node/venue/origin binding is checked on every use. It is never serialized, copied to a backup, streamed, exported as configuration or drained back to the primary.

Use the existing random token minting and SHA-256 hashing functions (`packages/identity/src/session-token.ts:9-27`). Only the cookie holds the raw bearer token, a secret that proves possession of the session. The map key is its hash. A map key, row ID or stored hash submitted as a token resolves nothing. No operational venue write is needed for sign-in, logout, last-seen, expiry or a refused attempt.

This store is conceptually node-local, but it is not a new classified table. If a later release persists it, that is a fresh design: node scoping, no cross-class foreign keys, encrypted local custody if needed, copying/restart behaviour, retention and personal-data disclosure all need review. Do not reclassify `management_sessions` from `state` to `local` to implement this proposal.

### Cookie and origin isolation

Use a separate cookie name `waitron_mirror_session_<scope>`, where scope is a stable digest of venue/environment, node ID and canonical origin including port. The runtime epoch stays in the store binding, not in the stable name. Give it HttpOnly, SameSite Strict, path `/`, no Domain and Secure on TLS. Do not set it on a GET primer or overwrite an unrelated primary cookie. Keep it a browser-session cookie; Remember saves only the email and method, never the token or a longer session.

The mirror parser reads only its exact scoped name. It never falls back to `waitron_management_session`, another mirror's scoped cookie, till cookies, a copied session row, or a header invented by the client. Primary mode reads only the primary cookie and never searches the mirror store. Distinct names plus server-side scope checks are required even for two listeners at `127.0.0.1` on different ports. The existing fixed primary name/path (`management-cookie.ts:10-21`) supplies no such mirror namespace. Real-browser tests of two ports and two mirror nodes are a release requirement; none ran here.

Use the configured canonical origin; do not derive cookie scope or redirects from an arbitrary Host or forwarded header. Mirror login/logout require same-origin requests, using the configured origin and the repository's trusted request/proxy handling. The supported browser path supplies Origin; reject absent or mismatched Origin on these two mutations. CLI clients must supply that configured origin and receive no exemption. Keep credentialed responses and protected data `no-store`. Non-loopback password sign-in requires qualified HTTPS; `WAITRON_MIRROR_ALLOW_EXPOSED` cannot relax that requirement. Loopback development keeps its explicit insecure-cookie path.

### Lifecycle and resource limits

Proposed defaults are a 30-minute sliding idle expiry, matching `IDLE_TIMEOUT_MS`, and an eight-hour absolute lifetime. Count activity once per successful deliberate request; automatic `x-waitron-live` reads, SSE, and rechecks with `touch:false` never extend it. Use monotonic elapsed time for in-process limits so moving the wall clock backwards cannot prolong sessions. A new sign-in always mints a token; logout deletes only the presented mirror session and clears only its cookie. It is idempotent even without a valid session.

Keep at most five active sessions per person and 1,000 per process. Expire entries first; a sixth successful sign-in revokes that person's oldest session. At the process cap, refuse a new sign-in without evicting another person's live session. Opening a new session and setting its cookie are one completion decision. If the local store fails or cannot accept it, issue no cookie. If an existing store becomes unusable, refuse protected reads and close its streams; never fall back to the copied primary sessions or ambient authority.

Reuse `createPasswordThrottle`'s per-address policy: one attempt in flight, three free failures followed by exponential waits capped at 60 seconds, idle reset after fifteen minutes (`packages/provisioning/src/password-throttle.ts:20-22`, `:56-69`, `:138-174`; `packages/identity/src/pin-throttle.ts:11-18`, `:60-70`). Apply it to existing and nonexistent addresses alike, including invalid second-factor attempts. Add a process cap of four concurrent password derivations and sixty login attempts per rolling minute before expensive work; do not trust a user-supplied forwarding address to evade it. Refuse rather than queue unbounded work; return a retry delay. One valid password awaiting its code is not a session or a cleared failure budget. A missing code uses the existing factor prompt without exposing status before the password succeeds.

Sessions and throttles vanish on restart. This loses sign-in continuity and resets throttles, an accepted proposed tradeoff for avoiding durable auth infrastructure. A remote attacker is not given a restart action. Process compromise or privileged memory capture remains outside what hashing the map can prevent. Copying `venue.db` alone copies no mirror-session authority.

The mirror remains a trusted holder of private venue data and password verifiers. A copied password hash permits offline password-guessing attempts, and the adopted account key can open the copied authenticator secrets. Personal sign-in restricts the HTTP reader; it does not encrypt those existing copies against the machine's operator or grant a less trusted host permission to hold them. No extra copy of these secrets is introduced by the local session store.

## 5. Snapshot freshness, revocation and replacement

“Fresh role” means re-read from the latest accepted copy, not magically know an unseen primary change. A disconnected mirror cannot infer a revocation it has never received. The proposed bound is **fifteen minutes from a qualified observation of source account authority**, for every protected read, login and download, including owners. This is a product/security proposal for approval, not a measured safe duration or a legal rule.

The copy owner must supply a small in-process freshness contract: venue/source identity, source incarnation and monotonically ordered revision, installed local generation, and elapsed time since an authenticated observation that this generation includes source account status, credentials and grants current at that observation. Installation and receipt acceptance happen together. A heartbeat, successful HTTP request, bucket file time, mirror boot time, copied `last_seen_at`, unchanged file hash, sales timestamp or old backup download does not establish this. Checking an unchanged snapshot with the source can renew freshness only if the source confirms the same account-authority revision is still current. A slow transfer consumes the allowance; receiving it does not reset its age.

**Current dependency, not new infrastructure:** this tree has no completed adoption/copy installer that supplies that receipt (`apps/server/src/finish-adoption.ts:26-41`; `docs/backlog/replication-cloud.md:404-413`). `persons` and the password reader exist; actual populated account-copy availability and a trustworthy freshness reader have not been qualified here. A1111 should consume the eventual copy owner's receipt, not invent a parallel identity sync service. Until that contract exists and is exercised through real boot, protected mirror access remains unavailable. Do not stamp every startup fresh, quietly use an indefinite old snapshot, or represent fixture-only sign-in as a usable deployed mirror. Publication of this design has no dependency; a usable release does. If planning finds no copy owner able to supply the contract, park that release dependency explicitly rather than building an unbounded offline fallback.

The policy is deterministic:

Invalidate local sessions and close streams. Reconnection requires a qualified observation and new login. Public health still reports its own documented meaning.    |
| New, verified forward generation in the same source incarnation                                                                            | Publish the whole generation atomically. The process retains the highest accepted revision only in memory. A restart therefore cannot prove offline rollback safety from its own history, which is why it needs a new source qualification. An explicit new-incarnation acceptance is owned by the trusted copy lifecycle, not by a public request or login form.

For a slow export, capture one generation, actor and subject before collecting data, then check the local session, current mode, current account/fingerprint, current permission and freshness again before releasing bytes. If the installed generation changed while building, discard that build and ask you to retry against the new snapshot. This prevents authorizing one snapshot and returning a silently mixed one. No bytes leave before this recheck. Already delivered bytes cannot be recalled; no bounded-staleness policy promises that.

## 6. Carry the person through the existing gates

Keep `requireManagementSession` as a token-shape/cookie boundary, with an explicit per-request cookie scope. Let `resolveManagementSession` select an explicit per-request backend: primary database sessions or this mirror's local store plus accepted snapshot. Scope that selection to the app instance, database and asynchronous request lifetime, including the SSE loop. Never use a process-global “current mirror”, infer the backend from token shape, or accept a browser-supplied principal. Missing mirror context on a mirror request is a refusal, not fallback.

This can use the same request-scoping mechanism already present for passive reads (`packages/identity/src/management-session.ts:15-20`), with a server-supplied mirror resolver interface. Identity need not import `apps/server`; primary calls outside mirror HTTP keep their normal backend. The builder can choose the smallest typed interface, but it must make backend provenance and mode checks explicit. Local `sessionRowId` is diagnostic only: no mirror path may pass it into a function that updates a primary-session row.

Promotion and other already-exempt lifecycle operations are a distinct trusted scope: their existing credential checker may mint a temporary database proof session and authorize/end that exact internally returned token using the database backend. Select this backend explicitly inside that operation, rather than falling back when mirror resolution fails. A browser cookie cannot select it or substitute for the operation's password/factor, owned-operation or break-glass proof. End the nested scope before returning to ordinary mirror handling. This avoids making `apps/server/src/promote-api.ts:164-177` fail merely because its ephemeral proof token is correctly absent from the mirror store, while preserving its existing authorized writes.

`authorizeManager` still invokes the resolver and `roleHasPermission`; module/domain route gates still run. Do not implement an “authenticated GET means allowed” gate or replace route checks with the UI's permissions list. Direct resolver callers, self-scope checks and account-profile reads must all resolve the same signed-in person. In mirror mode these resolutions touch only the local store. Read-only query execution must also avoid the existing transaction completion's housekeeping drain where it writes (`apps/server/src/personal-data-export-api.ts:67-71` already uses read-only write-lock turns). No adapter may suppress an unexpected venue write and report success; the future build must identify and remove or refuse it on the mirror-serving path.

### Explicit public and non-session boundaries

Protect personal/management data, not every URL. Keep health, help and certificate/trust pages at their existing mode boundary (`apps/server/src/boot.ts:1025`, `:1068-1085`), built assets/login HTML, login locale/deployment capabilities, and OPTIONS/preflight reachable without personal sign-in. Do not expose extra tenant/account data through the new public capability response.

Add public `GET /management-api/auth/capabilities`, describing this deployment's supported methods and readiness, never account enrolment. In mirror mode it says password is the offered method, whether local sign-in is ready, that recovery/passkeys/Google require the primary, and the snapshot confirmation time when available. It carries no roster, account existence, secret, grant list or raw connection configuration. An unready mirror still has a usable explanation and Retry/Stop controls.

In mirror mode add only exact `POST /management-api/session` and `DELETE /management-api/session` exceptions to the write gate. They select the local login/logout handlers, check Origin and mode again, and never dispatch the primary completion handler. No prefix exemption for `/management-api`, `/session/*`, `/me/*`, `/passkey/*` or `/account-actions/*`. Preserve the three existing operation exemptions listed in §2 and their own authentication. Mirror login exceptions do not automatically apply to fenced nodes.

Proposed HTTP contract: absent/unknown local sessions use `401 management_session.required`; idle/absolute expiry uses `401 management_session.expired`; wrong account credentials use `401 password.invalid`; missing enrolled code after a correct password keeps `totp.required`; missing route permission keeps `403 authorization.not_permitted`. Unsupported mutation/authentication endpoints keep `403 node.read_only` on mirror mode, including the safe-verb Google callback's explicit refusal. Deployment readiness, stale/unqualified snapshots and local-store failures use a registered `503 mirror.authentication_unavailable` with a deployment-level reason and retry guidance; process session capacity uses `503 mirror.session_capacity`. Rate limits use `429 password.throttled` and its retry delay. These new names are proposals for the shared error registry, with English/Spanish wording and common status mapping across server and module wrappers. Unknown resource IDs do not become an alternative way to distinguish unauthenticated visitors. Public capabilities can explain these deployment states without attempting a login.

Audit safe-verb handlers as well: the mirror's GET Google callback must refuse before claiming state, exchanging a code or writing; password-reset/account-actions/passkey endpoints and credential/profile writes remain unavailable. `/management-api/membership` currently verifies a peer credential by creating and ending a database session (`apps/server/src/management-api.ts:1043-1084`); it remains an independently authenticated source endpoint, but is unavailable on the mirror rather than being routed through personal login or permitted to do those writes. The deliberately public staff roster (`apps/server/src/management-api.ts:872-878`) is not mounted on a mirror, where no till PIN screen needs it. Preserve primary roster behaviour.

Signed or credentialed non-session endpoints retain their existing verifiers and mode restrictions. These include webhook/provider requests, discovery/device pairing, node role/status probes, Cloud public exchange paths, peer membership, adoption, promotion preparation/promotion and fenced retirement. Some are unmounted or refused on a mirror today; no new personal-session middleware may accidentally open them or turn their expected protocol response into an HTML login redirect. CORS is transport policy, not a substitute for route authorization (`apps/server/src/boot.ts:1690-1717`). Refuse copied till cookies on mirror reads at the till-session boundary; do not rely only on the blocked PIN POST to keep those reads unavailable.

### Live events and downloads

`GET /management-api/events` authenticates on connection and before later events/15-second wakeups (`apps/server/src/live-api.ts:95-104`, `:136-170`). Preserve that structure with the mirror backend and passive expiry. Close promptly on logout, freshness expiry, replacement or a mode transition, including a stream with no new data. Before any payload, re-read current authority; a queued change is not permission to send it later.

The current stream exposes resource identities and leaves resource authorization to later GETs (`apps/server/src/live-api.ts:88`, `:114-125`). For the first release, mirror events send only payload-free `reset` invalidations to a valid personal session, never resource IDs/types or data. Every venue change triggers the same general invalidation regardless of the requested resource types or IDs. Validate subscription syntax, then ignore its filters when deciding whether to send a mirror reset; retaining the current entity-filtered wakeup would still reveal activity against a guessed ID. Watched GETs then use their existing permission/subject checks. A reset can reveal that some venue activity occurred; it does not grant access to its records. Primary stream semantics remain unchanged. Re-read the shared query dependencies (`docs/developers/dashboard-live-updates.md:1-20`) when qualifying refresh behaviour.

**A980 S3 customer-data reads, proposed scope decision.** Once S3 is separately approved and built, a personally authenticated mirror account holding `personal_data.export` may use both `GET /management-api/invoice-customers/personal-data?taxId=…` and its `/export` sibling, with every S3 subject, validation, secret-exclusion and download check retained. This replaces S3’s temporary mirror refusal only after the complete A1111 authentication and freshness gates are installed. Without that readiness, protected reads refuse; there is no anonymous or ambient-cookie interval. If S3 has not landed, A1111 adds neither route nor invoice-rendering code. Its later builder applies the approved personal-auth contract in S3’s own change. This proposal changes neither fiscal writers nor invoice contents.

The reserved draft `feat/a980-s3-invoice-customer-download` at `ef0908ed0be3` names those two reads in `docs/superpowers/plans/2026-10-26-a980-s3-invoice-customer-download.md:73-76`; decision 14 at `:514-529` calls the mirror refusal temporary, until A1111 lands. That branch is not edited here. Reconcile its then-current plan and tests after approval, with a dated pointer retaining the historical expectation. A signed-in caller without `personal_data.export` must still be refused before any customer lookup, and a delayed download must repeat authorization before bytes leave.

All slow downloads that release protected data need the same pre-release authority and generation check, not just the S2c ZIP. Inventory attendance, reports, configuration and recovery downloads. This design does not add permission to export secrets: each existing source route retains its permission, proof, mode and secret-handling requirements. A read route that mutates venue or credential state must remain unavailable or get a reviewed read-only path; the verb gate alone is insufficient evidence.

## 7. What you see

Keep the venue banner and the shared login card, field primitives, semantic names and form messages. The mirror adds a visible “Read-only mirror” label and last-confirmed time. The public method choices depend only on mirror capabilities, never whether an email exists or has a factor/passkey. No modal passkey prompt or passive WebAuthn attempt starts here, even if a saved primary shortcut prefers passkeys.

Continue opens the password step; a correct password can open the authenticator-code step. Unknown, suspended, pending, wrong-password and wrong-code attempts retain the generic login refusal with no account-state field marking. Missing/malformed input follows normal validation. A deployment-wide unavailable method/freshness notice is the same for all visitors. Preserve Remember's consent rules (`conventions-ui.md:773-832`; `design-system.md:3730-3819`), scoped by mirror origin/node so it does not silently reuse another node's saved method. No optional passkey registration offer follows mirror login.

Your account menu shows your identity and Logout. Your profile is readable; credential, email, locale and profile saves remain primary actions. Theme/language choices may change this browser's presentation using existing client preferences; they cannot write a copied person row. Read-only mode quiets or omits mutation controls and explains why; routes still refuse direct mutation requests. Do not remove a read button merely because it is a download. Where a permitted primary action is useful, offer an explicit trusted primary link if one is available; never silently forward passwords or credentials between hosts.

If a read is forbidden, explain that this signed-in account lacks the required access and offer a deliberate sign-out/change-account action that returns to personal login. There is no PIN override or hidden Admin session. A fresh primary login is likewise deliberate, never opened by navigation or session expiry. Both English and Spanish guides/login wording change with the build; phone/desktop and both themes need future visual inspection. Text flows suffice for this design; no mockup images were requested or produced.

### Worked flows

1. **Owner downloads Marta's data.** You sign in as Alex, the venue owner whose current account holds `personal_data.export`. You open Users, Marta, Download their data. The server checks Alex's current permission before looking up Marta, builds Marta's file, then checks Alex again. Proposed response: `GET /management-api/staff/<Marta>/personal-data/export` with Alex's scoped cookie gives `200 application/zip`. The file names Marta as its subject; the session remains Alex's. With no cookie it gives `401 management_session.required`, not a primer cookie. Losing the permission during the build gives a refusal and no ZIP bytes.
2. **Manager reads reports.** You sign in as Sam, a manager. Report GETs requiring `report.view` work, and exports work only where Sam holds their own required permission. Sam cannot download Marta's personal-data file: the by-id route returns `403 authorization.not_permitted` before disclosing whether the target exists. Editing a report's settings remains read-only. The screen never promotes Sam because a button is visible.
3. **Waiter signs in without escalation.** You sign in as Lee, staff, using your dashboard password. You can read your own profile/data and the self-scoped views the source already allows. Lee cannot read admin reports or another person's data by typing a URL. A till PIN is not accepted on this form. Missing a dashboard password means use the primary's existing account setup, not a mirror-created account or an Admin fallback.
4. **An offline mirror has not received a revocation.** At 10:00 the source confirms the installed account generation. The connection drops. At 10:02 Lee is suspended on the primary, unseen by the mirror. Until 10:15 Lee can still authenticate/read the old account's allowed snapshot data; the stale notice says so. If the suspension arrives at 10:04, Lee loses access then. At 10:15 all protected mirror access stops, even Alex's; another login does not extend the deadline. This is the explicit accepted risk if you approve the default, not instant source revocation while disconnected.
5. **Restart.** You were signed in on the mirror. After restart your retained cookie resolves nothing, and the throttles have reset. If the source is available, it qualifies the snapshot again and you sign in again. If it is unavailable, you see why access is paused and can Retry or Stop; boot time does not make an old account copy fresh.
6. **Promotion.** Alex separately completes the existing promotion proof. The mirror changes to primary. All mirror sessions and streams are invalidated before another request can gain writable authority. Sending the old mirror cookie to `GET /management-api/session/me` gives `401 management_session.required`, and a write cannot reuse it. You use the normal primary sign-in. A separately held genuine primary session may still resolve under the existing primary-session survival rule; the mirror token is never converted into one.

## 8. Promotion, retirement, fencing and adoption

Use the current mode holder at resolution, local login completion and protected response release, not just a boot boolean. Invalidate the mirror store/streams as soon as the holder leaves mirror mode, before writable requests can authenticate. An in-flight login or export that began in mirror mode must not finish under primary authority. On a failed promotion that leaves the node a mirror, the old local store may be deliberately cleared; require a new sign-in rather than restoring tokens. Do not change promotion's fiscal transaction or proof requirements.

Primary account sessions remain stateful venue sessions. This proposal does not revoke all copied primary sessions on promotion or change the owner's #554 survival decision documented in `conventions-data.md:1466-1468`. During mirror mode they are ignored, even if the visitor presents their real token. After promotion normal primary resolution can use genuine primary tokens subject to current status, expiry and permissions. A hash copied from the database is never a token. The mirror cookie name cannot shadow the primary cookie on the same host/port.

Remove `ensureMirrorViewer`, `mirrorSession`, both fixed viewer IDs, the unusable-PIN marker and `endMirrorViewer` from production. Retire their boot calls, imports and adoption `ensureViewer` seat. Adoption completion becomes identity establishment followed by latch removal, with failures still retaining the latch; it does not grant a visitor a session. Do not use authentication work to bypass the currently missing initial venue copy or alter reserved fiscal identity establishment.

No compatibility cleanup, migration or revival of old viewer rows. Preproduction installations containing the synthetic viewer are reset before using the new build; primary startup no longer updates the viewer's session. Old ambient cookies find no mirror session in the new store. Do not carry a denylist of legacy fixed IDs as a permanent substitute for resetting those fixtures/installations. Preserve tests of malformed non-verifying PIN placeholders as generic behavioural assertions, rather than preserving the retired viewer account as a product concept.

Adoption-pending/setup/recovery boots do not mount the mirror personal-session surface. Keep their public minimal status and existing owned recovery actions. A retired node clears local authority and serves only its retirement/recovery surface. A fenced node does not obtain a mirror store or the new mirror login exemptions merely because it refuses writes; it retains the existing primary/fenced recovery and independently authenticated retirement paths. Mode transitions into these states invalidate any former mirror sessions. An identity-disabled module combination exposes no mirror login backend or synthetic substitute; public status explains unavailable authentication without boot touching identity tables for viewer cleanup.

`WAITRON_MIRROR_ALLOW_EXPOSED` remains an explicit operator consent to bind beyond loopback with the existing literal `true`/`1` parsing (`apps/server/src/mirror-bind-guard.ts:14-28`). It grants no session, permission, stale-data extension, Origin exception or plaintext remote login. Update the guard/error text and operator documentation to say exactly that. Qualification of the served HTTPS origin is separate from consenting to a network bind.

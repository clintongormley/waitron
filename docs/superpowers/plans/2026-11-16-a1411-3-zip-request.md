## Decisions (each with its default and why)

**D1. Where the file lives.** `<state>/scratch/tax-office/<build id>.zip`, the id a random UUID;
written as `<build id>.zip.part` through `pipeline(Readable.fromWeb(zipStream(...)),
createWriteStream(part))`, then `rename` to `.zip`. No flush: scratch is emptied at every start, so
a file that survived a power cut would be deleted anyway. A restart therefore removes a half-built
and a finished file alike, and the in-memory record goes with them. The folder name is a constant
`TAX_OFFICE_DOWNLOADS_DIR = \`${SCRATCH_DIR}/tax-office\`` beside `SPARE_FOLLOW_DIR`
(`state-layout.ts:49`). *Why:* scratch is already excluded from backups and cleaned at start, so
nothing new joins the layout, the backups or the reset.

**D2. How long, what removes it, full disk.** A finished or failed record and its file are kept
**24 hours** from when the build ended; the job's next pass after that deletes them (the pass
returns `nextDueAt` = the earliest expiry). A new request by the same person deletes their
earlier file at once. A request is refused with a new code `tax_office.space_low` when
`freeBytes(stateDir)` (`free-bytes.ts:6`) reads below `SPACE_OK_BYTES`; an unreadable reading
(`null`) does not refuse. A write failure (such as `ENOSPC`) fails the build and deletes the part
file. *Why:* starting at 2.5 GiB free, a 222 MB month keeps the disk above the 2 GiB line where the
free-space job starts deleting backups, and far above a disk-full stop. The status read and the
file fetch write nothing to the database, so a full disk does not take them down (the session's
last-seen stamp is existing behaviour).

**D3. One build at a time.** One build runs on the box at a time; each person holds at most one
record. A request answers:

| Situation | Answer |
| --- | --- |
| No build running | 202, `building`; one activity entry |
| This person's build of the same month running | 202, the running build's state; no entry |
| Any other build running | 409 `tax_office.export_running` (existing code and words) |
| This person has a ready or failed record | replaced by the new build; old file deleted |

*Why:* two renders at once would double the time the sale thread spends rendering (receipt
"Event-loop blocks"); queueing is more code for an event that needs two holders of
`invoice.inspect` pressing within the same three minutes.

**D4. Who may fetch; the activity entry.** Only the person who asked, and only while they still
hold `invoice.inspect` (`authorizeManager` on the fetching session). The activity entry stays where
#3543 writes it, once per accepted request, in the request's transaction; the fetch writes
nothing. The builder's end-of-build check on the requesting session (`tax-office-export.ts:174-182`)
is removed and `TaxOfficeMonth` loses `authorizedBy` and `sessionId`: no byte leaves the box before
the fetch's own check, and a build must not fail because the person's session went idle while they
waited. *Why:* the file holds every customer's name and tax number and the entry names the asker;
one entry per request keeps #3543's meaning ("when the download began") with no second write.

**D5. The notice.** A second `wt-toast` in the app shell (`dashboard-app.ts`, beside the alert
toast), not the alerts bell: alerts are venue incidents for managers, hidden from inspector-only
sessions, and need a recorded incident. The shell watches a new query `getTaxOfficeMonthDownload`
while the session holds `invoice.inspect`; dependency `tax_office_download`, in
`QUIET_WHILE_CONNECTED`, `refreshMs` 10 000. The server publishes `tax_office_download` on every
change of state. The shell shows a toast only for a change it saw happen (`building` → `ready`,
`failed` or `none`), never on its first read, so a reload does not repeat it.

**D6. Handover and restricted start.** Catalogue entry `"tax_office.month_zip"` marked

and shows the restart toast. A restricted start mounts no route and runs no job, so nothing changes
there and no test is added for it.

**D7. #3543's direct-download route.** Replaced, not kept beside: `POST

## Questions (each with the default this plan builds)

1. **How long is a finished file kept?** Default 24 hours, or until the same person asks again or
   the server restarts. Shorter means more rebuilds; longer means stale months for the current one.
2. **When is the activity entry written?** Default: at the request, as #3543 does, so an entry
   exists even if the build fails or nobody saves it. Alternative: at the first save (one more
   write on the fetch, which then needs a POST).
3. **Who may save the file?** Default: only the person who asked, while they hold
   `invoice.inspect`. Alternative: any holder of `invoice.inspect`.
4. **A second person asks while one build runs.** Default: refused with today's words, try again
   when it finishes. Alternative: queue it (more code, rare event).
5. **Low disk.** Default: refuse below 2.5 GiB free, and the free-space job does not delete
   finished files. The words tell the person to try later; on a box that stays low there is
   nothing they can do from Invoices, and an inspector cannot open Box status.
6. **How the browser saves it.** Default: as #3543 does, the whole file into the page's memory
   (about 200 MB), then saved. Alternative: a plain browser download (streams to disk, shows the
   browser's own progress), which needs the fetch to write nothing and its refusals handled outside
   the page.

## Decisions (each with its default and why)

**D1. Where the file lives.** `<state>/scratch/tax-office/<build id>.zip`, the id a random UUID,
written in place through `pipeline(Readable.fromWeb(zipStream(...)), createWriteStream(path))` and
deleted on failure. No part file and no rename: the file is served only once the in-memory record
says `ready`, so a half-written file is never offered; no flush, since scratch is emptied at every
start. A restart therefore removes a half-built and a finished file alike, and the record goes with
them. The folder is a constant `TAX_OFFICE_DOWNLOADS_DIR = \`${SCRATCH_DIR}/tax-office\`` beside
`SPARE_FOLLOW_DIR` (`state-layout.ts:49`). *Why:* scratch is already excluded from backups and
cleaned at start, so nothing new joins the layout, the backups or the reset.

**D2. How long, what removes it, low disk.** The file is deleted **as soon as it has been sent in
full once** (the read stream ended without the connection aborting), and an unsaved file **one hour**
after it became ready, by the job's next pass (the pass returns `nextDueAt` = the earliest expiry).
A failed record also lasts an hour. A new request by the same person deletes their earlier file at
once. *Why:* the scheduled backup's room step deletes old backups for any byte this file occupies
(above); deleting on save and capping an unsaved file at an hour keeps that to the rare backup that
starts within the hour, at most ~222 MB of extra deletion, once.

A request is refused with a new code `tax_office.space_low { freeBytes, neededBytes }` when
`lowestFreeBytes([stateDir, venueDir])` minus 256 MiB (above the receipt's largest month, 222 MB)
would fall below `SPACE_LOW_BYTES`; an unreadable reading (`null`) does not refuse. A write failure
(such as `ENOSPC`) fails the build and deletes the file. *Why:* the build then never takes the disk
below the line where the box warns and starts deleting backups, and the refusal never fires while
the box shows plenty of space for long: it fires only within 256 MiB of the warning line, and
states the numbers. The status read and the save write nothing to the database, so a full disk
does not take them down (the session's last-seen stamp is existing behaviour).

**D3. One build at a time.** One build runs on the box at a time; each person holds at most one
record. A request answers:

| Situation | Answer |
| --- | --- |
| No build running | 202, `building` with a new id; one activity entry |
| This person's build of the same month running | 202, the running build's view; no entry |
| Any other build running | 409 `tax_office.export_running` (existing code and words) |
| This person has a ready or failed record | replaced by the new build; old file deleted |

*Why:* two renders at once would double the time the sale thread spends rendering (receipt
"Event-loop blocks"); queueing is more code for an event that needs two holders of
`invoice.inspect` pressing within the same three minutes.

**D4. Who may fetch; the activity entry.** Only the person who asked, and only while they still
hold `invoice.inspect` (`authorizeManager` on the fetching session). The activity entry stays where
#3543 writes it, once per accepted request, in the request's transaction; the save writes nothing.
Its comment (`activity-kinds.ts:101-102`) becomes "Who asked for a month of invoices for the tax
office, which month (`YYYY-MM`) and how many invoices it held when they asked; never a customer
named in it." The builder's end-of-build check on the requesting session
(`tax-office-export.ts:174-182`) is removed and `TaxOfficeMonth` loses `authorizedBy` and
`sessionId`: no byte leaves the box before the save's own check, and a build must not fail because
the person's session went idle while they waited. *Why:* the file holds every customer's name and
tax number and the entry names the asker; one entry per request keeps #3543's moment with no second
write.

**D5. The notice.** A second `wt-toast` in the app shell (`dashboard-app.ts`, beside the alert
toast), not the alerts bell: alerts are venue incidents for managers, hidden from inspector-only
sessions, and need a recorded incident. The shell watches a new query `getTaxOfficeMonthDownload`
with `{ passive: true }` while the session holds `invoice.inspect`; dependency
`tax_office_download`, in `QUIET_WHILE_CONNECTED`, `refreshMs` 10 000. The server publishes
`tax_office_download` on every change of state. Each view carries the build's `id`.

The shell keeps the last view it saw (a failed read leaves it in place) and shows a toast when:
- a `ready` or `failed` view arrives whose `id` and `status` differ from the last view seen, except
  on the shell's first read of this sign-in (so a reload does not repeat it). The screen's POST
  answer counts as seen: the screen hands it to the shell (an app event,
  `tax-office-month-requested`, detail the view), so a month built inside one poll, which a polling
  inspector would see only as none → ready, still toasts;
- the last view seen was `building` and a `none` arrives (the server restarted).

**D6. Handover and restricted start.** Catalogue entry `"tax_office.month_zip"` marked
`{ stop: true }`: a stepdown aborts the job's signal, `stopIfAsked` throws at the next copy (within
one render: at most 97.2 ms in the receipt), the file is deleted and no record is left. The old box
then answers the shell's reads with 503 `handover.stepping_down` and, once restarted restricted,
has no such route, so the person gets no notice from it; Invoices on the main server shows no
record, and they press Download there. A restricted start mounts no route and runs no job, so
nothing changes there and no test is added for it. A plain restart is different: reads fail while
it restarts, then answer `none`, and the shell's kept `building` view gives the restart toast.

**D7. #3543's direct-download route.** Replaced, not kept beside: `POST
/management-api/tax-office/months/:month` keeps its path, own-page check and activity entry and
answers 202 with the view instead of the ZIP. New: `GET /management-api/tax-office/month-download`
(the person's view) and `GET /management-api/tax-office/month-download/file` (the ZIP, streamed
from the file, the handle closed on the connection's abort as `handover-source-api.ts:286-300`
does). `releasing` (`tax-office-api.ts:86-109`) and the `closed` dependency go.

**D8. The job's settings.** `minSleepMs` 1 000 (a wake is honoured within a second), `maxSleepMs`
3 600 000, `backoff` `{ firstMs: 60_000, maxMs: 3_600_000 }`, `applies: () => true`. A failed build
is recorded as `failed` inside the pass, never thrown, so the job keeps answering wakes and the
claim is released.

export type MonthDownloadView =
  | { status: "none" }
  | { status: "building"; id: string; month: string }
  | { status: "ready"; id: string; month: string; bytes: number; expiresAt: string }
  | { status: "failed"; id: string; month: string };
export const TAX_OFFICE_KEEP_MS = 3_600_000;
export const TAX_OFFICE_ROOM_BYTES = 256 * 1024 ** 2;
export interface TaxOfficeMonthBuilds {
  view(personId: string): MonthDownloadView;
  /** Synchronous, so two requests cannot both pass; throws tax_office.export_running (D3). */
  claim(personId: string, month: string): { claimed: boolean; view: MonthDownloadView };
  /** After the request's transaction commits: hands the build its inputs and wakes the job. */
  begin(personId: string, month: TaxOfficeMonth): void;
  /** The request's transaction failed after `claim`. */
  release(personId: string): void;
  file(personId: string): { id: string; path: string; bytes: number; month: string } | null;
  /** The file was sent in full: deletes it and the record. A later id leaves the record alone. */
  sent(personId: string, id: string): void;
  job(): JobDefinition; // name "tax_office.month_zip", settings D8
}
export function createTaxOfficeMonthBuilds(deps: {
  dir: string; // join(stateDir, TAX_OFFICE_DOWNLOADS_DIR)

  changed: () => void; // publishState(liveEvents, "tax_office_download", log)
  wake: () => void; // jobRunner.wake("tax_office.month_zip")
  log: Logger;
  keepMs?: number;
}): TaxOfficeMonthBuilds;

## Questions (each with the default this plan builds)

1. **How long does a finished file stay on the server?** Default: until it has been saved once,
   or one hour unsaved. Trade-off: every byte it holds when a scheduled backup starts makes that
   backup delete as many bytes more of old local backups (`backup-sweep.ts:236-262`,
   `backup-room.ts:221-290`); a longer keep (say 24 hours) lets the person come back next day but
   would make the nightly backup delete up to ~222 MB more; a save that fails after the whole file
   reached the browser means asking again (about three minutes).
2. **When is the activity entry written?** Default: at the request, as #3543 does, so an entry
   exists even if the build fails or nobody saves it. Alternative: at the first save (one more
   write on the fetch, which then needs a POST).
3. **Who may save the file?** Default: only the person who asked, while they hold
   `invoice.inspect`. Alternative: any holder of `invoice.inspect`.
4. **A second person asks while one build runs.** Default: refused with today's words, try again
   when it finishes. Alternative: queue it (more code, rare event).
5. **Low disk.** Default: refuse when building would take free space below 2 GiB (the line where
   the box warns and starts deleting backups), with words naming the sizes and pointing at
   Backups' "Keep at most". An inspector-only session cannot open Backups; for them the words still
   say what happened, and nothing on Invoices fixes it. Alternative: refuse only while the box's
   low-space warning is on, and let a build near the line set it off and delete backups.
6. **How the browser saves it.** Default: as #3543 does, the whole file into the page's memory
   (about 200 MB), then saved. Alternative: a plain browser download (streams to disk, shows the
   browser's own progress), which needs the fetch to write nothing and its refusals handled outside
   the page.

## As built (2026-11-16, after the pre-merge review)

- **The ready time is the browser's local time, not the venue's** (Amendment 2 asked for the
  venue's). No read the dashboard shell already makes carries the venue's time zone. The

- **The file route names the build:** `GET /management-api/tax-office/month-download/:id/file`,
  served only while `:id` is the person's ready file, otherwise `tax_office.download_missing`. Without
  the id, a second month built from another tab between the check and the download was served under
  the first month's Save.
- **The build re-reads free space as it writes** and, while free space can be read, stops, deletes
  the partial file and fails before free space would fall below 2 GiB. The check at the request
  stays; the 256 MiB allowance is only its estimate. `tax_office.space_low` answers 507, as
  `storage.disk_full` and the restore refusals do, and the person is offered Backups or an
  administrator sign-in beside it.
- **A build stopped this way fails with its own refusal, `tax_office.space_ran_out { writtenBytes }`**,
  not `tax_office.space_low`: it names how much the file had taken in when it was stopped, and
  offers the same Backups or administrator sign-in. Shown as free and needed space, the two
  figures came out nearly equal, because the partial file is deleted before the person reads them.
- **The activity entry is `tax_office.month_requested`**, not `tax_office.month_downloaded`.
- **The app shell alone reads the month-file status** and hands it to the Invoices screen; the
  status is read once a minute, and every 10 seconds only while this person's file is being
  prepared and the live stream is down.

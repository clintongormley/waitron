# Send CI jobs to the server before using GitHub

Fill the available Hetzner slots with eligible jobs as they become ready, then send overflow to GitHub. A second planner must see the first planner's grants before its jobs appear in GitHub. The watcher requested this plan on 18 November at 00:53 CET in Lane I's `questions.md`, quoting the owner on 8 November, “i don't want a queue on CI and to have hetzner idle”.

- [ ] **Prove the round trip.** In one owned qualification run, test a small request artifact from `changes`, read by the existing controller's GitHub App before the planner finishes. The controller replies through a repository variable read with the existing capacity credential. Measure two overlapping requests, reply time and API use. If the existing permissions and routing deadline cannot accommodate it, bring the result back before building. [Artifact API](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact) · [Variables API](https://docs.github.com/en/rest/actions/variables#get-a-repository-variable)
- [ ] **Grant capacity once.** In Cloud's `scripts/disposable-tests/{control,ci-canary,leases}.mjs`, use the controller's existing slot and memory admission and record the grants together before replying. Bind each to repository, workflow, run, attempt, head and exact job/shard. Count queued work and grants awaiting their GitHub job rows. Match the existing lease when the job appears, so it consumes one place. Start with a failing `ci-auto.test.mjs` case for simultaneous requests and repeat it across a controller restart. Check duplicate requests and release on a completed, superseded or timed-out request using verified run/job status.
- [ ] **Route jobs individually.** In `.github/workflows/ci.yml` and `scripts/ci-server-health.mjs`, derive ready keys from the existing gates and watchdog families, adding the stream job. Grant typecheck, root guards and lint first, then server shards in numeric order and the remaining keys in stable order. Use the granted keys in `runs-on` and the watchdog, keeping exact labels and existing trust, retry and health fallbacks. Test mixed matrices, missing grants, a failed planner's lint/root behavior and the exact watchdog subset in `scripts/ci-{hosted-route,server-health,server-first,workflow}.test.mjs`. [Actions contexts](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#context-availability)

The first split covers jobs that wait only for `changes`. Keep the bootstrap planner's current selection and use GitHub for dependent merges in that slice. Give the later merges fresh grants when their own prerequisites finish in a follow-on slice. Whole-run server-first is about 20–40 lines including tests and would queue the entire batch on Hetzner when even one slot is free. A fixed split can leave slots idle. A snapshot split can give the same slot away twice. Estimate for the grant and initial split is 300–450 implementation lines and 200–300 test lines after the transport proof, across separate Cloud and Waitron changes.

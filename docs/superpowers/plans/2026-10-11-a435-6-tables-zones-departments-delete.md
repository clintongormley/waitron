## Reconciliation and bounded decisions for the driver

The following are implementation defaults, not new owner decisions. Record them in the driver's FYI. Do not reopen resolved design questions interactively.

1. **Individual tables are already delivered by the floor dependency.** The old A435 statements that tables have `active`, labels are unique within a zone, and `/management-api/tables/:id` PATCH/DELETE disable them are superseded. At this base `dining-tables.ts:14` has eight columns and no `active`; `floor-plan-table-panel.ts:221` stages `deleteTable(draft, key)` with Undo/Redo; `saveZonePlan` checks revision/bookings, deletes saved joins/master rows and unlinks followers, leaving today's table until reset/catch-up. Labels remain unique **per location**, and become reusable on today's plan after actual removal. Keep POST/PATCH/DELETE `/management-api/tables...` and retired placement paths 404, including an `active` PATCH. Do not add an immediate table Delete route, two-call confirmation for a reversible draft edit, or an irreversible warning before Undo. Task 11 pins this reconciliation; Task 10 handles a deleted containing zone.
2. **Hierarchy deletion is immediate and all-or-nothing.** It refuses an open party that currently holds OR earlier used a child table; an open/placed delivery order or food still on its way; a booked/seated booking assigned to a child table, regardless of booking date; an open/placed order context; pending transfers; profile-only access; and the last department. It never forces table catch-up while live work remains. The stricter hierarchy booking policy is separate from the existing master-edit policy (upcoming `booked` only). Preserve that existing policy and its tests.
3. **Table history follows the later floor design.** Closed parties already release memberships and keep names as text (`parties.ts:667`). Successful hierarchy deletion uses the existing `removeLiveTables` release path: terminal bookings keep `tableLabel`, orders keep `deliveryTableLabel`, and their table pointers clear before physical removal. These two column updates are the approved floor exception to A435's older “no history column loses its database link”. Fiscal records and issued order labels never change. An unknown remaining table reference causes a domain refusal and rollback, not silent partial deletion.
4. **Profiles today have ONE department, not a department list.** `device_profile_service_access` has one parent per profile. Every nonretired, non-KDS profile bound to the deleted department refuses `department.profile_in_use`, even if no active device uses it. Do not remove that parent and turn the profile unrestricted. Zone deletion refuses an affected such profile if its effective allowed zones after deletion would be empty, including Every-zone profiles. Otherwise clear explicit memberships and replace a removed starting zone by the first surviving permitted zone ordered by display order/name/id. Keep Every as Every. Retired/KDS legacy service scopes may be removed; explicit kitchen-screen scope parents stay, including `every_zone = false` with zero memberships.
5. **Defaults are replaced without inventing configuration.** If deleting the default department, promote the first surviving active department by name/id; clear old `isDefault` before setting the replacement. If deleting the counter-default zone, choose the first surviving configured active zone in the same department, then the first elsewhere, by display order/name/id. If none survives, leave no counter default and retain `service_zone.default_missing` for unscoped order creation. Never fabricate a zone/menu or widen a profile. Count/name replacement in impact. A profile that cannot order never falls through to the venue counter default.
6. **Department receipts are retained internal data.** `receiptDepartmentForSale` and `readPrintedDepartmentReceipt` in `department-receipts.ts:158,233` use the stored department receipt configuration for reprints. Keep `department_receipts` and media-use retention, hide it from configuration export/edit choices, refuse editor reads/writes for the deleted department, and let internal sale/reprint readers use it. Removing it would change existing reprints; the old spec did not inventory this later table.
7. **Removed settings reflect today's tables.** There are no authored department-hours/zone-menu/watchers tables to restore: current hours/menu assignments are menu periods/timetables/slots, `zone_closed_times`, extensions and kitchen-screen zone memberships. Shared venue special dates, menus, holidays and service settings survive.

**Contradictions:** old table soft deletion/immediate route/within-zone uniqueness/history-link assertions conflict with the later explicit owner-approved floor decisions above; follow the latter and retain their tests. The department-list model and authored-hours inventory in the old spec are factual mismatches resolved by today's schema. No unresolved product decision remains under these bounded defaults. If the driver's fresh review rejects this precedence, revise this document before implementation; do not add a table sentinel or rewrite history to disguise the conflict.

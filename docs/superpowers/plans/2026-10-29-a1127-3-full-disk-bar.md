# A1127 slice 3: a red bar on every dashboard page while the full-disk stop holds

**Goal.** While the box's full-disk stop holds (the tills refuse every save), everyone signed in to
the dashboard sees a red bar under the banner, on every page, from the moment they sign in. It
says the disk is full so the tills cannot save anything, what old backups the box recently deleted,
and what Box status can still free; its button opens Box status, or, for someone who cannot open
Box status, offers a manager's sign-in in place. No dialog, no new delete route.

## Decisions this plan makes that the spec does not (each goes in the PR description)

1. **The bar's read is a new small route, `GET /management-api/disk-stop`, for any signed-in
   dashboard session** (staff, supervisor, manager, admin). It answers
   `{ stopped: boolean, deleted: { count, date, lastDate, severalDays } | null }` — no timestamp,
   which the bar does not need (review M8). Not `listAlerts`: its `storage.disk_full` is
   `system.manage` only and staff never watch it (`dashboard-app.ts:1251-1254`); widening that claim
   would also widen the bell. Not `getMe`: it runs at sign-in and on re-probes, never on a timer.
2. **The read never stamps the session and runs in ONE write-lock turn with no change-log drain**
   (`db.withWriteLock` + `resolveManagementSession(db, token, { touch: false })`), so it answers on
   a full disk with a change waiting, which is the only time the bar matters. A stated exception to
   one transaction per route ("Housekeeping writes must not take reads down on a full disk",
   CLAUDE.md §3), said in one line at the site. The bar's read is also passive on the client
   (decision 4).
3. **The bar follows `since()`, as the bell, the till strip, the email and Box status do.** It shows
   while the stop is noted and goes when the watch's next `full()` (≤ 60 s) or **Free** lifts it.
4. **The shell reads it passively from the first read, every 30 seconds, and again on any
   `incidents` change.** Passive, so an open dashboard does not keep its session alive (CLAUDE.md
   §3). 30 s, not Box status's 15 s: this read runs on every page of every signed-in tab and takes
   the write lock briefly; 30 s keeps the bar within half a minute of the stop lifting. On a failed
   read the bar keeps what it last showed (a read that fails is not news that the stop lifted) and
   the shell records `disk_stop.load_failed` in diagnostics. Signing out, expiry or a session
   refusal empties the bar's state (`#returnToLogin` sets it to null as well as releasing the
   query), so a later sign-in on the same tab never shows the previous person's bar (review I2).
5. **The deletion facts are the open `backup.archives_deleted` incident's, and only for a person
   holding the permission that alert's claim names** — read through `claimFor(registry,
   "backup.archives_deleted").permission`, with the same registry the alerts route uses, so the bar
   can never show what the bell hides if the claim changes (review M7). Today that is
   `system.manage`. They are read only while the stop holds. The first deletion's count, as the bell.
6. **Only a recent deletion is named: an open alert detected within the 24 hours before the read.**
   An unhandled alert can be days old, and its date is the day the backup was taken, so nothing in
   the line would tell the reader the deletion is old (review M9). The simplest honest default is to
   leave the sentence out past a day rather than add a second date. Not filtered by the stop's start:
   lane A's start-time deletion runs before the stop is noted. Owner question in the PR.
7. **The bar never says the box deleted "every old backup it may".** A1167 Q3 A's summary says so,
   but the read cannot know it: the watch deletes nothing while a backup run holds the staging turn
   or before its first reading after a start, and nothing at all where backups are off or on a
   standby (A1167 design §1, §2). Owner question in the PR.
8. **Words: one line per case (table below), built from `AlertMessageEntry` values** (the `one` and
   `severalDays` forms copied from `backup.archives_deleted`) and drawn through dashboard-kit's date
   formatting. To reach it the kit exports `alertWords(entry, params, locale)`, which `alertMessage`
   then calls; no alert's output changes. The first sentence says what the stop does — the tills
   cannot save anything — as the design's bar words, the bell and the till strip do, not "stopped
   selling" (lead's call on review M4).
9. **The button.** With Box status (`system.manage`): **Open Box status** / «Abrir Estado del
   equipo», which navigates there (`#selectScreen("box-status")`, which asks first when a screen
   holds unsaved changes); on Box status itself the bar draws no button. Without it: **Sign in as a
   manager** / «Iniciar sesión como encargado», which runs the existing in-place sign-in path
   (`#onLogout`, which asks first about unsaved changes) with Box status kept as the destination:
   `#returnToLogin` gains an optional `next` screen that it writes to the URL instead of null. A
   manager or administrator who then signs in with a password or passkey lands on Box status; a
   Google sign-in (whose redirect names no screen) and anyone without Box status land on their usual
   first page (staff on My schedule, supervisors on Overview). Box status after Google would need a
   server change to the redirect, outside this slice; listed in the PR. The words say the button
   signs the person out. No one is sent to somebody else (CLAUDE.md §3, refusal rule).
10. **"Red": `wt-banner` gains `tone`, `"info"` (default, unchanged) or `"error"`**, which paints the
    inline-start edge and the bottom border `--wt-color-danger`, as `wt-toast`'s error tone paints
    its edge. No tinted fill (no token for one; see above) and no icon (`wt-banner` registers none;
    the till's icon paths live in the till app). The words stay `--wt-color-text`. The bar keeps
    `wt-banner`'s default `role="status"`: it moves between the banner row and the floor plan
    editor's slot, and `wt-banner` refills its message on every move, so `role="alert"` would
    interrupt a screen reader each time the editor opens or closes (review M10); whether either role
    is read out has not been tested (`design-system.md:849`). A filled bar (`--wt-color-danger` fill,
    `--wt-color-on-danger` words) is possible with existing tokens and listed in the PR as the
    owner's alternative.
11. **Placement.** In `#notices(slot)`, before the update bar: under the banner, above the update
    bar when both show, and in the floor plan editor's `notices` slot while it is open. Never on the
    sign-in page (the read needs a session). At phone width it wraps as the update bar does
    (`.bar` is `flex-wrap: wrap`, `wt-banner.ts:23-29`).
12. **A manager sees the bar and the bell's error toast together** when the stop's alert arrives
    (review M5). Default: keep both. The toast is the bell's arrival notice, closes itself and leads
    to the bell, where managers mark alerts handled; the bar is the standing statement for everyone,
    staff included. Changing the bell or its toast is outside this slice. Both say the same thing in
    different words; owner question in the PR (keep both, or hide the toast for `storage.disk_full`).
13. **Guides.** `apps/server/src/guide/en/box-status.md` and `es/box-status.md`, section
    `{#out-of-space}`: one paragraph on the bar. No new heading.
14. **Backlog.** The A1127 slice 3 entry is deleted from `docs/backlog.md` and `docs/backlog/setup.md`.
    The owner questions go in the PR, not the backlog. A new backlog entry only if the LOOK task
    finds a defect it does not fix.

# A1127 slice 3: a red bar on every dashboard page while the full-disk stop holds

**Goal.** While the box's full-disk stop holds (the tills refuse every save), everyone signed in to
the dashboard sees a red bar under the banner, on every page, from the moment they sign in. It
says the tills have stopped selling because the disk is full, what old backups the box has already
deleted, and what Box status can still free; its button opens Box status, or, for someone who
cannot open Box status, offers a manager's sign-in in place. No dialog, no new delete route.

## Decisions this plan makes that the spec does not (each goes in the PR description)

1. **The bar's read is a new small route, `GET /management-api/disk-stop`, for any signed-in
   dashboard session** (staff, supervisor, manager, admin). It answers
   `{ stoppedSince: string | null, deleted: { count, date, lastDate, severalDays } | null }`.
   Not `listAlerts`: its `storage.disk_full` is `system.manage` only and staff never watch it
   (`dashboard-app.ts:1251-1254`); widening that claim would also widen the bell. Not `getMe`: it is
   not refreshed.
2. **The read never stamps the session and runs in ONE write-lock turn with no change-log drain**
   (`db.withWriteLock` + `resolveManagementSession(db, token, { touch: false })`), so it answers on
   a full disk with a change waiting, which is the only time the bar matters. A stated exception to
   one transaction per route ("Housekeeping writes must not take reads down on a full disk",
   CLAUDE.md §3), said in one line at the site. The shell's reads are all passive anyway (decision 4),
   so no stamp is lost.
3. **The bar follows `since()`, as the bell, the till strip, the email and Box status do.** It shows
   while the stop is noted and goes when the watch's next `full()` (≤ 60 s) or **Free** lifts it.
4. **The shell reads it passively from the first read, every 30 seconds, and again on any
   `incidents` change.** Passive, so an open dashboard does not keep its session alive (CLAUDE.md
   §3). 30 s, not Box status's 15 s: this read runs on every page of every signed-in tab and takes
   the write lock briefly; 30 s keeps the bar within half a minute of the stop lifting. On a failed
   read the bar keeps what it last showed (a read that fails is not news that the stop lifted) and
   the shell records `disk_stop.load_failed` in diagnostics. Signing out, expiry or a session
   refusal clears it with the rest of the shell (`#returnToLogin`).
5. **The deletion facts are the open `backup.archives_deleted` incident's, and only for a person
   holding `system.manage`** — the alert's own claim (`packages/db/src/alerts.ts:9`), so the bar
   shows no one a fact the bell would not. They are read only while the stop holds. One open at a
   time; it names the first deletion's count (as the bell does). A handled alert, none at all
   (backups off, a standby, bucket-only, only the newest backup kept), or a person without
   `system.manage`: no deletion clause.
6. **The bar never says the box deleted "every old backup it may".** A1167 Q3 A's summary says so,
   but the read cannot know it: the watch deletes nothing while a backup run holds the staging turn
   or before its first reading after a start, and nothing at all where backups are off or on a
   standby (A1167 design §1, §2). The bar says only what the open alert records. Listed in the PR
   as a question for the owner.
7. **Words: one line per case, below, built from an `AlertMessageEntry` table** (the `one` and
   `severalDays` forms copied from `backup.archives_deleted`) and drawn through dashboard-kit's
   date formatting. To reach it the kit exports `alertWords(entry, params, locale)`, which
   `alertMessage` then calls; no alert's output changes.
8. **The button.** With `system.manage`: **Open Box status** / «Abrir Estado del equipo», which
   navigates there (`#selectScreen("box-status")`); on Box status itself the bar draws no button.
   Without it: **Sign in as a manager** / «Iniciar sesión como encargado», which runs the existing
   in-place sign-in path (`#onLogout`, the same as "Sign in as an administrator") with Box status
   kept as the destination: `#returnToLogin` gains an optional `next` screen that it writes to the
   URL instead of null, so a manager or administrator signing in lands on Box status, and anyone
   else on Overview, as today's fallback for a screen they may not open. The words say it signs the
   person out. No one is sent to somebody else (CLAUDE.md §3, refusal rule).
9. **"Red": `wt-banner` gains `tone`, `"info"` (default, unchanged) or `"error"`**, which paints the
   inline-start edge and the bottom border `--wt-color-danger`, as `wt-toast`'s error tone paints
   its edge. No tinted fill (no token for one; see above) and no icon (`wt-banner` registers none;
   the till's icon paths live in the till app). The words stay `--wt-color-text`. The shell gives
   the bar `role="alert"`, as `wt-toast` uses for its error tone (`wt-toast.ts:153-154`). A filled
   bar (`--wt-color-danger` fill, `--wt-color-on-danger` words) is possible with existing tokens
   and listed in the PR as the owner's alternative.
10. **Placement.** In `#notices(slot)`, before the update bar: under the banner, above the update
    bar when both show, and in the floor plan editor's `notices` slot while it is open. Never on the
    sign-in page (the read needs a session). At phone width it wraps as the update bar does
    (`.bar` is `flex-wrap: wrap`, `wt-banner.ts:23-29`).
11. **Guides.** `apps/server/src/guide/en/box-status.md` and `es/box-status.md`, section
    `{#out-of-space}`: one paragraph on the bar. No new heading.
12. **Backlog.** The A1127 slice 3 entry is deleted from `docs/backlog.md` and `docs/backlog/setup.md`.
    The owner questions (decision 6's stronger phrase, decision 9's filled bar, the words) go in the
    PR, not the backlog. A new backlog entry only if the LOOK task finds a defect it does not fix.

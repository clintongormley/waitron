# Security change emails — implementation plan

**Goal / usable finish:** After a person changes their own account security, the existing mail sender delivers a short English or Spanish notice to their current address after commit. One PR; at most three build hours.
**Request:** Lane K `queue.md`, SECURITY-CHANGE-EMAILS, quoting `docs/backlog.md:1241–1244`: “Tell people by email when their account's security changes (owner, 2026-09-12): password changed, passkey or authenticator added or removed, recovery codes regenerated, email changed, Google login connected or disconnected. No link, one line on what to do if it was not them. Open: notify the OLD address on an email change; wording when an admin made the change; grouping a burst.”
**Handoff:** Separate plan-writer draft. Driver checks it, obtains Claude review, then watcher clearance before building; no owner approval of this plan is claimed.

## Reuse and boundaries

- Reuse `enqueueMail`, `MAIL_LIFETIME_MS`, `MailKindOwner`, and `runMailPass`; use a new `security_change` kind. `account-mail.ts:25–43` issues action tokens during claim, so do not reuse `account_action` or its composer.
- Source trace: `me-api.ts:240–345` calls own-account functions in `packages/identity/src/profile.ts`; passkey add is `/management-api/passkey/register/verify` (`management-api.ts:1938–1954`) → `finishPasskeyRegistration`; Google callback's link branch (`:818–826`) → `completeGoogleLink`. Production callers found by searching these producer names are these routes; keep notices in the identity producers, not duplicate route wrappers.
- Follow `role-membership-mail.ts:26–40`: read `persons.email` and `persons.locale` in the sender's claim transaction, on each attempt; fall back to venue locale, cancel if no address. Thus email confirmation uses the new address, and an address changed while mail waits replaces the earlier one. `mail-sender.ts:200–276,348` commits the claim before transport. No address snapshot in queue params, and no SMTP on the request path.
- Leave OLD-address notification, admin-change wording, and burst grouping open in the backlog. Leave the separate admin `email_changed` notice untouched. Exclude PINs, password reset/invitation flows, enrolment starts, pending email, refusals, replays, no-op removals/links, and ordinary Google login. No event ledger, framework, timer, or grouping policy.
- Preserve authentication, password hashing work, transaction boundaries, rollback and route answers. Queue only identifiers and the change name; no secrets or addresses in params or new log text. Any personal log field must use `log-personal-data.ts`'s declared keys.

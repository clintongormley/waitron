## Decisions and exact read contracts

**Routine executable defaults, for retrospective review:** own Hours opens the current **week**, with Week/Month and previous/next/date controls; weeks start Monday. Manager Hours opens the **configured current pay period**, normally monthly, with previous/next/date controls. Both use the server's venue business date for an omitted date, never browser timezone or UTC today. Retain the direct menu Fix my hours shortcut alongside My hours and put Fix my hours in the hours screen too; all lead to the same part-4 workflow. My Schedule Hours includes Fix my hours and own pending answers, using the existing command executor. The personal-phone exclusion concerns clocking, so no browser clock-in/out or break route is added. Existing scheduling remains the first tab. No automatic total timer; refresh on entry, explicit Refresh, after a known attendance result, and dashboard resource changes. These are implementation defaults, not further owner rulings.

Define additive, erased-import types in `packages/workforce/src/attendance-contract.ts` and re-export them from `packages/dashboard-modules/src/index.ts`. Existing `Period`, `TimeRecord`, `TimeEntryRecord`, `WorkSession`, `AttendancePrompt` and `CorrectionItem` retain their meanings:

- `HoursSelection = {kind:"week"|"month"|"pay-period"; date?:string}`. The date is a real four-digit `YYYY-MM-DD`, absent only for the current window. Own endpoints accept week/month; manager accepts pay-period. Reject empty/unknown/repeated query values, unknown keys, wrong mode and person selectors on own routes.
- `HoursDay = {date:string; sessions:WorkSession[]; workedMinutes:number}`. Produce every calendar date in the half-open period, including zero days and split shifts; daily and period totals sum **completed effective** sessions once. An overnight shift belongs to its existing local start date, with the end's full date/offset visible. No synthetic finish or elapsed minutes for an open shift.
- `HoursOpenShift = {start:TimeEntryRecord; breakStart:TimeEntryRecord|null}`. Derive the unmatched effective in and current unmatched break from complete history using existing `effectiveClockEntries`/ordering, rather than the latest raw requested row or a day-limited query. It is a read presentation, never an admission state or clock-write precondition. Show ongoing/open records separately even when their start is outside the selected period.
- `HoursClosure = {closureId:string; period:Period; clock:BusinessDayClock; scheduledCloseAt:string; closedAt:string; closureHash:string; frozenWorkedMinutes:number}`. Join these metadata to `record.closures` by id; frozen minutes come from the same person's stored snapshot. Keep the full stored period visible when it only overlaps a week/month. Never label an overlapping whole-month snapshot as a frozen weekly total.
- `PersonHours = {personId:string; locationId:string; selection:HoursSelection; period:Period; businessDay:string; clock:BusinessDayClock; asOf:string; days:HoursDay[]; workedMinutes:number; record:TimeRecord; openShifts:HoursOpenShift[]; pending:{prompts:AttendancePrompt[]; items:CorrectionItem[]; automaticEntryIds:string[]}; closures:HoursClosure[]}`. `asOf` is server time, not an elapsed-total endpoint. `pending` spans this person's outstanding work at the selected location **independent of the date filter**, including disputes; date/period changes cannot hide old obligations. `automaticEntryIds` identifies currently effective automatic ends still lacking worker acknowledgement, including those with a pending correction. Include the corresponding original/history rows in `record.entries` even outside the window, without adding their minutes to the selected totals. Preserve own closure filtering.
- `ManagerHours = {locationId:string; selection:HoursSelection; period:Period; businessDay:string; asOf:string; people:{personId:string; displayName:string; hours:PersonHours}[]}`. Include minimal person names needed by the current list and retained history, including suspended workers with records. A worker receives no such roster through own endpoints.

In new `packages/workforce/src/hours-reads.ts`, export `readPersonHours(tx:Transaction,input:{personId:string;locationId:string;selection:HoursSelection;clock:BusinessDayClock;now:Date}):Promise<PersonHours>` and `readManagerHours(tx:Transaction,input:{locationId:string;selection:HoursSelection;clock:BusinessDayClock;now:Date}):Promise<ManagerHours>`. The server supplies `readLocationClock`; workforce adds no reporting dependency. Internally use `readTimeRecord`, `readRecordedEntries`, `readAttendanceInbox`, `projectCorrectionItems` and existing closure readers. Do not change their authority or add a SQL event-date bound that loses late responses or retimes across months. Resolve a manager date inside an existing closure to its **stored period**, even if today's pay cadence changed; otherwise call existing `resolvePayPeriod(readPayPeriodSettings(...),date)`. Retain saved clocks/hashes and display current effective totals, frozen totals and `closedPeriodImpacts` as distinct facts. Never close a period while reading.

For manager assembly, reuse the person reader sequentially for each minimal listed person, without per-day queries. This deliberately retains the known complete-history read cost; no performance improvement is claimed. A future bulk implementation must preserve exactly these person/location and cross-window assertions. New read helpers own no transaction, reconcile no operational state, append no entries/markers, and mutate no question/mail row.

## Review focus

1. **Boundary dates:** a venue business day differs from UTC/browser today, and an overnight/DST session crosses a month. Expected: the default window follows the venue, stored start-date totals remain unchanged, and both offsets/dates remain visible. Tasks 1/2/4/5 pin this.
2. **Automatic/pending/open:** an automatic end is counted while unacknowledged, even when its prompt is suppressed by a pending request; open work and breaks never gain an invented finish. Tasks 1/4/6 pin totals and separate statuses.
3. **Frozen/late:** a later-node approval moves a session across a closed-period boundary or current cadence/zone changes. Expected: frozen snapshot/hash/clock remain exact and both current periods show the proper total/impact. Tasks 1/4/5/6 pin it.
4. **Identity and stale reads:** old operator/session/profile/location replies or an older read arriving after a newer snapshot cannot reveal another person's data, replace the selected view or enable a stale action. Tasks 2/3/4/5/6 include allowed controls and deferred replies.
5. **Recovery and authority:** a successful correction followed by failed refresh closes its editor; uncertain receipt/PIN replay remains the existing workflow; background recovery never erases an action refusal or edited draft. Tasks 3/4/6 pin it through actual owners.

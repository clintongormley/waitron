# A1003: Refuse a new record with a wrong fingerprint Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Before building, obtain the exact fiscal-test approval in [the implementation gate](#implementation-gate).

**Goal:** Refuse an invoice operation when the newly built record's fingerprint fails its local check, roll back the issuing transaction, and record a separate alert.

**Architecture:** Keep the check at `attemptAppend`, where both record types are complete and neither has been inserted. Carry a refusal and minimal incident context to the transaction owner, which records the incident only after rollback. Keep stored-predecessor verification and its report-and-continue policy separate.

**Tech Stack:** TypeScript, installed `@waitron/verifactu` 0.2.1, Drizzle over `node:sqlite`, existing core incidents, Hono error boundaries, Vitest and Chromium.

**Spec:** [Owner requirement below](#owner-requirement), plus [A985 findings §19](../../compliance/verifactu-findings.md#19-cancellation-replay-zero-total-and-wrong-fingerprint-added-2026-10-22-a985). No additional spec artifact is required.

## Review Focus

1. **R1, Task 2:** A valid-length, uppercase fingerprint is wrong for the complete new alta or cancellation; reject the operation rather than mistaking it for a malformed-hash case.
2. **R2, Tasks 1–3:** Repeated refusal and then a repaired retry of the same bill leave one open alert and use the same still-unused invoice number exactly once.
3. **R3, Task 4:** An edit, adjustment, cancellation, split or payment completion triggers issuance late in its transaction; refuse and undo that transaction's earlier changes too.
4. **R4, Tasks 1 and 4:** Alert persistence fails, or a card was captured before issuance; preserve the original refusal, preserve previously committed payment facts, and never charge again on recovery.
5. **R5, Task 2:** A stored predecessor fails verification while the newly built record verifies; retain the predecessor incident and continuation behaviour, with no edit to the stored predecessor.

## Decisions and file map

**One new domain code:** `fiscal.fingerprint_mismatch: Record<string, never>`, declared in `packages/fiscal-verifactu/src/errors.ts`. Use it for both the request refusal and its error-severity incident. Do not expose amounts, invoice identity, expected/found fingerprints, customer data or an attempted sale id in params.

**Check the new record only:** immediately after the existing `validate` call, detect an issue with code `HUELLA_MISMATCH` and throw the new refusal before `toRegistroRow`. Give that cause priority if validation also reports another issue. Keep the existing error/format refusal and totals/other-warning policies. No extra hash algorithm, second verifier, library fork, builder injection option or repair path is needed. Do not branch on `verifyChain.ok` or change backup verification. This checks the built object before row conversion; it does not independently revalidate the stored row or outgoing XML. Retain the existing row-roundtrip and hash suites. Narrow `chain.ts:177–181` to describe that scope rather than claiming the check covers everything stored or sent.

**Durable boundary:** add `IssuanceRefusal` and `withIssuanceTransaction` to the existing core `incidents.ts`, exported by core's `index.ts`. The fiscal module already depends on core; core does not import a module. The class carries an AppError plus non-enumerable origin and detection time. The wrapper awaits ordinary `withTransaction`; after it rejects with this class, it opens one separate `withTransaction` for `recordIncidentOnce`, then rethrows the same refusal object. Other errors pass through unchanged. Keep `@waitron/db`, `FiscalBackend`, `FiscalContribution`, server-kit and shared AppError APIs unchanged. An issuing transaction owner must adopt this wrapper to attempt the durable incident. Exported core/backend functions still accept ordinary caller-owned transactions: the append guard refuses there too, but cannot persist the incident after their rollback. The inventory covers the product owners found at this base; future owners must adopt the same contract. No universal after-rollback hook is proposed.

Always omit `saleId`, even for cancellation. Deduplicate to one open mismatch incident per source/device with null sale id. Keep its first detection time; handling it allows a later refusal to create a new incident. Success does not automatically acknowledge it. This deliberately bounds alerts per origin rather than per failed bill or tap.

**Alert failure decision:** attempt the separate incident write once, without background work or retries. If it fails, log the original refusal code with `incidentRecorded:false` and only the classified incident failure code; rethrow the original mismatch, including when the incident failed for full disk. The optional logger must not replace that error if it throws; fall back to a sanitized stderr line. Never attach the incident-write error as the refusal's cause. A process exit between rollback and incident commit can leave no durable alert; this design makes no atomic alert guarantee across that gap and adds no schema to close it. The issuance still refuses.

**Numbering and payments:** allocation may occur inside the failing transaction, but no number is committed or returned to a customer. Test that retry obtains that same unused number. Do not move or rewrite allocation. Connected-card collection already has separate P1/P2/P3 stages (`till-sale.ts:1141`, `:1360`, `:1399`; `bill-payments.ts:1387`). A previously captured payment is a committed fact and must stay available for recovery; compare state at entry to the issuing transaction, not before that prior charge. The new check makes no provider call. Refusal adds no tender, association, receipt or drawer job, and a repaired retry recovers the captured payment without another collection. Do not introduce a claim that this gate can undo money already moved.

# A1605. Identify the certificate this box replaces

After a repair, staff can use either certificate page to match the previous entry by name and fingerprint, including on devices they get to after the box restarts. The page shows the new name too. New roots have names staff can tell apart. Existing usable roots keep their installed trust.

## Name new roots

In `apps/server/src/self-signed-cert.ts`, use a name such as `Waitron box 2026-11-26 7f3a9ed276da`, with the UTC mint date and 12 hex digits from the end of the new root’s random serial. Initial repair only knows shared network names. Show the name of the offered certificate on each page so staff can match it later. Accept the existing fixed name and the exact new format in the existing root-role check. Keep the other chain checks. This takes the distinct-subject idea from [A917 §5.3](../specs/2026-10-20-a917-box-local-name-design.md#53-each-authority-is-distinguishable-round-1-finding-h2), with key identifiers outside this change. Existing builds that require the fixed name will refuse a newly named root in restore or handover. Record in the A1573 decision in `docs/backlog/setup.md` that boxes must run a compatible build before sharing newly named roots.

## Keep the previous certificate’s identity for later devices

[A1573](2026-11-26-a1573-constrained-box-signer.md) requires removing the previous root. The existing repair archive includes private material and is removed after the start has stayed up for two minutes. In `box-tls-repair.ts`, take the name and SHA-256 and SHA-1 fingerprints from the first certificate in the archived public `ca.crt`. Identify a self-signed Waitron CA even if expired. Accept the fixed name `waitron-setup-ca` with path length 0 or 1, or the exact new name format with path length 1. Keep this read separate from operational trust checks. In the existing repair lock, durably save one small public identity file under `tls/`, named in `packages/store/src/state-layout.ts`. Write it before a `new-required` replacement whose old fingerprint differs from the candidate, and bind it to the candidate’s SHA-256 fingerprint. A retained repair keeps the earlier record. On retries, use the already selected candidate. Read with the existing size-limited, no-follow reader. Show details only when the recorded fingerprint matches the current root, treating a failed read as unavailable. Use only the most recent replacement. Keep the archive cleanup and the existing backup and handover file lists.

Use this identity in the repair response, repair page and ordinary installation page, via `connection-bootstrap-page.ts`, `connection-bootstrap-strings.ts`, `trust-page.ts`, `i18n/trust-page.ts`, `trust-page-devices.ts`, `landing-app.ts` and `discovery-api.ts`. Have both ordinary page callers use one shared read. Show the name and SHA-256 together once the replacement is installed, updating the displayed details from the repair reply. Show the SHA-1 without colons in the Windows instructions, where the field is called **Thumbprint**. If there is no identifiable previous certificate, leave installed entries alone and offer the current one. Omit the numbered removal step if there is no match. Add a sentence in the English and Spanish Backup and recovery and Table service guides telling staff to compare the displayed name and fingerprint before removing a certificate. [Microsoft certificate dialog instructions](https://learn.microsoft.com/en-us/windows-server/networking/technologies/nps/nps-manage-certificates#obtain-the-sha-1-hash-of-a-trusted-root-ca-certificate).

## Test first

In `self-signed-cert.test.ts`, prove two mints for one network name have distinct subjects and that fixed-name roots in use still work. Keep the existing chain and reissue tests. In `box-tls-repair.test.ts`, compare the stored old name and fingerprints with the actual replaced certificate, using the old-set fixture for the fixed-name path-length-0 root. Compare the download fingerprint with the new root. Exercise the read after archive cleanup, a retained repair, an absent old certificate and a different current root. In the existing connection and trust-page tests, including `trust-page.browser.test.ts`, exercise replacement, retained and unidentified cases without weakening install, refusal or reconnect checks. Open both languages and themes at phone and desktop widths. Run the changed TLS, route, browser and guide checks and the state-layout guard.

Expect about 145 added production lines and 115 added test lines, with about 50 lines removed or replaced across the instructions. This change covers certificate identification during replacement. The existing repair and signing rules govern when certificates change and which names the signer can vouch for.

# A773-2 PR B3: the pass board and the pass's Fire — task plan

**Goal.** Since PR B1 (#2381) a waiter's fire can leave a kitchen item **Requested** (asked for by
the waiter, not yet given to its station), and since PR B2 (#2392) every other service action
handles such a dish. B3 builds the two things only the pass does: a **new board read** that shows
the pass Held, To fire, In progress and Ready cards (and the facts Overview counts), and the
**pass's Fire**, `POST /api/device/pass-screen/release`, which gives exactly the Requested dishes of
one card that this pass sees to their stations, once, with replay and print-once. The till keeps
today's pass routes; the new routes are used by tests only until B4 switches the screens. Every
station's "waits for the pass" setting stays false and has no editor until PR C, so no venue changes
behaviour.

**Words used here.** *Held*: both kitchen stamps null — the waiter has not fired it. *Requested*:
`requested_at` set, `fired_at` null. *Released*: `fired_at` set — the station has it.
*Initiated*: Requested or released (`initiatedAt`, `apps/server/src/kitchen-phase.ts:19-24`).
*Visible*: the item's station and its order's zone are both in this pass screen's choice
(`passSees`, `apps/server/src/pass-board.ts:32-40`). *Informational*: shown dimmed on the card but
not this pass's work. *Candidates*: the visible Requested items of one card — exactly what that
card's Fire releases. *Context*: a SHA-256 digest of the candidates' facts, read with the board and
sent back with Fire, so a stale card refuses. *HOLD paper*: the advance ticket of a held group.
*Pin*: a test of behaviour that is already right; every pin here has a mutation that turns it red.

## What the planning pass found (at `cbbec7ff2b`)

1. **Today's pass reads are per bill, not per card.** `listPassScreen` and `listPassMonitor`
   (`pass-board.ts:53-117`) narrow `readPassBoard`'s `ExpoOrder`s (`working-order.ts:8477-8491`),
   one per bill, sectioned by group or course. `readPassBoard` already reads held items too
   (`liveKitchenDish`, `:8502-8521`, has no `fired_at` test), computes readiness before narrowing
   (`pass-board.ts:69-75`), and returns no request time, phase, line id, station id, zone or
   `pass_controlled`. A group whose dishes sit on two bills of one party is two orders there. The
   master's card spans the group across bills (Contract 10), so B3 needs its own card builder over
   rows, not a filter over `ExpoOrder`s.

2. **One canonical row read can serve both boards.** `readPassBoard`'s select and presentation
   loop (`:8524-8730`) already build every display fact a card item needs (`ExpoItem`,
   `:8427-8452`). Factoring that loop into a row reader that also carries the kitchen stamps lets
   the old `readPassBoard` keep its exact output (its suites pin it) while the new board and the
   release read the same rows (Contract 9: "use one canonical snapshot builder for release
   comparison").

3. **Ungrouped dishes exist on bills with a party, not only on counter orders.** The master's
   `PassTarget` names a group or a counter order. But `addTabRound` writes `group_id` null unless a
   `groupId` is passed (`working-order.ts:3030-3062`), the legacy tab Send route
   `POST /api/working-orders/:id/lines/send` (`till-api.ts:4109-4135`) releases such lines, and
   B1's and B2's suites build Requested items that way on a seated party's tab. A counter bill moved
   to a table is grouped on arrival (`groupArrivingDishes`, `order-groups.ts:2473-2513`, selects
   `group_id is null` lines), so production writers I read group a party's dishes; the ungrouped
   party dish is read, not run, as reachable only through the legacy route on lines that were
   already ungrouped. The card builder must still place it (D45).

4. **The station's own advance bumps no revision and records no attendance on a device.**
   `advanceTicketItem` (`working-order.ts:7740-7783`) and `advanceTicket` (`:7786-7813`) update
   `ticket_items` only; the device route calls the former with no attendance
   (`device-api.ts:625-656`). The waiter's Ready on the pass (`bumpGroupReady`,
   `order-groups.ts:652-684`) checks and bumps the party revision, which the master forbids for
   the pass's Fire ("Two independent passes do not share an expected party-revision gate",
   Contract 8). So the release follows the station's advance (D49).

5. **Replay is in place.** `runServiceCommand` (`parties.ts:873-916`) replays by
   `(scope kind, scope id, submission id)` before anything else, compares a SHA-256 of the
   arguments (`fingerprint`, `:858-865`, which leaves out only `submissionId` and revision keys),
   refuses a changed repeat `submission.id_reused`, and for a party scope refuses a closed party
   (`requireOpenParty`, `:497`) only when the command is new. `service_commands.kind` is free text
   (`packages/db/src/schema/parties.ts:103-120`). A party scope and a bill scope both exist
   (`CommandScope`, `parties.ts:102-103`).

6. **Authority pieces exist; one is a screen flag.** Device proof:
   `requireDeviceProof` (`device-session.ts:323-331`) outside the transaction,
   `assertDeviceStillProven` (`:341-355`) inside it. Session: `requireSession` (`till-session.ts:93`)
   and `assertStillSignedIn` (`:145-166`). Action: `assertProfileAction` / `profileAllows`
   (`device-session.ts:363-372`; `packages/layouts/src/device-profile.ts:36-42`), which lets a shared
   display (`kds`) prepare, take and hand over only. `run-the-pass` is a `PROFILE_SCREENS` flag, not
   a `ProfileAction` (`packages/layouts/src/device-types.ts:52-60`), so it is checked as
   `capabilities.includes("run-the-pass")`. Screen: `kitchenScreenOf` (`device-api.ts:1012-1027`,
   module-private) reads `VENUE_SERVICE.readDeviceKitchenScreens`, refuses `device.unauthorized`

7. **Printing a release is today's waiter-release printing minus the parts already done at the

## Decisions

D1–D20 (slice plan) and D21–D43 (B2) bind unchanged. These are B3's, dated 2026-11-02.

- **D44 Two new reads; today's stay.** `GET /api/device/pass-board` answers the pass screen's
  `{ board: PassBoard, stations, zones }`; `GET /api/device/pass-monitor-board` answers the pass
  monitor's, with every card's `releaseTicketItemIds: []` and `releaseContext: null` (the monitor
  has no cooking write path, master "Review Focus" 5; the release refuses a monitor anyway). Both
  admit as today's reads do (`kitchenScreenOf(…, "pass" | "pass_monitor")`: available screen, and a
  signed-in person on a non-KDS device). Today's three pass routes are untouched until B4 (slice
  plan D15).

- **D45 One card per party group, or per bill for a bill's ungrouped dishes.**
  `PassTarget = { kind: "group"; partyId; groupId } | { kind: "bill"; workingOrderId }`. A group
  card holds every live kitchen item of the group, on every bill (lines keep `group_id` across
  bills; the group's `party_id` is current after a merge, `moveGroupsToParty`). A bill card holds a
  bill's live items whose line has no group: a counter order (spec §8), or the ungrouped party dish
  of finding 3. This renames the master's `counter` target to `bill` because it also covers that
  party dish, and because `runServiceCommand`'s matching scope is already `bill` (finding 5). The
  card's `kind`: a card whose every live item is held is `held`; otherwise the group's
  `request_kind` (D8), and `new_order` for a bill card (a counter order is a New order card by
  itself, D8). Column by the items, not the group state: **To fire** while the card has a candidate;
  else **Held** when every live item is held; else **Ready** when every live item is released and
  `ready`; else **In progress**. So D36's Requested extras of a made-here dish in a held group put
  that group's card in To fire, labelled Next course, with its held dishes shown held; when the
  waiter later fires the group, `requestHeldItems` leaves the extras alone (`heldItem()`) and the
  same card continues. HOLD paper keeps listing those extras (`printHoldTickets` reads
  `isNull(firedAt)`), and their release prints FIRE where the HOLD paper printed (D50): advance
  notice, then the fire, as for any held group. A card appears on a pass only when at least one of
  its live items is visible to that pass.

- **D46 Readiness and candidates are computed before any narrowing.** `allReady` reads every live
  item of the card, visible or not, informational or not (master Contract 10, "Review Focus" 3). An
  item is `informational` when it is not visible, or when it is not pass work: for a held item,
  its station does not wait for the pass now (Contract 10: "classify non-pass information from the
  current destination setting"); for an initiated item, `passControlled` is false (the frozen
  fact). So a Requested item moved to a station that no longer waits is still actionable (Contract
  2). `display.showNonPassStations` false drops informational items from `items` and from
  `overview` only; `allReady`, the column, `releaseTicketItemIds` and `releaseContext` are computed
  first and never change (Contract 9; B3.1 case 9 pins it). Default true until B4.1 supplies the
  policy. Made-here items are not on the board (`liveKitchenDish` excludes them); served-whole,
  cancelled-whole and recalled items are not live.

- **D47 The context covers exactly this pass's candidates.** `releaseContext` is the hex SHA-256 of
  the canonical JSON (keys sorted, as `canonicalJson`, `parties.ts:839-852`) of the candidates
  sorted by ticket item id, each as `{ id, lineId, orderId, groupId, stationId, zoneId,
  requestedAt, firedAt, passControlled, remaining, recalled, stationOpen }`, prefixed with the
  target. It is null when the card has no candidate. It leaves out informational rows and other
  passes' rows on purpose: a Bar drink turning ready, or the cold pass firing its part, must not
  make the hot pass's Fire refuse (master Contract 7: "Another pass's independent release cannot
  invalidate this pass's context"). It still detects every change the master names for the work it
  releases: a partial Serve or Undo (`remaining`), a cancellation (`remaining`), a same-id move
  between two stations both visible to this pass (`stationId`), a zone move (`zoneId`), a recall
  (the item leaves, or `recalled`), and the station closing or reopening (`stationOpen`). This
  narrows Contract 7's "visible rows" to visible Requested rows; "Departures".

- **D48 Authority first, then shape, then replay, then staleness.** The route takes the device
  proof (`requireDeviceProof`) and, on a non-KDS device, the session (`requireSession`, whose
  device must be the proof's) before its transaction. Inside it, in this order:
  `assertDeviceStillProven`; on a non-KDS device `assertStillSignedIn`; then `releasePassItems`
  re-reads the device's profile and refuses `device.forbidden_action { action: "prepare-orders" }`
  without that action (`profileAllows`), `device.forbidden_action { action: "run-the-pass" }`
  without the screen flag (the existing code and its existing till fallback; no new permission, no
  new action), `device.unauthorized` without an available `pass` screen (a monitor or station-only
  device), `session.required` for a non-KDS actor with no person; then
  `assertSubjectZones(profile, [{ partyId }] | [{ orderId }])`. Then the ask's shape
  (`management.request_invalid` with `field` `ticketItemIds` for empty, duplicate or non-UUID ids,
  `target`, `expectedContext` for anything but 64 lowercase hex characters, `submissionId`). Then
  `runServiceCommand` (party scope for a group target, bill scope for a bill target), kind
  `"pass.release"`, arguments `{ target, ticketItemIds (sorted), expectedContext, deviceId,
  personId }`, so a retry from the same device and person with the same ask replays, and any
  change under the same submission id is `submission.id_reused`. Then, inside the command, the
  staleness checks of D47 refuse `ticket.pass_context_changed` (409). Everything about the card's
  contents (an unknown, foreign, served, recalled, other-station or other-zone id; a missing
  candidate; a wrong context; a group no longer the named party's; a target with nothing visible)
  is that one code: the till's answer to each is the same refresh. Authority keeps the existing
  refusals (master Contract 7: "Out-of-scope access uses existing device/screen refusals").
  `take-orders` is never required (Contract 6).

- **D49 The release write.** One conditional update of the candidates,
  `where id in ids and requestedItem()`, setting `fired_at` and `queued_at` to the release time and
  leaving `requested_at`, `pass_controlled` (true, master Contract 1: "preserve it through release")
  and `state` (`queued`) as they are; a returned count other than the ids' count throws
  `ticket.pass_context_changed` and rolls back. It bumps no party or bill revision and records no
  attendance, as the station's advance on a device does (finding 4): a pass's Fire must not refuse a
  waiter's pending edit as stale. It writes no line, bill, draft, editor or money row.

- **D50 Printing the release.** Per bill of the released items, one
  `enqueueKitchenTickets(tx, cfg, orderId, items, { fire: { heldPaper } })` call, each item a
  `FiredItem` with `quantity` = its remaining quantity (finding 8: what the card showed is what
  prints), and `heldPaper` = the group's `heldPaperStations` (empty for a bill card), so a station
  that printed the group's HOLD paper gets a FIRE-marked ticket (master Task 6; spec §6). Output
  count follows each station's configured printers, never the number of screens (master "Review
  Focus" 5). No "From {station}" heading: a dish rerouted from a closed station at the request
  already had its MOVED slip there (`enqueueStationMoved`, `station-move.ts:148`), and the old
  station is not stored (finding 9); storing it would need a column this PR does not add. Then
  `notifyKitchenAllergyDestination(tx, cfg, releasedIds)` (D52).

- **D51 The pass never reroutes; a closed station is told at the moment it gets the dish.** The
  release gives each candidate to its current station, open or not (master Contract 8: reroute at
  waiter initiation only; an outside-scope destination can never gain authority through a reroute).
  A released item at a station that is inactive or not open now, and that neither the closing's
  "leave" (`station_retained_at_release`, `station-closing.ts:88-93`) nor a hand choice kept there,
  raises `route.released_at_closed_station` at the release, whose words ("went to {station}") are
  then true. The "kept there" test is `rerouteHeldAtRelease`'s own (`station-move.ts:77-84`),
  exported as `unchosenAtClosedStation(row, state)` so both use one rule. At the waiter's request,
  `alertStranded` leaves out rows whose station waits for the pass (they went nowhere; the release
  raises it if they are still stranded then). With no station waiting nothing changes. `queued_at`
  written by the reroute is overwritten by the release (D2), so nothing to change there. Station
  closing's "leave" therefore needs no B3 code: the release prints at the closed station without an
  alert, as a waiter's release of retained held work does today.

- **D52 Allergies at the release.** The snapshot stays frozen at the request (D7); the release
  freezes nothing and sends `notifyKitchenAllergyDestination` for the released items, which records
  a notice only where the guest's answer changed since the snapshot (`kitchen-allergy.ts:470-476`).
  `enqueueKitchenAllergyUpdates`' `exposed` test (`kitchen-allergy.ts:365-366`) stays on `fired_at`:
  a Requested dish is at no station, so a change while it waits updates its current block silently
  (`setTicketAllergyCurrent`, `:357`) and the release's notice carries it. The board keeps showing
  `originalBlock` on every item, as `readPassBoard` does (`working-order.ts:8650`). The other two
  `firedAt` reads in the file (`:384`, `:502`) choose the HOLD group label for a correction and are
  right for Requested work (no HOLD label unless HOLD paper printed, which D56 leaves to PR D). The
  release does not ask the party's allergy question again: the waiter's request already required it
  (`assertPartyAllergyAnswered`, `working-order.ts:2609-2615`).

- **D53 No order-number stamp at release** (finding 10). Pinned by B3.4b case 6.

- **D54 No warning before releasing to a station whose output is down, and the dark-pass window
  stays.** The closed-station printer-down alert rises when the dish is released

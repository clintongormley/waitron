# A773-2 PR B3: the pass board and the pass's Fire — task plan

**Goal.** Since PR B1 (#2381) a waiter's fire can leave a kitchen item **Requested** (asked for by
the waiter, not yet given to its station), and since PR B2 (#2392) every other service action
handles such a dish. B3 builds the two things only the pass does: a **new board read** that shows
the pass Held, To fire, In progress and Ready cards (and the facts Overview counts), and the
**pass's Fire**, `POST /api/device/pass-screen/release`, which gives exactly the Requested dishes of
one card that this pass sees to their stations, once, with replay and print-once. It also builds
the HOLD paper corrections for Requested work that master Task 8 requires (D56). The till keeps
today's pass routes; the new routes are used by tests only until B4 switches the screens. Every
station's "waits for the pass" setting stays false and has no editor until PR C, so no venue changes
behaviour.

**Words used here.** *Held*: both kitchen stamps null — the waiter has not fired it. *Requested*:
`requested_at` set, `fired_at` null. *Released*: `fired_at` set — the station has it.
*Initiated*: Requested or released (`initiatedAt`, `apps/server/src/kitchen-phase.ts:19-24`).
*Visible*: the item's station and its order's zone are both in this pass screen's choice
(`passSees`, `apps/server/src/pass-board.ts:32-40`). *Informational*: shown dimmed on the card but
not this pass's work. *Candidates*: the visible Requested items of one card — exactly what that
card's Fire releases, unless one is at a closed station nothing kept it at, which blocks the
card's Fire (D51). *Context*: a SHA-256 digest of the candidates' facts, read with the board and
sent back with Fire, so a stale card refuses. *HOLD paper*: the advance ticket of a held group.
*Pin*: a test of behaviour that is already right; every pin here has a mutation that turns it red.

## Decisions

D1–D20 (slice plan) and D21–D43 (B2) bind unchanged; B2 D26's hand-off to B3 is built here (D56),
and slice plan D6's "the pass's release refuses a stale destination" is D51. These are B3's, dated

- **D44 Two new reads; today's stay.** `GET /api/device/pass-board` answers the pass screen's
  `{ board: PassBoard, stations, zones }`; `GET /api/device/pass-monitor-board` answers the pass
  monitor's, with every card's `releaseTicketItemIds: []` and `releaseContext: null` (the monitor
  has no cooking write path, master "Review Focus" 5; the release refuses a monitor anyway). Both
  admit as today's reads do (`kitchenScreenOf(…, "pass" | "pass_monitor")`: available screen, and a
  signed-in person on a non-KDS device). Today's three pass routes are untouched until B4 (slice
  plan D15).

- **D45 One card per party group, or per bill for a bill's ungrouped dishes.**
  `PassTarget = { kind: "group"; partyId; groupId } | { kind: "bill"; workingOrderId }`. A group
  card holds every live kitchen item of the group, on every bill (lines keep `group_id` across
  bills; the group's `party_id` is current after a merge, `moveGroupsToParty`). A bill card holds a
  bill's live items whose line has no group: a counter order (spec §8), or the ungrouped party dish
  of finding 3. This renames the master's `counter` target to `bill` because it also covers that
  party dish, and because `runServiceCommand`'s matching scope is already `bill` (finding 5). The
  card's `kind`: a card whose every live item is held is `held`; otherwise the group's
  `request_kind` (D8), and `new_order` for a bill card (a counter order is a New order card by
  itself, D8). The ungrouped party dish of finding 3 also gets `new_order` although it is not a
  table's first send: accepted, because only the legacy tab Send route makes it. Column by the
  items, not the group state: **To fire** while the card has a visible Requested item that is pass
  work (a candidate, including one whose Fire D51 blocks); else **Held** when every live item is
  held; else **Ready** when every live item is released and `ready`; else **In progress**. So D36's Requested extras of a made-here dish in a held group put
  that group's card in To fire, labelled Next course, with its held dishes shown held; when the
  waiter later fires the group, `requestHeldItems` leaves the extras alone (`heldItem()`) and the
  same card continues. HOLD paper keeps listing those extras (`printHoldTickets` reads
  `isNull(firedAt)`), and their release prints FIRE where the HOLD paper printed (D50): advance
  notice, then the fire, as for any held group. A card appears on a pass only when at least one of
  its live items is visible to that pass.

- **D46 Readiness and candidates are computed before any narrowing.** `allReady` reads every live
  item of the card, visible or not, informational or not (master Contract 10, "Review Focus" 3). An
  item is `informational` when it is not visible, or when it is not pass work: for a held item,
  its station does not wait for the pass now (Contract 10: "classify non-pass information from the
  current destination setting"); for an initiated item, `passControlled` is false (the frozen
  fact). So a Requested item moved to a station that no longer waits is still actionable (Contract
  2). `display.showNonPassStations` false drops informational items from `items` and from
  `overview` only; `allReady`, the column, `releaseTicketItemIds` and `releaseContext` are computed
  first and never change (Contract 9; B3.1 case 9 pins it). Default true until B4.1 supplies the
  policy. Made-here items are not on the board (`liveKitchenDish` excludes them); served-whole,
  cancelled-whole and recalled items are not live.

- **D47 The context covers exactly this pass's candidates.** `releaseContext` is the hex SHA-256 of

  order: { orderNumber: number; tableLabel?: string; kitchenNote: string | null;

  held: PassCard[]; toFire: PassCard[]; inProgress: PassCard[]; ready: PassCard[];
  overview: OverviewFact[];
}

export function passCardKey(row: PassRow): string;

  scope: PassScope,

# A1578 — Shorten the wait for Bluetooth slips and receipts

The print agent gets enough time to discover the printer's channel and skips discovery after a successful print to that address. The first pull request fixes discovery and keeps a fresh Bluetooth connection per job. Once the spare has measured that change, decide whether the remaining wait justifies keeping connections open.

## First pull request

- In `apps/print-agent/src/rfcomm.test.ts`, let the lookup stub return channel 7 after 3.3 seconds. With the default lookup limit, check that two prints use channel 7 and make one lookup. Give that case its own test timeout above the lookup limit. Revise the existing failed-lookup and stalled-lookup cases so a successful channel-1 send is remembered. Keep checking that a timed-out lookup child exits, that a failed send clears the saved channel, and that each job is sent once. The first red run should show channel 1 instead of 7 and a repeat lookup instead of reuse.
- In `apps/print-agent/src/rfcomm.ts`, give the lookup five seconds. Move the cache write to the helper's success path, including when it used channel 1 after a lookup error. Keep clearing the entry on a failed send. The helper's success means the kernel took the bytes, so a fallback reported successful stays cached even if the printer produced no paper. Run `pnpm --filter @waitron/print-agent-app exec vitest run src/rfcomm.test.ts` red and green. Estimate 15 product lines and 55 test lines added.
- Update the Bluetooth cache decision in `docs/backlog/printers.md` and the printer section of `docs/backlog.md` with the remaining measurement. The change fits the current print-agent container and needs no venue reset.

## Measure on the spare before deciding on the second pull request

Use the owner's printer through waitron-b4, under the shipped print-agent profile, with the venue kept intact. Measure the old and new builds on the cold first print and at roughly 5, 30 and 60 seconds between prints. Time the slip and receipt separately from queue to visible paper and to the agent's result. Time cold channel discovery and compare cold connects with and without a preceding lookup. Compare the same long receipt with immediate and delayed socket close, checking for missing output and counting copies. Use the results to decide whether avoiding a fresh connect would recover a delay someone notices, or whether delayed close is needed for complete output.

Bring those results back before building connection reuse. A reused socket can accept bytes into the kernel without proving a silent printer is present. A later failure can also trigger the existing document retry (`packages/printing/src/runtime.ts`), with a risk of duplicate paper after a partial write. If reuse is still warranted, qualify a short printer reply check before job bytes, a power-off recovery, and one total send budget below the job lease. A second plan can then settle helper shutdown, reconnect and expiry, checking for interference with unpair and with another device. The watcher’s 18:20 note also proposes trying an early connection when a device picks up a Bluetooth printer or opens Pay. The measurements inform that decision too.

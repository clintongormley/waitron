# Stream configuration uploads during setup

During setup, you can upload and preview a large encrypted configuration export without the server collecting the whole request in memory. The existing binary upload, passphrase header, 64 MiB limit, export format, preview and later provisioning stay the same. This slice covers `POST /setup-api/configuration`. Recovery preparation, emergency handover and the browser stay outside it. Preview still decodes and parses the completed export, so the memory claim is about receiving the upload and reducing peak memory for the request.

## Receive and stage the upload

- In `apps/server/src/setup-api.ts`, send the raw request through the existing `receiveArchive` seat with the configuration limit. Keep content type and passphrase validation, and hold the existing setup latch through receive, preview and cleanup. Pass the owned upload path and request signal to the stage seat, and dispose of the upload in `finally`. In `setup-archive-upload.ts`, let this caller select `setup.request_invalid` with `field: "artifact"` for the byte limit alone. Count bytes as they arrive, even without `Content-Length`. Keep the existing recovery limits and reserve check. Use the 507 resource refusal for a full staging disk.
- In `apps/server/src/boot.ts`, point the configuration stage seat at a file-based entry in `packages/provisioning/src/configuration-import.ts`. Read the completed file for the existing decoder and use the existing validation and preview builder. Keep the existing byte-taking entry's snapshot guarantee. Share marker, wrapped-passphrase and cleanup logic between both entries. After validation and an abort check, publish the original encrypted upload with `publishFileDurable` and write the marker last. The old preview remains usable when a new upload is interrupted or validation refuses it before replacement. The staged bytes and restart reader keep their current layout. Use the boot-provided receiver under `scratch/restore`, where it already creates a private directory per upload.

## Check behaviour and peak memory

- In `apps/server/src/setup-api.test.ts`, first add a failing test that sends an open binary stream and shows the receiver has written bytes before EOF. Finish the stream and check the same passphrase, exact bytes and preview. A chunked request over the limit returns the existing 400 artifact refusal, cancels the upload and releases the latch for a retry. A disconnect removes the scratch copy. Exercise the real receiver for these cases and keep the current route assertions for refusal codes and the setup latch.
- In `packages/provisioning/src/configuration-import.test.ts`, prove the file path publishes the exact validated ciphertext and can be read after restart. A bad passphrase or invalid replacement leaves the prior staged import readable. Run the changed suites, `apps/server/src/setup-archive-upload.test.ts`, `apps/server/src/configuration-import.test.ts` and the configuration cases in `apps/server/src/boot.setup-routes.test.ts`.
- Stream the same valid near-limit encrypted export from a separate client to the real setup route before and after, with a fresh server process and the same Node version for each run. Record upload-phase and full-request peak resident memory in MiB, file size, environment and a successful preview in the PR. Generate the export outside the measured process. Report the remaining cost of decoding. Update `docs/backlog.md` and `docs/backlog/setup.md` to leave the recovery upload work open.

Estimate 70–120 changed implementation lines and 100–160 changed test and test-support lines.

# Stream configuration uploads during setup

During setup, you can upload and preview a large encrypted configuration export without the server collecting the whole request in memory. Keep the binary upload, passphrase header, 64 MiB limit, five-minute receive deadline, export format, preview and later provisioning. This slice covers `POST /setup-api/configuration`. Preview still decodes and parses the completed export. Recovery preparation, emergency handover and the browser stay outside the slice.

## Receive and stage the upload

- In `apps/server/src/setup-api.ts`, require both the existing `receiveArchive` seat and the configuration stage seat, or return `setup.not_ready` (503). Keep content type and passphrase validation and hold the existing setup latch through receive, preview and cleanup. Pass the owned upload path and request signal to the stage seat, then dispose of the upload in `finally`. In `setup-archive-upload.ts`, let this caller select the 400 `setup.request_invalid` artifact refusal for the declared-length check and both byte counters. Keep recovery's behaviour. For configuration, use the existing per-write free-space check with `reserveBytes: 0` and the 507 resource refusal when the box runs out of staging space.
- In `apps/server/src/boot.ts` and its `configuration-import.ts` re-export, wire the file entry in `packages/provisioning/src/configuration-import.ts`. Read the completed file for the existing decoder. Use one validation, preview and publication path with a thin wrapper for existing byte fixtures that preserves their snapshot assertion. After validation and an abort check, remove the old marker and flush its folder, publish the original encrypted file with `publishFileDurable`, write the wrapped key, then write the marker last. Keep the prior import when an interruption or validation refusal happens before replacement. Reuse the private upload directories under `scratch/restore` and keep the staged layout and restart reader.

## Check behaviour and peak memory

- First add a failing route test in `apps/server/src/setup-api.test.ts`. Send a binary stream and observe its scratch bytes before closing the stream. Check that the completed request passes the same passphrase and bytes to staging and returns the same preview. Pin declared and chunked over-limit requests at 400 with body cancellation, and disconnect cleanup with a successful retry. Use the real receiver and keep existing refusal and setup-latch assertions. Update the staging fixtures in `configuration-import.test.ts` and `configuration-import.previous-export.test.ts` to read from the owned upload. Check the recovery-preparation mocks for the changed setup dependency.
- In `packages/provisioning/src/configuration-import.test.ts`, check that a fresh reader sees the exact validated ciphertext, that a refused replacement preserves the previous import, and that a failure after artifact publication leaves no readable import. Run the changed suites, `apps/server/src/setup-archive-upload.test.ts` and the three configuration-import cases in `apps/server/src/boot.setup-routes.test.ts`.
- In a 1 GiB Linux `node:26-slim` container, send the same valid near-limit export to each fresh server from a separate client. Generate it outside the measured process from a disposable venue with several high-detail menu images. Sample the server's `/proc/<pid>/status` `VmRSS` before sending and during reception up to EOF, and read `VmHWM` after a 200 response with the expected venue preview. Report both phases, file size, image and Node versions, and the remaining decode cost in the PR. Update `docs/backlog.md` and `docs/backlog/setup.md` to leave the recovery upload work open.

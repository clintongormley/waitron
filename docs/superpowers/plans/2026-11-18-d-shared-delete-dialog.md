# Share the dashboard hardware delete dialog

Devices, Payments and Printers use one dashboard widget for Delete. Managers see the same confirmation, words and results for devices, readers, receipt and kitchen printers, and A4 printers. This completes the shared-dialog bullet in `docs/backlog/architecture.md`, under A435 loose ends.

- In `apps/dashboard/src/widgets/hardware-delete-dialog.ts`, add `HardwareDeleteDialog`. Make one per screen, with one `DashboardQueries` so later impact reads keep using the background client. `open(id, opener, query)`, `close(focusTo?)` and `render(testId, copy)` share the state and bindings for the existing `wt-delete-dialog`. Request a host update when state changes, release the query named at opening, and check that late completions belong to the same opening. Expose the target, whether Delete is sending, and `retryImpact()` for reading the impact again. `close(focusTo?)` uses the current opener when the caller supplies no element or cannot find Add. Keep read and action errors separate.
- In `apps/dashboard/src/screens/devices-screen.ts`, `payments-screen.ts` and `printers-screen.ts`, replace the copies. Pass the current impact into `send(id, impact)` for the reader acknowledgment. Each screen supplies its send call and what it does when the row is gone or Delete succeeds. The reader supplies `reader.provider_disconnected` as the answer that reads the impact again. The gone callback distinguishes an impact read from a send so each screen refreshes only where it does today. Use `device.not_found`, `reader.not_found`, or `printer.not_found` and `page_printer.not_found` for a vanished row. Let the send settle when an impact read reports not-found during Delete. Clear sending before handling the send's own not-found answer so the screen explains it. Keep the screens' own row cleanup and refresh.

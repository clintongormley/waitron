## Global constraints

- Holidays describe venue-local civil dates (`YYYY-MM-DD`), independent of reporting/business-day cutover. Use Hours' `LocalDate`, `HolidayFact`, `VenueScope` and date validation; add no second special-date registry.
- A holiday never automatically closes the venue, changes station routing, creates a special date, files anything, sets a wage rate or rewrites a dated record. Hours overrides remain explicit. Department hours never stop a sale; default station remains Always open.
- Ship only verified years and applicability. No extrapolated movable/observed dates, live API, runtime fetch or external dependency on the sale path. A publication check occurs during data maintenance, never during a request.
- National-origin holidays can apply only in selected regions. Retain the annex's per-region membership and source category; do not union every national row into every region. Special territorial notes are part of the dataset.
- Official shipped names retain the source's Spanish wording, including any named local-language form; EN/ES translates UI actions, scope/coverage labels and hours descriptions. Your local label stays exactly your wording after trimming; it is not automatically translated. An official name copied into an editable special-date name becomes an owner-editable name.
- Writes use one route `withTransaction`, helpers take `tx: Transaction`, statements are awaited in order. Stored reads use that same transaction; no nested transaction or second connection. Database tests use `useVenueDb`, catch refusals outside the transaction, assert domain codes and unchanged rows.
- Forms use shared primitives, semantic names, required marks, field feedback and one localized bottom message. Request refusals stay retryable; a successful write closes its editor before a separate refresh. Use declared `--wt-*` tokens, table cell `part` styling and pinned final `actions` columns. Preserve upstream keyboard and accessibility behavior.

## Recommendations needing owner approval

1. **Town identity:** use the venue's existing `locations.city` as the suggested town name, then show it read-only and ask you to confirm it in Hours › Local holidays. This step confirms the stored address name; it does not offer an editable town-name draft. Correcting an address needs the separately approved venue-details path. Store a module-owned town UUID with country, canonical province code and confirmed name; do not treat a postcode, city spelling or name match as a verified municipality code. No municipality directory or new core address column is needed for this scope. Compare names by NFC normalization, trimmed/collapsed whitespace and case, preserving accents and punctuation. Reconfirmation reuses the same scoped identity; another location or province cannot share it implicitly. This keeps a stable reference for local entries without claiming the free-text address identifies an official municipality.
2. **Geography changes:** retain town identities and entries. On a country/province/city mismatch, suppress the old town's local facts from the current venue read and show “Confirm town for local holidays”; do not delete or relabel them. Show retained towns read-only until explicitly reselected after the current address matches, or explicitly deleted with their entries. Returning to the same geography lets you confirm and reuse them. Province-derived shipped facts follow the current geography immediately. Do not authorize or implement address editing: step 7 decides whether each venue detail may change after sales. These are retention/read rules if another approved path changes geography.
3. **Territorial selection:** derive region from province. Where the verified annex requires more detail, offer an explicit holiday-area choice from that year's sourced options (Canary island, or Arán/rest of Cataluña). Save it with the confirmed town. Do not infer that detail from free-text city. Until selected, return only facts whose applicability is certain and mark `area_required`; a source-qualified holiday must not be guessed. This does not expand existing fiscal setup availability for excluded territories.
4. **Local entries:** allow zero, one or two distinct dates per town per civil calendar year; names required, trimmed, at most 200 characters. A date matching a shipped holiday is allowed and counts as one local entry. Two local entries on the same date are refused even with different names. Local entries are owner assertions, never marked officially verified. “None entered” is not a declaration that the municipality has no holidays; there is no completeness confirmation workflow in this step.
5. **Multiple labels and defaults:** retain every distinct applicable fact; coalesce repeated occurrences of the same fact ID only. Display distinct labels in deterministic national, regional, local order, then fact ID; collapse identical text only in the joined display/default name, never in the fact array. Join with `·`. Duplicate uses the target date's joined holiday name; with none, preserve the source special name. Make this a special date uses the target's holiday name; otherwise use the original day heading's canonical `YYYY-MM-DD` as its initial name. You can edit that creation draft. Explicit later rename/date edits never auto-rename a saved row. Unknown coverage with no known label uses the same fallback plus a visible coverage notice, not a guessed holiday. No name truncation: preserve all labels in the panel and copied name; the joined name is not constrained by the local-entry name limit. Re-read the landed Hours special-name validator and storage limit before implementing: retain the full joined name when valid, and refuse an over-limit duplicate batch with `hours.invalid` (`field: name`, offending target date) without creating any target. A Make-special draft keeps the full suggestion and lets you edit it into a valid name. Never bypass the Hours validator or truncate silently. This refusal behavior is part of this recommendation for approval.
6. **Permissions and placement:** retain the Hours-plan-supplied permission contracts, rechecking them after its build lands: `venue.view` read permission and `venue_service.manage` for local entries, town confirmation/area choice, and special-date actions. Add a Local holidays section to Hours, not a new sidebar/calendar or a Venue details edit control. Read-only supervisors see facts, source/coverage and retained entries but cannot mutate. Step 7's `venue.configure`/venue-detail rights remain separate.
7. **Storage:** add three editable venue-service leaf tables (below), with no existing-table rebuild, backfill, schedule conversion or compatibility reader. Bump the module's effective schema version by the new generated journal entry, not its package version. Refuse older configuration bundles through the existing version check. Fresh venues have no local entries and an unconfirmed town. A reset is not proposed for this additive step; declare any reset the measured build actually requires before shipping.

# A582 slice 1 — the help badge and the help switch's state in `packages/ui`: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `packages/ui` gains everything help mode needs that is shared: one app-wide "help is on"
switch held in memory, and a way for `wt-help-tooltip` to act as a help-mode badge — drawn only
while help is on, hanging over the top trailing corner of the thing it explains, and taking no room
on or off. Three field primitives that lack it gain the `help` slot `wt-input` has, and
`wt-disclosure` and `wt-dialog` take a badge beside their heading. **Nothing a person sees changes
in this slice**: every "?" on main today stays exactly as it is, because nothing turns help on
until slice 2 adds the banner switch.

**Spec:** `docs/superpowers/specs/2026-10-18-a582-help-mode-design.md`, approved by the owner
2026-10-18. Slice 1 is §8 item 1; the badge sizes are §3.2; the state is §5 and §6; today's "?"
buttons are §7. The owner's one change on approval (the till's "?" never moves into More; menus get
a "?" beside options that have help) belongs to slices 2 and 4 and changes nothing here. The
revised spec text is on `main` at `9acc3c8aa` (§3.3, "Badges inside menus"); its §8 item 1 now says
outright that badges inside menus are not part of slice 1. This plan does not edit the spec.

## Words used in this plan

- **badge** — the small filled circle with a "?" that help mode shows on a part of a page.
- **the switch** — the in-memory "help is on / off" state every badge follows. In this slice it is
  a module with functions; the button that drives it (in the dashboard banner) is slice 2.
- **always mode** — how `wt-help-tooltip` behaves today: an outlined, muted "?" with a 44 px target,
  always visible, taking room in the layout.
- **help mode (of a badge)** — the new behaviour: hidden while the switch is off, a hanging badge
  while it is on, never taking room.
- **hang over the corner** — the badge's centre sits on the top trailing corner of the box it
  explains (top right in English, top left in a right-to-left page), half inside and half outside,
  as in `docs/backlog/mockups/a582-help-mode/01-dashboard-off-on.png` and `02-badge-box.png`.

**Decision: the default stays always mode; help mode is opt-in through a new `mode` attribute.**
`<wt-help-tooltip>` with no `mode` (or `mode="always"`, or any value it does not know) behaves
exactly as on `main`. `<wt-help-tooltip mode="help-mode">` follows the switch. Slice 1 changes no
file outside `packages/ui` and `packages/ui-core` and no existing test assertion. Slice 2 adds the
banner switch and, in the same pull request, puts `mode="help-mode"` on the dashboard's five, so the
moment they become hidden-until-on is the moment the switch that turns them on exists. The setup
wizard never needs touching, because always mode is its permanent behaviour (§7).

Why this is the most conservative of the options:

- **Main stays working with this slice alone, by construction.** No consumer file changes, so no
  "?" can vanish. The alternative — make help mode the default and add `mode="always"` to every
  current use — edits twelve consumer files across three packages, and any one missed (or added on
  another branch meanwhile) silently disappears with no switch to bring it back.
- **Always mode is needed forever anyway** (the setup wizard), so it is not a temporary flag that
  slice 2 must remember to remove.
- **No existing assertion changes** (listed under "Existing tests" below), which is the cheapest
  evidence that behaviour on main did not move.

The cost: a future screen that adds a badge must remember `mode="help-mode"`. Slice 2's own badges
(table columns and tabs) are drawn by the primitives, which set it themselves; the design-system
entry (Task 5) says so for the rest. Recorded as an open risk for slice 2.

**Name kept.** The spec leaves `wt-help` versus `wt-help-tooltip` to the plan (§5). The name stays
`wt-help-tooltip`: a rename would touch the same twelve consumer files and their tests for no change
in behaviour.

## Other decisions made in this plan (for the reviewer)

1. **Badge size comes from two tokens, not an attribute.** `--wt-help-badge-target` (24px) and
   `--wt-help-badge-size` (20px) are declared in `packages/ui-core/src/tokens/structure.css` beside
   `--wt-stepper-button-width` (`structure.css:96`, read), with the dashboard's values (§3.2). Slice 4
   sets `32px` and `24px` on the till's theme root. The tokens are declared under
   `:where([data-wt-theme-root])` (`structure.css:1`, read), which has no specificity, so any rule in
   an app wins. A 24px target is below `--wt-tap-min` (44px, `structure.css:29`); it is WCAG 2.2's
   level AA minimum (2.5.8), the same exception the owner made for the stepper's buttons (A263,
   `docs/developers/design-system.md:634`, read), and §3.2 of the approved spec sets it.
2. **The badge hangs by `position: absolute` against the nearest positioned box, and every primitive
   that offers a `help` slot makes that slot's wrapper positioned.** For the field primitives that
   wrapper is `.row` in `fieldStyles` (`packages/ui-core/src/field-styles.ts:132-136`, read), which
   gains `position: relative`. This was measured before writing the plan — see "Measured while
   writing this plan" below. **The stepper is the exception: it gets no `.row`.** Its slot goes
   inside its existing `.control` grid, after the `.field`, and `.control` gains `position: relative;
   grid-auto-flow: column; column-gap: var(--wt-space-2); align-items: center`. A `.row` wrapper
   would break the two till dialogs that stretch the stepper with `--wt-stepper-field-width: 100%`
   inside a flex column (`apps/till/src/widgets/reset-table-dialog.ts:53-55`,
   `split-joined-dialog.ts:51-53`, read): the plan reviewer measured that field at 400px today and
   48px inside a `.row`. With the slot inside `.control` the reviewer measured the field still 400px,
   a help-mode badge centred on the field's corner, and an always-mode 44px "?" 8px beside the
   field (reviewer's measurement, 2026-10-18; not re-run while revising this plan). An empty slot
   adds no grid column, so no gap (it is `display: contents` with nothing in it).
   **For slice 2's menu badges** (§3.3 of the spec), which take their own square instead of hanging:
   a menu row can put the badge back in the flow with `::slotted()` rules of its own, because a rule
   from outside a shadow root beats the element's own `:host` rule (CSS Scoping's cascade order;
   read, not run). Slice 1 adds nothing for menus.
3. **Off is `display: none`.** It takes no room, is not in the tab order and is not read by a screen
   reader (§6: "reachable with Tab only while help is on").
4. **On, the badge is filled `--wt-color-primary` with an `--wt-color-on-primary` "?"**, as the
   mockups draw it, so it reads as distinct from always mode's outlined muted "?"
   (`wt-help-tooltip.ts:16-42`, read). That colour pair is the primary button's.
5. **Turning help off closes an open help box.** A box left open over the page after its badge has
   gone would have nothing to anchor to and no badge to tap again.
6. **No custom event in this slice.** The switch is driven by calling `setHelpMode(on)`; badges hear
   it through a Lit reactive controller. Slice 2's banner button calls the function. (The theme
   choice has an event, `wt-theme-selected`, because a shared chooser component sends it,
   `packages/ui/src/theme-choice.ts:7`, `:110-113`, read; there is no shared help switch component
   yet, so an event would have no sender.)
7. **The state is not saved anywhere** (§6): a module variable, as `choice` is in
   `theme-choice.ts:13` (read), but with no `localStorage`. A reload starts with help off. Turning it
   off on sign-out (dashboard) and on lock or a change of person (till) is slices 2 and 4.
8. **A badge that was out of the page when help changed shows the right state when it comes back.**
   The controller asks its host to redraw on reconnect. `ThemeChoiceController.hostConnected`
   (`theme-choice.ts:98-102`, read) does not, and nothing in this slice changes that one.
9. **`wt-disclosure`: the badge hangs over the top trailing corner of the whole heading row, not
   just after the heading's words.** The heading text lives inside the header `<button>`
   (`wt-disclosure.ts:280-291`, read), and a badge is a button, which cannot sit inside another
   button. So the `help` slot goes beside the header button in a new positioned wrapper, and the
   badge hangs over that row's trailing corner. The mockup (01) draws it just after "Variants";
   slice 2 looks at it on Products and may move it (for example with CSS anchor positioning) if the
   owner wants it there. Listed under open risks.
10. **`wt-dialog`: the `help` slot sits beside the `<h2>` in a positioned wrapper as wide as the
    heading's text**, so the badge hangs over the heading's trailing corner. It is outside the `<h2>`
    on purpose: the dialog is named by `aria-labelledby` pointing at the `<h2>`
    (`wt-dialog.ts:439`, `:452`, read), and a badge inside it would add "Help: …" to the dialog's
    name. A dialog with no `heading` draws no help slot. **`wt-modal` gets the same slot without
    being edited**, because it extends `WtDialog` and keeps its `render`
    (`packages/ui/src/components/wt-modal.ts:6`, read: the file has no `render`), so every modal in
    every app draws the new wrapper round its heading. The wrapper changes the `<h2>`'s width from the
    body's to its text's (`width: fit-content`), which shows only if something paints the `<h2>`'s
    box; nothing in `wt-dialog.ts:86-90` or `wt-modal.ts:14-59` does (read).

## Measured while writing this plan

A throwaway browser test (deleted after the run) mounted `wt-input` with a 400px-wide host, four
ways, and read `.field`'s box. Run 2026-10-18 in this worktree, `packages/ui`, Vitest 4.1.11,
Playwright 1.64.0's Chromium, with
`AI_AGENT= CLAUDECODE= pnpm exec vitest run src/zz-probe-a582.test.ts`. Before the run, the failing
case was stated: an absolutely positioned element in the `help` slot that still took room would show
the field narrower than 400; one placed against the wrong box would show its corner away from the
field's.

| What was in the `help` slot | `.field` width | The help element's top-right corner |
| --- | --- | --- |
| nothing | 400 | — |
| a `display: none` span | 400 | — |
| a 24×24 span, `position: absolute; inset-block-start: 0; inset-inline-end: 0` | 400 | (414, 0): against the page, not the field |
| the same span, after setting `position: relative` on the shadow root's `.row` | 400 | (400, 112): exactly the field's top-right corner, which was (400, 112) |
| a 24×24 `display: inline-block` span (the control: in flow) | 368 | — (24px plus the row's 8px gap, `field-styles.ts:135`) |

So: neither `display: none` nor `position: absolute` takes room in the field's row, an in-flow
element does, and `.row` must be positioned for the badge to find the field's corner. This is the
receipt for decisions 2 and 3, for `wt-input` only; Tasks 3 and 4 measure every other host.

Sketch (shape copied from `theme-choice.ts:13-16`, `:32-37`, `:76-108`, without storage, other

```ts
let on = false;
const listeners = new Set<() => void>();

export function setHelpMode(next: boolean): void {
  if (next === on) return;
  on = next;
  for (const listener of listeners) listener();
}
```

**Switching on axe's target-size rule.** axe 4.14.0 ships `target-size` (WCAG 2.5.8, the 24px
minimum this badge relies on) switched off (`enabled: false` in
`packages/ui/node_modules/axe-core/axe.js:37970-37973`, read), and `expectNoA11yViolations` runs
axe's defaults (`a11y-helpers.ts:64`, read). Give the helper an optional second argument,
`{ enable?: readonly string[] }`, passed to axe as `{ rules: { [id]: { enabled: true } } }`. It can
only add rules to the default set, never take one away, so the helper's "the ruleset is never
narrowed" rule (design-system.md "Accessibility testing (axe)") still holds. Its case in
`a11y-helpers.test.ts`: a 10×10px `<button aria-label="x">` passes with no option and fails with
`{ enable: ["target-size"] }` (the control and the probe in one case).

**What changes in the component** (everything else in it stays — the box's opening, placement,
Escape, outside click, focus leaving: `wt-help-tooltip.ts:67-121`, read):

```ts
@property({ reflect: true }) mode: "always" | "help-mode" = "always";
readonly #help = new HelpModeController(this);

override willUpdate(): void {
  // Only the help-mode CSS reads this attribute, so it follows the switch alone.
  this.toggleAttribute("data-help-on", this.#help.on);
}

override updated(): void {
  if (this.mode === "help-mode" && !this.#help.on) this.popup.hidePopover();
}
```

`willUpdate`; the plan review showed that check was invisible to every test, because no rule reads
the attribute without the mode, so it is gone.) `updated` calls `hidePopover()` without first asking
whether the box is open: a check there could not be told apart by any test. Measured 2026-10-18 in
`packages/ui` with a throwaway browser test (Vitest 4.1.11, Playwright 1.64.0's Chromium): calling
`hidePopover()` twice on a popover that was never shown threw nothing. Its `mode` check is needed
and killable: without it, an always-mode box would be closed by the render that follows its own
opening whenever help is off, which the existing `wt-help-tooltip.test.ts` cases would catch. The
box's `toggle` event then removes the document listeners, through the existing `onToggle`
(`wt-help-tooltip.ts:67-76`).

`packages/ui`'s floor of 90 is gated by the nightly sharded run only, on the merged score; a local
`pnpm --filter @waitron/ui mutation` prints a score and gates nothing
(`docs/developers/ci-and-gates.md:325`, read). So a thin test here goes green on the pull request and
reddens the next night. The new logic, and the case that kills each likely mutant:

| Logic | Mutant | Killed by |
| --- | --- | --- |
| `setHelpMode`'s early return | removed; `===` → `!==` | "setting the value it already has tells nobody"; "turning it on tells every listener once" |
| the unsubscribe's `listeners.delete` | removed | "an unsubscribed listener hears nothing more" |
| `HelpModeController.hostConnected`'s `requestUpdate()` | removed | "a probe out of the page … comes back" and "a badge put back after help changed" |
| `hostDisconnected`'s unsubscribe | removed | the `requestUpdate` spy case |
| `willUpdate`'s `toggleAttribute("data-help-on", on)` | `on` → `true` / `false` | "while help is off …" / "while help is on …" |
| `updated`'s `mode === "help-mode" && !on` | whole condition → `false`, or `hidePopover` removed | "turning help off closes an open box …" |
| the same | `mode === "help-mode"` → `true`, or `&&` → `\|\|` | the existing always-mode cases in `wt-help-tooltip.test.ts` (an always-mode box would close straight after opening while help is off) |
| the same | `!on` → `true` | "tapping it opens its box, as always mode does" (a help-mode box could never stay open) |
| the `mode` default `"always"` | → `""` | "with no mode it is in always mode" (every other case would pass either way, because `""` also draws as always) |

Whether Stryker mutates the text of Lit's `css` templates was not checked while writing this plan;
if it does, the measured layout cases (Tasks 2–4) are what kill those mutants. Optional local
reading, not run while writing this plan: `pnpm --filter @waitron/ui exec stryker run --mutate src/help-mode.ts,src/components/wt-help-tooltip.ts`
(it runs the package's whole browser suite first; check free memory).

## Review focus

1. **Nothing visible on main changes.** No file outside `packages/ui` and `packages/ui-core` is
   edited; every existing `wt-help-tooltip` test, the setup wizard's and the dashboard's, passes
   unchanged.
2. **"No room" is measured against a control that does take room**, in every host (Tasks 2–4), so
   the measurement could have failed.
3. **`.row { position: relative }` reaches every field in every app, and the price, file and
   stepper fields change structure.** Task 3 re-runs every suite known to measure them (including
   the till dialogs that stretch the stepper to its column); the run-it seat should look at a real
   dashboard form and at the till's reset-table and split dialogs.
4. **The badge never becomes part of what it explains**: outside the disclosure's header button
   (a tap does not toggle the section) and outside the dialog's `<h2>` (the dialog's name is
   unchanged).
5. **Every `wt-modal` heading gains the wrapper** (decision 10), with no edit to `wt-modal.ts`.
   Task 4 re-runs every `packages/ui` suite that names `wt-dialog` or `wt-modal`; a screen's own
   modal tests in the apps are left to CI.

## Open risks

- **A future badge left in always mode by mistake** shows permanently. Slice 2's own badges (table
  columns, tabs) are drawn by primitives that set `mode="help-mode"`; anything a screen slots in
  relies on the design-system entry. Slice 2 may want a guard (for example: outside `apps/setup`,
  every `<wt-help-tooltip` literal carries `mode="help-mode"`).
- **A badge sticking out of its box.** A badge hangs half its target (12px on the dashboard, 16px
  on a till) outside its box. Inside a box with `overflow: auto` (a dialog's or modal's body,
  `wt-dialog.ts:75-79`) it adds a sideways scrollbar; inside `overflow: hidden` it is cut off. At
  phone width a modal's side padding is 12px (`structure.css:66`), exactly the dashboard badge's
  overhang, which Task 4's 390px case pins. **For slice 4:** a till's 32px target hangs 16px, 4px
  more than that padding, so a full-width field in a till modal at phone width would scroll sideways
  (Task 4's control shows it) unless the till's modals get more side padding or the badge hangs
  less. Table cells and the till's tight bars are slices 2 and 4 to check.
- **For slice 4: a folding section's top padding.** `wt-disclosure`'s `.section` has `--wt-space-3`
  (12px) of block padding (`wt-disclosure.ts:35-37`, read). The badge hangs half its TARGET above
  the header (the margin in Task 2 is `--wt-help-badge-target / -2`): 12px on the dashboard, which
  fits exactly. On a till the 32px target hangs 16px, so its tappable box reaches 4px above the
  section into whatever is above; the visible 24px circle, centred in the target, hangs 12px and
  stays inside the padding. So on a till a tap 1-4px above a section can land on the badge.
- **The disclosure's badge sits at the end of the heading row, not right after the heading's
  words** as mockup 01 draws it (decision 9). Slice 2 should show the owner Products' Variants
  section with help on.
- **A badge slotted somewhere with no positioned wrapper** hangs over some far ancestor's corner
  (measured above: (414, 0) against the page). Every primitive in this slice positions its wrapper.
  Four of the dashboard's five current "?" sit in a `wt-combobox`'s `help` slot: Department and
  Starting zone (`device-profiles-screen.ts:2121-2137`, `:2182-2198`), the Staff status filter
  (`staff-screen.ts:385-402`) and a unit's decimal places (`unit-form.ts:353-373`), all read. The
  fifth, SumUp's, is not in any slot: it sits loose in a `<div class="affiliate-label">` beside a
  `<span>` label (`packages/payments-sumup/src/dashboard/sumup-connect-form.ts:245-252`, read). Slice 2
  must give that one a positioned wrapper (or move it into a primitive's slot) before switching it
  to help mode, or it will hang over a far ancestor's corner.
- **The stepper's baseline and narrowing** rest on the stepper's own suite and the staffing, till
  and floor-plan suites passing unchanged; nothing else checks them. The stepper's slot lives inside
  `.control` rather than a `.row` for this reason (decision 2), so the stepper's layout differs from
  the other fields' and the design-system entry must say so.

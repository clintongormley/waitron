## Review focus

1. A timed-out submit may already have committed: exact replay retains answer/ticks and prints once (T3/T4/T6).
2. A held dish, recalled source or relocated bill must retain its earlier consideration and assignment without being offered again merely because it has not fired (T3/T4/T8).
3. A late read or confirmation for another party, bill, operator, API instance or dialog opening must not submit or overwrite the active draft (T5/T6/T7).
4. Deleting the last guest must preserve Allergies; the before-image of deleted ticks must remain available to the future kitchen-notice implementation (T2/T5/T8).
5. Whole-group/course actions may affect dishes on other bills/stations; determine the entire set before mutation, retain admissions and roll everything back on refusal (T4/T7/T8).

## Contracts and decisions

**Ownership and authority.** The send routes currently require an open session and profile action `take-orders`, with zone checks; they declare **no separate person ordering permission** (`mountCourseVerb`, `requireSession`, submit/group routes). Match that policy, do not invent `orders.take` or another permission. New session reads/edits recheck session, active device/location, current profile action, `canUseDeviceProfile` admission and subject zones inside their transaction, following the stronger held-line route. GETs are passive. Existing send routes retain all bill/editor/payment/source-reservation gates. KDS fire retains device proof, KDS form factor, action and effective pass-screen zone admission, never a fabricated person id.

**Offered before.** Count a dish as considered only after its successful initial table submission/adoption, including `hold` and `join` before any HOLD output, even when no HOLD paper is configured. Opening/cancelling a window, a failed save or a rolled-back send does not count. All fresh submitted dishes are offered, not only immediately fired dishes. A later held fire checks the answer but does not re-offer those dishes. Recalled rows resolve to their retained `sourceLineId`; an editor can always retick every party dish explicitly. `orderGroups` membership, retained source identity and existing send/ticket facts are the proposed durable evidence, not the presence of a positive tick. T3/T8 must distinguish a successfully considered unticked held dish from a never-submitted fresh one, through restart, recall, no-preparation, moves and split. A counter dish newly adopted into table service must be considered before adoption sends it; its old counter send is not evidence of a table offer. If these facts cannot satisfy that distinction without new state, apply the migration gate above, not an approximation.

**Clashes.** Follow the spec's intersection of allergen **codes**, displaying cereal/nut kinds in the reason; do not invent kind-based exemptions. Use A668's own-dish effective allergens, selected variant included; show extras separately as A668 does. `null` nutrition is unknown, not known allergen-free; it grants no safety claim and never disables Send. A whole quantity-two line gets one guest or none. No automatic line splitting.

Extend `packages/module/src/party-allergy.ts` for shared wire types beside `PartyAllergySnapshot`; its existing index already exports this file type-only. Server and till import these types from `@waitron/module`; do not introduce an app-to-app import. Use the existing type-only `AllergenMap` import. New types:

- `AllergyLineRef = {kind:"draft";id:string} | {kind:"working";id:string} | {kind:"submitted";groupIndex:number;lineIndex:number}`. Submitted refs are valid only for direct `submitGroups`, mapped by input parent order to preassigned row ids, never insertion-return order.
- `AllergyGuestInput = {id?:string;who:string;allergens:AllergenMap;note:string|null}`; `AllergyPatch = {party?:{answer:"none"|"allergies";guests:AllergyGuestInput[]};ticks:{line:AllergyLineRef;guestIndex:number|null}[]}`. Guest indexes address the post-edit ordered guests, or the read snapshot when `party` is absent. Omitted party keeps the answer; absent `allergy` keeps existing state; explicit null objects are invalid. Tick entries replace only named lines; null guest clears a tick. Reject duplicates, cross-party/child/stale targets and targets outside the action's eligible set. Full editor may name any valid party dish.
- `AllergyCommand = {submissionId:string;expectedPartyRevision:number;allergy?:AllergyPatch}`. Draft/group submissions and party fires extend their current command with `allergy?`; retain every existing field. Legacy line/course sends accept an optional command alongside their existing arguments/body. Counter calls keep their current shape. Matching ids replay; changed allergy payload under that id refuses `submission.id_reused`.
- `AllergyDish = {line:AllergyLineRef;billId:string;name:string;quantity:string;allergens:AllergenMap|null;extras:{name:string;quantity:string;allergens:AllergenMap|null}[];sentAt:string|null;offeredBefore:boolean}`; `PartyAllergyRead = {partyId:string;snapshot:PartyAllergySnapshot;dishes:AllergyDish[]}`. Dishes span all party-family bills and saved drafts, excluding extras as assignable rows. Each extra appears under its parent with its own effective nutrition, including null for unknown and {} for reviewed-empty; never union its allergens into the parent field. Do not filter down to the active bill or hide paid bill lines needed by the editor.
- `AllergySendTarget = {kind:"draft";draftId:string;lineIds:string[]} | {kind:"lines";orderId:string;lineNos:number[]} | {kind:"group";groupId:string} | {kind:"held-line";lineId:string} | {kind:"course";orderId:string;courseId:string}`. Server resolves actual parent sets, including course-wide groups and empty-line-list semantics; client ids never establish authority.
- `AllergyChangeSet = {partyId:string;before:PartyAllergySnapshot;after:PartyAllergySnapshot;workingLineIds:string[]}` includes old AND new assignments for edited/deleted guests and changed ticks. This is an in-transaction handoff, not a delivered notice or durable notification queue.

New server `party-allergy.ts`: `readPartyAllergyView(tx:Transaction,cfg:TillConfig,partyId:string):Promise<PartyAllergyRead>`; `readAllergySendView(tx:Transaction,cfg:TillConfig,partyId:string,target:AllergySendTarget):Promise<PartyAllergyRead>`; `applyPartyAllergyPatch(tx:Transaction,partyId:string,patch:AllergyPatch,operatorId:string,allowedTargets:readonly ResolvedAllergyTarget[]):Promise<AllergyChangeSet>`; `assertPartyAllergyAnswered(tx:Transaction,partyId:string):Promise<void>`. Define server-local `ResolvedAllergyTarget = {ref:AllergyLineRef;draftLineId:string|null;workingLineId:string|null}`, requiring exactly one stored id, so a submitted index resolves explicitly to its inserted parent. Mutators take `Transaction`; routes own transactions and revision bumps. Resolve targets before deleting/replacing drafts or releasing any group.

Add venue-service seat `writePartyAllergy(tx,partyId,input:unknown,operatorId):Promise<void>` by extracting the existing validated replacement body; it performs no revision bump. Existing `savePartyAllergy` keeps its signature/check/bump and calls it. The server checks/bump ONCE via `checkAndBumpParty` within the existing replay callback, then applies patch/ticks through the seat and reads the final snapshot. Do not call today's revision-bumping save with yesterday's revision after a send has already bumped it. Tick-only edits also move the party revision once.

New `party-allergy-api.ts`, mounted from `till-api.ts`: `GET /api/parties/:id/allergy` (editor/banner); `POST /api/parties/:id/allergy/send-preview` (read-only target resolution after an explicit Send action; active session activity); `PUT /api/parties/:id/allergy` (`AllergyCommand`, replayed save). Client methods `readPartyAllergy(partyId,options?)`, `previewPartyAllergy(partyId,target,options?)`, `savePartyAllergy(partyId,command,options?)`. Only automatic GET polling is passive; preview POSTs retain normal session activity. No GET changes state. Read failure stays unread and blocks the dependent send; never convert it to unanswered or none.

**Counter-to-table adoption.** Add read-only `POST /api/bills/:id/move/allergy-preview`, with the current move body `{to,bills,...MoveBillRevisions}`; restrict this preview to table destinations. Recheck source bill and destination identities/revisions without changing them. Do not call `resolveDestination`/`readTargetTable` unchanged in this read, because the latter bumps the destination revision. Client `previewBillMoveAllergy(billId,to,bills,revisions,options?)` returns `AllergyMoveRead = {billId:string;tableId:string;partyId:string|null;snapshot:PartyAllergySnapshot|null;dishes:AllergyDish[]}`. Null party/snapshot means a currently free table, not a stored No allergies answer. Resolve existing-party guests and arriving parent line ids authoritatively; parent working refs remain stable through a merge. The dialog consumes `PartyAllergyRead | AllergyMoveRead`, opens the question for a null snapshot and returns a patch plus the preview's destination identity. Revalidate those expectations in the move transaction.

Extend current `MoveBillOptions` and move JSON with paired optional `submissionId:string` and `allergy:AllergyPatch`; retain all current `MoveBillRevisions` fields, including explicit `otherPartyId:null` for a free table. Client `moveBill` gains a final optional `{submissionId:string;allergy:AllergyPatch}` argument. For this counter-to-table command, `runServiceCommand` uses `{kind:"bill",workingOrderId:billId}` and kind `bill.move.allergy`, fingerprinting authenticated `operatorId`, target, merge choice and full patch before existing source/destination guards. The server supplies the actor from the session; a second operator reusing the same id refuses `submission.id_reused`. A matching retry returns the original party/bill result even after relocation; a changed patch refuses `submission.id_reused`. Inside that callback, recheck editor/admission/source/destination expectations, create a free-table party if needed, and apply the patch after party attachment but BEFORE `adoptZone`, `takeIntoParty` or `groupArrivingDishes` can send. Split `takeIntoParty`'s attachment from its sending continuation at this boundary; do not add a second transaction. Existing-party destination revision ownership remains with the move, and a new party does not pretend to have a client-read revision. Cancelled previews create no party and send no move; destination occupation, changed bill lines or changed destination guests require a new preview/confirmation. Exact network retry retains the immutable packet. This contract is integrated with B/A796 only after checking its current move/carry-on ownership; no payment behavior is rewritten.

**A669-4 boundary.** Every explicit edit, send-time answer/guest edit, deletion, No allergies and tick change passes through `applyPartyAllergyPatch`. Capture before state before cascades delete ticks. Its returned change set is the precise future call site for slice 4 to enqueue notices and update frozen copies before this same transaction commits. T2 tests the deleted line ids remain in it. Slice 4 must cover fired work and held work with printed HOLD, omit served work, route station-specific notices and deduplicate replay. This PR exposes deletion but does not deliver those notices; say so prominently in its description and retained A669-4 backlog detail. Do not mark A669 complete or ship a dummy notice implementation.

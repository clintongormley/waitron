# A841 slice 5 — the editor: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every implementer is dispatched as `subagent_type: "implementer"`; one that passes about 150 tool calls with its task unfinished stops at a passing (or cleanly red) point, commits, and returns a handover.

**Goal:** A manager opens Settings → Appearance, sees the theme in use on a read-only Look card, presses Edit, changes the brand colour, background and corners while a Light and a Dark preview repaint from the draft, is warned (never refused) about a brand colour that is hard to read with a one-press fix, and saves — through a "Hard to read" dialog when a warning is still unfixed — after which this dashboard repaints at once.

**Architecture:** One new dashboard page, `dashboard-appearance-screen`, owns a live, passive read of `GET /management-api/themes` and hands it to `dashboard-look-card`, which shows the theme in use read-only and edits it in place with a draft scope. The browser works the draft out with slice 1's `deriveTheme` for the preview and the warnings; the server works it out again on save and answers its own warnings, which the saved card shows. The preview paints two theme roots inside its own shadow root from `themeSheet`, so nothing outside the panels changes until Save. No server route, no migration, no `@waitron/ui` change.

**Tech Stack:** Lit 3 in `apps/dashboard` (Vitest 4.1.11 browser mode, real headless Chromium), `@waitron/ui-core/theme` (slices 1–2), `@waitron/ui` primitives, Markdown user guides served by `apps/server`.

**Spec:** `docs/superpowers/specs/2026-10-19-a841-theme-editor-design.md` — section 16 item 5 is the scope; sections 4, 7, 8b, 9, 10, 13, 15 and 18 are the detail. Executors read both.

## Decisions this plan makes (the design left them open)

**D1. Save while Waitron's theme is in use: there is no Edit until slice 13.** The design's first save
from Waitron's theme opens the name dialog (design lines 1765-1768), and section 16 gives the name
dialog — "the first save from Waitron's theme" included — to slice 13 (lines 2620-2624). The ways a
slice-5 Save could work without it each invent something the design does not have: a default name
for an automatically created theme (product text, and a row named by nobody), or a Save that is
drawn and does nothing. So in slice 5 the Look card offers **Edit only while a custom theme is in
use** (and only to a person holding `layout.configure`, D5). While Waitron's theme is in use the card
is read-only for everybody; slice 13 adds Edit there with its name dialog. Consequence: on a venue
that has never stored a theme, the editor is reachable only after a theme is put in use through the
management API (`POST /management-api/themes` with `inUse: true`, `apps/server/src/themes-api.ts:97-112`)
or a configuration copy. The driver step says so in the backlog, so lane A can order slice 13 next.
The editor's line under the heading still covers both cases from the design's own words (D7).

**D2. "Save as new theme…" is slice 13's.** It opens the name dialog (design lines 1762-1764), which
is slice 13's (line 2620). Slice 5 draws no "Save as new theme…" button; mock-ups 02 to 05 and 16
draw one, and the visual check (Task 9) lists that as an expected difference.

**D3. Which server answer the editor reads, and where warnings are worked out.**
- The page reads `GET /management-api/themes` (`themes-api.ts:86-95`): `{ themes: ThemeAnswer[], inUse: string | null }`,
  each `ThemeAnswer` being `{ id, name, updatedAt, choices, light, dark, warnings }` (`themes-api.ts:39-47`).
  The theme in use is `themes.find((t) => t.id === inUse)`; `inUse === null` is Waitron's theme.
- **The saved card** shows the server's `warnings` of the theme in use (keys only: `field`, `mode`,
  `fix`, `blockedBy`, `against`), worded in the browser (design lines 2027-2031: "the saved card —
  which a supervisor also sees — reads them from there rather than working them out itself"), and
  takes a taken fix's shade from the answer's own `light` / `dark` `--wt-color-primary`.
- **The editor** works the draft out in the browser with `deriveTheme(draft.choices)`
  (`packages/ui-core/src/theme/waitron.ts:8-10`) on every change, for the preview, the warnings, the
  fixes and their shades; `fixAll` and `canFixAll` (`packages/ui-core/src/theme/theme.ts:104,132`)
  decide Fix all and Fix and save. The server re-derives on `PUT` (`themes-api.ts:114-124`) and its
  answer replaces the card's copy.

**D4. The page's read is passive after its first read and follows a live subscription.** The page
watches `listThemes` through `QueryController` and `dashboardQuery` like the Defaults card
(`apps/dashboard/src/screens/venue-defaults-panel.ts:92-101,315-349`): the first read counts as
activity (the person opened the page), every later one is sent passively
(`apps/dashboard/src/api/live-queries.ts:575-581`), and `QUERY_DEPENDENCIES.listThemes` is
`["custom_themes"]` (beside `getVenueTheme: ["custom_themes"]`, `live-queries.ts:97`), so another
dashboard's save, a switch through the API or an import refreshes the card. `custom_themes` is
already a change source (slice 3, D5), so `scripts/live-subscriptions.test.ts` accepts the name.

**D5. Permissions** (design section 13). The Appearance item names `requiresPermission: "venue.view"`
(supervisors and up, `packages/identity/src/permissions.ts:45-54`, through `SUPERVISOR`), so the shell's existing gate
(`#mayOpen`, `apps/dashboard/src/dashboard-app.ts:1907-1914`, and `#permittedScreen`, `:1946`) hides
the item and refuses a typed address without it; a staff session is sent to Orders or My schedule as
for every page. The card offers Edit only when the shell passes `canEdit` =
`#sessionPermissions.includes("layout.configure")`, held by managers and admins, not supervisors
(`permissions.ts:55-59`). No server change: every theme write already checks `layout.configure`
in `@waitron/layouts`, and the read `venue.view` (`themes-api.ts:90`).

**D6. This dashboard repaints at once after a save of the theme in use** (design step 7, line 553).
After a successful `PUT` of the theme the latest read names as in use, the card runs
`readVenueTheme(() => api.getVenueTheme())` and `applyVenueTheme(answer, sentAt)` from `@waitron/ui`
(`packages/ui/src/venue-theme.ts:95-126`): the read is numbered when it is sent, so an answer the live
read applied after it is never undone (slice 3, D8). The live read (`dashboard-app.ts:1200-1206`)
also re-reads on the `custom_themes` change; the explicit read does not wait for the stream, which
the backlog says may not open ("A dashboard that signs in takes a fresh theme from its live stream
alone"). `readVenueTheme`'s first call after a start reuses the start-up answer (`venue-theme.ts:93-99`);
in the app the shell's watcher makes that first call at sign-in (`dashboard-app.ts:1197`), before
any screen can save, so the card's call always sends. Tests that call `startVenueTheme` consume the
start-up reading first, as the shell does.

**D7. The line under the editor's heading follows the latest read.** It says "Theme in use: {name}.
Saving changes every screen." while the edited theme's id is the read's `inUse`, and "Not in use.
Saving changes no screen until you use it." otherwise — both the design's words (line 609). In
slice 5 the second shows only when another manager switches or deletes through the API while this
editor is open; D6's repaint runs only when the saved id is the one in use.

**D8. Hand-set colours in a slice-5 theme.** Only the API or an import can put them there before
slice 6. The draft keeps `handSet` exactly as stored, and Save sends it back unchanged. Their warnings
take part in Fix all, `canFixAll` and the Save dialog, because those are the design's one rule
(`fixAll` fixes every warned colour). They are worded with the design's saved-card sentence,
"{name} ({light / dark}) is hard to read." (line 634), in the dialog as on the card — **a departure**:
the dialog's own hand-set line names what the colour is hard to read on (line 632), which needs a
plain name for every colour a rule can name, the meaning colours and station groups included;
slice 6 brings those names and replaces the dialog line. A hand-set warning with no fix uses the
design's dialog lines as written ("… no shade can be read." and "… while {name} is set by hand to
{colour}."). So this slice adds the 22 plain names of section 5 (line 699-706), which slice 6 needs too.

**D9. The brand colour field.** `colorField` (`apps/dashboard/src/widgets/color-field.ts:133-252`)
gains three optional options, leaving its four callers unchanged: `legend` (replaces "Colour"),
`noneChoice: { label, chip }` (replaces the "no colour"/"inherit" choice's label and chip; it still
calls `change(null)`, which is exactly `brandColor: null`, Waitron's), and `code` (a `wt-input`
beside the custom picker holding the colour as text). The brand field passes legend "Brand colour",
the none choice "Waitron's" with a chip of Waitron's light button colour
(`WAITRON_DEFAULTS.light["--wt-color-primary"]`, `#1f6feb`), the picker named `brandColorPicker` and
the code field named `brandColor` — the name `theme.invalid`'s `field` uses (design line 2145), so a
refusal lands under it. The code field's accessible label is new text the design does not give:
"Colour code" / "Código de color", heard only by a screen reader (`hide-label`). Flagged.

**D10. What the code field accepts.** A value that, trimmed, matches `/^#[0-9a-f]{6}$/i` is taken as
the brand colour in lower case at once (the preview follows as the person types); anything else
leaves the brand colour as it was and is the form's own failed check, "Enter a colour as # and six
digits or letters a–f." (design line 636), shown only after the first press of Save (house rule,
`docs/developers/design-system.md:2426`). An empty code field is valid only while "Waitron's" is
chosen. The draft compares the code field by its trimmed, lower-cased text, so typing the stored
colour in capitals is no change.

**D11. Picking another brand colour drops the brand fix** (design step 6, line 543); choosing
"Waitron's" drops it too (`normaliseChoices`, `theme.ts:73`). Background and Corners keep it.

**D12. The Fix all line counts every warning in the draft** ("{n} colours are hard to read.") and
shows when two or more of them carry a fix (design step 5, line 536). With brand warnings alone it
never shows: no brand colour warns on both kinds of screen — probe `both-modes.mts` below found 0 of
8,192 Neutral and Tinted brand colours warning in both modes, against 6,757 warning in one (the
control that the probe sees warnings). So in slice 5 it shows only for a theme with hand-set colours
(D8), and its tests use one.

**D13. The preview** (design step 2, lines 487-490; section 10, lines 2006-2017). Slice 5 draws, in
each panel: a sidebar item selected and one not, a field with focus, Save and Cancel buttons, a
switch that is on, a link and a two-way choice — not the banner strip (slice 8, line 2575) nor the
till button and bill line (slice 10, line 2590). It is static markup styled only from tokens, in
`dashboard-theme-preview`'s shadow root, marked `aria-hidden="true"` below each visible panel
heading: it is a picture of the look, and real controls there would add tab stops and a second
focused field. Its words are existing strings, so nothing new is invented: the nav labels
`nav.appearance` and `nav.devices`, `venue_details.name` with the theme's name as its value,
`action.save`, `action.cancel`, `help.guide_link`, and the Theme setting's `theme.light` /
`theme.dark` as the two-way choice. Each panel is passed to `applyTokens(panel)`
(`packages/ui-core/src/tokens/index.ts:18-25`), which adopts the token layer into the preview's
shadow root, carries `data-theme="light"` or `"dark"`, and takes the draft from one constructed sheet
in the same shadow root whose text is `themeSheet(derived)` (`packages/ui-core/src/theme/sheet.ts:19-32`).
Probe `preview-scope.mts` (below) ran exactly that shape against the real token files.

**D14. "Use Waitron's look" is slice 5's** (design step 8, lines 557-565; it sits on the card's
button row in pictures 02-04). It sets the draft to `WAITRON_CHOICES` (`theme.ts:20-26`) — "Waitron's",
Neutral, Standard, no fix, nothing set by hand — and the code field to empty; it saves nothing. It is
not a save, so it follows the not-a-save rule (`design-system.md:2694-2703`): disabled and drawn
`secondary` while the draft already is Waitron's look, `secondary` (its own variant, as the pictures
draw it) and enabled otherwise. Logo and text size join it in slices 8 and 10.

**D15. The Save dialog's main button.** With Fix and save offered it is the main (`primary`) button
and Save anyway is `secondary` (design line 1905, picture 16). When Fix and save is not offered,
Save anyway is the main button. Choosing either closes the dialog and saves through the card's own
save, so a refusal lands in the card's form like any other.

**D16. The saved card's Brand colour row.** "Waitron's" with Waitron's chip; otherwise a chip and the
colour, prefixed "Custom · " when it is not one of the 24 swatches (`CATEGORY_PALETTE`), then, for
each kind of screen whose fix is taken, " · light screens {chip} {shade}" or " · dark screens {chip}
{shade}" (design line 470-472 gives the dark form; the light form is its mirror — flagged as derived
text). A palette colour shows no "Custom" because the field calls it a swatch, not Custom.

**D17. No help tooltip on the page in slice 5.** The design gives the page no help text, so none is
added and `help-guide.ts` gains no link. The guide serves no index page: the page is reached by its
address (`/help/en/appearance`, `/help/es/appearance`) and from the list of pages the guide's
not-found page draws (`apps/server/src/guide-pages.ts:169-176`). So nothing in the dashboard leads to
it in slice 5. Flagged for the owner.

**D18. An unreadable theme in use** (slice 2, D7: `choices: null`, served as Waitron's look). The card
shows its name in "Theme in use" and Waitron's values in the other rows (what the screens show), and
Edit opens on `WAITRON_CHOICES`; Save stores a valid document over it.

- A readability warning is not a field error: it never goes in a field's `error`, never in the bottom
  correction message, never disables Save (design lines 574-576).
- Save follows `draftScopeFor` / `saveActionState` with an early return while unchanged
  (CLAUDE.md §3); every form change goes through the draft scope.
- Browser-test traps (CLAUDE.md §4): wait for a dialog's `wt-close` (`dialogClosed`,
  `apps/dashboard/src/widgets/test-helpers.ts:137-139`) before asserting what a close does; use
  `userEvent.click` where a click's outcome depends on an update one listener schedules; restore the
  screen language (`setLocale("en-GB")`) in `afterEach`; never count `history.length`.
- Every commit `git commit -s`. Run focused tests while implementing; CI owns the package suites.

## Review Focus

1. **Another dashboard changes the theme while this one edits** — a save of the same theme, a switch
   to another, or a delete, all through the API. Expected: an unchanged draft follows the new stored
   choices; a changed draft is kept; the editing line flips to "Not in use…" after a switch (D7); a
   save of a deleted theme shows the refusal at the bottom and Save stays enabled. Tests: Task 6.
2. **The stored theme in use cannot be read** (`choices: null`). Expected: the card shows the name and
   Waitron's values, Edit opens on Waitron's choices, Save stores a valid document (D18). Test: Task 2
   (card) and Task 5 (edit and save).
3. **A theme carrying hand-set colours** (API-made). Expected: Save sends `handSet` unchanged; Fix all
   and the dialog count and word them (D8, D12). Tests: Task 5 (sent unchanged), Task 7 (dialog lines,
   Fix all line).
4. **The colour typed rather than picked** — capitals, spaces, a short code, an empty field. Expected:
   D10. Tests: Task 4 (field) and Task 5 (draft rules).
5. **A double press** — Save anyway or Fix and save pressed twice, or Save pressed while a save is
   sent. Expected: one `PUT`. Test: Task 7.

# A652 Photo Framing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans`, inline and task by task. Read the TDD skill before writing implementation or tests. The owner authorizes autonomous implementation, finish and land; do not request conversational approval.

**Goal:** Adjust a photo's framing and replace its picture without losing its names or uses, with only Edit photo's Save persisting the draft.

**Architecture:** Keep each existing photo ID, original hash filename and original bytes. Add a media-owned current-picture pointer and framing overrides, and resolve that stable reference to immutable source/rendition URLs at display time. Published and queued documents retain their exact bytes and hashes; receipt configuration gets refreshed printable pictures atomically with a photo save.

**Tech Stack:** TypeScript, Lit, existing `wt-modal`, `wt-slider`, file field and buttons, sharp, Drizzle SQLite migrations, Vitest Chromium and axe. No new dependency or lockfile change.

**Spec:** [A652 backlog detail](../../backlog/catalogue.md#a652--frame-a-photo-for-its-thumbnails), [backlog entry](../../backlog.md), both [mockup boards](../../backlog/mockups/a652-photo-framing/), the owner's decisions recorded there. Text takes precedence over illustrative board styling.

## Global Constraints

- Separate Adjust framing window: drag, Zoom, Lists square preview, Till buttons 4:3 preview, Reset centre/no zoom, Done back to unsaved Edit photo. Only outer Save writes.
- One point and zoom per photo, everywhere. Replace preserves names, products, variants, sections, include folders, receipt-logo choices and published/queued menu references; reset framing when a replacement is chosen, then allow reframing that draft.
- No fiscal writer, fiscal hash, invoice numbering, alta, register or restore changes. Do not rewrite published documents, `content_hash`, `menu_version_images`, issued records or queued print/delivery payloads.
- Read repository `CLAUDE.md` and developer UI, data, testing, design-system, products, writing-claims, workflow and CI/gates topic files before execution. Keep behavioural assertions and demonstrate intended RED before GREEN. Database suites use `useVenueDb`; queries inside one transaction run sequentially.
- Generate new migrations in `packages/media/drizzle` only. Never edit shipped SQL, snapshots or journals by hand; no core/catalogue rebuild or migration squash, and no backward-compatibility/data-conversion project. Sparse overrides make untouched photos use their original picture and centre/100% by definition.
- Every implementation commit uses `git commit -s`; never bypass hooks.

## Review Focus

1. A replacement whose bytes already exist must not merge two photo identities, names or uses; uploading a retired original must not silently return a different picture (Task 2).
2. A published/queued photo must change visually without changing the stored menu document or its hash; an old immutable URL must still return its original bytes (Tasks 2–4).
3. Concurrent photo saves and receipt-settings saves must not install a raster prepared from an older picture; failure rolls back names, picture, framing and rasters together (Tasks 2 and 6).
4. Touch cancellation, keyboard-only placement, orientation, extreme portrait/landscape ratios and zoom limits must agree between previews and server crops (Tasks 1 and 5).
5. A mounted list/till, hidden tab, disconnect, failed refresh or late response must not retain the wrong photo indefinitely, overwrite drafts or keep a dashboard session active (Tasks 3–5).

### Identity, storage and collisions

Use stable image ID plus blob indirection. Do **not** replace references across every table or put replacement bytes behind an old hash URL. Retain the original filename as the existing reference/alias to that image ID; it also still identifies its original immutable bytes. The current-picture pointer is explicitly separate. This avoids changing any menu document or lower-package reference schema.

Add declarations to `packages/media/src/schema/images.ts`:

- `media_image_blobs`: `hash` primary key, exactly 64 lowercase hex characters, with a declared CHECK on length/alphabet and no embedded NUL; `bytes` binary, prepared WebP <=1600. New replacement sources are always prepared WebP, so their public filename is `${hash}.webp`. Validate both the WebP type and bytes digest on insert/import. Identical blobs share this key; never update bytes under a hash. Existing original filename/data rules remain unchanged.
- `media_image_edits`: `imageId` primary key, FK to `media_images.id` with cascade; nullable `sourceHash`, FK to `media_image_blobs.hash` with restrict; `focusX`, `focusY` through `@waitron/db` `count`, SQL defaults 5000, bounds `0..10000`; `zoom` through `count`, SQL default 100, bounds `100..400`; `revision` through `count`, SQL default 1, bounds `1..9007199254740991`. Declare `typeof(column) = 'integer'` with each bound, rather than relying on integer affinity. Add nullable `originalFilename`: the current upload's basename, at most 255 characters with no NUL, CR or LF, displayed as text. The server strips both slash forms before validating; absent names remain null. Null source means the image's original data. Missing row means `{ x:5000, y:5000, zoom:100, revision:0 }`. A framing-only edit creates a row with null source hash. New uploads create an edits row at revision 1 even without an upload name; old/seeded photos without an edits row remain revision 0 and display their hash filename as fallback. Capture `File.name` on upload and replacement, include it in the outer draft and transfer, and preserve it on names/framing-only saves and duplicate reuse. Every successful names/picture/framing save advances the revision, including names-only saves, so stale names cannot overwrite newer edits.
- No raster/thumbnail table: deterministic rendition URLs describe source, framing, shape and algorithm version. Generate small WebP on demand outside transactions and cache bounded bytes in memory. Original and replacement sources remain in venue.db and travel with configuration/backup. Keep replacement blobs for this feature; do not add a garbage collector that could invalidate an issued rendition URL.

Keep upload deduplication intentional: match **current source bytes** first, return the earliest `(createdAt,id)` match with its names/framing unchanged and `created:false`. Replacement with another photo's source shares only immutable bytes and never merges image IDs or references. If no current match exists but the upload's original-hash alias is occupied by a photo now showing different bytes, return `image.reference_conflict` (409), with that image ID and localized “This photo's original file already belongs to another library entry. Edit that photo or choose another file.” Do not pretend the returned picture matches the upload or restore that entry implicitly. This is an implementation policy, not a newly attributed owner decision. For any same-filename insertion compare bytes; unequal bytes refuse `image.hash_conflict` (409), never overwrite or absorb it with an untargeted conflict clause.

### Framing, APIs and caching

- Browser-safe media `framing.ts`: `ImageFraming = { x:number; y:number; zoom:number }` in the integer units above; `DEFAULT_FRAMING`; `validateFraming(unknown): ImageFraming`; `cropRect(width:number,height:number,ratio:number,framing:ImageFraming): { left:number; top:number; width:number; height:number }`. Reject null, arrays, missing/extra fields, strings, fractions, NaN/infinity and out-of-range values with `image.invalid_framing` (400, `{ field:"framing" }`). Ratio is `1`, `4/3`, or source aspect for full-aspect display/logos. Take the largest continuous in-bounds rectangle at that ratio, divide both sides by `zoom/100`, centre at `(x/10000*width,y/10000*height)`, then clamp left/top. Keep fractional coordinates at this stage. Add shared `rasterCrop(width,height,ratio,framing)`: floor left/top, ceil right/bottom, clamp to source bounds, keep dimensions >=1. Server extracts that integer rectangle, then sharp resizes with `fit: "cover"`, centred placement and `withoutEnlargement: true` into the shape target. Browser previews use that same integer rectangle and centred, aspect-preserving cover inside their square/4:3 frames. Pin a maximum one-source-pixel edge tolerance between the continuous target and the rasterized preview and forbid stretching or blank edges. Tiny sources may produce a native raster whose aspect differs from 4:3; their visible frame still has the requested ratio and covers without stretching. State output dimensions explicitly in tiny/asymmetric tests, rather than promising exact 4:3 pixels where none fit. Do not implement zoom with `object-position` alone.
- `readImage`/list records add `framing`, `revision`, `sourceFilename` and nullable `originalFilename`; `sourceFilename` is derived from `sourceHash` when present. Retain `filename` as the stable original reference. `readImageBytes(tx,filename)` keeps its immutable meaning and also finds replacement blobs; add `readCurrentImage(tx,reference)` returning `{ imageId, revision, sourceFilename, framing, bytes } | null` for preparation. Batch metadata lookups must not select image payloads or read per row.
- PATCH `/management-api/images/:id` accepts JSON `ImageEditInput = { names:Record<string,string>; framing:ImageFraming; expectedRevision:number }`, or multipart JSON fields `names`, `framing`, `expectedRevision` plus `file`. `ImageApi.updateImage(id:string,edit:ImageEditInput,file?:File): Promise<{ image:LibraryImage }>` sends one request. Revision must be a nonnegative safe integer. Same upload bounds/type/pixel checks as POST; validate/authorize before expensive work and re-authorize inside the final transaction. Replacement alone resets framing; the client may send a subsequent adjusted framing for that replacement in this same outer save. Return `{ image }`; stale revision returns `image.changed` (409, `{ imageId }`), retaining the draft, with an explicit reload action rather than automatic overwriting/retry. Register all new codes in media `errors.ts`, route status maps and EN/ES code messages; `image.reference_conflict` carries `{ imageId }`, `image.hash_conflict` carries `{ filename }`, and `image.busy` carries no parameters.
- Pixel preparation and receipt-raster preparation occur outside the write lock. For every pixel/framing save, prepare both receipt widths even when the initial logo-user query is empty: a department may attach during preparation. Names-only saves need no raster preparation. Final `saveImage(tx:Transaction,id:string,edit:ImageEditInput,prepared:PreparedImage|null,rasters:ReceiptLogoRasters|undefined,fallbackLanguage:string): Promise<ImageRecord>` checks revision and metadata, inserts/reuses blob, updates names/override and all **currently matching** department logo rasters in one `withTransaction`. Null prepared source means no replacement; unchanged pixels/framing require no raster work. Query current logo users inside that transaction, including retained inactive departments; do not replay an earlier list of department IDs or overwrite their receipt JSON/policies. A pixel change with a matching logo user and absent prepared rasters refuses before mutation, including a logo attached during preparation. Throwing at any stage rolls everything back. No second transaction for the logical save.
- GET `/media/presentations?references=<comma-separated refs>`: max 100 unique valid original filenames, response `{ images: Record<string,{ id:string; revision:number; source:string; square:string; till:string; display:string }> }`, omit missing references, `Cache-Control: no-store`. Values are same-origin URL strings; `source` is `/media/<current-source-hash>`. This is public/passive like existing image bytes, never touches management sessions. Repeated/oversized/malformed queries receive the registered `image.invalid_query` refusal. Mount this static route before `/media/:filename`; the existing dashboard/till Vite `/media` proxies and boot's `/media/*` CORS rule already cover this namespace (`apps/dashboard/vite.config.ts:19`, `apps/till/vite.config.ts:40`, `apps/server/src/boot.ts:1494`). Test those real origins.
- Renditions: `/media/renditions/v1/<source-hash.ext>/<square|till|display>/<x>-<y>-<zoom>.webp`. Square = 480×480, till = 480×360; display retains source aspect, bounded to 1600 on its long edge. Do not enlarge tiny inputs; return the crop at its native size when smaller. WebP quality 80. All geometry/shape arguments bounded and canonical; source must already exist. Serve immutable with nosniff, correct WebP type and ETag of response bytes. Never put these recipe URLs in `MEDIA_FILENAME` or claim the recipe text hashes its bytes. Bump the recipe version if an encoder/geometry change can change the result.
- Limit rendition work to one active sharp operation, share in-flight work by canonical recipe, keep at most 32 MiB of completed bytes, and at most 100 pending distinct recipes. Overflow returns retryable `image.busy` (503), no failed entry cached; always release the gate on failure. Cache eviction/restart regenerates from durable source and recipe. Do not hold a transaction while sharp runs.
- New direct-import UI Lit directive `liveMediaImage(reference,shape)` in `packages/ui/src/live-media-image.ts`, shape `source|square|till|display`. One browser-page resolver batches visible consumers into <=100-ref GETs, initially and every 15 seconds while the document is visible; immediate refresh on visibility return/reconnect. Keep last successful URL on a failed refresh, ignore older generations and stop when no consumers remain. No timestamp cache-busting of immutable URLs and no empty `src` while resolving (use Lit `nothing`). Media Save explicitly invalidates its local resolver; other open tabs/tills refresh within the next successful visible poll. Direct-import this utility, without UI index/demo exports or a new `wt-*` primitive. It requires no new package dependency and no till root/client changes.

### Measurement receipt and choice

Measured during plan authoring, Node v26.11.1/sharp 0.35.5, one sharp thread, cache off, WebP80. Read all 45 `apps/server/scripts/demo-seed/media/*.png`, prepare with `resize(1600,1600,{fit:'inside',withoutEnlargement:true})`, then compare 480-long-edge/480-square/480×360 copies. Prepared originals total **120,752 bytes**, sorted first 24 **57,224**; each tested small form's first 24 **56,950**. These tiny seeds do not substantiate the backlog's “about 4 MB” estimate. `apps/server/.env` was absent, so this invocation measured no live venue library.

A distinguishing stress control used 24 separate 1600×1200 RGB buffers, xorshift32 starting at 652 (`n ^= n<<13; n ^= n>>>17; n ^= n<<5; byte = n>>>24`), then WebP80: full copies **31,589,190 bytes**, 480-square **2,280,340**, 480×360 **1,483,202**. These are synthetic noise, not a restaurant-photo average. Choose 480-pixel small renditions: they bound grid input dimensions and cut that measured large-input control by 92.8% for squares. Do not repeat the 4 MB estimate as a measured fact. Task 3 measures actual HTTP response bodies, including metadata, and Task 5 checks picture quality at rendered tile sizes and 2× device scale.

# A679 First Live Fiscal Setup Implementation Plan

> **For agentic workers:** use `superpowers:executing-plans` and implement inline, as the owner selected. Read the TDD skill before writing implementation or tests. Work task by task; record observed failures before implementing. No automatic delegation.

**Goal:** let you complete first Live setup through the real wizard, with either a new outside paper kit or an existing custodian, without a checkout, shell or Cloud subscription.

**Architecture:** a downloaded, self-contained offline tool owns real custody keys, encrypted-file recovery, secret-paper recovery and public signing. The box owns a durable claimed setup attempt and independently collected public trust/current-master statements; existing module preparation and allocation activation perform the venue transaction. Readiness uses A680 in its separate retained preproduction database; Live consumes a distinct outside production allocation.

**Tech stack:** TypeScript, Lit/shared `wt-*` controls, Hono, Node filesystem/crypto, browser Web Crypto, existing SQLite allocation tables, Vitest/real Chromium and the installed `@waitron/verifactu` validator. No new crypto dependency or workspace package.

## Global constraints

- BOTH new-kit and existing-custodian routes converge on public import and the same authority checks. Subscribers use public import too; C3 does not supply wizard fetching.
- One named custodian, one writable paper-original current master; all other public copies are snapshots. Private-key retention is BOTH a protected saved file and recoverable secret paper for the SAME key, outside the box/backups and separate from the public original.
- Reopen the actual saved file; restore by transcribing the actual printed paper in a separate clean offline session. Require the complete fingerprint and a harmless challenge check. A download click, print preview or generated in-memory key cannot satisfy either check.
- No real custody private key, passphrase or recovered material enters the box, network, browser storage, telemetry, logs or venue backups. Only explicit protected-file and secret-print outputs may contain it. A680's disposable preproduction signer remains its separately approved exception.
- Reserve and consume outside before activation. Failure/abandonment never frees an entry. Local files, signatures and uploaded snapshots establish neither current-master currency nor remote fencing.
- Preserve H2: **do not edit `registerSif`, `restoreFiscal`, alta builders, hash paths, numbering, golden huella or inmutabilidad assertions**. Existing fiscal assertion edits require exact-line owner approval; never change a guard to pass. New append-only table enumeration additions alone have standing scope, but this plan adds no tables and needs none.
- Reuse landed W41s4/6, A680 and C3; no second ledger migration, identity conversion, compatibility layer, automatic rotation, Cloud fetching or new legal claims. Keep ordinary issuance local and external services outside its transaction.
- Future implementation uses signed-off commits, TWO installed Claude run-it reviews, normal hook and required current-head CI. Landing remains the driver's H11/H12 procedure. This bounded writer writes only this file and performs none of those actions.

## Locked implementation choices and file ownership

**Host persistence:** no new SQL schema. Add `packages/provisioning/src/first-setup-state.ts` for a bounded, version-1 `<stateDir>/first-setup.json`: current claim, immutable frozen identity/scope, monotonic revision, hashed owner credential/capability, public imported input and outcome/event history. Keep separately enrolled module trust in `<stateDir>/module-operation-public.json`; uploaded inputs cannot write that file. Neither file is outside continuity evidence. Neither new JSON file contains a certificate, SMTP password, raw admin secret, custody key or owner bearer token; existing credential sealing remains in its current path. Use file fsync, rename and parent-directory fsync; serialize under the existing exclusive venue hold plus an in-process queue, re-reading/checking revision inside it. Do not reuse `setup-operation.lock` as a cross-process fence. CLI obtains the same venue hold before checking claims. Files: 0600, parent 0700, reject symlinks/non-regular files, malformed versions and >1 MiB state / >64 KiB trust before parsing. No fallback to “empty/new” on corruption. Keep abandoned attempt records; capacity refusal requires explicit operator resolution, never pruning consumed history.

**Owner:** claiming binds the normalized future administrator identity and existing `hashPassword`/`hashPin` verifiers, not an authenticated account. Before sending claim, the tab saves a random 32-byte client claim nonce in `sessionStorage`; the server persists only its SHA-256 verifier. The response supplies a separate random 32-byte owner capability, also stored only as a hash on the server. `POST /resume` requires the original client nonce and proof against the frozen administrator credential verifier; it rotates capability and owner generation for the SAME attempt/node/admin/module IDs, invalidating every older capability, grant and request generation. Repeating resume after a lost resume response rotates again without repeating allocation or consumption. Losing both the nonce and credential proof leaves a conflict for explicit incident resolution; it never starts a fresh event automatically.

The client retains only these non-custody credentials and attempt ID in `sessionStorage`, takes an exclusive Web Lock for the attempt, and never saves the wizard's secret draft. Server revision/generation checks govern every mutation across devices. A password reconfirmation plus the current capability is required separately before block use and activation. Derive secrets before the venue transaction, then recheck state inside the common coordinator. Use same-origin checks and credential headers, never URLs or logs. Nonce/credential loss is an explicit recovery limit; after recovering the surviving proof, abandonment still preserves outside consumption.

**Shared exclusion and CLI discovery:** add one `FirstSetupCoordinator.run<T>(body: () => Promise<T>): Promise<T>` per opened venue, covering the complete claim/resume/abandon callbacks and all incompatible legacy operation callbacks. Separate route/store latches and a pre-callback check do not replace it; recheck state after entering this coordinator. Re-entrant internal helpers take the already-held context rather than queueing themselves. Hashing may precede entry, but no side effect may precede the check inside it.

Write and fsync a refusal-only `<venueDir>/first-setup-claim.json` marker (maximum 16 KiB; exact fields `{version:1,attemptId,venueDir,stateDir,status}` with status `claiming|active|complete|abandoned`) BEFORE exposing a claim in the state root. It records version, attempt, canonical venue/state-root bindings and lifecycle status, with no authority or secrets. CLI and every server boot inspect this fixed venue path under the existing venue hold, even when `WAITRON_STATE_DIR` is missing or different. An orphan, corrupt, mismatched-root or unresolved marker refuses competing work; it cannot enrol trust or confer current evidence. Retain it while consumption/publication is uncertain, and retain a terminal marker after verified completion so a lost state file cannot look like a fresh attempt. Pre-consumption abandonment may retire it only after durable history is recorded. Test every marker/state write ordering; never infer that a missing env setting clears a claim.

**Bindings:** host generates attempt/node/administrator UUIDs with cryptographic randomness. Each selected offering module gets its own random event ID and source ID `first-setup:<attempt UUID>`; action is `setup`. `recipientVenueId` is that same stable source ID, an opaque allocation recipient label, not a fabricated existing location row. Store module selection/versions, country/taxpayer, target environment, complete purpose/base set and normalized venue/admin identity in the frozen snapshot. No planned location UUID or change to `applyVenue`'s location creation is needed. A scope edit explicitly abandons/supersedes this event; signed input never silently follows an edit.

**Module boundary:** add types in `packages/module/src/initial-setup.ts` and an optional `ModuleProvisioning.initialSetup` seat; server loops selected modules. Add browser-only `packages/dashboard-modules/src/setup.ts`, importing module browser contributions by explicit subpath, without importing the dashboard registry or server module barrel. `apps/setup` mounts this registry generically. Fiscal module owns all `S`/`W1`/series/signature/custody copy. A non-filing module offers no seat and skips it. Do not grow module-seam allowlists. Add explicit export maps/dependencies only where these subpaths need them; no workspace dependency cycle.

**Crypto choice:** new `waitron-custodian-key` version 1 JSON, native Web Crypto Ed25519 and AES-256-GCM. Password derivation is **PBKDF2-HMAC-SHA-256, exactly 600,000 iterations, random 16-byte salt, 32-byte key**; GCM has a fresh random 12-byte IV and 128-bit tag appended to ciphertext. This deliberately uses browser-native facilities instead of importing Node's existing scrypt server-bundle code. It is a distinct format, with no compatibility reader or change to that code. Treat these as pinned implementation choices requiring interoperability/runtime qualification, not external security or legal claims.

Envelope exact keys: `kind, version, kdf, cipher, scope, fingerprint, ciphertext`. `kdf={name:"PBKDF2",hash:"SHA-256",iterations:600000,salt}`; `cipher={name:"AES-GCM",bits:256,iv,tagBits:128}`. Binary fields use canonical padded standard Base64. AAD (authenticated additional data) is UTF-8 JSON of the ordered array `[kind,version,kdf,cipher,scope,fingerprint]` with the nested field orders just stated; scope is ordered `{custodianId,taxpayerNif,softwareId,environment}`. Decrypted exact payload is `{version:1,pkcs8}`. Limit envelope/paper text to 16 KiB, plaintext to 4 KiB, passphrase to 12–1024 UTF-8 bytes; no trimming/normalization. Reject other parameter values, field sets and lengths before derivation. A wrong passphrase/authentication tag gives one value-free refusal. Never fall back to the original key.

Private material is canonical **48-byte Ed25519 PKCS#8 DER**, prefix `302e020100300506032b657004220420` plus the 32-byte seed. Validate structure and derive/export its 32-byte public `x`; SPKI is prefix `302a300506032b6570032100` plus `x`. Pin Node↔browser import/export/signature/fingerprint interoperability before enabling the tool. Unsupported crypto or offline file-origin capability refuses with instructions to use a supported local browser, never a server crypto fallback.

**Secret paper v1:** one page, “SECRET / SECRETO”, `waitron-custodian-paper`, version, `Ed25519 / PKCS8-DER / HEX`, scope, complete 64-lowercase-hex SPKI fingerprint and `page 1/1`. Encode all 48 private bytes as twelve indexed groups `01`–`12`, each eight uppercase hex characters. Each group carries the first eight uppercase hex characters of SHA-256 over UTF-8 JSON `["waitron.custodian-paper.group",1,scope,fingerprint,index,group]`; final checksum is the full SHA-256 over `["waitron.custodian-paper",1,scope,fingerprint,pkcs8UpperHex]`. Accept ASCII whitespace/group separators only where specified by the renderer; reject duplicate/missing/reordered indices, wrong hex/checksum/length/version/scope/key/fingerprint before challenge signing. Checksums detect transcription corruption; they confer no custody authority. No QR dependency or unencrypted key-file download.

**Public signing:** retain version-1 paper block/consumption bytes and Base64url signatures exactly. Extract pure shape/canonical-byte helpers from `paper-evidence.ts` into `paper-protocol.ts` using `Uint8Array`/UTF-8, leaving Node verification/signing wrappers' signatures/behaviour intact. Browser signs those same bytes using Web Crypto; the existing Node verifier is the acceptance oracle. New initial blocks contain 1–100 entries, bounded by the existing 64 KiB public-file limit as well as the existing protocol's 1,000-entry maximum; shorten/split only before outside reservation, never truncate an issued block. Initial serials are `S000001`–`S999999`, selected from the current master, never automatically assumed free.

## Shared interfaces

New names below are implementation decisions, not claims that these exports already exist. Define them in Task 1 and use them unchanged thereafter.

```ts
// packages/module/src/initial-setup.ts (type-only, browser-safe)
type InitialSetupContext = {
  attemptId: string; binding: OperationBinding; administratorId: string;
  country: string; taxId: string; environment: "production" | "preproduction";
  recipientVenueId: string; bases: readonly {code: string; purpose: string}[];
  request?: unknown; // Host-owned frozen public request for import/confirmation/commit lookup.
};
type InitialSetupImport = { input: unknown; summary: unknown };
interface InitialSetupContribution {
  candidates(context: InitialSetupContext, proposal: unknown): unknown;
  request(context: InitialSetupContext, validatedCandidates: unknown): unknown;
  inspect(context: InitialSetupContext, input: unknown): InitialSetupImport;
  enrol(context: InitialSetupContext, publicKey: unknown, comparison: unknown): unknown;
  confirmation(context: InitialSetupContext, imported: InitialSetupImport,
    statement: unknown): unknown;
  committed(tx: Transaction, context: InitialSetupContext,
    input: unknown): Promise<unknown | null>;
}
// packages/module/src/operation-preparation.ts
interface ModuleOperationHost {
  environment: Readonly<Record<string, string | undefined>>;
  readPublicEvidence(binding: OperationBinding): Promise<
    {trust: unknown; current: unknown} | undefined>;
}
// optional addition on ModuleOperationPreparation:
// configure?(host: ModuleOperationHost): ModuleOperationPreparation
// helper: configureModuleOperations(modules, host): readonly WaitronModule[]
```

`committed` reads existing module allocation/result state; it neither activates nor treats a host marker as a commit. `inspect` checks public shape/signatures/scope without granting current authority. `enrol` and `confirmation` are called only by separate owner-bound host steps. `configure` lets each module choose the bound public reader or its existing explicitly supplied host env configuration. An enrolled-but-invalid source refuses; it never falls back to uploaded trust or another source. No global `process.env` mutation.

The fiscal `request` value has exact shape `{version:1,kind:"first-fiscal-setup",attemptId,binding,operatorId,recipientVenueId,taxpayerNif,softwareId,environment,requiredBases,candidates,candidateDigest}`; map `operatorId=context.administratorId`, `taxpayerNif=context.taxId`, `requiredBases=context.bases`, and supply `softwareId` and the validated complete candidate list/digest in the fiscal module. It contains no credentials. The host persists the exact request and canonical digest; the tool imports these read-only values, and activation compares public input with the stored set rather than trusting an imported validation flag. Offline output `input` is exactly `{allocation,approval}`: existing `FiscalAllocation` with `source:"initial-paper"` and `reservationEvidence:{block,consumption}`, plus existing `RecoveryApproval` with `oldMachineAbsent:true`, `oldMachineOffline:false`, `noParallelRecovery:true` and the frozen event/operator/source/node. Export the custodian public key separately for the independent enrolment step. The host constructs `InitialVenueInput` from its frozen IDs/module bindings and that inspected input; it never accepts replacement IDs from the upload.

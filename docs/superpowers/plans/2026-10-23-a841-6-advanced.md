# A841 slice 6 — Advanced: the colours set by hand: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every implementer is dispatched as `subagent_type: "implementer"`; one that passes about 150 tool calls with its task unfinished stops at a passing (or cleanly red) point, commits, and returns a handover (what is done, what is left, the files, each check's state).

**Goal:** In the Look card's editor, a manager opens a closed **Advanced** section, sees the 22 colours with a Light and a Dark value each, sets any of them by hand with a colour picker or a typed code, puts them back one at a time or all at once, takes a readable shade offered under a row, and gives the dark version a button colour of its own from a link under Brand colour — all as draft changes that the preview shows at once and Save stores.

**Architecture:** The draft (`look-draft.ts`) learns the hand-set values and the code text typed for them; a new element, `dashboard-theme-advanced`, draws the section from the draft and the derived theme the card already works out, and reports every press as one `hand-change` event; the Look card applies those to its draft, records which values a fix replaced (for Undo), runs the form's own check over the typed codes, and adds the dark-screens link and line under Brand colour. Wording lives in `theme-words.ts`. No server change, no migration, no change to `@waitron/ui` or `@waitron/ui-core`.

**Tech Stack:** Lit 3 in `apps/dashboard` (Vitest 4.1.x browser mode, real headless Chromium), `@waitron/ui-core/theme` (slices 1–2), the shared primitives `wt-disclosure` (`packages/ui`), and `wt-input` and `wt-button` (`packages/ui-core/src/components/`, re-exported through `@waitron/ui`), `wt-icon`, Markdown user guides served by `apps/server`.

## Decisions this plan makes (the design left them open)

**D1. A row has two values; "22 rows" is 44 values.** Every theme has a light and a dark version
(design section 7, line 1296: "Per version: each has a light and a dark value"), and Advanced shows
"one row each, with a Light and a Dark value" (line 500). So the section draws 22 rows in
`THEME_COLOURS` order (`packages/ui-core/src/theme/tokens.ts:3-26`, the design's order, line 699),
each with a Light value and a Dark value, each value a colour picker and a code field: 44 pickers
and 44 code fields. Each value is set by hand on its own (line 509-510: "setting the light page leaves
the dark page worked out").

**D2. The field: a dashboard helper, no primitive grows.** The design asks for "the `<input
type="color">` of `colorField`'s custom choice plus a code field from the shared input primitive,
without the 24 swatches" (lines 582-584). `apps/dashboard/src/widgets/color-field.ts` gains an export,
`colourValueField`, drawing that native colour input and the existing `codeInput` (`:289-302`, a
`wt-input` with `hide-label`). It is a template helper like `colorField`, not a `wt-*` primitive, so
the two-tests rule for a new primitive does not apply; its token and axe cases are in Tasks 3 and 7.
A colour input is allowed by `scripts/native-form-fields.test.ts` (`color` is in `NOT_TEXT`, `:20-31`)
only when `type="color"` is written as a literal attribute: the guard reads attributes as text with
bindings blanked (`:75-104`), so a bound `type=${…}` would count as a text field.
The focus-ring defect of backlog "The colour field's custom colour box shows no focus ring" comes from
the `.on` class (`color-field.ts:103-106`); the Advanced picker never carries `.on`, so the base
`:focus-visible` ring (`packages/ui-core/src/base-styles.ts:21-24`: `outline: var(--wt-focus-ring);
outline-offset: var(--wt-focus-offset)`) applies — provided the rendering element's `styles` include
`baseStyles`, which `dashboard-theme-advanced` therefore lists first (as `look-card.ts:110` and
`color-field.test.ts:13`'s host do). "Outline style is not none" cannot tell the focus ring from the
selected ring or the browser's own: the review's probe (`~/waitron-campaign/a841-review/plan6-probe/focus-ring.mjs`,
Chromium 156) read `solid` with the base ring, `solid` with an `.on`-style rule (offset `-2px`) and
`auto` with no rule. So Task 3's case compares the focused picker's `outline-color` and
`outline-offset` with those of a probe element in the same shadow root styled `outline:
var(--wt-focus-ring); outline-offset: var(--wt-focus-offset)` (`--wt-focus-offset` is `2px` and
`--wt-selected-ring-offset` `-2px`, `packages/ui-core/src/tokens/structure.css:119,125`), with an
unfocused picker as the control (`outline-style` `none`).

**D3. Names.** The code field's `name` is the field `theme.invalid` uses, `handSet.light.bg`
(design lines 585, 2148); the picker's is `handSetPicker.light.bg` (the brand field's pair is
`brandColorPicker` / `brandColor`, `look-card.ts:607,616`). The picker's accessible name is
"{name}, {light screens / dark screens}" ("Page, light screens"); the code field's label, hidden as
the brand one is, is "{name}, {light screens / dark screens}, colour code". New text, flagged.
Up to 44 buttons read "Use worked-out colour", and several "Use #…" and "Undo", so each row button's
accessible name also names its value: `aria-label` "{action}: {name}, {screens}" ("Use worked-out
colour: Page, light screens"), set through `wt-button`'s `aria-label`, which it hands to its inner
`<button>` (`packages/ui-core/src/components/wt-button.ts:139,161`). The visible words come first, so
the name still contains the label a speech user says. New text (`appearance.hand_action`), flagged.

**D4. What the draft holds.** `LookDraft` (`apps/dashboard/src/widgets/look-draft.ts:10-13`) gains
`handCodes`: per mode and colour, the text typed into a code field, kept as typed so typing never
moves the caret (CLAUDE.md §3, "Normalising a field while typing preserves the native selection").
A typed text that is a colour (trimmed, `/^#[0-9a-f]{6}$/i`) also sets `choices.handSet` to it in
lower case at once, so the preview follows; any other text leaves `choices` as they were and is the
form's own failed check (an empty field included: Use worked-out colour is the way back). The picker
and a taken fix set `choices.handSet` and clear that value's typed text. `sameDraft` compares
`choices` as today (`look-draft.ts:38-52`) plus the typed texts that are **not** colours, by trimmed
lower-cased text: a valid typed text is already in `handSet`, so typing the stored value in capitals
is no change (D19 of slice 5).

**D5. Setting Main buttons by hand drops that mode's fix from the draft** (design lines 504-508).
`setHand` and `typeHandCode` delete `brandFix[mode]` when the colour is `primary`; Use worked-out
colour on that row does **not** bring the fix back (line 507-508: "goes back to the brand colour as
picked, with its warning and fix offered again"). `withBrand`'s rule that returning to the opened
brand colour brings its opened fix back (`look-draft.ts:54-62`) skips a mode whose `primary` is set
by hand, so the draft never holds a fix the server refuses (`document-check.ts:96`). Probe
`dark-main.mts`: Bar Lucía with dark Main buttons `#5a9c74` paints `#5a9c74` with no warning; with
it put back and no fix, the green paints and warns with the fix `#437e5b` (design section 15,
lines 2393-2397).

**D6. Each value's state words** (design lines 502-511, mock-ups 12, 37). A value set by hand (or
holding typed text) is drawn bold, with a **Set by hand** tag and a **Use worked-out colour** link.
Otherwise it says **Worked out**, except Main buttons, which says **Brand colour**, or **Fixed** while
that mode's brand fix is taken. With "Waitron's" brand colour, Main buttons also says **Brand
colour**: "Waitron's" is the brand colour chosen (my call; the design names no case).

**D7. A warning under a row: which sentence.** The design has two forms, "hard to read on {names}"
when the warned colour is drawn on the others, and "{names} hard to read on it" when they are drawn
on it (line 656-658). The browser tells them apart from `THEME_RULES[mode]`: an `against` key `k`
of a warning on colour `c` is "on" when a rule has `a = c, b = k`, "under" when `a = k, b = c`.
Probe `orientation.mts`: no pair of colours is held both ways in either mode, so each key has one
side. Four colours (five in dark) are drawn both on top and underneath (`surface-lifted`, `track`,
`primary`, `primary-hover`, and dark `primary-disabled`), so one warning can need both forms: probe
`mixed.mts` found light Main buttons pointed at `#787878`, against Main buttons (on) and Text on
main buttons (under), fix `#666666`. Then the row shows both of the design's sentences, one after
the other, and the dialog line both clauses — no new joining words (my call). The same split words
the Save dialog's hand-set lines (design table line 632), replacing slice 5's departure (D8 there).
A warning drawn both ways with **no** fix is reachable too: probe `revise-fixtures.mts` found light
Menus and dialogs (`surface-lifted`) `#000000` with Page `#000000` and Text `#777777` set by hand:
fix `null`, `blockedBy [text]`, on `[bg]`, under `[text-muted, danger]`. Two sentences would each end
"Pick another colour." or repeat the same "while …", so the row says it in one sentence with the
ending once: "Light screens: no shade of this colour can be read on Page and lets Secondary text and
Error colour be read on it while Text is set by hand to #777777." (new strings
`appearance.hand_none_both` and `_both_blocked`, flagged). The Save dialog's no-fix lines stay
slice 5's.

**D8. Names a warning can give that are not among the 22** (new text, flagged). Probe
`against-keys.mts` listed every key a rule pairs with one of the 22: the 15 station fills, the 15
station dots, five zone tab tints, and seven others. Stations fold as the lane A ruling says (design
line 628). The five zone tab tints fold the same way, into "the 5 zone tab colours" / "{n} zone tab
colours" (my call, by analogy: "two fixes"' text warning otherwise lists five tab names in a row).
The seven get plain names: `danger` Error colour, `danger-disabled` Delete buttons, switched off,
`warning` Warning colour, `google-button-line` Google button outline, `highlight` Search highlight,
`table-calm` Floor map tables, `table-calm-edge` Table card edge. A count of one reads "1 station
colour", "1 station dot", "1 zone tab colour". Lists join with ", " and the existing
`appearance.and` before the last, so English has no comma before "and" as the design's example has
none (line 531-532).

**D9. "Fixed from … · Undo" until the editor closes** (design lines 534-536, 1177-1179). The card
keeps, per value, `{ from, to }` for a fix taken under that row or by Fix all (and Fix and save): the
value before and the fixed shade. The line shows while the value still equals `to`; Undo sets the
value back to `from` and forgets the record. Records are forgotten when the editor opens or closes,
on Use Waitron's look and on Reset all. A record is card state, not draft: two drafts with the same
colours are the same draft whatever their Undo history. Fix all records only the values it changed,
and it may change fewer than it warned about: on "two fixes" `fixAll` moves light Text to `#4a4a4a`
and leaves Sunken areas `#bbbbbb`, after which no warning is left (probe `revise-fixtures.mts`), so
only Text gets a fixed line. The **Fix all** line itself shows only while two or more warnings carry a
fix (`look-card.ts:467`; design lines 534-536, "When two or more warnings with a fix show").

**D10. The kept-colours note** (design lines 540-545, table lines 617-618) shows under Brand colour
after the brand colour or the background changes while any colour is set by hand, and stays while
any is, until the editor closes. Corners do not raise it (design line 1195: "Corners touch no
colour"). It names every hand-set colour as the saved card's row does ("Page (light)").

**D11. Advanced is closed whenever the editor opens** (lines 514-517: "Advanced stays closed each
time the editor opens"). Rebuilding is not automatic: `edit()` on another theme while one is open
calls `#begin` (`look-card.ts:271-305,309-322`) and the card renders the same template, so Lit would
keep the same element, and `wt-disclosure`'s `open` is its own state — an Advanced left open (or
forced open by `has-error`, which a cleared error leaves open, `wt-disclosure.ts:211-219`) would stay
open on the next theme. So the card keeps an edit-session number, `#session`, raised in `#begin`, and
renders the section inside `keyed(this.#session, …)` (`lit/directives/keyed.js`, as
`apps/dashboard/src/widgets/product-editor.ts:13,1607` does): each session gets a new element, closed.
It opens itself while one of its values shows an error (`has-error`,
`packages/ui/src/components/wt-disclosure.ts:20-23,214`); a warning does not open it. Its closed line
is `wt-disclosure`'s `summary`: "None set by hand. Waitron works out every colour and text size." or
"{n} set by hand: {names}", then " · " and the count while a value warns, counting hand-set warnings
only (a brand warning sits under Brand colour). The count reuses the Themes card's words,
`countOf("appearance.hard_to_read_count", n)` (`apps/dashboard/src/widgets/count-text.ts:3,21`;
`strings.ts:3107-3108`, Spanish `:6350-6351`: "{count} hard to read" / "1 hard to read").

**D12. Advanced's heading and opening line drop "text" until slice 11** (a departure, flagged as new
text). The design's heading is "Advanced: set colours and text by hand" and its opening line ends "A
text size you set here grows and shrinks with Text size. Waitron still checks both can be read."
(table lines 596, 613). In slice 6 nothing in Advanced sets text, and there is no Text size slider
until slice 10, so those words would promise controls the screen does not have. Slice 6 shows
"Advanced: set colours by hand" and "A colour you set here stays as you set it when you change the
brand colour, background or corners. Waitron still checks it can be read."; slice 11 puts the
design's words back. The closed line keeps the design's words: "Waitron works out every colour and
text size" is true today.

**D13. The dark version's own button colour** (design section 7, lines 1306-1314). While
`handSet.dark.primary` is not set, a link **Pick a different colour for dark screens** sits under
Brand colour's lines; it opens Advanced (one flat list until slice 12) and moves focus to the code
field of Main buttons' Dark value (section 16 item 6: "moves focus to the Dark value of its Main
buttons row"). The code field, not the picker: it takes a typed code from the keyboard. Once set, the
link gives way to "Buttons on dark screens: {colour}, set by hand · Use the brand colour", drawn with
the existing Undo line's markup so a wrapped link drops the "·" (`look-card.ts:147-168`); **Use the
brand colour** is Use worked-out colour on that value. The design gives the light version no such
line (lines 1312-1314). The link and **Use the brand colour** are disabled while a save is under way,
as the brand fix's Undo is (`look-card.ts:436`).

**D14. The saved card's Brand colour row** names each version's button colour (design lines
470-473, 1338-1339): after the brand value, for each mode in light-then-dark order, " · {light
screens / dark screens} {chip} {colour}, set by hand" when that mode's Main buttons is set by hand,
else the taken fix's shade as today (`look-card.ts:86-91`). With "Waitron's" it is "Waitron's" plus
those suffixes. The light form mirrors the design's dark one (flagged as derived text, as slice 5's
D16 did). **Two chips, not three**: the design gives the row as "Custom · #1e5b3a · dark screens
#417c59" for a fix and "· dark screens #5fa77a, set by hand" for the dark version's own colour (lines
470-473), and says "Brand colour (a swatch and the value)" (line 466); it never draws a third chip.
`brandRow` draws one chip for the brand and one per suffix (`look-card.ts:78-93`), and a mode cannot
hold both a hand-set Main buttons and its fix (`document-check.ts:96`; `normaliseChoices` drops the
fix, `theme.ts:75`), so Bar Lucía with its own dark colour draws two: `#1e5b3a` and `#5fa77a`.

**D15. A server refusal of a hand-set value lands under that value.** `theme.invalid` whose `field`
is `handSet.{light|dark}.{one of the 22}` shows "Enter a colour as # and six digits or letters a–f."
under that code field and "Correct the highlighted fields to continue." at the bottom, Save still
enabled (CLAUDE.md §3: "puts a refusal beside a field by what the error CARRIES"); any other field
keeps slice 5's bottom message (`look-card.ts:519-527`). The editor sends only checked, normalised
values (D4), so only a script-made race reaches it. The error clears on the next hand-set change
(Reset all included, being one) and on **Use Waitron's look**, which puts every value back to worked
out, so no refusal may stay under a value it no longer describes.

**D16. Server: no change.** Probe `server-accepts.mts` ran `readThemeDocument` over all 44 values set
in capitals beside a fix in each mode: the raw document is refused `brandFix.light`
`fix_with_hand_set` (what a document the draft never holds would get), and the normalised one, as the
card sends it, is accepted, as is `fixAll`'s output for it and a Waitron's brand with only a dark
Main buttons.

**D17. A picker drag sends at most one change per animation frame** (review M5). A drag fires an
`input` per pointer move; each change re-derives the theme. In a heavily hand-set theme a derive is
far over a frame: the review's `drag-worst.mts` (Bar Lucía with the first 11 colours of each mode set
to clashing greys, the memo shared as the dashboard shares it) read 35.6, 39.9 and 45.8 ms median per
step, 66.7 ms max, against 16 ms for a frame. So `dashboard-theme-advanced` keeps the latest picked
colour and sends one `pick` from a `requestAnimationFrame` callback; a further `input` in the same
frame replaces the colour without asking for another frame. Any other action (typing, Use worked-out
colour, a fix, Undo, Reset all) first sends a waiting `pick` at once, so actions arrive in the order
they were made; `disconnectedCallback` cancels a waiting frame. Code fields stay unthrottled (a
half-typed code derives nothing). This bounds the work to one derive per frame and always shows the
latest colour; it does not make a 40 ms derive fit a frame, so a drag in that theme still repaints at
about 20-25 times a second — Task 9 records it.

## Performance: what runs per keystroke

- A key in a code field sends one `wt-change` (`packages/ui-core/src/components/wt-input.ts:75-80`).
  The card makes a new draft; `choices` change only when the text becomes a colour, and the card
  derives only when `choices` change (`look-card.ts:265-269`). So a half-typed code derives nothing,
  and a completed one derives once. Picker `input` events derive at most once per animation frame
  (D17), always on the latest colour (design line 520: every change repaints the preview at once).
  `canFixAll` runs only while the Save dialog is open
  (`look-card.ts:572`) and `fixAll` only on a press.
- Measured (`timing-cold.mts`, each call on an empty cache — the derivation remembers results across
  calls, `packages/ui-core/src/theme/derive.ts:68-76`, so `timing.mts`'s repeated calls read 0.1 ms):
  Bar Lucía 0.5 ms; cream page 0.4 ms; cream + sage, which searches a fix, 3.9 ms median, 5.5 ms
  max; pure blue cards 2.8 ms; dark own colour 0.2 ms; eleven values per mode set to clashing greys,
  19 warnings, 79 ms median and 102 ms max. A picker drag through 40 new values with the cache warm
  costs 0.3-1.1 ms median and under 3 ms max per value in the easy themes; in the eleven-greys theme
  the review's `drag-worst.mts` read 35.6-45.8 ms median and 66.7 ms max per step. Slice 1 measured
  8-9 ms for the review palette.
- So the code fields are not throttled (a key derives nothing until the code is whole), and the
  picker is coalesced to one change per frame (D17): ordinary edits cost a few milliseconds, and in
  the worst theme a drag repaints at frame boundaries without queueing a derive per pointer move. The
  render redraws 44 values per change; Task 9's visual check records, with Advanced open, the time
  from one picker `input` to the preview's repaint in Bar Lucía and a 40-step drag in the
  eleven-greys theme, as readings for the PR, not a gate.

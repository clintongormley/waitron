## Data and API contract

Define browser-safe types in new `packages/workforce/src/attendance-contract.ts`. Export it as `@waitron/workforce/attendance-contract`; use erased type imports, never the server barrel in browser code. The registry re-exports these types for dashboard consumers. Existing `ClockEntryKind`, `TimeRecord`, `AttendanceDay`, `Origin` and `Period` retain their meanings.

- `AttendanceChange = { target: {entryId:string} | {missingKind:ClockEntryKind}; at:string; offsetMinutes:number }`. A command contains one change, or exactly two missing changes (`in,out` or `break_start,break_end`) in chronological order. No mixed targets, duplicate kinds or arbitrary multi-retime batch. A missing whole shift is submitted/decided atomically after validating its complete final sequence; do not validate either half as a transient standalone shift.
- `AttendanceCommandPayload = {action:"confirm"; questionId:string} | {action:"request"; questionId:string|null; locationId:string; changes:AttendanceChange[]; reason:string} | {action:"propose"; personId:string; locationId:string; changes:AttendanceChange[]; reason:string} | {action:"approve"|"decline"|"accept"; itemId:string} | {action:"disagree"; itemId:string; reason:string}`; `AttendanceCommand = {commandId:string; expectedRevision:string} & AttendanceCommandPayload`. `commandId` is a client UUID retained through reconciliation. Till cannot call `propose`; dashboard cannot call worker `confirm/request/accept/disagree` through the manager adapter. Extra actor/node/origin/recorded-time fields are refused.
- `CorrectionItem = {id:string; requestEntryIds:string[]; personId:string; locationId:string; direction:"worker_request"|"manager_proposal"; status:"waiting-manager"|"waiting-worker"|"approved"|"declined"|"disputed"|"overtaken"; readyToApply:boolean; responseEntryIds:string[]; changes:AttendanceChange[]; reason:string; requestedByPersonId:string; selfApproved:boolean; history:TimeEntryRecord[]}`. Group new paired requests by command receipt; older library-created requests without a receipt remain singleton items. Derive terminal states from linked responses and effective targets, never `requested` alone. `readyToApply` concerns sequence validity, not caller authority; only ready items offer approve/accept. A blocked item can still be declined/disagreed by an eligible actor. If existing individual library calls partially answered a bundle, project its terminal history and remaining requests as singleton items, not another all-or-nothing answer to the old group. Keep nonactionable history visible.
- `AttendancePrompt = {id:string; questionId:string|null; itemId:string|null; personId:string; locationId:string; locationName:string; businessDay:string|null; day:AttendanceDay|null; kind:"automatic-out"|"missing-times"|"proposal"; automaticEntryId:string|null; missingKinds:ClockEntryKind[]; timeZone:string; history:TimeEntryRecord[]}`. A proposal points to its item; a question uses its canonical id and saved bounds. `history` carries the original automatic/target events, every request/response in the relevant correction lineage and the effective replacement, with exact stored event instants/offsets and attribution. Items carry the same scoped `history`; neither screen invents a calendar date from the business-day label. Prompt `timeZone` is the current named location zone for new edits; reopening an original time retains its stored offset, as below. Resolve originals and responses against complete subject history before selecting these rows; do not omit a linked original because its calendar date differs from the question business day.
- `AttendanceInbox = {personId:string; revision:string; prompts:AttendancePrompt[]; items:CorrectionItem[]; locations:{id:string;name:string;timeZone:string}[]}`. Own inbox spans the person's historical locations; no other worker's history. `AttendanceDayView = {personId:string; locationId:string; date:string; timeZone:string; revision:string; record:TimeRecord; items:CorrectionItem[]}` uses **calendar work date**, independently of a question's **business day**. A selected date calls `backend.timeRecord` with `[date,nextDate)` after complete subject lookup. Inbox and item history are independent of this selected-day response; sign-in renders them directly without a guessed date read. `AttendanceCommandResult = {commandId:string; entryIds:string[]; replayed:boolean}`; do a separate refresh after success.
- `AttendanceLookups = {viewer:{personId:string;canSelfApprove:boolean}; locations:{id:string;name:string;timeZone:string}[]; people:{personId:string;displayName:string}[]}`; manager-only minimal names, including people/locations needed by retained history, without credentials/contact details. The adapter supplies `viewer` from current authenticated authority; it is presentation guidance, never an authorization input. `AttendanceManagerQueue = {locationId:string; items:CorrectionItem[]}` includes outstanding requests/proposals and disputes, with response links; a date selector must not hide old outstanding work.

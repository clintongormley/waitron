# A461 Product Search Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** You can find matching products and categories in flat dashboard search results, find sections alongside products on the till, and gather a selection across searches before moving it.

**Architecture:** Add an opt-in flat search presentation to `wt-data-table`, leaving its ordinary tree and flat-table defaults intact. Products and Menu Structure supply ancestor paths and keep domain-eligible selections even when search or filters hide them. Till search combines section and product candidates through the existing shared matcher, using the existing menu-selection event to open a section from another served menu.

**Tech Stack:** TypeScript, Lit, `@waitron/shared` text search, Vitest browser mode with real Playwright Chromium, existing dashboard catalogue APIs.

**Spec:** The complete A461 section in `docs/backlog/catalogue.md`, quoted below, and its summary in `docs/backlog.md`. A454's `docs/superpowers/specs/2026-10-09-search-everywhere-design.md` and `docs/superpowers/plans/2026-10-09-search-everywhere.md` supply the matching rule. A461 supersedes their ancestor-tree presentation only on Products and Menu Structure. The scope is owner-approved; do not insert another design approval gate.

**Planning boundary:** This document is the only output of the plan-writing session. No implementation, tests, commits, pushes, development servers or campaign-file changes are authorized in that session. All checkboxes below describe future implementation work.

## Review Focus

1. **A matching parent and matching descendant overlap:** an expanded Coffee category must show Iced coffee once, with its real key, and not leave a second selected copy at the top level. Task 1 owns the table test; Tasks 3–4 own screen fixtures.
2. **Whitespace, punctuation and a completed word:** `"   "` restores the tree, `"&"` gives no matches, and `"gin "` excludes Ginger tea. Search-session expansion must not replace pre-search expansion. Task 1 owns tests; Tasks 3 and 7 pin matching at the consumers.
3. **A hidden selected row changes live:** renaming or changing availability keeps its tick; deletion or loss of ownership removes it from selection and open operation snapshots. Task 5 owns Products/Menus tests; Task 2 owns selection emission tests.
4. **Several selected members share a section or destination:** drag must carry hidden selected members, suppress descendants carried by a selected section, deduplicate repeated placements, and refuse a cyclic, duplicate or stale destination without silently moving only one row. Task 6 owns real pointer probes and integration assertions.
5. **A section exists only before the diet lens, or in another menu:** show a disabled matching section only if unfiltered orderable offers populate it; tapping an enabled other-menu section clears search, selects that menu and opens the right copy without adding a product. Tasks 7–8 own ranking, locale, diet, inclusion and parent-event tests.

## Executable defaults

1. **Search mode and ordering.** Introduce `flatTreeSearch: boolean = false`. It applies only with `rowParent` and `textSearch(rawQuery) !== undefined`; if both search flags are set, it takes precedence. Switch only Products and Menu Structure from `searchOpensPath` to this flag. Keep `searchOpensPath` behavior and tests for default consumers. Flat search roots are actual own matches, without the synthetic All products/menu root or unmatched ancestors. Rank all roots by their own match first, then existing `rowGroup`, then chosen column sort, then incoming order. This puts closeness ahead of the Products category/product grouping only in the new mode. Menu Structure has no heading sort; tied roots retain its current menu traversal order.
2. **Expansion during search.** Every branch starts collapsed for a new nonblank raw query, even if expanded before search. A matching category/section/product with children keeps its disclosure control. Opening it shows its immediate filter-passing contents, including nonmatches; deeper branches start collapsed and can be opened. Intermediate rows needed to reach a filter-passing descendant remain as muted context beneath the explicitly opened branch. A matching descendant rendered beneath an opened branch is suppressed as a separate root, so each key appears once. Closing the branch restores its descendant matches as flat roots. No unmatched ancestor is promoted to a root. Product variants appear only after their product or containing branch is explicitly opened, in the existing variant order.
3. **Tree restoration.** Keep search expansion in a separate transient key set. Query changes reset that set; column-filter changes retain it for still-existing keys. Toggle, Expand all/Collapse all, `isExpanded`, `setExpanded` and `revealRow` use the effective session state while flat search is active. They must not write `:expanded` storage or the ordinary collapsed set. Clearing to blank/whitespace restores the original tree, including remembered expansion. Search expansion must not change Products' category URL or Menu Structure's current path: suppress those consumers' normal expansion-to-navigation handlers and the Structure collapse observer during active flat search. A write or an explicit navigation retains its existing navigation semantics; a search-only toggle does not navigate.
4. **Paths and wrapping.** A flat root's category/section path contains ancestors only, in order, joined by ` › `. Products use the primary category, not every assigned category. Thus `Iced coffee  Drinks › Coffee`, `Coffee cake  Desserts`, and category `Coffee  Drinks`; an uncategorised product/top-level category has no path. Menu roots use section/include ancestors within the menu, without the menu's synthetic root or the current row's name. Retain separate rows for distinct member paths. Render name and muted path in one wrapping inline flow with a token gap, not a forced column or always a second line. If they fit at 1280 they share a baseline; at 390 long text wraps inside the room before Actions, including unbroken text. Rows revealed under an expanded search root use ordinary indented cells, without an additional flat-root path.
5. **Ticks and filters.** On Products and Menu Structure only, raw search edits, clearing, column-filter edits and filter Clear all keep domain-eligible ticks. Hidden ticks stay in the existing selected count and in bulk Move/Remove snapshots. Leaving select mode/Done, switching menu or departing the screen, successful bulk moves/removal and successful dragging clear affected ticks as their operation requires. Products' drag clears moved keys; its existing dialog completion behavior remains. Failed/cancelled moves do not lose ticks. Live disappearance/loss of ownership trims keys; a renamed or newly filtered-out row does not. Root, variants and read-only included-menu rows remain ineligible. Units and every other table keep their existing selection behavior.
6. **Select all.** Add only checkbox-eligible rows actually rendered now, including explicitly expanded contents. Do not add collapsed descendants, filtered-out rows or invisible ticks. If every visible eligible row is already selected, deselect only those visible keys; preserve hidden keys. The header's checked/indeterminate state concerns visible eligible rows; the selected count concerns the entire retained set. When there are no visible eligible rows, select-all changes nothing.
7. **Dragging.** Products may still drag during search. Dragging a ticked row takes the full retained selection, including hidden keys; an unticked row takes itself. Menus keeps drag disabled while any nonblank search is typed, punctuation included. Enable selected-set dragging after clearing through select mode as well as existing reorder mode. Existing unselected single-row and keyboard reorders remain. New selected-set pointer moves use one existing `moveSectionMembersInto` request in tree order, deduplicated through the same domain rules as Move; never issue one request per tick. A same-list selected-set drop is also a batch move with its insertion point computed after removing the moving set.
8. **Till names, ranking and ties.** Search products by `productName(product)`, as today, and sections by the actual `#sectionName` label, with distinct test labels. Product variants keep today's product-tile behavior. Each menu's result block has one mixed grid, ordered only by `compareSearchRanks`; ties retain deterministic candidate traversal order, with no type priority. Build candidates in displayed document depth-first order using `shownMembers` and `tilePaths`, keeping product deduplication per menu and section-copy paths. Search an included menu shown directly on its visible children, not its invisible wrapper. Do not append all sections before all products. A section whose name alone matches must not pull in unrelated product tiles.
9. **Till diet, menus and tapping.** Filtered products remain absent; sold-out offered products and populated sections retain existing tile behavior. Search sections in an unfiltered index whose offers already exclude `not_sold_separately`; omit genuinely empty/unserved sections. If the matching section's filtered path has no offers, render the existing disabled grey section tile. Do this for all served orderable menus, preserving current-menu block first, `orderableMenus` order for others, and all existing no-results messages. Other-menu groups containing only a matching disabled section still appear. Use the currently selected menu's result-grid display settings for all blocks, as `#results` does today. Tap an enabled section to clear the query and open its stored `SectionStep[]`; an other-menu tap first sends the existing bubbling/composed `menu-selected` event `{ id }`, then opens after that menu's input arrives. Do not add to the basket or rewrite its menu offers. Disabled taps send no event and leave the search in place.
10. **A454 tie wording.** Its precise-rule paragraph says caller order, but its table task and current design-system text specify column sort for ties. `wt-data-table.ts:#sortByColumn` uses column sort. Preserve that shipped rule for dashboard ties (after the new mode's rank-first order), and stable candidate order for the till. The owner confirmed table-sort ties in Lane D’s A461 queue on 2026-10-10: “Keep A454's ranking rules (ties follow the table's sort, owner 2026-10-10).” The implementation keeps that ordering; retire the matching open question from the current backlog in Task 9 and add a dated decision pointer to the historical A454 spec rather than rewriting it.

## Task 2: Keep eligible hidden ticks without changing table defaults (target 25 calls)

**Files:** Modify `packages/ui/src/components/wt-data-table.ts`; test `packages/ui/src/components/wt-data-table.test.ts`.

**Interfaces:** Add optional `rowSelectionAllowed?: (row: Row) => boolean`. When supplied, it defines domain eligibility for retained selected keys and rejects absent keys; `rowSelectable` still decides which visible rows offer a checkbox.

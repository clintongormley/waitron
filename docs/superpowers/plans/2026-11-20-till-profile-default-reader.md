# Use a profile’s default card reader at Pay

The 20 November Lane F report describes a till on **Use default** showing **None** even though its profile names a reader. When an administrator saves a free default for one till using the profile default, that till should offer it at **Pay**. When the administrator changes the default, the signed-in till should pick up the replacement without reloading.

`setProfileReaderList` releases holds that no longer match but never assigns a new one. `readReaderRole` only resolves a reader the device holds, and both the till’s start read and its equipment read use that rule. The current payments tests show the difference between saving a profile and explicitly pressing **Use default**.

Expect the current code to return no resolved reader. Keep the existing two-device case, where saving cannot choose which device gets a free reader. Check that saving cannot take a held reader or one busy with another device’s payment.
- [ ] In `packages/payments/src/device-readers.ts`, extend the existing profile-save transaction after it settles obsolete choices and holds. Give the default to the active device that held the previous default and is still on **Use default**, or to the sole active device on **Use default**. If several such devices have no previous default holder, leave the reader free for the existing choice flow. Reuse the payment-in-progress check and the hold update that requires a free reader. A new hold requires a reader that is enabled and paired. Keep explicit choices that the profile still lists and keep payment admission as it is.

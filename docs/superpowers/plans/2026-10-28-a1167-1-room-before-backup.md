# A1167 slice 1: each backup run makes room for itself, or is refused before it copies anything — implementation plan

> **How this plan runs:** subagent-driven (superpowers:subagent-driven-development). Every task goes to an implementer dispatched as `subagent_type: "implementer"` (medium effort), test-first, committing each task with `git commit -s`. Each task is sized well under 100 tool calls; an implementer that passes about 150 calls with the task unfinished stops at a passing or cleanly red point, commits, and returns a handover (done, left, files, each check's state), and a fresh implementer continues from it.
>
> **Per-task reviews (FULL path).** After each code task (1–15), a fresh-context reviewer (default model, high effort, no `model` field) reviews that task's commits against this plan and the spec. A task that edits the same files starts only after that review's findings are folded; a task on other files may start meanwhile. Reviewers put any mutation or probe in a throwaway copy (`git worktree add --detach "$(mktemp -d)/wt" <task's commit>`, `pnpm install` in it, removed after), never in this worktree. Tasks 0 (preflight), 16 (guides and docs), 17 (the look) and 18 (final checks) take no per-task reviewer; `/finish-branch` reads them.
>
> **Order.** 0 → {1, 2, 5, 6} → 3 (after 2) → 4 (after 3) → 7 (after 6) → 8 (after 7) → 9 → 10 → 11; 12 (after 3, 5, 8) → 13; 14 (after 8); 15 (after 1, 12, 14); 16 (after 8–15); 17 (after 13, 14); 18 last.

**Goal.** Before each backup run copies anything, it works out the room it needs on the disk that holds its working folder: twice the database file's size (the working copy and its encrypted file, as today), plus the database file's size once more for each backup folder on that disk (the gap the probe measured). If the free space plus every old backup the box may delete still falls short of that plus 256 MiB, it deletes nothing and is refused, with the sizes. Otherwise it deletes its oldest deletable backups, one at a time, until it has the need plus 2 GiB (or, when that cannot be reached, the need plus 256 MiB). Once the encrypted file exists, a second check does the same with its real size before any destination is tried. When the box deletes backups by itself it records an alert, `backup.archives_deleted`, shown on the bell and emailed to managers and administrators; a refused run is also emailed.

## Deviations from the design (each goes in the PR description)

1. **Q1 B and Q2 A (owner).** No administrator-only permission and no per-alert recipients (design §4, Q1's option A cost, gone). The deletion alert is claimed with `system.manage`; both emails go to `readManagerEmailRecipients`. The email duty learns to read the refusal from the backup run's memory (Task 13).
2. **The words are the owner's (design §5 replaced).** No environment-managed variant (design §5's fourth bullet dropped).
3. **The `backup` source is added for `incidents` only, so one table is rebuilt in one migration set, not five tables in two.** Read: the design's list is right. The tables whose column takes every source are `incidents` (`packages/db/src/schema/incidents.ts:29,79`), `working_orders` (`orders.ts:69,126`), `order_amendments` (`order-amendments.ts:39,70`) and `unpaid_departures` (`unpaid-departures.ts:28,52`) in core's set (`packages/db/drizzle`), and `time_entries` (`packages/workforce/src/schema/time-entries.ts:60,226`) in workforce's set. But rebuilding `working_orders` meets every child that points at it (6 cascade, 7 restrict and 4 no-action foreign keys across core, venue-service, payments, adjustments and bookings, read in the schema files), and the last such change (#1174, `b4777ae00`, core 0094–0097) had to drop and recreate 15 behavioural triggers and needed a venue reset, because the upgrade walk refused existing rows at core/0095 and workforce/0003 (`scripts/migration-upgrade.test.ts:447-449, 502`). A backup job writes only incidents. So `@waitron/shared` gains `INCIDENT_SOURCES` (every source plus `backup`), `IncidentOrigin` and `readIncidentOrigin`; only `incidents` takes the wider column. This mirrors `SALE_SOURCES` (`packages/shared/src/origin.ts:22-27`), a per-table source list that already exists. `incidents` has no foreign keys pointing at it (read) and no migration trigger names it (run: of the 46 files in `packages/*/drizzle/*.sql` holding a `CREATE TRIGGER`, `/usr/bin/grep -l -i incidents` matched none; the same search for `working_orders` matched, as a control). Triggers installed by code rather than migrations are checked by Task 3's guard runs. The precedent for rebuilding `incidents` alone is core 0078/0079.
4. **The claim lives in core's `CORE_ALERTS` (`packages/db/src/alerts.ts:4-9`), not in a claim the server adds.** Read: every claim comes from a module (`apps/server/src/modules.ts:52-54`) and `scripts/alert-codes.test.ts:121` reads only `ALL_MODULES`; a server-only claim would fail that guard (design §4 says to teach it). A `backup.` claim on the core module (which every box has, `packages/composition/src/modules.ts:151`) needs no guard change. Server-written codes claimed by a module already exist (`payment.` codes written by `apps/server/src/bill-payments-loop.ts`).
5. **When the current installation began comes from a new optional fiscal seat member, `installationStartedAt(tx, nodeId)`.** The Veri*Factu module answers the live `registro_sif` row's `registrado_en` (`currentSif`, `packages/fiscal-verifactu/src/registro-sif.ts:160-179`), not the minute decoded from the installation name: every activation writes `registrado_en` (`allocation.ts:430-442`, read), only hour-source names decode (`allocation-envelope.ts:199-201`), and `registrado_en` is the later of the two, so it can only keep more archives. The no-regime module does not implement it, so on such a box nothing is ever deleted (A1127 §4's "offers nothing"); nothing durable marks when its database began (`tenants.created_at`, `nodes.created_at` and `deployment.stamped_at` travel inside the archive, read). No A1127 slice 1 or 2 code reads an installation start or lists archives (read: no match in `spare-space.ts`, `first-setup-entry.ts`, `node-entry.ts`).
6. **"The box's disk" is the disk holding the run's working folder (`<state>/backup-staging`), where the run reads free space today (`backup-sweep.ts:108-116`).** A backup folder counts as on it when its nearest existing folder (after `realpath`) has the same device number, as `disk-usage.ts:87-100` decides for the venue folder. Design §1 says the venue folder's disk; on a box the venue, state and backups volumes share one disk (design "What happens today"), and the working folder's disk is the one the run fills.
7. **The room step runs where today's first check runs** (`backup-sweep.ts:157-158`, after the manifest and the state files are collected, which copy nothing), not before the manifest (design §2). The folder it measures is created just before (`:156`); `statfs` on a missing folder answers nothing and the check would be skipped (`free-bytes.ts:6-15`).
8. **The deletion log is `backup.archive_deleted` with `destination`, `key`, `bytes` and `reason: "backup_room"`**, not a `name` field: `name` is one of `scripts/personal-log-params.test.ts`'s person words (`:170-171`).

15. **The real-disk cases are a new file with its own small filesystem** (`WAITRON_FULL_DISK_DIR_BACKUP_ROOM`, a fourth CI tmpfs), as testing-guide.md requires of each file that fills one (`docs/developers/testing-guide.md:1242-1330`).

# Trading window implementation plan

The owner asked on 20 November for separate end and start times so staff have a window to close tables, run reports and take backups. With a 03:00 end and a 09:00 start, the owner put a 04:00 sale in the day starting at 09:00. The finish line is two editable times in Venue details, with that sale in the new day's totals and automatic closing and archives following the end.

**1. Save and read the two times.** In the current Business day start editor, preview and save both venue-local times with the existing revision check. Keep the dated start rows. Save dated end changes in the existing `business_day` settings document and preserve them on other writes to that document. Default the end to the saved start until a separate end takes effect, including for a fresh venue. No SQL migration. Give a change the first opening date for which both old and proposed boundaries are still ahead. Reuse the existing history refusal and local-time conversion. Reject a change that would reorder days. The end before each opening is the last configured end at or before that opening, on the preceding civil date when the end is later on the clock. Keep the existing start-based clock for opening hours, special days, seasons, staffing and attendance. Implement in `packages/shared/src/business-day-clock.ts`, `packages/db/src/{venue,venue-settings}.ts`, the existing settings writers, server `business-day-{start,changeover}.ts` and venue-details route/types, and dashboard `business-day-start-editor.ts`, its API types and English and Spanish wording. Update the opening-hours guides.

**2. Route the trading readers.** Use the interval between successive ends for sales and takings reports, their date defaults and the till's sale and bill lookups. Label it by the opening date inside it. Use the latest elapsed end for the existing table-close pass in `apps/server/src/close-of-day.ts`. Keep its existing bill eligibility, clock and primary checks. Anchor automatic archives in `backup-schedule.ts` to that end, with the existing delay, jitter and actual closing date's weekday. Keep explicit backup schedules. Pass the new bounds through `packages/reporting/src/{business-day,types}.ts`, `apps/server/src/report-api.ts` and the trading callers that construct their own date windows. Keep tax periods, invoice operation dates and the fiscal issue path as they are. Reconcile the close job with lane L's #3398.

**Report decision for clearance.** The dashboard already computes its daily report on demand, and the frozen report writer requires a person and physical cash counts. Use the new cutoff so staff can run the closed day's report during the window. Confirm whether the queue's “reports … run at the END time” calls for automatic generation too, and whether a ticket issued by the closing pass must count in the day it closes when its actual issue time is later than the cutoff. This plan applies existing event timestamps to the report windows.

**Tests first.** In `business-day-clock.test.ts`, pin 02:59, 03:00 and 04:00, a 22:00 end ahead of the following 09:00 opening, and a daylight-saving transition. In `business-day-start.test.ts`, pin the saved default, a dated change and old totals' bounds. In `business-day-start-editor.test.ts`, check the two-field preview and saved payload. In `close-of-day.test.ts` show eligible bills close at 03:00 while a bill opened in the gap survives until the next end. In `report-api.reports.test.ts` put real sales either side of the end. In `backup-schedule.test.ts` show auto follows the end and an explicit time still fires as set. Run these files and update the backlog with the result.

**Estimate** about 420 production and 300 test lines, one pull request for the two times and their consumers.

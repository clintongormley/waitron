# A1308 dv17: drawer opens are recorded in `activity_log` — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended)
> or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`)
> syntax for tracking.

**Goal:** `drawer_opens` moves into the shared, append-only `activity_log` as kind `drawer.opened`,
naming the drawer's kick job as its subject, so the audit can show whether the drawer was actually
kicked. The five places that record an open queue the kick first and record the open second. The
personal-data download reads the openings through `readActivityForPerson`, which learns slice 2's
`personFields` for the one person id kept inside `data` (`authorizedBy`). Measurement M7 checks that
read's cost.

**Why after the refunds slice:** product logic never decides from `activity_log` (README §3 R2), and
the one decision made from drawer history today is "a refund opens the drawer at most once"
(`apps/server/src/receipt-print.ts:636-640`). The refunds slice (os12/os13) adds the set-once
`refunds.drawer_opened_at` under its merged guard trigger and moves that check onto it
(`2026-11-08-a1308-os12-refunds.md`, "`drawer_opened_at`: which slice adds it"). Doing it there, not
here, means the refund guard trigger (a money table, owner-landed) is changed once, in the slice that
rewrites it; this slice then needs no money-table change and the lane lands it. Both slices are lane
1's, so the order costs no cross-lane wait. (Alternative rejected: add the column to today's
`tender_refunds` and `bill_payment_refunds` here and carry it into the merge: two guard-trigger edits
on money tables and an owner landing in this area.)

## M7: the measurement (Task 1, before the reader changes)

**What runs, twice on the same machine** (README U11: "Pass and fail compare before and after on the
same machine"): **before**, today's read (`select … from drawer_opens where person_id = ? or
authorized_by = ?`, `apps/server/src/personal-data-actions.ts:171-186`) over 270,000 `drawer_opens`
rows; **after**, the read as this slice writes it
(`readActivityForPerson(db, person, { kinds: ["drawer.opened"] })` inside `db.withWriteLock`, the
turn `apps/server/src/personal-data-actions.ts:171` takes), timed over a venue holding five years of
`drawer.opened` rows (270,000, about 150 a day) among 4.15 million other `activity_log` rows, for a
person who is operator on 1% and authoriser on 0.1% of them. Data: slice 0's year-of-trading bench
venue if its second pull request has landed, with the rows added by a throwaway script in the
session scratchpad (never committed); otherwise a scratch venue filled the same way. **Where:** the
reference micro PC (README U11, "The bench"); if none is reachable, the build machine, with the
machine named in the result.

**Failing result** (`tables-devices.md` §8 M7: "a wait a person at the till would notice"): the
after read's median is more than one and a half times the before read's **and** more than 50 ms
slower than it, on the same machine (five runs each). Absolute figures are recorded but do not decide
(the design's stand-in took about 64 ms on a developer Mac; a fixed limit near that figure would
decide on noise). **The design's fallback:** `activity_log` gains a second person
column with an index and a key to `persons`, which changes README §3; the builder stops and the
watcher takes it to the owner before anything is built (rules §5.4).

## What it builds

- **The kind** (`packages/db/src/activity-kinds.ts`, slice 2's registry):

  ```ts
  /** A cash drawer was opened. Subject: the kick job. `person_id`: the operator; `device_id`: the
   *  till, null on a calibration from the dashboard. `authorizedBy` is a person id (personFields). */
  readonly "drawer.opened":
    | { readonly reason: "calibration"; readonly authorizedBy: string }
    | { readonly reason: "manual"; readonly authorizedBy: string | null; readonly viaOverride: boolean }
    | { readonly reason: "cash_sale"; readonly saleId: string }
    | { readonly reason: "card_slip"; readonly saleId: string } | { readonly reason: "card_slip"; readonly billPaymentId: string }
    | { readonly reason: "bill_payment"; readonly billPaymentId: string }
    | { readonly reason: "bill_refund"; readonly billPaymentId: string; readonly refundId: string; readonly authorizedBy: string; readonly viaOverride: boolean }
    | { readonly reason: "tender_refund"; readonly saleId: string; readonly refundId: string; readonly authorizedBy: string; readonly viaOverride: boolean };
  ```

  The seven reasons and their fields are what `drawer_opens_target_ck` required
  (`packages/db/src/schema/drawer-opens.ts:57-70`); "One typed function writes every `drawer.opened`
  row, with the seven reasons as a type whose fields match" (§5). Registry entry:
  `{ subject: "print_job", personFields: ["authorizedBy"] }`. (`refundId` names the merged `refunds`
  row; the bill path passes its refund id now that os12 gives it one.)
- **`personFields`** (slice 2 fixed the name; this slice builds it): `ActivityKindRule` gains
  `readonly personFields?: readonly string[]`, and `readActivityForPerson` also returns entries of
  such kinds where `json_extract(data, '$.<field>') = ?`, through the `(kind, at)` index.
- **One writer:** `recordDrawerOpen(tx, open: { printJobId: string; personId: string; deviceId:
  string | null; data: ActivityKindData["drawer.opened"] })` in `apps/server/src/drawer-opens.ts`
  (new, beside `receipt-print.ts` wherever the package move put it), calling `recordActivity` with
  `kind: "drawer.opened"`, `subjectId: printJobId`.
- **The five sites**, each now `const { jobId } = await enqueuePrintJob(…, "drawer")` first, then
  `recordDrawerOpen` (§3: "The four `receipt-print.ts` sites insert the open before they queue the
  job, so they swap that order"): `enqueueManualDrawerOpen` (`receipt-print.ts:407`/`:415`),
  `enqueueBillDrawer` (`:552`/`:560`), `enqueueTenderRefundDrawer` (`:643`/`:652`), `enqueueSaleDrawer`
  (`:671`/`:678`), and the calibration route (`apps/server/src/print-api.ts:1260-1266`, already
  queue-first; it switches to `recordDrawerOpen` with `deviceId: null`). The tender path's earlier-row
  read (`:636-640`) is already gone (os13); if it is not, stop (stop 2).
- **The download** (`apps/server/src/personal-data-actions.ts:171-186`) reads
  `readActivityForPerson(db, person, { kinds: ["drawer.opened"] })` in the same write-lock turn and
  maps each entry to today's fields, `{ id, reason, at, saleId, billPaymentId, viaOverride, personId,
  authorizedBy }`, in the same order (`at`, then id). Slice 2's reader orders ties by `rowid`, not by
  id, so the download sorts the entries by `at` then `id` in code to keep today's order. The download's
  shape does not change.
- `drawer_opens` is deleted with `packages/db/src/schema/drawer-opens.ts`, its classification entry
  (`packages/db/src/classification.ts:36`), its exports (`packages/db/src/index.ts:223-224`) and the
  test fixture list (`apps/server/src/testing/zone-payment-venue.ts:134`). `DrawerOpenReason` moves to
  `activity-kinds.ts`.
- `endUnpairedPrinterJobs`' comment (`packages/printing/src/runtime.ts:139-150`, "`drawer_opens`
  holds no job id, so its audit row is unchanged") is cut: the entry now names the job.

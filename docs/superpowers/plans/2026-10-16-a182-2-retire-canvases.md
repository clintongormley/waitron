# A182-2: Retire Canvases Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans, inline, task by task. The owner authorised unattended implementation/finish/land. No subagents are needed for these coupled tasks. This document is a plan, not an implementation receipt. Publish these reviewed planning documents before starting the implementation branch.

**Goal:** Replace configurable canvases with today's fixed device screens and remove the complete canvas contract in one implementation PR.

**Architecture:** The server sends a device form factor instead of a canvas. The till chooses from closed primary destinations and mounts existing screens directly; Counter owns its fixed widget markup. Profile, receipt, theme, menu-home and floor-plan capabilities retain their existing contracts except for removal of canvas selection.

**Tech Stack:** TypeScript, Lit, Hono, Drizzle/SQLite, Vitest with the existing real-Chromium provider, pnpm.

**Spec:** [A182-2 retirement design](../specs/2026-10-16-a182-2-retire-canvases-design.md). Read it with this plan. Source citations refer to the design's base SHA; proposed new files are marked **Create**, and are not existing links.

## Global Constraints

- Ship ONE complete implementation PR after separate planning publication. No intermediate PR may break the boot/profile/schema contract.
- Delete canvas persistence, authoring, selection and rendering. Do not rename the generic canvas renderer or retain a cards/config/spans registry behind fixed defaults.
- Preserve business assertions, exact money and VAT results, permissions, login refusals, drawer rules and fiscal invariants. Do not edit golden fixtures, golden huella, `inmutabilidad` or other fiscal filing/hash checks.
- No data migration, backfill or compatibility reader before a real venue is live. Do not claim a reset is necessary without measuring the final candidate against a populated predecessor.
- Keep device types, capabilities, navigation screens, profile actions, receipt settings, tenant themes, menu Device Home Page Handheld/Till displays and the floor-plan editor.
- Preserve counter, table-order, station, pass and pass-monitor modes; starting screens, URLs/history, drafts, polling and resource cleanup. Preserve A743 kitchen notes and landed/in-progress A737 behavior.
- Use existing EN/ES wording, `wt-*` primitives and declared `--wt-*` tokens. LOOK in EN/ES, light/dark, at measured widths 390/1280.
- Root guards under `scripts/` are controversial test changes. Obtain the specific owner answer before changing their pins; scope approval alone does not grant that answer.
- Every implementation task has observed RED then GREEN and signed-off commits (`git commit -s`). Keep coverage `98/98/98/95` and mutation floors unchanged.
- Preserve foreign work and root instructions. Keep campaign state outside the repository and recheck live collisions before implementation and landing.

## Review Focus

1. Missing/refused identity or a stale URL must not produce a blank screen, unlock a KDS as an operator, or grant an action. Tests in Tasks 1/3 cover fixed-home fallback and each front door.
2. A handheld waiter leaves Order with a note-only draft while another read completes: retain the correct party/revision and flush once; keep the no-table Order state. Task 3 owns the real-Chromium cases.
3. A KDS changes from station to pass monitor while an old request waits: mount the selected read-only mode, reject stale work and stop removed resources. Task 3 owns the mode/narrowing cases.
4. Waiting rows exist with no held orders, or a counter Place/payment is running without a connected reader: retain the lists, cash/reader gates and exact payment facts. Task 2 owns these assertions.
5. Find bill is open over a basket and a refund/receipt response arrives after Back, logout or profile switch: retain basket/page/attempt identity without applying the old answer. Task 3 owns the landed A737 cases and collision-gated refund integration.

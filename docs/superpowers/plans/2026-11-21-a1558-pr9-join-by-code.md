## How it works

### Who talks to whom, and what each side trusts

- **Two channels.**
  - Box to box: the new box sends HTTPS requests to the main box. The main box never opens a
    connection to the new box. It does not have to dial an address a stranger supplied, and it
    could not check the new box's self-signed certificate anyway.
  - Browser to box: the person's browser talks to each box's own page. The main box's page is
    trusted. The new box's page was reached by accepting a warning (PR 7).
- **Nothing rests on the connection between the boxes.** The new box reads the main box's `/ca.crt`
  without checking it, as today, and uses it as the connection's authority. Anyone who answers at
  that address can pass that. The protocol protects each message itself:
  - every input that matters is in the code the person compares (below);
  - the bundle is encrypted to a one-join key of the new box's, so only the new box can read it;
  - the main box signs its answers that matter with its node key (the identity key that signs its
    endorsements), and that key is in the code;
  - the main box refuses a request that did not come from one of the network addresses the new
    box lists in its hello.
- **What those protections do not cover.** Someone who can open a backup holds the main box's node
  key (above). Placed between the boxes, such a person can relay honestly until the tap and then
  hand the new box a bundle of their own, locked to the new box's public encryption key and signed
  with the real node key. The lock still stops anyone **without** a backup. The address check
  stops such a person unless they also take over the new box's network address on the local
  network. This is the remaining risk in owner question 3.
- **The new box authenticates the main box by the code comparison.** The main box's node id and
  node public key are in the code. If the codes match, the node key the new box holds is the real
  main box's.
- **The main box authenticates the new box the same way.** The new box's node public key, its
  encryption key and its addresses are in the code, and every request after the hello is signed
  with its node key.
- **Plain http** stays allowed only to a loopback address, as today (`primary-url.ts:3-6`).
- **A main box using the operator's own certificate files** serves no authority at `/ca.crt`
  (`boot.ts:4165-4166`). It is refused at **Join** with `mirror.bundle_fetch_failed`, as today.

### The protocol, step by step

Terms, translated once:
- A **hash** here is SHA-256: a 32-byte fingerprint of some bytes. Any change gives a different
  result, and nobody can work back from it.
- A **nonce** is a fresh random value used once.
- A **commitment** is the hash of a nonce, sent before the nonce itself. Whoever sent it cannot change
  the nonce afterwards, and nobody can learn the nonce from it.
- **X25519** is a standard way for two sides to agree a secret key over an open connection. The new
  box makes a fresh X25519 key pair for this join only and sends its public half. The main box uses
  that public half to lock the bundle so that only the new box, which holds the private half, can
  open it. The public half is public: anyone can lock something to it, which is why the main box
  also signs what it sends.
- **AES-256-GCM** is the standard cipher that does the locking; it also detects any change to the
  locked bytes. **HKDF** is the standard way to turn the agreed secret into the cipher's key.

**How every signed message is built (requirements, not options).**
- The signed bytes are length-prefixed fields: each field is preceded by its length as 4 bytes,
  big-endian. The first field is the message's label (for example `"waitron box join reveal v1"`),
  then the request id, then `seq` as a whole number, then the message's own fields.
- Those bytes are turned into base64 text and that text is what `signBytes` signs and `verifyBytes`
  checks. So two different byte strings can never become the same signed text, and a signed join
  message can never be read as canonical JSON (an endorsement or a chart body), because base64 text
  never begins with `{`. No join route signs canonical JSON.
- The new box makes a fresh node key pair for every attempt, so no signature from one attempt fits
  another.

1. **Hello** (new box → main box, `POST /api/node/join/hello`).
   - The new box makes its node key pair (`generateStandbyIdentity`), a one-join X25519 key pair
     (public half `Ek`) and a 32-byte nonce `Nn`. It sends, signed with its node key:
     - `protocol: 1`;
     - its node id, node public key `PKn`, contact address and store address (the four fields
       today's bundle route takes, `mirror-bundle-api.ts:158-170`);
     - `Ek`;
     - `addresses`: its own network addresses (every interface address that is not loopback);
     - `at`, its clock, used only for the clock check.
     It does **not** send `Nn` or any commitment to it.
   - The main box checks that the address the request came from (`requestAddress`) is one of
     `addresses`, the clock gap and the box name (`mirror.join_address_mismatch`,
     `mirror.clocks_apart`, `mirror.standby_name_taken`) and the hello limits below. It makes a
     request id and its own 32-byte nonce `Nm`.
   - It answers `{requestId, mainNodeId, mainPublicKey, Cm, expiresAt}`, where
     `Cm = SHA-256(len‖"waitron box join commitment v1" ‖ len‖requestId ‖ len‖Nm)`. Nothing is
     listed on the Servers page, and the answer tells the sender nothing about the main box's code.
2. **Reveal** (new box → main box, `POST /api/node/join/reveal`). **One reveal per request.**
   - The new box sends `Nn` and `seq: 1`, signed with its node key.
   - The main box checks the signature and the reveal limit below, and counts this reveal against it
     whatever happens next. It works out the code.
   - If the code equals any code a listed request shows, real or decoy, it answers
     `mirror.join_code_taken` **without sending `Nm`**, and the request ends.
   - Otherwise it makes two decoys, lists the request on the Servers page, stores its answer, and
     answers `Nm` with a signature by its node key over the label `"waitron box join reveal v1"`,
     the request id, every hello field it received (node id, `PKn`, `Ek`, contact address, store
     address, `addresses`), `Nn` and `Nm`.
   - **A second reveal for the same request:** the same `Nn` and `seq` get the stored answer again,
     byte for byte, and count nothing more. Any other `Nn` answers `mirror.join_invalid` and ends the
     request. Without this rule, a sender that has seen `Nm` could search for an `Nn` that gives a
     code of its choosing: the second reader's probe hit a chosen code in 108,939 tries (213 ms),
     and in 755,720 tries (2.5 s) when I reran it.
   - **A lost reveal answer:** the new box sends the same reveal again, up to 3 times over 10
     seconds. If none is answered it shows `mirror.bundle_fetch_failed`'s words, sends a signed
     cancel (best effort) and forgets the attempt; the person chooses Start again. On the main box,
     a reveal that never arrived leaves the hello unrevealed, dropped after 30 seconds; one that
     arrived leaves a listed request whose code the new box never showed, which ends on a cancel,
     a Dismiss or after 15 minutes.
   - The new box checks that the hash of `Nm` matches `Cm`, that the signature is good, and that the
     signed hello fields are the ones it sent. Then it works out the code and shows it, with its own
     addresses. Any failure ends the attempt with `mirror.join_invalid` and a signed cancel.
3. **Waiting** (new box → main box, `POST /api/node/join/poll`, every 2 seconds).
   - Each poll is signed and carries `seq`, one more than the last request's, and a fresh `at`. The
     main box refuses a `seq` that is not greater than the last one it accepted (the repeated reveal
     above excepted), and keeps the latest `at` and when it received it. A clock corrected during
     the join changes `at`, not `seq`, so it no longer fails every poll.
   - The answer is `waiting`, `ended` (with the reason) or `approved`.
4. **Check and tap** (the person's browser → main box; the routes are listed below).
   - The main box runs the venue checks that need no writes (`refuseBeforeReserving` minus the box
     name). The clock check uses the latest poll's `at`. Then it shows the three codes.
   - A right tap builds the bundle in that same request, under the person's live sign-in. The main
     box makes a one-use X25519 pair, agrees a key with `Ek`, derives the cipher key with HKDF over
     `"waitron box join bundle v1"`, the request id and both public halves, and locks the bundle.
     It keeps only the locked bytes. A wrong tap ends the request.
5. **Collect and finish** (new box).
   - Every poll in the 2 minutes after approval receives `approved` with the locked bundle, the main
     box's one-use public half, and a signature by the main box's node key over the label
     `"waitron box join approved v1"`, the request id, the one-use public half and the hash of the
     locked bytes. So a lost answer is collected on the next poll.
   - The new box checks the signature against the node key from the hello answer, unlocks the bundle,
     checks that `bundle.primaryPublicKey` and `bundle.designated.nodeId` are that key and id
     (replacing today's `sameAuthority` check, `mirror-bundle-fetch.ts:677-686`), and keeps it in
     memory.
   - The tab holding the handle (below) shows "The main box approved a join with code 482 913" and
     **Finish joining**. Choosing it posts `/setup-api/adopt`, which runs `adoptFromPrimary` with the
     attempt's key pair and the held bundle, answers the server key once, and restarts the box, as
     today.
6. **Start again** (new box). The new box sends a signed `POST /api/node/join/cancel` and forgets the
   attempt. The cancel is best effort: if the main box cannot be reached, its request ends by itself.

### Why neither side, nor a box between them, can choose the code

- **The order.** The main box fixes `Nm` (by sending `Cm`) before it sees `Nn`. The new box sends
  `Nn` after it has `Cm` and before it has `Nm`, so `Nn` cannot depend on `Nm`. The request takes
  one `Nn` only, so nothing either box sends afterwards changes the code. One commitment is enough
  when it comes from the side that reveals last, as in Bluetooth's numeric comparison.
- **A box in the middle, facing the new box,** must answer the hello with a `Cm″` before it sees
  `Nn`. So it cannot steer the code the new box shows.
- **The same box, facing the main box,** learns the main box's code for a request only from the
  reveal answer, which comes after it has sent its one `Nn′`. That reveal lists the request and
  counts against the reveal limit. So every try at matching is listed on the Servers page and
  counted; none is hidden.
- **Measured on a toy version, not the implementation** (`odds-r4.mjs`, two-digit codes so the effect
  shows): a box in the middle opening 100 hellos, with a limit of 3 reveals, matched the new box's
  code in 63.7% of 20,000 runs under revision 3's order (expected 63.4%) and 3.0% under this order
  (expected 3.0%).

### The code

- **Inputs.**
  `V = SHA-256(len‖"waitron box join code v1" ‖ len‖newNodeId ‖ len‖PKn ‖ len‖Ek ‖ len‖contactUrl ‖ len‖storeUrl ‖ len‖addresses ‖ len‖mainNodeId ‖ len‖PKm ‖ len‖Nn ‖ len‖Nm ‖ len‖requestId)`.
  - Each `len` is 4 bytes, big-endian. `addresses` is the sorted list, joined by newlines.
  - The keys are their DER bytes.
  - `PKm` is the main box's node identity public key.
  - A box in the middle that swaps `Ek`, `PKm`, an address, or the contact or store address changes
    one side's code. The reveal's signature also catches a changed hello field before any code is
    shown.
- **The code** is the first 8 bytes of `V`, read as a whole number, taken modulo 1,000,000 and
  written as six digits with leading zeros, shown as two groups of three. Taking a 64-bit number
  modulo a million favours some codes over others by less than one part in 10^13, which is nothing
  that matters.
- **The odds, counted per pair** (`odds-r5.mjs`; arithmetic, not a measurement of the code). A pair
  is one code the new box showed and one live code the main box listed while it was shown. A box
  in the middle wins only if a pair matches.
  - **One pair:** 1 in 1,000,000 for a person who compares. For a person who might misread one
    digit, the worst case counts the exact code and its 54 one-digit neighbours (6 places × 9 other
    digits): 55 in a million, about 1 in 18,182.
  - **The second reader's example,** 3 listed requests × 5 codes shown (four Start agains): 15
    pairs, 1 in 66,667 careful, 1 in 1,213 with a one-digit misread.
  - **The most the limits allow without a wrong tap or a Dismiss:** a code lives up to 15 minutes,
    so it can meet the codes of the 30 minutes around it, at most 12 reveals by the limit below. If
    the person made `s` of them, the pairs are at most `s × (12 − s)`, which is largest at 6 × 6 = 36
    pairs: 1 in 27,778 careful, 1 in 506 with a one-digit misread. Each wrong tap or Dismiss frees
    one more reveal.
  - Grouping the digits as "482 913" and showing them large helps against misreading.
  - **Against a person who taps without comparing:** any request is approved 1 in 3, whatever the
    code length. Ending the request on a wrong tap stops a second guess, and the address on the
    Servers page, the new box's own address on its screen, and the guide's sentence ("check that the
    address is the new box's and the code is the one it shows") are the rest of the defence.
  - **Two digits**, the till's length (`join-requests.ts:104-108`), would give 1 in 100 per pair. Six
    digits is the most a person can compare at a glance.
- **Decoys.**
  - Two random six-digit codes per request, made when the request is listed, fixed until it ends.
  - They differ from the real code and from each other, and avoid every code any listed request
    shows.
  - The real code cannot be redrawn, so a reveal whose code equals a listed code is refused
    (`mirror.join_code_taken`), as above. That happens about 3 times in a million for each other
    request listed (its three codes).
  - The shuffle runs on every read, as `challengeFor` does. The dashboard is never told which code
    is real.

### Waiting requests: where they live and their limits

- **No new table, no migration.** The main box keeps waiting requests in memory. The new box keeps
  its one attempt in memory too. A restart of either forgets them, and the other side then answers
  `mirror.join_not_found`, so the person chooses Start again.

> of the new box forgets only its own attempt. Its request stays listed on the main box's Servers
> page until it is dismissed there, a new request from the same address replaces it, or it expires
> (`JOIN_REQUEST_TTL_MS`, 15 minutes, in `apps/server/src/box-join-requests.ts`), as Codex's
> run-it review measured.

- **Limits on the main box.** Time is measured on a steady clock, so a clock step cannot stretch any
  of them.
  - Hellos: at most 1 unrevealed hello from one address at a time and 5 hellos a minute from one
    address; at most 20 hellos a minute in total, counted like Cloud's passkey challenges
    (`cloud-remote.ts:171-184`). A hello not revealed within 30 seconds is dropped. Unrevealed hellos
    tell the sender nothing, so these limits only stop a flood.
  - Listed requests: at most 3 at once, and at most 1 from one address. A reveal from an address
    that already has a listed request ends the older one.
  - **"Started again" flag:** a request from an address whose earlier request ended by a cancel or
    by being replaced in the last 15 minutes is flagged on the Servers page: "This box started
    again. Tap only a code it showed after that." / "Este servidor empezó de nuevo. Toca solo un
    código que haya mostrado después."
  - Reveals: at most **6 in any 15 minutes**, in total. A reveal counts however it ends, except that
    a **wrong tap** or a **Dismiss** gives its place back: in both a person looked at the request. A
    cancel, a replacement, an expiry or `join_code_taken` does not give its place back. So a person
    can choose Start again five times in 15 minutes before the limit stops them, where revision 4's
    limit of 3 locked them out after two.
  - Why Dismiss frees a place, stated honestly: it lets a person clear requests they do not
    recognise and carry on. It does not defeat someone blocking on purpose, who can fill the place
    again at once. The one-per-address rule means such a person needs several addresses, and
    `mirror.join_full` says which limit was hit.
  - A request ends 15 minutes after its hello, as a till's does (`join-requests.ts:35`).
  - An approved request keeps its locked bundle for 2 minutes, then forgets it. The bundle lives
    only in memory, and only locked.
  - An ended request keeps only its reason, for 2 minutes, so the new box can say why.
  - Body limit 64 KiB on each box-to-box route.
- **What someone on the network can always do: delay a join.** They can use up the hello limits or
  the reveal limit from several addresses. Nothing is gained towards approval: no request is listed
  until it is revealed, and none is approved without a tap.
- **Venue facts stay behind sign-in.** Hello refuses only on the address, the clock and the box name.
  "A spare has already joined", "Continuous copy is on" and "no backup encryption key" are told at
  **Check**, to a signed-in person, on the box where they are fixed. Today a stranger cannot learn
  them without the password, and that stays true.

### The server key, and the one handle that remains

- The spare's server key can promote that spare, so it must reach only the person's page. The new
  box's routes are open to the whole network.
- So **Join** answers a one-time handle: 32 random bytes, kept in the tab's session storage. The new
  box keeps only its hash. **This is a tab secret, which the owner's shape said there would not be**;
  owner question 2 asks the owner to accept it.
- **The handle is needed to see the code and to finish.** `GET /setup-api/join` shows the code, and
  `/setup-api/adopt` answers the server key, only to a request carrying the current attempt's handle.
  - A page without the handle shows: "A join was started from another page or device. This page
    cannot show its code. Choose **Start again** to start one here; the other page's join then ends."
  - The tab whose handle no longer matches (its attempt was cancelled or replaced from elsewhere)
    shows: "This page's join was ended from another page or device, so its code no longer counts. Do
    not tap it on the main box. Choose **Start again** for a new code."
- **Start again without the handle only once the handle's tab has gone quiet.** A cancel (or a start
  over an existing attempt) without the current handle is refused while the tab holding it has read
  the state in the last 15 seconds; the holding tab reads it every 2 seconds. After that a page
  without the handle may Start again, so a lost tab does not strand the box.
  - Refused words, `mirror.join_in_use` (409): "This box's join is open on another page or device
    right now. Finish or cancel it there. If that page is closed, wait 15 seconds and choose
    **Start again** here." / "La unión de este servidor está abierta ahora en otra página o
    dispositivo. Termínala o cancélala allí. Si esa página está cerrada, espera 15 segundos y elige
    **Empezar de nuevo** aquí."
  - What it leaves open: a tab that stops reading (closed, or a phone that locked its screen while
    the person walked to the main box) can be replaced by a stranger after 15 seconds. The
    stranger's request then lists under the new box's real address, and the main box flags it as
    started again. A person who taps without comparing (1 in 3) would then hand the stranger the
    approval, and the stranger could choose Finish joining and read the spare's server key.
- **Every new setup route checks the page it came from** (`sentFromThisOrigin`, refusing
  `setup.owner_required`, as `setup-api.ts:1110` does) and HTTPS (`setup.connection_insecure`),
  except on loopback. That stops another website open in the person's browser from driving the
  join. It does not stop a program on the network, which can send any page header it likes.
- The handle proves nothing about the join itself. It only keeps the server key and the code on the
  page that asked for them.

### A join that stopped partway

- **While waiting:** **Start again** cancels the request, as above.
- **After the new box started writing** (`setup.adopt_incomplete`, `setup-app.ts:2329-2330`):
  - The reset route takes no proof. `resetProof` is no longer written, and the field (the typed email
    and the hash of the administrator's password) is dropped from the operation record's type, not
    only left unread. `matchesResetProof` and the reset throttle go.
  - What a stranger on the network can then do: make a box whose join already stopped partway start
    over. The next start's checks (`reset-request.ts:79-94`) still refuse to wipe a box that has a
    `trading.env`, holds a tenant, or holds an operational venue. The security reads judged this
    acceptable.
  - The main box may still list the reset box in its chart. Its start-up peer check counts a listed
    box only once it holds a `nodes` row for it (`boot-peer-check.ts:143`), which a box whose join
    stopped before its copy store answered never gets. A test runs this (task 15).
- **An approved join the new box never finishes** (its page was closed, Finish joining was not
  chosen, or the box restarted) leaves the new box's row on the Servers page, which **Remove**
  clears. This is the state today's code reaches when the bundle's answer is lost after the writes
  (`mirror-bundle-api.ts:194-195`).

### What each attacker can still do (reasoned from the code; the review seats test it)

| Who | What they can do |
| --- | --- |
| A stranger on the network sends a hello of their own | Their request appears with their address and uses a reveal place. It is approved only if the person taps its code: 1 in 3 for a person who taps without comparing, odds per pair as in "The code" for one who compares. |
| A box between the new box and the main box, without a backup | A relay from its own address is refused at hello. One that has also taken over the new box's network address can relay, and if a pair matches it still reads nothing and changes nothing: the bundle is locked to the new box's one-join key, the answers are signed by the main box's node key, and a changed field changes the code or fails the reveal's signature. |
| The same, holding a backup it can open (a former spare, or anyone with a backup file and the backup key) | It can sign as the main box. If it has taken over the new box's network address and the person taps a code, it can install a bundle of its own on the real new box, for example one that makes the new box copy from it. The real venue's secrets it already holds. |
| A box posing as the main box, which never relays | The real main box never lists the new box. It can send the new box a bundle of its own. **Finish joining** asks the person to confirm they tapped this code on the main box, which they cannot have done. This is all Finish joining stops. |
| Someone between the person's browser and the new box (the person accepted a warning for it, PR 7) | They can show the person the code of their own box's request. If the person taps it, their box receives the whole bundle: the venue's certificate authority key, the key ring that unseals the main box's identity key, and the backup encryption key. They can also read the real new box's server key as it passes. They never get the main box's password or code, which today they read. |
| Anyone on the network, on the new box | Once the person's tab has gone quiet for 15 seconds, end its join and start one of their own, which the main box flags as started again (above). Reset a join that stopped partway. |
| Anyone on the network, on the main box | Delay joins by using up the hello or reveal limits. |
| A page in a frame | The dashboard's pages gain `frame-ancestors 'self'`, so a page on `box-xxxx.waitron.local`, which counts as the same site, cannot frame the Servers dialog and steer a tap. |

## Questions for the owner

1. **Finish joining on the new box: recommended, and in the tasks.** After the main box approves,
   the new box says "The main box approved a join with code 482 913" and offers **Finish joining**,
   "only if you tapped this code on the main box". One tap, nothing typed. It stops one thing only:
   a box pretending to be the main box, which never passes anything on to the real one, making the
   new box join a venue of its own. The plan builds it unless you say no.
2. **One tab secret, for you to accept.** You said no tab secret. The plan keeps one invisible handle,
   in the tab where the person chose Join. Without it, anyone on the network could read the new
   box's code or collect the spare's server key, which can promote that spare. While that tab is
   open and awake, nobody else can restart the join. What remains: if the tab stops for 15 seconds
   (closed, or a phone that locked its screen on the way to the main box), someone on the network
   can restart the join and hold the new handle. The main box then marks the request "This box
   started again; tap only a code it showed after that". Only a person who taps without comparing
   the code (1 in 3) would then hand that someone the spare's server key. Do you accept the handle
   with that limit?
3. **For you to know, not to decide:**
   - Your shape says the main box "sends the bundle straight to the new box". In the plan the new
     box fetches it: it asks the main box every 2 seconds and receives it on the first ask after
     the tap. The main box then never connects to an address a stranger gave it. The person sees
     no difference.
   - **Two risks remain.**
     - Someone between the person's browser and the new box (which the person reached by accepting
       a browser warning) can show the person their own box's code. If the person taps it, that
       someone's box receives everything the venue's boxes share: the certificate authority key,
       the key ring that unlocks the main box's identity key, and the backup encryption key. Today
       the same person would read the main box's password instead.
     - Someone who can open a backup (a former spare, or anyone with a backup file and the backup
       key) can sign as the main box. If they also take over the new box's network address, sit
       between the two boxes and the person taps a code, they can install their own setup on the
       real new box, for example one that makes it copy from them. They already hold the venue's
       secrets, so the venue loses nothing new; the new box would not be a working spare.

## Security read of revision 4: findings and answers

Each finding was checked against the code or the plan before applying it. None was rejected.

1. **A second reveal let the sender choose the code. Accepted.** Revision 4 said nothing about a
   second reveal on one request. Rerun of the reader's probe: with `Nm` known, a chosen code took
   755,720 hashes (2.5 s); the reader saw 108,939 (213 ms). Applied: one reveal per request; the
   same `Nn` and `seq` get the stored answer; any other `Nn` is `join_invalid` and ends the request;
   lost answers are specified on both boxes (step 2); tests in task 3, and the new box's retry in
   task 8.
2. **A stranger could still hold the handle for a request under the new box's real address.
   Accepted.** Revision 4 left cancel and start open without the handle. Applied: a cancel or start
   without the handle is refused while the holding tab has read the state in the last 15 seconds;
   the main box flags a request from an address whose earlier request was cancelled or replaced in
   the last 15 minutes; every new setup route checks HTTPS and the page it came from
   (`setup-api.ts:1109-1110` is the existing use). The plan says what remains (owner question 2)
   and that the page check stops only another website, not a program on the network.
3. **Anyone holding a backup could sign as the main box. Accepted.** Checked: `backup-sweep.ts:238`
   snapshots `node.db`; `state-layout.ts:270` lists the venue folder with its databases under
   backup; `readNodeSigningKey` (`node-signing-key.ts:103-120`) opens the node key with the ring;
   `adopt.ts:110-111` keeps the ring in `secrets.env`, a required backup file. Not checked: whether

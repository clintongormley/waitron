# A1308 slice rules — read before building any A1308 slice

Every A1308 slice plan cites this file. It holds what is the same for every slice, so the plans hold
only what each slice decides. Where a slice plan says something different, the slice plan wins and
says why.

- **Design:** [`docs/superpowers/specs/2026-11-02-rationalisation/README.md`](../specs/2026-11-02-rationalisation/README.md)
  (approved by the owner, 2026-11-04) and its appendices. Where an appendix and the README disagree,
  the README wins (README, opening).
- **Backlog:** `docs/backlog/architecture.md`, "## A1308." and "## Bundle: Small checks and indexes
  that are cheap only inside A1308's fresh tables".
- **Order of slices:** [`2026-11-08-a1308-build-order.md`](2026-11-08-a1308-build-order.md).

## 1. Size

- One slice is one pull request, buildable in about 3 hours, with **at most about 1,000 changed
  lines written by hand**, tests included.
- Not counted against that cap (owner, 2026-11-08): the output of a rename script committed in the
  same pull request; pure deletions; and the generated migration files (`drizzle/*.sql`,
  `drizzle/meta/*`, `scripts/migration-baseline-epoch.json`) that the rebuild command writes.
- A rename script is committed under `scripts/a1308/` and is idempotent: running it again on its own
  output changes nothing. The reviewer reads the script, re-runs it on the base, and checks the tree
  equals the pull request. Hand edits after the script are listed in the pull request description.
- An implementer that passes about 150 tool calls with its task unfinished stops at a passing (or
  cleanly failing) point, commits, and hands over (global rule).

## 2. How a slice changes a starting migration

Since A760 each migration set has one starting migration (`drizzle/0000_baseline.sql`), and
`scripts/migration-baseline-epoch.json` records each one's journal date and SHA-256. A slice never
adds a `0001_*` migration: it changes the starting migration itself.

**The method (tested 2026-11-08 on `main` d908a5b8d4, in a docs worktree, nothing committed):**
regenerate the set's starting migration from its TypeScript schema with `drizzle-kit generate` into
an empty `drizzle/` folder, append the set's hand-written triggers, and record the new date and hash
in the epoch file. On core's set with no schema change, the protection list then differed from
before only in column order (150 tables) and the change-feed update triggers that list columns in
that order (50); `migration-upgrade`, `migrations-match-schema`, `schema-constraints`,
`append-only-triggers` and `behavioural-triggers` passed (5 files, 518 tests). Control: with one
hand-written trigger (`tenders_reject_post_settlement`) removed from the appended text, the
protection list printed `missing trigger tenders_reject_post_settlement` in all six builds.

Only core's set carries hand-written triggers (42 at d908a5b8d4: `grep -c "CREATE TRIGGER"` over each
set's `drizzle/*.sql`); the other seven sets carry none, because append-only and change-feed triggers
are installed by code at migration and at start.

Slice 1 turns this into one command and lands the one-off column-order change on its own, so later
slices compare cleanly. From then on:

1. Change the TypeScript schema (and, for core, the hand-written trigger source file slice 1a
   creates, `packages/db/triggers/core.sql`).
2. Run `pnpm --filter @waitron/server migration-baseline rebuild --set <name>` for each set the
   slice changed (slice 1a builds it).
3. Never edit `drizzle/*.sql`, `drizzle/meta/*` or the epoch file by hand (CLAUDE.md §3).
4. **On rebase, a conflict in any of those generated files is resolved by taking `main`'s copy and
   re-running the rebuild command**, never by merging text. This is what lets two lanes change core's
   tables at once (slice 1 tests it with two branches).

Every slice that changes a starting migration resets every venue. Its pull request's first line
says so: "Every venue is reset: <set names>; backups and exports from before this cannot be restored
or imported." (CLAUDE.md §3, "Editing a shipped migration file"). After it lands, dev-stack slots
and the Santet venue are reset (`wa-wt reset`); the owner's own box stays quarantined until the end
of A1308 (design §6).

## 3. The protection list: predicted, then checked

Before writing any code, the builder runs, from `apps/server`, on the base commit:

```bash
pnpm protection-list list --out <empty absolute dir A>
```

and after the slice:

```bash
pnpm protection-list list --out <empty absolute dir B>
pnpm protection-list compare --old <A> --new <B> --report <absolute file>
```

(How the tool works: `docs/developers/testing-guide.md#the-protection-list`.)

**Every slice plan has a section "Expected protection-list difference"** listing, per table, what
`compare` must print: `missing`, `extra` and `changed` objects, with the design's reason for each
(design appendix §5, "Protections"). The builder pastes the real report into the pull request and
marks each line against the prediction. **A line the plan did not predict is a stop** (§5), not
something to explain afterwards.

How the tool prints things a prediction often gets wrong (read from `compare.ts` and a run at
`d950d5f404`): a live-update trigger's column list is its `when` field, so a table that gains,
loses or reorders columns prints `changed trigger waitron_change_<table>_update.when`, not `.body`;
`notNull` prints `true`/`false`; a declared primary or unique key prints as
`table <name>.keys[…]`. Build the prediction from a real `list` run where you can. The tool also
reports each trigger's position among the triggers on the same table, timing and event, so a
rewritten trigger keeps its place in `triggers/core.sql`; a new one is added after the existing ones
for its table, and its `.order` line is predicted.

## 4. Tests

- A behaviour test keeps its assertions. It may be re-pointed at a new table or column, and its
  set-up may change; a test that passes only after its assertion changes means behaviour moved, and
  is a stop (design §6, "The behaviour suites stay"). The one exception: an assertion the slice's
  plan lists under "Assertions that change, by design", each with the design section that changes
  the behaviour (a new field in an answer, a renamed refusal path). Nothing else may change.
- Test first for every new behaviour, as usual. A new database rule (CHECK, trigger, unique index,
  foreign key) gets a case that the database refuses the bad row with the expected domain error or
  constraint, and a case that the legitimate write still succeeds (CLAUDE.md §4, "a proof by
  deletion says nothing about what the guard wrongly refuses").
- Person-id columns gain foreign keys to `persons` (design U11). A fixture that invents a person id
  creates the person first.
- The guards are updated, never loosened: `scripts/append-only-triggers.test.ts`,
  `scripts/behavioural-triggers.test.ts`, `scripts/schema-constraints.test.ts`,
  `scripts/classification-complete.test.ts`, `scripts/live-subscriptions.test.ts`, and any other a
  slice's plan names.
- Run focused tests locally. A pull request's CI tests only the packages the slice changes, not
  their dependents, which only the nightly run tests (#2619, A1461; CLAUDE.md §2: "A PR only
  typechecks dependents and the nightly tests them, so run the affected consumers' tests locally").
  So the builder also runs, locally, the suites of any package the slice leaves unchanged that reads
  a table, column or export the slice changes.

## 5. Stop points — ask the watcher, do not decide

The builder stops, commits what passes, and writes the question to the lane's `questions.md` when:

1. a line the plan cites no longer says what the plan says it does (a cite that has only moved,
   because an earlier slice landed, and still says the same thing is not a stop: find it, use it,
   and note the new line in the pull request);
2. the protection list prints a line the plan did not predict;
3. a behaviour test can only pass with a changed assertion;
4. a measurement the plan runs gives the result the plan names as failing (the design names the
   fallback; the watcher confirms it before the builder takes it);
5. the slice would touch a file or table the plan does not list, beyond a test fixture or an import;
6. the slice would exceed the size cap by more than about a fifth.

## 6. Who lands

The owner lands every slice that changes `sales`, invoice numbering, `verifactu_records` (today
`registros_facturacion`), the fiscal identity, AEAT sending, or any value that feeds a fiscal hash,
including the venue's time zone (design U11, "Which slices the owner lands"). Each such plan says so
in its header. The lanes land the rest themselves (watcher rule).

## 7. Two lanes

Owner, 2026-11-08: A1308 runs in two Codex lanes, split by area so that no two in-flight slices change
the same tables. The build-order file says which lane takes which slice. Because generated migration
files are regenerated, never merged (§2.4), two lanes may both change core's set. Claude reviews each
pull request (roles reverse when Codex drives).

## 8. Other work beside A1308 (owner, 2026-11-08)

- Work that changes no table or column goes ahead in any lane. It rebases across A1308 merges; where
  A1308 renamed something, it re-runs the committed rename script after rebasing.
- Any schema change, A1308 or not, is made with the rebuild command (§2): no set ever holds a
  second migration, and hand-written SQL lives only in the set's `triggers/` file. Slice 1a adds a
  guard that refuses a `drizzle/0001_*` file, because a rebuild would otherwise delete a
  hand-written one without a word.
- A schema change in an area whose A1308 slice has landed is built on the new tables.
- A schema change in an area A1308 has not reached lands before that area's slice starts (the slice
  folds it in) or waits until the slice lands. It is never built while that area's slice is in flight.

## 9. Housekeeping every slice does

- The commit that moves a table into core's set cites design §5 U1 as the stated reason (CLAUDE.md §3).
- A slice that changes what a configuration export carries raises the bundle's format version by
  one from `main`'s value when it is built; on rebase it takes the next number after `main`'s, so an
  export from before the slice is refused as outdated rather than as an invalid request.
- Classification, configuration-export lists, live-subscription names, backup-verification lists and
  `scripts/write-path-tables.json` follow every renamed, merged or deleted table.
- Delete the backlog entries the slice finishes, in `docs/backlog/architecture.md`'s bundle and its
  "What A1308 retires" list, and any other entry the plan names (CLAUDE.md §6).
- Docs and guides that describe a changed behaviour are updated in the same pull request (CLAUDE.md
  §1, "A behaviour change retires every receipt about the old behaviour").
- Run `/finish-branch` before the pull request exists; CI runs once per push, so push once.

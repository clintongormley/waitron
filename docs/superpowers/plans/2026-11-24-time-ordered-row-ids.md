# Time-ordered row IDs

**Finish line.** Newly minted Waitron row IDs sort by their creation millisecond, so a day's inserts can touch fewer old database pages. Existing and supplied IDs keep their values. An ID minted in the browser reflects that browser's clock. Rows minted in one millisecond still have random ties. Use the UUIDv7 layout, with UTC milliseconds at the start and random bits after the version and variant. [RFC 9562 §5.7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7)

**Generators.** In `packages/shared/src/ids.ts` expose `newRowId()` through the existing shared barrel. Use the timestamp from `Date.now()` and the random tail of the platform UUID. Point `packages/db/src/schema/columns.ts`'s `newId` at it, keeping the return shape and existing Drizzle defaults in db, bookings, VeriFactu, node-db, payments and workforce. In `packages/db/src/change-feed.ts` keep the existing trigger expression and use SQLite's current millisecond for the same prefix. Those triggers are rebuilt by `installChangeFeed`. Keep starting migrations and import or restore of existing IDs byte-for-byte.

**Explicit writers.** Use `newId` in server bill actions, parties, working orders, portion and printed-bill splits, upgrade sales and print-agent enrolment. Cover core sale lines and replacement, menu categories, extras, options and modifiers, identity account creation, and provisioning configuration transfer where it deliberately mints replacement IDs. Use `newRowId` where dashboard extra items, option labels and set-menu lines, the venue-service opening-hours editor, and the till's working-order draft mint an ID that becomes a row key. Point the demo option-list and sales seeds and bench row builders at the same generator. Leave fixtures that explicitly model old IDs, command IDs or adverse order on their chosen values. The reviewer brief carries the call-site inventory, including the service-step editor's temporary key.

**Exceptions and reading paths.** Keep randomness for tokens, codes, claims, passkey challenge handles, temporary names, revisions, provider keys, request and signed operation IDs. Preserve box and venue identity generation because of short box names and signed references, and preserve fiscal installation and series IDs supplied by allocation. Keep outgoing mail IDs random where the same value is a signed Cloud request ID. Trace internal fiscal row IDs from insertion through `registro-row.ts` and `chain.ts` into filing and hashing, and check wire bodies and exported or signed evidence before changing a writer. Check ID-based tie breakers and shortened IDs, including menu-copy ordering, anonymised exports and existing payment-order tests. Check ID exposure on invoice and email delivery, the customer menu and public links. Authenticated row IDs expose mint time. Bearer links and public identifiers whose randomness they rely on keep their existing formats.

**Checks.** Start with failing tests in shared `ids.test.ts` for a known clock's prefix, increasing milliseconds and distinct IDs within the same millisecond. In db `schema/columns.test.ts` check a defaulted insert alongside an explicit old ID and in `change-feed.test.ts` check an ID made by the trigger without changing the event. Use existing working-order, payment tie-break, setup, import and delivery suites for the writers they cover, adding only a missing high-traffic creation-path assertion. Update version checks only for changed writers, including till drafts, option labels, demo export aliases and configuration transfer. Preserve the payment test's deliberate reverse order. Run VeriFactu's unedited `write-path.e2e.test.ts` and `inmutabilidad.test.ts`.

**Measure.** Use two lane-owned checkouts and copies, the same Linux bench runtime, seed, profile and trading date. Take before and after page fingerprints around one matching 250-bill day from the same compatible random-ID checkpoint. If a year checkpoint is incompatible, make a short checkpoint at the base and give its actual age. Record completed sales and changed old pages, new pages and bytes. If the benefit does not show, the candidate prints about as many old pages rewritten as the base. Keep the runs and raw comparison with the PR and update the backlog pointer with the measured scope.

One PR, estimated 220 added production lines and 150 test lines. No migration, new ID store or new time source.

# Time-ordered row IDs

Newly minted Waitron row IDs sort by minting millisecond to reduce writes to old database pages. Existing and supplied IDs keep their values. Use the UUIDv7 layout with UTC milliseconds at the start and a random tail. IDs from one millisecond have random ties. Browser-minted IDs carry the browser's time. [RFC 9562 §5.7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7)

**Default.** Export `newRowId()` from `packages/shared/src/ids.ts` through the barrel. Use `Date.now()` and the random tail of the platform UUID so the bench can set the clock. Point `packages/db/src/schema/columns.ts:180`'s `newId` there and keep the Drizzle defaults in db, bookings, VeriFactu, node-db, payments and workforce, with the exceptions below. The SQL generator in `packages/db/src/change-feed.ts:30` stays random. Its rows are deleted inside the transaction by `schema/change-log.ts:36`. Starting migrations need no edits. The standalone `bench/sqlite-failover/src/model.ts` runs its own synthetic ledger under native Node and retains independent random fixture IDs.

## Bench result, 24 November 2026

On a local Linux arm64 `node:26-slim` container, Node 26.13.1 reported SQLite 3.54.1, 4,096-byte pages and no STAT4. The watcher cleared this host at 18:17 after SSH to the bench server timed out. The 30-day history came from `9546a9f00fc9493f852bb65a43280e33583be39d`. Both copies traded 250 bills on 3 December 2025 with seed 1. The candidate was `7bf9b53d303c952b3a23fe4643e9ac4f97d3ca31`.

The random-ID day changed 14,075 existing pages and added 8,322. The time-ordered day changed 1,044 and added 8,352. The ratio was 7.42%, below the 25% limit. A comparison of the random-ID day against itself printed `FAIL — 14,075/14,075 old pages (100.00%), limit 25%.` Both copies ended with 7,750 sales. The candidate kept every ID from the checkpoint in sales, working orders, tenders and VeriFactu records. New VeriFactu record IDs were UUIDv4 and the other three checked tables used UUIDv7. This was a synthetic trading day.

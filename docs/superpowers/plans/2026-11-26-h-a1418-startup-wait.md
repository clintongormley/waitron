# A1418 slice 4 implementation plan — wait after an unexpected stop

After a power cut, a solo main box with backup streaming configured waits up to 60 seconds for the bucket before it sells or files. A clear answer ends the wait. A verified replacement keeps it stopped. The box page explains the wait, and managers get an email whenever it starts after silence. Restart and unconfigured storage skip the pause. [Approved design §§3, 6 and 9](../specs/2026-11-07-a1418-box-stop-intent-design.md) · [Landed replacement stop](2026-11-26-h-a1418-replacement-stop.md)

## PR A — wait on the box and email after silence

- In `boot.ts`, check after restore first-start processing and before commerce, filing or their workers. Exempt that restore boot using the phase read before processing. Use the peer check's answer about whether it counted a peer. A never-finished or demoted spare can be in the chart without making the box take the peer wait. Keep slice 3's stricter chart rule for declaring a replacement. Leave mirrors, fences and the saved replacement hold in place. The real entry points supply the prior stop: no mark waits even without a heartbeat, and a valid restart skips. Direct `startServer` calls without stop information keep their current behavior. Extract the existing waiting listener wiring to `startup-wait.ts` to stay under the `boot.ts` cap.
- In `stream-host.ts`, distinguish no settings, clear, silence and verified replacement. Use the existing stream-ID read and local signature check. A successful missing-pointer reply or a verified local pointer at or below the held term is clear. Bucket errors, unreadable configured settings and unverified pointers are silence. A missing chart supplies no basis for the solo check. A verified newer pointer uses slice 3's stop. No change to the enrolled-peer reader or trust for different identities.
- Ask once for up to five seconds before opening the waiting page. Reuse `waiting-start.ts` and `waiting-page.ts` with bucket wording in `i18n/waiting-page.ts`, no carry-on form and the current peer timing. One steady 60-second limit from the first ask bounds retries and cancels pending reads. Keep a verified replacement through the listener handoff, even when the deadline fires. If the evidence is in hand before commerce starts, stay stopped and retry the local save using slice 3's retained-evidence pattern. A later verified answer goes into the existing stepdown, with no need to read it again. Pending reads abort at shutdown and waiting listeners close before the next listener opens.
- In `stop-alert.ts`, replace an open `start.selling_unconfirmed` incident on each such start, following `recordUnexpectedStop`. The alert describes what happened, so a later clear reply leaves it in history. The existing `start.` box area covers it. Add it to `errors.ts`, Dashboard `alert-messages.ts` and `INCIDENT_EMAIL_CODES` with both languages in `box-alert-email.ts`. Update the English and Spanish `servers.md`, `docs/backlog.md` and the two startup rules and receipts in `CLAUDE.md` and `docs/developers/conventions-data.md`.
- Start with failing tests. `stream-host.test.ts` checks the bucket verdicts. `waiting-start.test.ts` checks deadline, abort and listener handoff. `boot.stop-mark.test.ts` checks who waits, no sales or filing while waiting, saved and failed-save replacement stops, and the timeout incident, including a chart that still lists a spare that never joined. `box-alert-email.test.ts` checks email wording. Re-run peer and restore boot tests. Prove a removed wait fails the boot assertion in a disposable copy. About 220–320 product lines and 190–280 test lines.

## PR B — show the reason on the till

- Until this PR, the till's existing waiting message covers PR A. Add `waitingFor: "bucket"` to `node-api.ts` only while waiting. In `server-router.ts`, track and clear that reason with the current main box's probe and include it in the state change signal. Use it in `till-lock-screen.ts`, `server-connection-notice.ts` and `i18n/strings.ts`. Keep the message choice in the notice and lock screen. Pass the router reason through the existing bindings in `till-app.ts` without raising its cap, with both `till-notices.md` guides. Start with failing tests for a reason-only change in `server-router.test.ts` and the message in `till-lock-screen.test.ts`. Verify the real waiting probe, both languages and affected file caps. About 55–90 product lines and 45–80 test lines.

Run the touched suites and the alert and guide guards. Run the fiscal and menu gates only if the change touches those files. Administrative shutdown and its startup hold, Cloud and other replacement evidence stay in their own slices.

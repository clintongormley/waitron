**Goal:** the labels a venue makes up and puts on a table (VIP, Allergy, Birthday) are gone
everywhere — the database table, the column and trigger, the till's and dashboard's routes and
codes, the till's Status section and floor chip, the dashboard screen and with it Venue settings'

**Architecture:** nothing replaces the feature (spec §2: VIP and Birthday go in the party's name;
an allergy goes through A669). Tasks are numbered in the order they run: the server (routes,
codes, floor read, the writes that cleared a label), the configuration transfer (format 4 → 5), the
till, the dashboard (its tests moved off the Tables tab first, then the tab and screen removed), and
only then the core schema — one hand-written migration drops the trigger, one generated migration
drops the table and rebuilds `dining_tables` without `status_id` — so no commit leaves a dashboard
subscription naming a table that no longer exists. Then the docs, then a look in real Chromium.

**Tech stack:** TypeScript, Drizzle on `node:sqlite`, drizzle-kit 0.31.11, Hono routes, Lit, Vitest
(browser mode for the till and dashboard).

**Spec:** `docs/superpowers/specs/2026-10-17-a757-table-states-design.md` — §2 (venue-made statuses),
§10 (the Tables tab goes), §11 item 2, and the Decided section (Q15: A, retire entirely).

## Decisions (with receipts)

1. **The migration set is core** (`packages/db`): the table is
   `packages/db/src/schema/table-service-statuses.ts:9-25`, classified in
   `packages/db/src/classification.ts:123-127`, and the column and its key are
   `packages/db/src/schema/dining-tables.ts:23` and `:35-39`. The trigger
   `parties_clear_table_status` is core's too (`packages/db/drizzle/0139_floor_retire_recreate_table_triggers.sql`).

2. **Two migrations: a custom one that drops the trigger, then a generated one.** Measured
   2026-10-19 in this worktree at `811f53619` (then reverted; `git status` clean afterwards):
   `pnpm exec drizzle-kit generate --custom --name drop_table_status_trigger` (in `packages/db`)
   wrote an empty `drizzle/0180_drop_table_status_trigger.sql`, filled with
   `DROP TRIGGER parties_clear_table_status;`. With the schema changed as Task 6 says,
   `pnpm exec drizzle-kit generate --name retire_table_service_statuses` wrote
   `drizzle/0181_retire_table_service_statuses.sql` holding, in order: ``DROP TABLE `table_service_statuses`;``,
   then the rebuild `PRAGMA foreign_keys=OFF` / `CREATE TABLE __new_dining_tables` (no `status_id`,
   keys to `floor_plan_tables`, `locations`, `floor_zones`) / `INSERT … SELECT` of the seven kept
   columns / ``DROP TABLE `dining_tables` `` / rename / `PRAGMA foreign_keys=ON` / the unique index
   `dining_tables_location_label_key`. A rebuild, because SQLite will not drop a column a foreign
   key uses. **Why the trigger goes first, in its own file:** its body updates `dining_tables`
   (`0139:5-9`), and a trigger on another table whose body names the rebuilt table fails the
   rebuild's rename (`docs/developers/conventions-data.md:1483-1496`, measured 2026-09-23); `0137`
   dropped the same trigger before `0138` rebuilt `dining_tables` for the same reason (`0137:1-2`).
   I did not run the generated rebuild without the drop first, so that order rests on that receipt,
   not on a control of mine. The numbers 0180/0181 are what drizzle-kit gave at `811f53619`; if core
   gains a migration before this lands, take the numbers drizzle-kit gives (and regenerate on a
   rebase collision, CLAUDE.md §3).

3. **What points at what.** From the latest core snapshot (`packages/db/drizzle/meta/0179_snapshot.json`,
   read 2026-10-19 with a script over every set's latest snapshot): the only key into
   `table_service_statuses` is `dining_tables.status_id` (no action). Keys into `dining_tables`, all
   `no action`: `bookings.table_id` (bookings set), `working_orders.delivery_table_id`,
   `floor_reset_tables.table_id`, `floor_today_join_tables.table_id`,
   `floor_today_split_parts.joined_table_id` and `.part_table_id`, `floor_today_tables.table_id`,
   `party_tables.table_id`. None cascades, so the rebuild's `DROP TABLE dining_tables` deletes
   nothing silently; with foreign keys on inside the migrator's transaction it **refuses** whenever
   any of those children holds a row (conventions-data.md:1499-1521). Separately, the first
   statement `DROP TABLE table_service_statuses` refuses on a venue where a table still carries a
   status (read-only reasoning from the same rule; not run).

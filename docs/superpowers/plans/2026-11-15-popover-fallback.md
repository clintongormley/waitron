# Popover fallback implementation plan

**Outcome and authority.** Existing menus, dropdowns and help bubbles work without native Popover in setup, dashboard (including public module pages) and till. The owner chose “Build the fallback” on 2026-11-15 ~13:40, recorded in Lane F `queue.md`, POPOVER-FALLBACK. Codex drafted this plan; Claude reviews it and the watcher clears the build. No owner approval of this design is claimed.

**Prerequisite run.** `node /tmp/lane-f-popover.3bEH2M/probe.mjs` exited 0: real `wt-row-actions` and `wt-help-tooltip` opened, positioned below their triggers inside 390×844 and dismissed on trusted outside clicks with OddBird 0.7.3 loaded before shadow-root creation. The control without it failed with `popup.showPopover is not a function`. Receipts: `~/waitron-campaign-f/receipts/popover-fallback-20261115/shadow-root-{receipt.md,result.json}`. Chromium retains native hiding CSS after API removal, so the probe used an open-class display shim; this proves those two simulated cases, not old Safari or every layout.

**Reuse and limits.** Reuse current components, placement, events, keyboard handling, dialog guards and npm notice generation. The polyfill patches JavaScript selector methods; keep existing open-state queries unless a test disproves compatibility. Reuse its shadow-root stylesheet injection by finishing initialization before the first mount. Exclude new controls, positioning rewrites, custom portals, unrelated web fixes, production CDNs, top-level await and Vite target changes. Native browsers keep their APIs and synchronous mount. Lane C overlap is permitted; whoever lands second resolves collisions.

1. **Shared startup, test first.** Create `packages/ui/src/popover-startup.ts` with `startWithPopover(start: () => void): void`, exported from `src/index.ts`. Detect `popover` on `HTMLElement.prototype`: call `start` immediately when present; otherwise dynamically import `@oddbird/popover-polyfill`, then start once. Add pinned 0.7.3 in `packages/ui/package.json` and regenerate `pnpm-lock.yaml`. `src/popover-startup.test.ts` owns native synchronous mounting, no polyfill load and unchanged API/selector/attachShadow descriptors.
2. **Wire the apps and styles.** Gate mounting in `apps/{setup,dashboard,till}/src/main.ts`, keeping theme/diagnostic initialization order. Each app’s new `src/main.popover.test.ts` checks only its mounting waits for fallback readiness and happens once; existing route tests retain route behavior. Join native and escaped class open selectors with forgiving `:is()`/`:where()` in `packages/ui/src/menu-popover.ts`, `apps/dashboard/src/widgets/product-appearance.ts` and `packages/venue-service/src/dashboard/paint-grid-parts.ts`. Caller tests own their grid/flex styling, not library behavior.
3. **Fallback acceptance.** Create `packages/ui/src/popover-fallback.test.ts`, `packages/ui/test/popover-fallback-setup.ts` and an isolated Chromium instance in `packages/ui/vitest.config.ts`. Remove the four APIs before initialization; retain a failing uninitialized control and only the documented Chromium display shim. Test real row-actions, help-tooltip, combobox, colour-chooser, relative-time, data-table filters and language/theme choosers: initially closed, open by trusted action, visible correct placement and outside dismissal at phone/desktop widths. Include address lookup through combobox and nested menu help. Shared tests own Escape/focus, selection and enclosing-dialog behavior, including ui-core form-actions’ open-overlay query. Preserve existing assertions.
4. **Layout and delivery.** Before completion, run pointer hit-testing in a real `wt-dialog` and scrolling/clipping container, including resize/scroll placement. The polyfill has no true native top layer: if these required cases fail, stop with the run and ask the watcher; do not add a portal system. Inspect EN/ES, light/dark, phone/desktop. Build all three apps and check their lazy chunks and `THIRD-PARTY-NOTICES.txt` include the library licence through `scripts/npm-bundle-notices.mjs`. Update `docs/developers/design-system.md` Browser support and this item in `docs/backlog.md`; change guides only if staff behavior changes.

**Focused verification.** Run new UI suites with `pnpm --filter @waitron/ui exec vitest run src/popover-startup.test.ts src/popover-fallback.test.ts`; each app’s new main suite through its package. Run affected `product-appearance.test.ts` and paint-grid caller suites, plus existing UI row-actions, help-tooltip guard, combobox, data-table filters/sorting and dialog suites. Every new behavior starts with its observed expected failure. Normal push hook, current-head scoped CI and `finish-branch` complete verification; no whole-package local run.

**Size and finish line.** One PR, within three hours of build time after watcher clearance. Estimate 100–200 production lines added, 180–300 test/support lines added; count additions/removals separately, including existing entry/style edits and generated lockfile lines. Finish only when every named family works through the simulated missing-API path, required layouts pass and the native path remains unchanged. Nothing has shipped yet.

# Count affected menus before archiving products

A manager selecting 500 products can see how many active menus the products come off. When deleting categories, the count follows the choice to keep or delete their contents, and counts a menu once even when it offers several of the affected products. Scope comes from A347's second and third bullets in `docs/backlog/menu.md` and the Lane D queue.

## Request and count

1. Change `DashboardApi.countProductMenus(productIds, categoryIds = [])` and `apps/server/src/menu-api.ts` together. POST `{ productIds, categoryIds }` to `/management-api/products/menus` and return `{ menus }`. Reuse `readJsonBody`, `idList` and the existing manager permission. The server treats this preview as a read for menu revisions, and the dashboard does not record it as a menu write. Follow the existing user-triggered routing-preview request for dashboard activity. The old GET reached the Node HTTP handler for one product (200) but failed before the handler for 500 (431, 20,030 request-target bytes).
2. In `packages/menu/src/product-items.ts`, resolve active top-level products in the selected category subtrees using `FolderTree` and the batched lookup used by `deleteProductItems`. Share that lookup with deletion. Pass their IDs plus the explicit product IDs to `menusHolding`, which already counts distinct active menus and resolves an explicitly selected variant through its parent. A request with no categories takes the current product-only path.
3. In `menu-api.test.ts`, keep the existing distinct count, zero, bad UUID and manager access assertions. Start with a failing 500-ID POST that counts offers at both ends of the selection, a mixed selection that reaches the same menu via two products in different places, and a count that leaves the menu revision alone. In `apps/dashboard/src/api/client-routes.test.ts`, pin the exact body and that the count preserves the client's last menu write revision.

# A841 slice 13 — the Themes card and the name dialog: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every implementer is dispatched as `subagent_type: "implementer"`; one that passes about 150 tool calls with its task unfinished stops at a passing (or cleanly red) point, commits, and returns a handover.

**Goal:** Settings → Appearance gains a Themes card listing Waitron's theme and the venue's own, which one is in use, and a row menu on each; a manager can make a new theme, edit any theme (the one in use, Waitron's while it is in use, or one not in use), save a draft as a new theme, make a copy, rename, delete, and put any theme in use on every screen — each confirmed by its dialog — while a supervisor sees the same list read-only.

**Architecture:** Two new server routes (`PATCH` and `DELETE /management-api/themes/:id`) over two new store functions in `@waitron/layouts`; copy and switch use the routes slice 2 already landed. In the dashboard, a new `dashboard-themes-card` sits under the Look card on the Appearance page and owns the Rename, Make a copy, Use on every screen and Delete dialogs; the Look card's editor learns three ways in (the theme in use, Waitron's theme while it is in use, and New theme or a row's Edit), and a shared `dashboard-theme-name-dialog` names a theme for Save as new theme…, Make a copy, Rename and the first save from Waitron's theme. The page keeps the one passive live read of `listThemes` it already has and applies its own writes to it at once.

**Tech Stack:** Hono and `@waitron/layouts` over `node:sqlite` (`apps/server`, `packages/layouts`, Vitest with a real `useVenueDb`); Lit 3 in `apps/dashboard` (Vitest 4.1.11 browser mode, real headless Chromium); `@waitron/ui` primitives (`wt-data-table`, `wt-row-actions`, `wt-dialog`, `wt-delete-dialog`, `wt-input`, `wt-switch`); Markdown user guides served by `apps/server`.

**Spec:** `docs/superpowers/specs/2026-10-19-a841-theme-editor-design.md` — section 16 item 13 (line 2620) is the scope; section 4 (the product-text table, lines 589-654), 8b (lines 1727-1828), 10 (lines 2039-2040), 11 (routes, lines 2134-2142; error codes, 2143-2158), 12 (lines 2255-2261), 13 (lines 2305-2310), 15 (lines 2467-2469 and 2470-2480) and 18 (pictures 31, 32, 33) are the detail. Executors read both. The slice 5 plan (`docs/superpowers/plans/2026-10-21-a841-5-theme-editor.md`) is the code this slice extends; its D1 and D2 are what this slice closes.

## Decisions this plan makes (the design left them open)

**D1. Which routes.** The design names them (section 11, lines 2134-2139), so this plan follows it
rather than choosing:
- **Make a copy is the existing create route**: "`POST /management-api/themes` creates one (New
  theme's first save, Save as new theme, Make a copy)". The browser sends the source theme's stored
  `choices` as `theme`, the name from the name dialog, and `inUse` from its switch
  (`apps/server/src/themes-api.ts:97-112` already takes all three). No copy route.
- **Rename is its own route**, `PATCH /management-api/themes/{id}` with `{ name }`, not a field of
  save: `PUT …/{id}` takes `{ theme }` only (`themes-api.ts:114-124`).
- **Delete** is `DELETE /management-api/themes/{id}`. It answers `200 { inUse: string | null }`,
  which theme is in use after the delete, read inside the same transaction, so the screen knows
  whether to repaint without trusting its own copy of the list (D3).
- Both new routes follow `PUT …/{id}`'s shape exactly: the body is read first
  (`management.request_invalid` naming `name` for a missing or non-string name, by `requireString`,
  `packages/server-kit/src/request-screens.ts:55-58`), then one `withTransaction` holding the
  `layout.configure` check, the id check (`theme.not_found` for an unknown or malformed id,
  `requireTheme`, `packages/layouts/src/theme-store.ts:49-58`), the name check (`parseThemeName`,
  `packages/layouts/src/theme-input.ts:12-16`) and the write. The answer is worked out after the
  transaction (`themeAnswerOf`, `themes-api.ts:49-57`).

**D2. No new error code.** Every refusal slice 13 needs already exists and is registered in
`packages/layouts/src/errors.ts:46-48`: `theme.invalid` with `field: "name"` and `reason` `empty`,
`too_long` or `reserved`; `theme.name_taken` with `field: "name"`; `theme.not_found`. Siblings
grepped (`git grep -n '"theme\.' -- apps packages`): no other `theme.*` code exists. What is new is
their screen wording (D13).

**D3. Deleting the theme in use, and a delete racing a switch.** `deleteCustomTheme` deletes the row
in one transaction. Deleting the row that holds `in_use = 1` leaves no row holding it, which *is*
"Waitron's theme in use" (`readThemeInUse` answers `null`, `theme-store.ts:90-96`; `/api/theme`
then answers `WAITRON_THEME_ANSWER`, `apps/server/src/venue-theme.ts:15-19,28-29`, and the till's
`themeHash` is that answer's hash, `apps/server/src/till-setup.ts:127`). Probe
`rename-delete.mjs` ran it on the real table's DDL: deleting the theme in use left no row in use.
Nothing else points at `custom_themes` (design line 2074), so the delete removes no other row.
A delete and a switch run in two transactions and the store's one write queue orders them; whichever
commits second sees the first's result. If a switch to theme X commits after this browser drew X's
delete dialog without the in-use sentence and before its delete is sent, the delete still deletes X
and Waitron's theme goes in use. That is the design's chosen behaviour for deleting the theme in use
(lines 1801-1805), reached here without the sentence having been shown; the DELETE's answer
(`inUse: null`) makes this dashboard repaint, and the live list shows Waitron's theme in use.
**Lane A ruled (2026-10-22) to accept this**: the delete wins, no row is left in use, Waitron's theme
is in use, and no new code or sentence is added. The delete dialog reads the live list, so a switch
that arrives while the dialog is open redraws it with the in-use sentence (D12).

**D4. Who sees what** (design section 13, lines 2305-2310). A supervisor (`venue.view`, not
`layout.configure`) sees the Themes card with its rows, colours and tags, **no New theme and no row
menus at all** — every item a row menu offers (Use on every screen, Edit, Rename, Make a copy,
Delete) changes something — so the table has no `actions` column for them. The Look card's Edit
follows the same `canEdit` (now also while Waitron's theme is in use, D6). **A person who loses
`layout.configure` while a dialog is open:** when the shell's `canEdit` turns false (it is
re-read with the session, `apps/dashboard/src/dashboard-app.ts:1180-1182,2540-2544`), every open
Themes-card dialog (name, switch, delete) and the Look card's name dialog close without a write, the
editor closes without a write as it already does (`apps/dashboard/src/screens/look-card.ts:236`), and
New theme and the actions column go. When the browser has not yet learned it, the server refuses
with `authorization.not_permitted` and the dialog shows that code's sentence
(`apps/dashboard/src/i18n/codes.ts:406`) at its bottom, its action still enabled.

**D5. Live updates.** Confirmed: the page already follows `listThemes` through one passive live
read whose dependency is `custom_themes` (`apps/dashboard/src/screens/appearance-screen.ts:53-79`,
`apps/dashboard/src/api/live-queries.ts:98`), and every write of this slice changes `custom_themes`,
so another dashboard's rename, copy, delete or switch reaches this card with no new subscription.
This dashboard's own writes are applied to the page's list at once and counted as writes, so a read
sent before the write cannot undo it — the guard `#saved` already uses (`appearance-screen.ts:68-88`).
Task 5 generalises `#saved` to every write (`ThemesChanged`, Task 5's interface).

**D6. The editor's three ways in, and what each heads and says.** The Look card's editor
(`look-card.ts:452-554`) edits one of:
- **a stored theme** (Look card Edit while a custom theme is in use, or a row's Edit): headed
  "Look" while it is the theme in use, and "Edit theme: {name}" (design line 1759) otherwise; Save
  stores into it with `PUT` as today.
- **Waitron's theme while it is in use** (Look card Edit while `inUse` is `null`; design lines
  1765-1768): opens on `WAITRON_CHOICES`, headed "Look", line "Theme in use: Waitron. Saving changes
  every screen." (the existing `appearance.editing_in_use` with `BUILT_IN_THEME_NAME`); Save opens
  the name dialog with the switch on.
- **a new theme** (the Themes card's New theme; line 1768-1769): opens on `WAITRON_CHOICES`, headed
  "New theme" (the button's own words; the design gives no heading for an unnamed theme), line "Not
  in use. Saving changes no screen until you use it."; Save opens the name dialog with the switch
  off.

The line follows the latest read as slice 5's D7 does: for Waitron's-in-use it says "in use" while
`list.inUse === null`. Save stays quiet and disabled until the draft changes in all three (the house
rule; a copy of Waitron's look unchanged is what Make a copy on Waitron's row is for). The editor
opens in the Look card's place, whichever way it was opened; opened from the Themes card, the card
scrolls into view (`scrollIntoView({ block: "start" })`), since the row that opened it can sit below
the fold. Focus is not moved: the design asks for no focus change, and `settingsCard`
(`apps/dashboard/src/widgets/settings-card.ts:63-83`) has no way to make its heading focusable, so
lane A's ruling drops the move rather than change a helper other cards share. A row's Edit while the
editor already holds a changed draft asks through the editor's leave coordinator first (reason
`"cancel"`, as `#requestCancel` does, `look-card.ts:296-310`); Edit on the theme already being
edited only scrolls.

**D7. Save as new theme… and the first save ask "Hard to read" first.** The design says the Save
dialog comes first when a warning is unfixed (section 10, line 2020) and is silent for Save as new
theme…; with its switch on, Save as new theme… puts a theme in use on every screen, which only the
owner's Save anyway may do with an unfixed warning (anti-goals, lines 103-109: "Only the owner's 'Save anyway' puts it on the tills"). So both the first
save from Waitron's theme / New theme and Save as new theme… run the same path as Save: with a
warning, the Hard to read dialog opens; Save anyway goes on with the draft as it is and Fix and save
with `fixAll`'s draft (kept in the editor if the name dialog is then dismissed, as slice 5 keeps a
refused Fix and save's fix); then the name dialog opens. Without a warning, the name dialog opens at
once. Back in either dialog returns to the editor with the draft.

**D8. "Save as new theme…" is drawn only while editing a stored theme**, in the `secondary` slot
before Cancel (picture 02), `variant="secondary"`, never quiet-and-disabled for an unchanged draft
(design lines 1790-1792), disabled only while a request is being sent or a colour code fails its
check (the forms rule, CLAUDE.md §3). For Waitron's-in-use and New
theme it is not drawn: Save itself opens the same name dialog there, so a second button would do the
same thing. Its name dialog opens with "{name} (copy)" from the edited theme's latest name, switch
on exactly when the edited theme is in use when the dialog opens (lines 1762-1765).

**D9. After a save that creates a theme, the editor closes.** The draft now lives in the new theme
(Save as new theme… leaves the edited theme as it was saved, line 1763). The page applies the
created theme to its list (D5), and when the name dialog's switch was on, this dashboard repaints at
once through the same read slice 5 uses (`look-card.ts:265-271`, moved to a shared helper in Task 2).

**D10. The name dialog.** One element, `dashboard-theme-name-dialog`, used by the Look card (Save as
new theme…, first save) and the Themes card (Rename, Make a copy):
- Fields: Name (`wt-input name="name" required`), and the switch "Use it on every screen now"
  (`wt-switch name="inUse"`) for every kind **but Rename** — the design's table lists one dialog for
  all four (line 650), and 8b says "Rename, Make a copy and Delete change no screen" (lines 1798-1799), so a
  Rename that could switch would contradict it. Flagged as a departure. Buttons Back and Save
  (picture 33).
- Opening: Rename with the current name and Save quiet until it changes; first save with the field
  empty and Save quiet and disabled until a name is typed; **Make a copy and Save as new theme…
  open already savable** with the proposal (design lines 1786-1792, stated there as the exception;
  the house rule allows it, `docs/developers/design-system.md:2479-2480`, "enabled at once if it
  opens already savable"), through the existing option
  `saveActionState(scope, { savableAtOpen: true })` (`packages/ui/src/leave-controller.ts:141-147`;
  used the same way at `apps/dashboard/src/screens/floor-plan-add-tables.ts:240` and
  `printers-screen.ts:3737`). The draft scope's baseline is what the dialog opened with, so Back on
  an untouched dialog asks nothing; the "unchanged" early return in Save is
  `saveActionState(scope, { savableAtOpen }).unchanged`, so it holds only for Rename and the first
  save.
- **Hard to read, while the switch is on.** The dialog takes `warningLines: string[]`, and while the
  switch is on and the list is not empty it shows "Hard to read:" over one list item per line —
  the switch dialog's own heading and wording (D16, design line 1796), so a theme put in use from the
  name dialog lists its warnings exactly as a switch would. Make a copy passes the source theme's
  server warnings, worded by `saveDialogLine`; Save as new theme… and the first save pass the
  draft's warnings as they stand when the dialog opens (after Save anyway, the warnings the manager
  chose to keep; after Fix and save, none). The design keeps the switch in the copy's dialog (line
  650, picture 33), so the list is added rather than the switch dropped. Like the switch dialog, it
  lists and never refuses.
- Checks, in the browser, after the first press of Save (house rule, `design-system.md:2436-2437`):
  `checkThemeName` (`packages/ui-core/src/theme/names.ts:15-24`) → "Enter a name." / "Use 60
  characters or fewer." / "\"Waitron\" is the built-in theme's name. Pick another." under the
  field, "Correct the highlighted fields to continue." (`form.fix_fields`) at the bottom, Save
  disabled until fixed.
- Refusals: `theme.name_taken` and `theme.invalid` with `field: "name"` put the matching sentence
  under the field (by `reason`; `name_taken` → "A theme with this name already exists.") with
  `form.fix_fields` at the bottom, Save still enabled (`design-system.md:2462-2476`); every other
  refusal goes in the bottom message through `codeMessage`, Save enabled.
- Its draft is `{ name: string; inUse: boolean }`, compared by the trimmed name and the switch.

**D11. The copy proposal.** "{name} (copy)" / "{name} (copia)" (`appearance.copy_name`), the name
shortened, in NFC code points, until the whole fits 60 (design line 1787; `checkThemeName` counts
the same way, `names.ts:14-19`), with spaces left at the cut trimmed. Probe `copy-name.mts` ran this
over a 60-character name, 53 and 54 characters, 60 decomposed accents, 60 emoji, a space at the cut
and "Waitron", in both templates: every proposal was at most 60 and passed `checkThemeName`; the
control, the 60-character name with " (copy)" and no shortening, was 67 and refused `too_long`.
A proposal that another theme already holds (copying the same theme twice) is not checked in the
browser: the server refuses it as `theme.name_taken` under the field and the manager edits it
(Review Focus 2).

**D12. The delete dialog is the shared `wt-delete-dialog`** (design line 1801), handed a
`DeleteImpact` the Themes card builds from its live list rather than read from a new impact route:
`{ target: { id, name }, refusals: [], ends: inUse ? [{ key: "theme_in_use", count: 1, targets:
[{ id, name }] }] : [], removes: [] }`. A delete of a theme ends nothing else and removes nothing
else (D3), so the list is all the impact there is, and it is live (D5). The copy's `item` writes
"{name} is in use on every screen. Deleting it puts Waitron's theme on every screen." (line 654)
under a group heading "What changes", and the dialog's heading is "Delete theme?" — both new text,
flagged. `refusals`, `irreversible`, `retry` and `loading` reuse the printer copy's words as the
course copy does (`apps/dashboard/src/widgets/course-delete-copy.ts:6-16`). A refused delete goes in
`actionError` with Delete still usable.

**D13. Wording for the codes** in `apps/dashboard/src/i18n/codes.ts` (both columns, as its header
asks, `:4`): `theme.name_taken` "A theme with this name already exists." (design line 651) / "Ya
existe un tema con este nombre."; `theme.not_found` "This theme no longer exists." / "Este tema ya
no existe." (new text, flagged). `theme.invalid` keeps the generic sentence outside the name dialog
(slice 5's D20).

**D14. The Themes card's rows and columns** (design lines 1749-1756; pictures 31, 32):
- Rows: Waitron's first, then the venue's themes in the server's order (by name key,
  `theme-store.ts:78`); a theme this dashboard creates or renames is placed by `themeNameKey`
  (`names.ts:5-6`) until the next read.
- Columns: `name` ("Name": the name, plus a "built in" tag on Waitron's row), `colours` ("Colours":
  three chips — the brand colour, the light page, the dark page. The brand chip is the theme's
  chosen brand colour, `choices.brandColor`, as §8b's words say ("brand colour", line 1750) and as
  the Look card's own Brand colour row does (`look-card.ts:72-86`), not the worked-out button
  colour `light["--wt-color-primary"]`, which is the fixed shade when a light fix was taken.
  Picture 31 cannot tell the two apart: its themes took dark fixes only, so their light button
  colour is their brand colour. The pages come from the row's own `light` and `dark`
  `--wt-color-bg`. A `null` brand colour, and Waitron's row, take `WAITRON_DEFAULTS`' light
  `--wt-color-primary` and pages, and a theme whose `choices` is `null` shows Waitron's three,
  which is what the screens show for it, slice 2's D7),
  `status` (the "In use" tag and the "{n} hard to read" tag with the warning icon; the picture draws
  this column with no heading, but a column needs a label, so it reads "Status" — flagged) and, for
  `canEdit` only, `actions` (`pinned: "end"`, `scripts/pinned-actions-column.test.ts`).
- **At phone width the colours column is left out** (picture 32), at the dashboard's existing
  phone breakpoint: the card drops the column while `matchMedia("(max-width: 48rem)")` matches,
  repeating `DRAWER_BREAKPOINT`'s literal (`apps/dashboard/src/dashboard-app.ts:161`, read the same
  way at `:1028`) as `settings-card.ts:43` repeats it in CSS, and listening for its `change`. Below
  that width the side menu is a drawer and the card has the window's width less the page's
  padding. Whether the four columns fit between 48rem and a desk window with the side menu open is
  not measured here; Task 10 measures it (provisional until then).
- Tags and chips are markup handed to `wt-data-table` as cells, so they are styled with
  `part=`/`::part()`, never a class (CLAUDE.md §3).
- Row menus: a custom theme offers Use on every screen (not while it is in use), Edit, Rename, Make
  a copy, Delete (not while the Look card's editor is open on it, D19); Waitron's offers Use on every
  screen (not while it is in use) and Make a copy (lines 1754-1756). Every item is
  `align="start" variant="ghost"` except Delete, `variant="danger"`, as picture 31 draws it and as
  `apps/dashboard/src/screens/modifiers-screen.ts:470-474` already does inside `wt-row-actions`.

**D15. Make a copy of Waitron's theme, or of a theme this release cannot read** (`choices: null`)
sends `WAITRON_CHOICES`: that is the look the screens show for both (slice 2's D7). Its proposal is
"Waitron (copy)", which `checkThemeName` accepts (probe `copy-name.mts`).

**D16. The switch dialog** (lines 1793-1799, 652; picture 33): `dashboard-theme-switch-dialog`
wrapping `wt-dialog`, heading "Use {name} on every screen?", the line "Every dashboard changes now,
and every signed-in till within 15 seconds.", and, when the theme has server warnings, "Hard to
read:" over one list item per warning worded by slice 5's `saveDialogLine`
(`apps/dashboard/src/widgets/theme-words.ts:35-52`, the Save dialog's wording, as line 1796 asks);
Back and Use it. It sends `PUT /management-api/theme-in-use` (`themes-api.ts:126-136`) with the
row's id, or `null` for Waitron's. A refusal shows at the dialog's bottom and Use it stays enabled;
a double press sends once. "Text on the tills changes size too." is slice 10's: a theme has no text
size until then (`ThemeChoices`, `packages/ui-core/src/theme/theme.ts:11-18`), so the line is not
drawn (departure). The till sentence is the design's word for word; the backlog entry "A cash
register on the floor plan with no counter zone misses a theme change" records that one kind of till
does not meet it today (`docs/backlog.md:3295-3303`), and this plan does not reword product text the
owner approved — flagged for the driver.

**D17. The image library's "Logo of theme {name}" moves to slice 8.** Section 16 lists the wording
in item 13 and again in item 8 (line 2581). It labels an `ImageUsage` of kind `theme_logo`,
which slice 7 adds (`packages/media/src/images.ts:53-101` has no such kind today), and nothing in
slice 13 stores a logo. Building it now would be a dead string; slice 8 builds it with the use.
Departure.

**D18. One repaint helper.** The Look card's `#repaint` (`look-card.ts:265-271`) becomes
`repaintVenueTheme(api: DashboardApi): void` in `apps/dashboard/src/widgets/venue-theme-repaint.ts`,
called after every write that can change what `/api/theme` answers: a save of the theme in use (as
today), a create with `inUse: true`, a switch, and a delete whose answer's `inUse` differs from the
list's `inUse` before it.

**D19. When this page changes the theme its own editor has open** (lane A ruling 2026-10-22). The
design says nothing about it: §8b is silent, and its nearest words, in §11, are that themes are
"each renamed, deleted and edited on its own" (line 2047) and "two managers editing two different
themes do not overwrite each other" (line 2048). So the most conservative shape that never loses a draft silently:
- **Delete**: while the Look card's editor is open on a stored theme, that theme's row offers no
  Delete. The page passes the edited id to the Themes card (`editingId`, from a `look-editing`
  event the Look card sends when its editor opens and closes).
- **Rename** (from this page or another dashboard): the editor's heading follows the live list's
  name — `#form` already reads the name from the list first (`look-card.ts:455`).
- **Switch** (from this page or another dashboard): the draft and the editor stay as they are; only
  the heading and the line follow the read (slice 5's D7, and D6 here), since editing a theme not in
  use is allowed.
- **Delete from another dashboard** keeps slice 5's behaviour: the draft is kept, the line says "Not
  in use…", and Save answers `theme.not_found` at the bottom with Save enabled (the case "a theme
  deleted elsewhere keeps the draft", `apps/dashboard/src/screens/look-card.test.ts:507-521`; the
  draft is kept because `#adopt` returns when the theme is missing, `look-card.ts:253-264`). The
  heading keeps the last name it read (`look-card.ts:455` falls back to the name the editor opened
  with); Save as new theme… is the way to keep the draft.

## Global Constraints

- Coverage `98/98/98/95` in `apps/dashboard`, `apps/server` and `packages/layouts` (CLAUDE.md §2);
  never an exclude or ignore comment over reachable code. None of the three is mutation-tested.
- No migration and no schema change (design section 16: only slice 2 migrates). An implementer who
  finds one needed stops and reports.
- General code is English only; Spanish goes only in `apps/dashboard/src/i18n/strings.ts` (the `es`
  block, from `:3104`), the `es` column of `apps/dashboard/src/i18n/codes.ts`, and
  `apps/server/src/guide/es/appearance.md`.
- Product text is the design's table (lines 589-654) and section 8b word for word; new text is only
  what this plan lists as flagged.
- Every colour, spacing, radius and font reads a `--wt-*` token; text in the brand colour reads
  `--wt-color-primary-text`; the only literal colours are data painted into a chip's `style`, as the
  Look card's `chip()` does (`look-card.ts:68-70`). Markup handed to `wt-data-table` as a cell is
  styled with `part=`/`::part()`.
- Forms follow `draftScopeFor` / `saveActionState` with the early return (CLAUDE.md §3), the bottom
  correction message, and refusals that never disable the action.

# A1308 slice 2: the shared activity log — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the one shared, append-only history table `activity_log` with one typed writer and two
people-facing readers, and move the two write-only membership audit tables into it.

**Architecture:** The table lives in core's migration set in `venue.db`, classified `ledger` and
append-only. A registry in `packages/db/src/activity-kinds.ts` declares every kind ("what happened",
such as `membership.node_removed`), its subject kind and its data's TypeScript type, so a call with
the wrong data does not compile. Inserts belong in `recordActivity` alone;
`scripts/write-path-tables.test.ts` keeps them in its file, and is weaker than that sentence: it
reads text, judges files rather than call chains, and skips tests, `testing/` folders and
`apps/<app>/scripts`. `readActivityForSubject` and `readActivityForPerson` are the readers, for
screens and the personal-data download.

**Tech Stack:** TypeScript, drizzle-orm on `node:sqlite`, Vitest.

**Spec:** [`docs/superpowers/specs/2026-11-02-rationalisation/README.md`](../specs/2026-11-02-rationalisation/README.md)
§3 R2 and "Shared tables", §5 U11 "`activity_log` scope"; appendix
[`tables-venuebox.md`](../specs/2026-11-02-rationalisation/tables-venuebox.md) §3 and §4 (the two
membership kinds) and §5 (their protections). Every slice follows
[the slice rules](2026-11-08-a1308-slice-rules.md); this plan cites them as "rules §n" and does not
repeat them.

**Base:** `main` after slice 1a has landed (it provides
`pnpm --filter @waitron/server migration-baseline rebuild --set <name>`). Line numbers below were
read at `a086eedfb7` (main `d908a5b8d4` plus two docs commits); slice 1a regenerates core's starting
migration, so only the cites into `drizzle/` may have moved. A cite in any other file that no longer

**Owner lands:** no. Read, not run: the slice changes no `sales` row, invoice number,

## Global Constraints

- Rules §1–§9 of [the slice rules](2026-11-08-a1308-slice-rules.md) apply in full.

- Every write goes through `recordActivity(tx, …)` inside the caller's transaction (CLAUDE.md §3,

```ts
/** Each kind's data. Keys are camelCase. Rules in the file header (below) apply to every entry. */
export interface ActivityKindData {
  /** Second box. Who removed a never-joined standby from the membership chart, at which term. */
  readonly "membership.node_removed": { readonly contactUrl: string; readonly term: number };
  /** Second box. Who cleared a removed machine from the chart, freeing its place, at which term. */
  readonly "membership.node_cleared": { readonly term: number };
}
export type ActivityKind = keyof ActivityKindData;

export interface ActivityKindRule {
  /** What `subject_id` names for this kind; fixed per kind, so a caller never passes it. */
  readonly subject: string;
}
export const ACTIVITY_KINDS = {
  "membership.node_removed": { subject: "node" },
  "membership.node_cleared": { subject: "node" },
} as const satisfies Record<ActivityKind, ActivityKindRule>;

export type ActivitySubjectKind = (typeof ACTIVITY_KINDS)[ActivityKind]["subject"];
```

```ts
export interface ActivityInput<K extends ActivityKind> {
  readonly kind: K;
  readonly subjectId: string;
  /** The person who did it: the signed-in person whose request this is. Null only when no person acted. */
  readonly personId: string | null;
  /** The device the request came from, when there was one. Defaults to null. */
  readonly deviceId?: string | null;
  readonly data: ActivityKindData[K];
  /** Defaults to the server clock's now. */
  readonly at?: Date;
}
export interface RecordedActivity { readonly id: string; readonly at: Date }

/** The only writer. Inserts one row in the caller's transaction; writes no log line. */
export function recordActivity<K extends ActivityKind>(
  tx: Transaction,
  entry: ActivityInput<K>,
): Promise<RecordedActivity>;

export type ActivityEntry = {
  [K in ActivityKind]: {
    readonly id: string;
    readonly at: Date;
    readonly kind: K;
    readonly subjectKind: string;
    readonly subjectId: string;
    readonly personId: string | null;
    /** `persons.display_name` read now, so an anonymised person shows as anonymised. */
    readonly personName: string | null;

}[ActivityKind];
```

**The rules the registry's file header states, for every kind:**

1. `data` never holds a person's name, email, telephone or tax number, nor a guest's health details.
   A person appears only as an id: `person_id` (who did it), the subject (`subject_kind = 'person'`),
   or a field listed in `personFields` (devices slice). Why: A980 erases a person by anonymising
   their `persons` row; a name copied into an append-only row could never be erased, and the
   readers return `personName` and `subjectPersonName` from `persons` at read time instead.
2. A kind's data shape never changes in a way an older row cannot satisfy: rows are never rewritten.
   Add an optional field, or a new kind.
3. Ids inside `data` carry no database key and may name a row that has since gone; nothing decides
   from them.
4. A per-kind rule (such as "a count only") is stated in that kind's comment in `ActivityKindData`.

**What "never decides from it" allows.** A people-facing screen may enrich entries by id with its
own read of other tables: the orders slice's `readReprints`, for example, joins `print_jobs` on
`data.printJobId` for the printer's name and keeps only receipt copies
(`apps/server/src/orders-list.ts:1103-1118` today). The rule forbids product DECISIONS from
`activity_log` (refusing, allowing, counting towards a limit, choosing what to do next), not joins
for display.

**Two deliberate overrides of the appendices**, so later slices do not relitigate them:

- `data` keys are camelCase (`authorizedBy`, `printJobId`), where the appendices wrote
  `authorized_by` and `print_job_id` (`tables-devices.md` §3, `tables-ordersales.md` §3).
- `data` names people only by id, never by name, where `tables-devices.md` §3 (at line 512) says
  "`data` carries names, not ids". Reason: A980 erasure anonymises a `persons` row, and an
  append-only copy of a name could never be erased. Names of things (a role, a profile, a menu)
  may still go in `data`.

**For A1002's second cut** (its design §7, "Integration defaults": "write the activity entry and
queue row in the role-change transaction"; "`dedupe_key = role-membership:<activity-entry-id>`";
plan Task 3: "Membership events identify actor and affected person explicitly; subject is the
affected person"): `recordActivity` takes the role change's `tx`, returns the entry's `id`, records
the actor as `personId`, returns the affected person's name as `subjectPersonName`, and A1002 declares `role.member_added`/`role.member_removed` with
`subject: "person"` and its lifecycle and permission kinds with `subject: "role"`, with the role
labels in `data` (labels are not personal data).

**Decided, open to the owner:**

- *No guard on who calls the readers.* A text scan cannot tell a screen's read from a decision, and
  the owner wants this simple. The CLAUDE.md line says "nothing guards the readers' callers"; review
  holds the rule.
- *`device_id` has a key to `devices`, refusing deletion.* Devices are never deleted, only marked
  (`apps/server/src/device-delete.ts:208-218` sets `deleted_at`), and `drawer_opens.device_id`
  already holds such a key (`packages/db/drizzle/0000_baseline.sql:917` at the cite commit).
  Reasoning, not run: a `set null` key would blank the id with an update, which the append-only
  trigger would refuse, so the device's delete would fail.
- *No CHECK on `kind`, `subject_kind` or `data`.* One shape serves every kind
  (`tables-devices.md` §5, the `drawer_opens` row). Once a venue is live, a CHECK listing kinds
  would mean a table rebuild for each new kind; during A1308 each slice regenerates the starting
  migration anyway, so the cost is a post-go-live one, but the decision stands so the table never
  needs one. The typed writer, kept in its file by the write-path guard, is the refusal.

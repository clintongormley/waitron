# A1557 Back up now implementation plan

> Implement inline with test-driven development under the watcher's 20:27 clearance on 20 November, following Claude's review.

A manager can press **Back up now** on the primary box's **Backups** screen once scheduled backups are on. Live status shows which kind of backup is running and when it started. The existing destination rows show what was stored and any upload or retention error. An early stop shows the sweep's existing stop code. The owner asked “i don't see the option to backup now” on 20 November during the A1549 rehearsal, recorded in Lane D's queue under A1557.

## Run the same backup

- [ ] Start in `apps/server/src/backup-supervisor.test.ts`. Hold a backup at a destination with the existing fixtures and prove a manual and a scheduled run cannot overlap in either order. Check that a due run retries without changing the saved schedule, and reload drains a manual run before closing its handles. Run `pnpm --filter @waitron/server exec vitest run src/backup-supervisor.test.ts` for the failing cases and again after the change.
- [ ] In `backup-sweep.ts` and `backup-supervisor.ts`, send the due and manual paths through one supervised call to `runOnce` using the loaded destinations and existing staging, retention and result callbacks. Check and take the shared slot synchronously and hold it through Cloud delivery. The slot only admits or refuses. The staging turn remains the only queue. Keep deadline-only passes outside that slot. A due run that meets a manual run retries through the existing retry timing. The running process keeps its calculated deadline. At restart, Cloud still resumes from its most recent stored copy. Reload or stop aborts and drains both the pass and the backup before closing resources.
- [ ] Publish start and finish through `backup_status` along with the existing destination updates. Expose the active run kind and start time and the existing `runStopped` code in `status()`. Keep the existing destination rows as the record of outcomes. A manual failure leaves the saved settings in place.

## Start it and show it

- [ ] In `backup-api.route.test.ts`, prove that `POST /api/backup/run-now` returns 202 while an admitted run is still held. Send two requests together and assert that the other returns 409 with `backup.run_in_progress`. Check that refused requests start no backup. Require `system.manage`, fresh management sign-in like the other archive writes, and the live primary role. In `backup-api.ts` finish authorization before admitting the run. Map `backup.run_in_progress`, `backup.not_enabled`, `backup.not_primary` and `backup.reload_in_progress` to 409. Register the first two in server `errors.ts`. Run `pnpm --filter @waitron/server exec vitest run src/backup-api.route.test.ts` before and after.
- [ ] In `apps/dashboard/src/screens/backup-screen.test.ts`, prove that an authorised manager with backups on can press once, sees an active run from live status, and sees the partial result on a later read. Check the action is unavailable when backups are off or a run is active, and that a busy reply explains why. Run `pnpm --filter @waitron/dashboard exec vitest run src/screens/backup-screen.test.ts` before and after.
- [ ] In `apps/dashboard/src/api/client.ts` add the POST and live status fields. In `backup-screen.ts` use the existing secondary button, status region and destination rows, guarding repeat presses while the POST is pending. Add EN/ES action and outcome text in `i18n/strings.ts` and refusal text in `i18n/codes.ts` and `codes.test.ts`. Update `apps/server/src/guide/{en,es}/backup-recovery.md` to say where to start a run and that its copies count toward the saved retention limit. Look at the card in both languages and themes at phone and desktop widths.

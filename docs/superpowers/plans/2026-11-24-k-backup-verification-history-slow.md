# Keep fiscal backup-history fixture edits fast on slow disks

The history tests should leave time for the rest of fiscal shard 2 to run within the existing deadline. The watcher assigned `BACKUP-VERIFICATION-HISTORY-SLOW` in Lane K's queue on 24 November at 06:49.

All five cases that only read the fixture copies finished in 0.45–1.19 s in both 14 November logs. The 24 November log prints two of those case times, 0.39 s and 0.87 s. Many cases that edit the copies took several seconds each. The key-only PDF case failed on 14 November and passed on 24 November. [First 14 November job](https://github.com/clintongormley/waitron/actions/runs/43548232659/job/132304715811), [second 14 November job](https://github.com/clintongormley/waitron/actions/runs/43604245865/job/132475525462), [24 November job](https://github.com/clintongormley/waitron/actions/runs/45330023321/job/138229178179).

In Linux with Node 26.13.1 and SQLite 3.54.1, the 107-case file ran 53,587 separate trigger drops and creates over 200 fixture edits, each copy using WAL mode and full disk synchronization. Adding 2 ms before real disk flushes on the copies moved test time from 53.51 s to 247.57 s. Trigger statements account for 183 s of the 194 s increase. An extra 4.7–5.4 ms per trigger statement would account for 250–290 s across the full file. For the four-case sample without the delay shim, test time was 0.72 s unloaded, 3.57 s with synchronous disk writes and 1.64 s with two CPU load processes in the same two-CPU container. The CI logs lack disk timings, so the exact conditions on those runners remain unverified.

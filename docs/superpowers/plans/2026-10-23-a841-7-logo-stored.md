# A841 slice 7 — the logo, stored and served: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A theme's document can name a venue logo — a library image, and optionally a second one for
dark screens — which the server checks on every save and import, the image library counts as a use
and refuses to delete, `/api/theme` serves as image addresses whose changes move its hash (and so the
till's `themeHash` and the dashboard's live read), and whose light image is drawn into receipt dots
(`printedLogo`) on save and on every library edit — stored, though nothing prints them until slice 9.

**Architecture:** `@waitron/ui-core/theme` learns the document's `logo` and checks its shape;
`@waitron/layouts` stores `printedLogo` beside the choices in the same JSON column, never hands it
back as a choice, requires it beside a logo, and checks both on import; `@waitron/media` counts a
theme's logo in both usage counters and redraws `printedLogo` inside a library edit's transaction;
`apps/server` checks the images, draws the dots between a read transaction and the write
transaction (the department receipt route's pattern), and adds the logo's addresses to `/api/theme`
and the till's start read. No screen changes, no migration.

**Tech Stack:** TypeScript, Hono, drizzle-orm on `node:sqlite`, sharp (through `@waitron/media`),
Vitest 4.1.x (`apps/dashboard` and `packages/media/src/dashboard` in real headless Chromium).

**Spec:** `docs/superpowers/specs/2026-10-19-a841-theme-editor-design.md` — section 16 item 7
(lines 2571-2577) is the scope; section 8a (lines 1406-1726, especially 1423, 1545-1551, 1587-1598,
1636-1648, 1702-1708), section 11 (lines 2046-2177, especially 2105, 2133-2136, 2153-2157 and the
configuration-copy paragraph), section 12 (lines 2178-2274, especially 2186-2203, 2249-2256),
section 13, section 14 (the logo paragraph) and section 15 (lines 2422-2453) are the detail. The
slice 2 plan (`docs/superpowers/plans/2026-10-21-a841-2-stored-themes.md`, its D11 and Task 10) and
slice 3 plan (`2026-10-21-a841-3-theme-delivery.md`) describe the code this slice extends.

## Decisions this plan makes (the design left them open)

**D1. The document's shape.** `ThemeChoices` (`packages/ui-core/src/theme/theme.ts:11-18`) gains
`readonly logo: ThemeLogo | null`, with `export interface ThemeLogo { readonly light: string;
readonly dark?: string }`. The values are the image library's **names** (`media_images.filename`,
`"3f9a….webp"`), as the design's section 11 says (lines 2094-2096) and as a department's receipt
logo already stores them — not image ids (the brief's word). A name is stable across a library edit
(the edit changes `media_image_edits`, never `filename`, `image-edits.ts:82-97`) and across a
configuration copy (the import rewrites only `id` and foreign-key columns, and the media check
requires `filename` to be the hash of the bytes, `packages/media/src/configuration-transfer.ts:59`).
Framing is not in the document: it belongs to the library image, and `/api/theme` reads it there.
`WAITRON_CHOICES.logo` is `null`. `logo` is **required**, like every other key (`"missing"` when
absent): a client that forgot the key would otherwise remove a logo without a word. It is checked
**last**, after `checkFixes`, so every existing refusal keeps its order.

**D2. The shape check, in `@waitron/ui-core`** (no database): `null`, or an object with keys only
`light` and `dark`. Refusals, all `theme.invalid`:

| Sent | `field` | `reason` |
| --- | --- | --- |
| key absent | `logo` | `missing` |
| not `null` and not a plain object (`"a.webp"`, `[]`, `7`) | `logo` | `bad_value` |
| a key other than `light`/`dark` | `logo` | `unknown_key` |
| `{}` | `logo.light` | `missing` |
| `{ dark }` with no `light` | `logo.dark` | `dark_without_light` |
| `light` not a string | `logo.light` | `bad_value` |
| `dark` present and not a string (`null` included) | `logo.dark` | `bad_value` |

`dark_without_light` names `logo.dark`, the field whose value is refused, as `fix_without_brand`
names the fix rather than the brand colour (`document-check.ts:95`). **In the server** (needs the
library): a name that is not a library name (`MEDIA_FILENAME`, `packages/shared/src/media-filename.ts:5`)
or names no image is `{ field: "logo.light" | "logo.dark", reason: "image_not_found" }`, as the
design says (line 2153-2156) and as the department route checks it (`department-receipt-api.ts:46-55`).
`"dark_without_light"` joins `ThemeRefusalReason`; `"image_not_found"` joins only the `theme.invalid`
params union in `packages/layouts/src/errors.ts:46`, since ui-core never answers it. No new error
code.

**D3. `printedLogo` lives in the stored document, never in the choices.** The stored JSON is
`{ ...choices, printedLogo }` when `logo` is not `null`, and the choices alone when it is.
`printedLogo` is a `ReceiptLogoRasters` (`{ "58mm", "80mm" }`, `packages/layouts/src/types.ts`).
A request that sends `printedLogo` is refused `theme.invalid` `{ field: "theme", reason:
"unknown_key" }` — the existing row `document-check.test.ts:75` already pins that — so a client can
never supply dots. Every read of choices goes through `json_remove(theme, '$.printedLogo')` inside
the `json_valid` guard (probe P2), so `GET /management-api/themes`, `/api/theme` and the till's poll
never carry the ~20 KB of dots out of SQLite, and `readThemeDocument` never sees them.

**D4. "Outside the transaction", in order** (design lines 1636-1648; CLAUDE.md §3 "Splitting one
logical change across transactions is a commented decision"). Drawing decodes with sharp, which
must not run while holding the write lock (`receipt-logo.ts:12`); the design's reason is the same as
the department route's. So `POST` and `PUT` take **two** transactions **only when the sent
document's `logo` is neither `null` nor absent** (a peek at the raw body); otherwise they keep their
one transaction exactly as today. With a logo:

1. **Read transaction** — `prepareThemeSave` (layouts): authorize `layout.configure`; for `PUT`,
   `theme.not_found` for an unknown id; parse the choices (`theme.invalid`); and, for `PUT` only, the
   stored `printedLogo` when the stored document names the same light image and its pictures are
   printable (the department's "kept" rule, `department-receipt-api.ts:122-125`). Then
   `snapshotThemeLogo` (server): `image_not_found` for a bad light or dark name; the light image's
   id and revision; its source bytes and framing unless the dots are kept.
2. **No transaction** — `printedLogoFor`: the kept dots, or `drawLogoRasters(renderRendition(bytes,
   "display", framing))`.
3. **Write transaction** — the store's own create or save (which authorizes, re-finds and re-parses
   as today) with `printedLogo`, then `recheckThemeLogo`: the light image missing →
   `logo.light` `image_not_found`; its revision different from the snapshot's → `image.changed`
   `{ imageId }` (409, the department route's code); the dark image missing → `logo.dark`
   `image_not_found`. A throw rolls the whole write back.

A library edit between steps 1 and 3 cannot be missed: the edit bumps the revision
(`image-edits.ts:91`), and step 3 compares it. Step 3 is where the commented decision sits.

**D5. Redrawn on a library edit.** Only an edit that changes pixels (a reframe or a replaced source,
`image-edits.ts:45-49`) redraws, inside `saveImage`'s own transaction, matching rows by the theme's
`logo.light` there (design line 1707). A name-only edit draws nothing (today's `pixelsChanged`). The
route already draws `rasters` once for any pixel change (`routes.ts:222-228`), so a theme adds one
`UPDATE` statement, not another drawing. A theme naming the image only as `dark` is not rewritten
(dots come from the light image only, lines 1605-1606); its `/api/theme` address still moves (D7).
`saveImage` throws a plain `Error` when a theme names the image as light and `rasters` is missing,
as it does for a department (`image-edits.ts:74-75`). The redraw leaves `custom_themes.updated_at`
alone: no choice changed (the department redraw stamps its own row, but `updated_at` on a theme is
what the Themes card reports as the theme's last save).

**D6. Deleting the image.** It is refused exactly as a department receipt logo's is: `deleteImage`
answers `{ deleted: false, uses }` from `listImageUsages` (`images.ts:399-415`), so the new
`theme_logo` member does it. `ImageUsage` gains `{ kind: "theme_logo"; id: string; name: string }`
(the theme's id and name — what slice 8's "Logo of theme {name}" and its link need). A theme naming
the same image as light and dark is **one** use, in both counters. Order: after the department rows,
by `name_key`, then `id`. A theme whose stored document is not a JSON object, or whose `logo.light` /
`logo.dark` is not text, holds no use (probe P3). No database trigger, like the department logo (the
W111 entry gains a line, Driver steps).

**D7. `/api/theme`'s logo, cache and hash.** `logo` is `null`, or `{ light, dark }` holding the
`display` rendition addresses (`dark` `null` when the theme has none, or when its image is gone); a
theme whose light image is gone answers `logo: null` and still its colours (design lines 1549-1551).
`themeHashOf(css, logo)` hashes `{ css, logo }` as today, so Waitron's hash
(`venue-theme.test.ts:38`) does not move. The cache key becomes `JSON.stringify([id, choices,
logo])`: the addresses are made of each image's source file and framing (`presentation.ts:10-16`),
which is the design's key (lines 2196-2203). A reframe therefore misses the cache and works the
sheet out again; a reframe is a rare manager action and the sheet takes milliseconds — I keep one
cache rather than a second one for the sheet alone.

**D8. One reader for both deliveries.** `readVenueThemeSource(tx)` in `apps/server/src/venue-theme.ts`
returns `{ inUse: ThemeInUse | null; logo: VenueLogo | null }`, reading `readThemeInUse` and, only
when the choices name a logo, `readPresentations` — awaited in turn on the one transaction.
`/api/theme` and `readTillSetup` both call it; `venueThemeAnswer(source)` runs after the transaction.
The name avoids `readVenueTheme`, which `packages/ui/src/venue-theme.ts` already exports.

**D9. The dashboard follows a library edit.** `getVenueTheme` depends on
`["custom_themes", "media_images"]`. `saveImage` updates `media_images` on every edit
(`image-edits.ts:82-85`), and `media_images` is a change source (`packages/media/src/module.ts:10-12`).
`listThemes` is unchanged: a reframe changes no choice. The image library's own read
(`packages/media/src/dashboard/live-queries.ts:1-14`) gains `custom_themes`, so its counts follow a
theme saved with or without a logo (as `department_receipts` does today).

**D10. The import check, and the bundle format.** `validateThemeConfiguration` splits `printedLogo`
off each row's document, checks the rest with `readThemeDocument`, and, with a logo, requires
each named image among the bundle's `media_images` filenames (the library's tables travel in every
copy: media is a mandatory module, `packages/media/src/module.ts:29-33`) and `printedLogo` printable;
without a logo, `printedLogo` must be absent. Every refusal is `setup.request_invalid` `{ field:
"custom_themes.theme" }`, like today's. **Which check runs first does not matter** (design line
2175): both read the bundle's tables, not the database, and every module's check runs before any
write (`packages/provisioning/src/configuration-transfer.ts:591-614`); a bad image row is refused by
the media check whichever runs first. **The format moves 6 → 7**: `logo` is required (D1), so a
format-6 copy holding a theme would otherwise be refused as `setup.request_invalid`
`custom_themes.theme`, the generic refusal the convention moves the format to avoid
(`docs/developers/conventions-data.md:1605-1626`); a format-6 file is refused as
`setup.configuration_outdated`. A theme whose logo image the copy does not carry is refused, not
imported without its logo.

**D11. A stored theme from before this slice** (no `logo` key) reads as a document this release
refuses: `/api/theme` serves Waitron's look until the theme is saved again, and the Look card opens
it on Waitron's look (`look-draft.ts:32-35`). Nothing converts it: CLAUDE.md §3, "No
backwards-compatibility or data-migration code until Waitron is in production". The PR description
says so.

## Probes (run 2026-10-23, in `~/waitron-campaign/a841-plan7/probes/`, outputs beside them)

Node v26.11.1, SQLite 3.54.0, one Mac. `node_modules` there is a symlink to this worktree's

- **P1, the cost of drawing (`draw-cost.mts`, `draw-cost.out`).** Command:
  `apps/server/node_modules/.bin/tsx draw-cost.mts` from the probes folder. It runs `prepareImage`,
  then six times `renderRendition(…, "display", default framing)` + `drawLogoRasters`. A measurement,
  not a pass/fail probe. Printed: a 1200 × 400 PNG logo with a see-through background (Bar Lucía's
  shape) took 25.8–30.2 ms per run, dots 480 × 160 at 80 mm and 360 × 120 at 58 mm, 20,105 bytes as
  JSON; a 1600 × 1600 JPEG of noise (the library's largest kept size, the worst case) took
  294.9–298.6 ms, 160 × 160 both, 8,641 bytes.
- **P2, `json_remove` over stored documents (`json-remove.mjs`).** `case when json_valid(x) then
  json_remove(x, '$.printedLogo') else null end` turned `{"a":1,"printedLogo":{…}}` into `{"a":1}`,
  left `{"a":1}` (the control), `[1,2]`, `42`, `null` and `"s"` unchanged, and gave NULL for
  `{broken`. So a stored non-object still reaches `readThemeDocument` and is refused there.
- **P3, the logo match expression (`logo-match.mjs`).** `case when json_valid(doc) and
  json_type(doc) = 'object' and json_type(doc, '$.logo.light') = 'text' then json_extract(doc,
  '$.logo.light') else null end` (and `dark`) gave the names for `{"logo":{"light":"a.webp","dark":
  "b.webp"}}` and NULL, without an error, for `{"logo":null}`, `{"logo":"a.webp"}`,
  `{"logo":{"light":7}}`, `[1]`, `42`, `{broken` and `{"logo":[{"light":"a.webp"}]}`. `json_set(doc,
  '$.printedLogo', json(?))` kept every other key.

## Performance: what runs when

- **Per save that sets or changes the light image** (and per create or copy with a logo): one read
  transaction (an image row by its unique name, the stored row), one decode and draw outside any
  transaction — about 26 ms for a realistic logo, about 0.3 s at worst (P1) — then the write
  transaction with one extra read of the image rows. The write lock is never held while drawing.
- **Per save keeping the light image, or changing only the dark one:** no drawing (kept dots).
- **Per save with no logo:** exactly today's single transaction.
- **Per library edit changing pixels:** no extra drawing (the route draws once already); one
  `UPDATE custom_themes … json_set` inside the edit's transaction.
- **Per `/api/theme` request and per till poll:** the theme row read through `json_remove` (P2), so
  the dots stay in SQLite, plus — only with a logo — one `readPresentations` query by name (unique
  index `media_images_filename_key`). The sheet is cached; a cache miss happens only after a save,
  a switch or an edit of a logo image.
- **Stored size:** about 20 KB more per theme with a logo (P1); it travels in configuration copies.

## Words used here

- An **adjustment** is one row of the adjustments module's `adjustments` table: an item cancelled
  on a bill, a comp (an item given away free), or a discount (a percentage or an amount off one
  item or off the whole bill), with the reason chosen and who asked and who approved
  (`packages/adjustments/src/schema/adjustments.ts:34-85`; the four actions `cancel`, `comp`,
  `discount_percent`, `discount_amount` at `packages/adjustments/src/policy.ts:6-11`).
- A **line void** is what the till's **Void…** on a sent line does (`table.void_line`,
  `apps/till/src/i18n/strings.ts:1112`, Spanish «Cancelar…» `:2845`): it opens the **Cancel item**
  dialog (`cancel_item.title`, `:52`). It is not the whole-sale void that `actions.json` lists.
- The dialog's choices (`apps/till/src/widgets/cancel-item-dialog.ts:402-412`; which are offered,
  `:180-188`):
  - **Cancel, still charge** keeps the charge: the food is cancelled and the guest still pays for
    it. On a bill already paid the same choice reads **Cancel** (`table.cancel_line`,
    `apps/till/src/i18n/strings.ts:1113`).
  - **Cancel, don't charge** removes the charge, once preparation has started.
  - **Remove** removes the charge when preparation has not started, and asks no reason.
  - **Cancel and refund {amount}** (`cancel_item.refund`, `:63`), on a paid bill only: the till
    sends it as a kept charge with a refund handed to a till (`apps/till/src/till-app.ts:13387-13388`),
    and the money goes back later through **Refund a payment** on the receipt
    (`cancel_item.refund_at_till`, `:57-58`).
- The **Voids and comps** page is where a venue sets the reasons staff choose
  (`packages/adjustments/src/dashboard/strings.ts:12-14`; Spanish «Cancelaciones y descuentos»,
  `:181-182`). The rows themselves are listed on the **Adjustment report** (`:108`; «Informe de
  ajustes», `:280`).
- A **part** is one contributor's share of the download: the file names it may add and the code
  that reads and builds them (`packages/module/src/personal-data.ts:26-36`). A **module part**
  fills the `personalData` seat on a module's description; a **server part** is one the server
  adds itself (`actions.json` is one).
- The **snapshot turn** is the first write-lock turn of the download, in which every part's
  `prepare` reads (`apps/server/src/personal-data-export-api.ts:71-80`). While it runs, a sale
  waits behind it. The **build** runs after it closes (`:84`), then a second turn checks the
  caller again (`:85-88`).
- An **actor column** records which person did something to a row (who asked for a comp, who
  approved it), as distinct from whom the row is about.
- An **index** is a sorted copy of one or more columns that lets the database find a person's rows
  without reading the whole table; adding one is a **migration**, a numbered file every box runs at
  start.

## What this slice builds, and what it leaves

1. **`adjustments.json`**, a new module part filled by the adjustments module itself, in both
   download routes (own and admin) whenever the person asked for or approved at least one
   adjustment: how many of each action, then one entry per adjustment with when, the order number,
   the item and how much of it, the amounts, the reason, and the person's part.
2. **Two indexes** on `adjustments` (who asked, who approved), so that read finds the person's rows
   without reading the venue's whole history inside the snapshot turn.
3. **A guard in the adjustments package** that holds every actor column of its tables, and every
   column of `adjustments`, to a list saying whether the file carries it.
4. **The core guard's change**: `line_service_cancellations.actor_id` leaves the "not in the
   download yet" list for a new list of columns another part already covers (decision 3).
5. **Words**: the README's lines for `adjustments.json`, the own-data guide section and the Profile
   page's help text, English and Spanish.
6. **The worked example** as a test, through the real cancel code.

Left for later, on purpose (each becomes a backlog point in Task 10):

- **Whose sale an adjusted item counted as** (`adjustments.credited_to`), beside core's
  `working_order_lines.credited_to`, which S2c already left for later (decision 8).
- **The invoice number of an adjusted bill's sale** (decision 9).
- **The table an adjustment's bill was served at** (decision 9).
- Every other core and module actor column the S2c backlog point lists.

## Decisions this plan makes that the spec does not

   touched.** S2b put workforce's and staffing's tables in their own modules' parts
   (`packages/composition/src/modules.ts:223`, `:382`) and S2c put core's tables in a server part
   (S2c decision 1: "Its tables are core tables"). The `adjustments` table belongs to the
   adjustments module's own migration set (`modules.ts:348-357`), so by that precedent its part is
   the module's own: `ADJUSTMENTS_PERSONAL_DATA` in `packages/adjustments/src/personal-data.ts`,
   exported from the package index and set as `personalData` on the adjustments entry in
   `ALL_MODULES`. The module owns its testing too (the guard of decision 12 lives in its package).
   - **A correction to the brief this plan was written from**, which said shared code "must never
     name the adjustments module — `scripts/module-seams.test.ts`". That guard checks the swappable
     fiscal regime only (its header, `scripts/module-seams.test.ts:10-14`: "The boundary is the
     REGIME, not 'any module'"; `REGIME_PACKAGES` at `:31` lists `@waitron/fiscal-verifactu` and
     `@waitron/verifactu`), and `apps/server` already imports `@waitron/adjustments` in five
     product files (`git grep -n "@waitron/adjustments" -- 'apps/*/src/**' ':!*.test.ts'
     ':!**/testing/**'` on 2026-10-25: `adjustments-api.ts`, `adjustments-apply.ts`,
     `line-cancel.ts`, `receipt-adjustments.ts`, `tender-refund-reservation.ts`). So the guard would
     not refuse a server part; the reasons for the seat are the S2b precedent and the house rule
     that a module fills the contract seats (home CLAUDE.md §3).
   - The adjustments module is `tier: "mandatory"` (`modules.ts:350`), and boot hands the download
     every migrated set's name (`apps/server/src/boot.ts:2156`, `setsToMigrate.map((m) => m.name)`),
     so the part is enabled on every box.
   - Default: the part's file list is `["adjustments.json"]`.

2. **The file is `adjustments.json`, and its shape is** (keys in this order):

   ```text
   adjustments.json { counts: { cancel, comp, discount_percent, discount_amount },
                      entries: [{ action, at, order, item, quantity, percent, takenOff,
                                  listValue, reason, stage, chargeKept, preparationStarted,
                                  yourPart }] }
   ```

   - The name matches the **Adjustment report** where these rows are listed, and keeps the word
     "voids" out of a second file name: in `actions.json`, `voids` means whole sales voided after
     they were recorded (S2c decision 3).
   - `counts` has all four actions, each the number of entries with that `action`, zero included.
     Keys are the stored action names so a reader can match them to `action`.
   - `action` is the stored action. `at` is `created_at` as stored (ISO 8601 UTC text, a
     `tsString` column, `adjustments.ts:84`). `order` is the bill's order number,
     `working_orders.order_number`, the number printed on the ticket
     (`packages/db/src/schema/orders.ts:79-82`) and shown as **Order** on the Adjustment report's
     entries (`packages/adjustments/src/reports.ts:126`, `:338`). `item` is `line_name` and
     `quantity` is how much of the line the adjustment covered, through `thousandthsToDecimal`;
     both null on a discount on the whole bill (`adjustments_bill_level_ck`,
     `adjustments.ts:115-120`). `percent` is `basisPointsToDecimal(percent_bp)` on a percentage
     discount, else null (`packages/shared/src/scales.ts:110`). `takenOff` is `reduction` (what came
     off the bill) and `listValue` is `nominal_value` (the list value of what was adjusted), both
     through `centsToDecimal`, so `1235` becomes `"12.35"` (the report's "Taken off" and "List
     value", `packages/adjustments/src/dashboard/strings.ts:132`, `:162`). `reason` is `reason_name`
     as recorded. `stage` is the stored `unsent`, `held`, `fired` or `served`, null on a bill
     discount. `chargeKept` and `preparationStarted` are the stored flags (the second may be null).
   - `yourPart` is `["requested"]`, `["approved"]` or `["requested", "approved"]` (decision 5).
   - **Order**: by `at`, then row id, so the output is the same on every run. The id is read for
     that and never written. Task 1's fixture gives the rows fixed ids in the reverse of their time
     order, and two rows one time, so both halves of the sort are tested.
   - **No row, no file** (S2b decision 3): a person on no adjustment gets no `adjustments.json`, and
     the README lists only built files. This leaves every existing whole-ZIP assertion unchanged
     unless its fixture already holds an adjustment.

5. **Whose rows, and the person's part.**
   - `requested_by` is the person who made the adjustment (`adjustments-apply.ts:962`,
     `line-cancel.ts:366`); `approved_by` is whoever entered a PIN when the policy asked for
     approval (`adjustments-apply.ts:762-778`), or, on a cancel that handed a refund to a till, the
     person whose PIN authorised that refund (decision 4).
   - **A row marked `by_guest` is not the requester's own request.** The Adjustment report counts
     such a row as the guests', never the requester's (`packages/adjustments/src/reports.ts:463-470`;
     one person's list filters `byGuest = false`, `:528-533`). Default, the same here: the read
     selects rows where (`requested_by` is the person and `by_guest` is false) or `approved_by` is
     the person, and `requested` is in `yourPart` only on the first condition. A `by_guest` row the
     person approved still shows `["approved"]`. No product code sets the flag today: no caller
     passes `byGuest` (decision 8), so Task 1 writes such rows directly.
   - `yourPart` lists `requested` then `approved`, as S2c's `yourPart` does. The file never names
     the other person, by id or name.

6. **The read runs in the snapshot turn, like every module part, through two new indexes.**
   - A module part is handed a `Transaction`, whose type offers no `withWriteLock`
     (`packages/module/src/personal-data.ts:33-36`; the line at `:31-32` allows turns of its own
     only to "a server part constructed with the `Database`"), so S2c's short turns of its own are
     not open to a module part without changing the shared seat, a cross-package contract change
     this slice does not make.
   - Without an index the read scans the whole table: `adjustments` has one index, on
     `(working_order_id, reason_id)` (`adjustments.ts:92`; the newest adjustments snapshot,
     `packages/adjustments/drizzle/meta/0008_snapshot.json`, read by a `node` walk on 2026-10-25,
     lists only `adjustments_order_reason_idx`). The table grows with every void and comp in the
     venue's history, and every other part's read and every waiting sale share that turn.
   - Three small models (raw `node:sqlite`, 100,000 bills and 200,000 adjustments, so lower
     bounds) measured the read without and with the indexes, for a heavy person on 6,667 rows:
     about 72 ms against 10 ms (`round1-review.md`, experiment 3), 28.8 ms against 22.7 ms
     (`round1-claims.md`, claim #88) and 21.8 ms against 14.0 ms (`round3-review.md`,
     experiment 4). For the heavy person the gain is uneven; the case for the indexes rests on the
     light, typical person: 9.9 ms against 0.1 ms for one on 50 rows (`round3-review.md`,
     experiment 4), because without an index every person's read costs a scan of the whole table.
     The plan was `SCAN` without and `MULTI-INDEX OR` / `SEARCH … USING INDEX` with, decision 5's
     `by_guest` condition included (`round1-review.md`, experiment 3; `round3-review.md`,
     experiment 3). Nothing in `packages/store`, `packages/db` or `apps/server` runs `ANALYZE`
     (`round3-review.md`, experiment 1), so the planner's choice there is the one a box makes.
   - S2b met the same problem the same way: workforce migration 0010 added indexes for its module
     part's reads in that turn (c7b15483d, "Three new indexes … as one migration of plain CREATE
     INDEX statements (no table rebuild)").
   - Default:
     - `index("adjustments_requested_by_idx").on(t.requestedBy)` and
       `index("adjustments_approved_by_idx").on(t.approvedBy)`, one per side of the `or`, which
       SQLite combines (S2b's `shift_swaps` pair did the same).
     - Generated by `pnpm --filter @waitron/adjustments db:generate --name
       personal_data_person_indexes`; the number is whatever drizzle-kit assigns (today the journal
       ends at `0008_harsh_kulan_gath`, so `0009` is expected). If the generated SQL holds anything
       but two `CREATE INDEX` statements, the implementer stops: a table rebuild of an append-only
       table is not in this slice (`adjustments` is `appendOnly()`,
       `packages/adjustments/src/classification.ts:10-14`).
     - A case pins the read's query plan: no line of it starts with `SCAN` (S2b's pattern,
       `packages/workforce/src/personal-data.test.ts:1076-1148`).
     - The indexes stay whatever Tasks 3a and 3b measure: they turn a whole-table scan into a
       search for the typical person. Those tasks decide only whether the slice stops
       (decision 13).

9. **No table and no invoice number.**

     (`orders.ts:89-94`), and the bill's `label` is operator text before filing that may name a
     guest, which filing overwrites with the frozen table grouping (`orders.ts:83`: "Optional

     Default: no table in the file; "the table in `adjustments.json`" becomes a short backlog entry.
   - The invoice number of the sale later filed from the bill could be found through
     `sales.working_order_id` (unique, `sales_working_order_id_key`), but formatting it means
     `formatInvoiceNumber` from `@waitron/core` (`packages/core/src/record-sale.ts:105`), a new
     dependency for the adjustments package, and one more lookup per row inside the snapshot turn.
     Default: the order number only, which is what the Adjustment report itself shows of each
     entry; the invoice number becomes a backlog point. **Review focus**: a reviewer may want it.

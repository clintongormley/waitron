# Set menus, piece 4: paying a set-menu bill, its receipt and its invoice — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every implementer is dispatched as `subagent_type: "implementer"`.

**Goal:** A bill holding set menus can be paid, comped and discounted, like any bill. Its ticket and
full invoice list the set menus and surcharges, not every covered dish at 0.00, and its VAT and
sales reports come out right.

**Architecture:** Under the revised design, a set-menu dish's place and price are written once,
when piece 2 places it, and change only by a move the waiter chooses. Nothing reprices a bill, so
nothing needs freezing at payment. Piece 2 refuses money on a bill holding set menus; this piece
removes that refusal. It also stops the two actions that would undo an amount money or an
adjustment rests on: removing a set menu, and re-placing a dish on another bill. Sale lines gain
the set-menu role, so every document and report can tell a set menu from a covered dish. Covered
dishes are left off the printed documents, never out of `sale_lines`.

**Tech Stack:** TypeScript 7, drizzle (core migration set, `migration-baseline rebuild`), Hono
routes in `apps/server`, `packages/core` (sale recording), `packages/reporting`, Lit screens in
`apps/till` and `apps/dashboard`, Vitest 4.

## Decisions this plan makes (the builder's, for the owner)

Marked **my call** where they first appear in a task.

1. **Money on a set-menu bill works as on any bill.** Piece 2's refusal is removed from the three
   places it sits: `beginBillPayment`, `planAdjustment`, and `priceStoredOrderForIssuance`, through
   which every ticket is priced. A whole payment writes no `bill_payments` row (lane M F1, run),
   which is why piece 2 refuses at the ticket path too. Nothing new runs at payment: places and
   prices never change by themselves (spec §3).
2. **Removing a set menu follows today's rule for cancelling a line.** Piece 2 lets − and Cancel
   remove a set menu that holds no dishes, without asking a reason. Today a cancel refuses only a
   line with an item payment on it (`refusePaidLines`, `bill-payments.ts:439-451`, code
   `bill.line_paid`). It deletes a comped or discounted line, and `adjustment_lines.line_id` has no
   key so that the delete goes through (`packages/db/src/schema/adjustments/adjustment-lines.ts:5-9`).
   So the removal path calls `refusePaidLines` with nothing kept, and a comp or discount does not
   stop it. A bill-wide discount is spread onto every line (`spreadBillDiscount`), so refusing
   adjusted set menus would have stopped − on every set menu after one. Removing an empty set menu
   from a bill that holds contributions stays allowed while the money received fits the new total
   (`assertBillInvariant`, `bill-payments.ts:459-473`).
3. **A set-menu dish carrying a comp or discount moves to another bill only with its set menu.**
   Moved on its own, it is placed again on the target and priced there (spec §4), which would
   overwrite the adjusted price. So that move is refused `set_menu.move_adjusted`. Moved with the
   set menu it is placed on, it keeps its place and price (piece 2). An item-paid line cannot move
   at all today (`working-order.ts:4462-4466`).
4. **An included dish or a drink supplement in the set menu carries the set menu's VAT classes.**
   A 0.00 line at a rate no other line has adds a zero-base row to the VAT breakdown.
   The first review probed `rateLines` on 14.00 at 10% plus
   0.00 at 21% and got a second row with base 0.00; the control, both at 10%, gave one row. That row
   reaches AEAT as its own Desglose line (`packages/fiscal-verifactu/src/backend.ts:132-140`).
   Dropping such rows would make every later correction of the invoice unusable
   (`packages/core/src/correction-allocation.ts:191-207`). Write both classes with the price
   when a dish is placed or moved. Drinks ordered separately use their own classes.
5. **The till's pay-by-items list leaves out a set-menu dish whose amount, extras included, is
   0.00.** It lists each set menu by its name and price. A covered soup with a paid extra is listed
   at the extra's amount, because paying a dish pays its extras (`bill-payments.ts:988-990`).
6. **Receipt layout** (lane L's recommendation, for the owner to confirm before Task 5a is built):
   - A covered dish with no priced child is left off the ticket, with its free option answers. A
     **priced child** is one with gross above 0.00, a list price or an adjustment, so a comped
     bread under a covered soup still prints.
   - A covered dish with a priced child prints its name with the amount left blank, and its
     children under it as today.
   - A surcharged dish prints its own name with the amount written "+5,00" (the owner's form,
     "Solomillo +5,00"). No new receipt label is needed.
   - The full invoice follows the same rule only if the adviser says yes to question 26. If the
     answer is no, covered dishes print under their set menu with no price (spec §4 fallback).

   ```text
   Menú del día            14,00
   Solomillo               +5,00
   Sopa
     Pan                    1,50
   ```
7. **Category sales put set-menu lines in a "Set menus" group of their own**, not under "Not
   recorded" (`packages/reporting/src/category-sales.ts:111-123`). Top sellers needs no change: it
   groups by the sale line's name, so each set menu is its own item, and covered dishes count at
   €0 (spec §4).

## The fixture every task uses

The spec's example (§2, the unfolded summary):
- **Daily menu:** €14.00, class `reduced`, with Sirloin at +€5.00.
- **Special menu:** €20.00, class `reduced`, with Sirloin and Sea bass included.
- **Shared dishes:** both list Soup and Hake. Each set menu has one "1 × Starter" line and one
  "1 × Main" line.
- **Soup** has an optional paid extra, Bread, at +€1.50.
- **The bill:** a seated eat-in bill with 2 Daily and 2 Special, added in that order. It has
  4 Soup, 1 Hake, 1 Sea bass and 2 Sirloin, sent in that order.
- **Placed as piece 2 places them** (cheapest open place; between equals, a line accepting fewer
  courses, then the set menu added first):
  - the soups fill the four starter places;
  - the Hake goes to Daily 1;
  - the Sea bass goes to Special 1, the only set menu that lists it;
  - the first Sirloin goes to Special 2 at 0.00;
  - the second goes to Daily 2 at +5.00.

  Total 73.00. Sent in the other order, the second Sirloin would take Special 2's main and leave
  the Sea bass no place.

**Bottle to take home:** a test-only drink on the Daily menu, with its own VAT classes different
from the Daily's. It exercises decision 4 both included and with a supplement.

## Review Focus

1. **A whole payment, or a ticket issued without one.** Pay whole by cash, by hand-keyed card or
   at the reader; place then collect; record an unpaid departure; close as deferred; Print the
   bill. Each is accepted and files the stored lines (lane M F1). Pinned in Task 2a.
2. **A part payment on a printed set-menu bill.** It is taken and writes no line. Pinned in Task 2a.
3. **A 10% bill discount on a set-menu bill, then the ticket.** The discount spreads over the set
   menus and surcharges (rows at 0.00 take none, `adjustments-apply.ts:444,504`). The ticket's lines
   and total match the stored lines to the cent. Pinned in Task 2b.
4. **A set menu with open places.** Two set menus and one soup, printed and paid, are charged as
   two set menus in full (spec anti-goal). Pinned in Task 4a.
5. **A comped set menu, then a removal, and the offered move once money is allowed.** An empty comped
   set menu can be removed, and one paid by items cannot. The till's offered move never names a
   comped, discounted or item-paid dish. Pinned in Task 2b.

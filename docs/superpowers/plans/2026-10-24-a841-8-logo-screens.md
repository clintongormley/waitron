# A841 slice 8 — the logo on the screens: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A manager picks the venue's logo (and an optional one for dark screens) in the Look card's
editor, sees it in the preview and on the saved card, and every screen that drew Waitron's mark —
the dashboard banner, a handheld's bar, the till and handheld sign-in — draws the venue's logo
instead, following each screen's Light / Dark / Follow device setting, with "Powered by Waitron"
under both sign-in forms.

**Architecture:** Two pull requests (D1). **8a, the editor side:** the plate token, a small helper
that tells a component whether its screen is light or dark, one shared primitive that draws a venue
logo in a fixed box and retries an image that failed (`wt-venue-logo`), the draft's logo rules, a
`venue-logo` mode of the existing image picker field, the Logo field, the preview's banner strip,
the saved card's Logo row, the image library's wording and link, and the guide's Logo section. The
logo is stored by slice 7's routes; no live screen changes yet. **8b, the live surfaces:** the
`/api/theme` answer's logo typed and checked, a venue-logo state beside the venue theme sheet in
`packages/ui/src/venue-theme.ts` (waiting / none / a logo, marked failed while its image cannot be
loaded), a `wt-powered-by` primitive, then the banner, the dashboard sign-in, the handheld bar and
the till sign-in reading that state, and the guide's "Where your logo shows".

**Tech Stack:** TypeScript, Lit 3, Vitest 4.1.x in real headless Chromium (`packages/ui`,
`packages/ui-core`, `apps/dashboard`, `apps/till`, `packages/media`'s dashboard), Markdown guides
served by `apps/server`.

## Decisions this plan makes (the design or the brief left them open)

**D1. Two pull requests.** The work is 20 implementer tasks and two visual checks, past the brief's
twelve. **8a — the editor side** (Tasks A1-A11, visual A12) and **8b — the live surfaces** (Tasks
B1-B9, visual B10). Each leaves main working: after 8a a manager can set, preview, save and remove a
logo, the library names its use, and every live screen still draws Waitron's mark exactly as today
(the guide says so); 8b then puts the saved logo on the screens. 8b is branched from main after 8a
lands (its tasks import 8a's `wt-venue-logo`, `ColorSchemeController` and the plate token).

**D2. One shared primitive for the logo's box, `wt-venue-logo`, in `packages/ui`.** Six places draw
the same thing — an image fitted inside a fixed box, a dark image or a plate on dark screens, an
empty box while waiting, a fallback and a retry when the image fails: the banner, the handheld bar,
the till sign-in, the preview's two strips and the saved card's row. A second app (the till) needs
it, so it belongs in `packages/ui`, with the primitive's token-painting test and its axe test in
both themes (CLAUDE.md §3). The editor's own picture box is **not** this primitive: it is a
button-adjacent picture always on the plate's white, drawn by the image picker field (D7).
"Powered by Waitron" is a second primitive, `wt-powered-by` (B3), because both apps draw it.

**D3. Which image a box draws is decided by the host's computed `color-scheme`, not by a
`<picture>` source.** The design names `<picture>` with `darkLogoMedia` (line 1382). The plate must
switch with the image, and a `<picture>` would switch the image in the browser while the plate
waited for script; one boolean read from `getComputedStyle(host).colorScheme === "dark"` drives
both. It follows the nearest theme root, so inside the preview's `data-theme="dark"` panel it
answers dark on a light page with no extra property (probe P3). **It is read on every render**
(`hostUpdate`), as well as on `subscribeThemeChoice` (`packages/ui/src/theme-choice.ts:76-81`) and
on a `change` of `matchMedia("(prefers-color-scheme: dark)")`, which request a render when the
answer changed. Reading only at connect is not enough: a box rendered in the preview's first render
connects before `ThemePreview.firstUpdated` makes its panel a theme root, and reads `normal` there
(the review's probe P-A printed `["connected:normal","update:dark","after-settle:dark"]`). None of
these sends a request to `/api/theme`. The image is the browser's to fetch, as the design accepts
(line 1386). The dashboard's own Waitron lockup keeps its `<picture>` (unchanged).

**D4. `--wt-color-logo-plate`** is declared `#ffffff` in all four blocks of `colors.css`, directly
after `--wt-color-scrim` (light `:30`, media-dark `:165`, forced light `:293`, forced dark `:420`).
`deriveTheme` does not write it: `THEME_COLOURS` (`packages/ui-core/src/theme/tokens.ts:3-26`) is
unchanged, so no sweep, warning count or token-list length moves. The guard
`tokens.test.ts:17-26` excludes it beside the scrim (Changed test checks). Its light and dark values
are both white (design line 1517).

**D5. The live logo is a state beside the venue sheet** (8b, B2), so no surface fetches anything:
`currentVenueLogo()` answers `{ kind: "waiting" }`, `{ kind: "none" }` or `{ kind: "logo", logo,
failed }`. Before `startVenueTheme` runs it is `none` (so every existing test that never starts the
theme keeps Waitron's mark). `startVenueTheme` makes it the stored copy's logo (or `none`), or
`waiting` when there is no stored copy, and forgets every failure; the first applied answer makes it
that answer's logo, even when its hash equals the stored copy's; **the start's own request**
(`inFlight === controller`, as `settle()` is guarded today, `venue-theme.ts:68-71`) ending with
nothing applied (refused, failed, not JSON, the 5 s limit) turns `waiting` into `none` — a request
dropped by a later start never ends that start's wait. `failed` is `true` while a box has reported
that logo's image failing (`reportVenueLogoFailure`) and not since loaded it
(`reportVenueLogoLoaded`). Listeners hear only real changes. `VenueLogoController` redraws a Lit
host on change and can call back on each change (B7 needs that, M3).

**D6. Box sizes, read from tokens** (design lines 1442-1449), **and a logo always keeps its own
shape** (lane ruling on M2). `size="banner"`: the box is 40 px tall
(`calc(var(--wt-space-6) + var(--wt-space-2))`) and the logo at most 160 wide
(`calc(var(--wt-space-6) * 5)`); `size="bar"`: 32 tall (`var(--wt-space-6)`), at most 128
(`calc(var(--wt-space-6) * 4)`); `size="sign-in"`: 96 tall (`calc(var(--wt-space-6) * 3)`), at most
320 (`calc(var(--wt-space-6) * 10)`). The box (`.box`) has the fixed `block-size` and
`max-inline-size`, `min-inline-size: 0`, `display: inline-flex`, `align-items: center`. The image is
`inline-size: min(<width>, calc(<height> * var(--wt-venue-logo-ratio)))`, `max-inline-size: 100%`,
`block-size: auto`, `aspect-ratio: var(--wt-venue-logo-ratio)`; `--wt-venue-logo-ratio` is declared
`0` on `:host` and set on `.box` to `naturalWidth / naturalHeight` when the image loads, and back to
`0` when the drawn address changes. So a small image is drawn up to the box (line 1543), a wide one
is capped at the width with its height shrinking inside the box ("at most 96 px tall"), a tall one
fills the height, nothing is stretched or cropped, and the box keeps its height while loading
(probe P4). With the plate the box keeps its outer size and the image sits `var(--wt-space-1)` (4
px) inside, on `var(--wt-color-logo-plate)` with `var(--wt-radius-sm)` corners (line 1515). The
preview strip uses `bar`; the saved card's row uses `banner`.

**D7. The Logo field reuses the department Receipt tab's picker**, `dashboard-image-upload`
(`department-receipt-editor.ts:706-720`), in a new `venue-logo` mode (A6): with no image, one dashed
"+ {addLabel}" button; with one, the picture on `--wt-color-logo-plate` (not a button), then
**Replace** (opens the same `media-image-picker`) and **Remove**, each a `secondary` `wt-button`
(picture 17). The receipt `logo` mode is untouched. Picking or uploading needs `image.manage`, as
today (design line 1582). The field (`dashboard-theme-logo-field`, A7) holds two of them: the main
image, and under "For dark screens (optional)" the dark one, offered only while there is a main
image; Remove on the main image clears both (line 1421).

**D8. The draft.** `sameDraft` counts the logo (light names equal, dark names equal with absent and
`undefined` the same), so the quiet-Save rule, the leave question, `#adopt` and Use Waitron's look's
quiet state all see it. Use Waitron's look already empties it (`waitronLook`). Cancel drops it (the
scope's restore closes the editor, `look-card.ts:403-419`). The save carries it through
`normaliseChoices` to slice 7's routes; no route changes.

**D9. Refusals beside the field** (CLAUDE.md §3, "by what the error CARRIES"): `theme.invalid` with
`field: "logo.light"` puts "That image is no longer in the image library. Pick another." under the
main image, and `field: "logo.dark"` puts it — or, for `reason: "dark_without_light"`, "Add the main
logo before a version for dark screens." — under the dark image; both mark the picker `invalid`, put
"Correct the highlighted fields to continue." at the bottom, focus the first invalid control, and
never disable Save. A logo change clears them. `image.changed` stays a bottom message through
`codeMessage` (its wording is registered by the media module's strings,
`packages/media/src/dashboard/strings.ts:170-199`). A logo refusal inside the name dialog (first
save, Save as new theme…) stays at the dialog's bottom, as every non-name refusal does there today.

**D10. The preview's banner strip** (picture 17): one strip at the top of each panel, the panel's
logo (the draft's light image on the light panel, the dark image or the plate on the dark one, by
D3) or, with no logo, Waitron's lockup in that panel's drawing, then the tenant's legal name, which
may wrap (`min-width: 0; overflow-wrap: anywhere`, as the banner's `.venue-name` does,
`dashboard-app.ts:674-686`). The legal name reaches the preview as `legalName` from
`dashboard-app`'s `venueName` (`dashboard-app.ts:1001`) through `dashboard-appearance-screen` and the
Look card. The draft's names are drawn through `liveMediaImage(name, "display")` bound to the
primitive's `light` and `dark` attributes.

**D11. The saved card's Logo row** is second, after Theme in use (picture 20): "None", or the image
in a `banner` box (alt `""`), then "Dark screens: own version" or "Dark screens: on a light plate".
The image follows the page's own Theme setting (D3), so a dark dashboard shows the plate.

**D12. The banner rule** (CLAUDE.md §3, design lines 1455-1462): the venue logo replaces only the
picture before the name; the legal name, full width, stays. Its alternative text is `""` in the
banner (the name is beside it) and the legal name in the handheld bar and on the till sign-in.

**D13. Before the first answer, while loading, on failure** (design lines 1548-1552, 2211-2218).
- `waiting` draws an empty box of that place's height and no width — in the banner (`banner`), the
  handheld bar (`bar`) and the till sign-in (`sign-in`) — and no "Powered by". The legal name beside
  the banner's box therefore moves sideways when the logo arrives (said in 8b's PR).
- `none` draws today's screen: Waitron's lockup in the banner, the word in the handheld bar, nothing
  on the till sign-in, no "Powered by".
- `logo` draws the venue's logo and "Powered by Waitron". While loading, the box keeps its height
  (D6).
- **A failed image** (D14): each place draws what it draws with no logo — the lockup in the banner,
  the word in the handheld bar, nothing on the till sign-in — through the box's `fallback` slot, and
  no "Powered by" (`failed` is `true`).

**D14. A failed image is tried again every 60 s, inside the box** (lane ruling on L1: a till runs
for days). `wt-venue-logo` keeps the address it is drawing. When that image fails it sets its
reflected `failed` attribute, shows only its `fallback` slot, sends `wt-logo-error`, and starts one
timer of `VENUE_LOGO_RETRY_MS = 60_000`. When the timer fires and the drawn address is unchanged, it
renders a new hidden `<img>` with the same address (a new element asks the server again: probe P5);
that image's `load` clears `failed`, shows the logo and sends `wt-logo-load`; its `error` starts the
next 60 s timer. An address change (a new answer, Replace, or the Theme setting switching between
the light and the dark image) clears the timer and the failure. Disconnecting clears the timer;
reconnecting while failed starts a fresh one. A failure of the dark image alone falls back on dark
screens only, and on light screens the light image still shows; the state's `failed` flag is per
logo, so "Powered by" goes while any box reports the logo failing and comes back on the next
successful load.

**D15. Help mode adds nothing.** No control on the Look card carries a help badge today (receipts
above); the field's two hints are text under the pictures, as the design's table and picture 17
give them and as the house rule wants a short explanation ("a hint, not a '?' button"). No new
`wt-help-tooltip`, so `scripts/help-tooltip-mode.test.ts` sees nothing new.

**D16. The counter till's bar is unchanged in slice 8**: it draws neither the venue's logo nor
Waitron's word, exactly as since #1905 (`till-shell.ts:996`); slice 14 adds the logo there. A
counter till still shows the logo on its sign-in screen and "Powered by" under it.

**D17. The till sign-in before anyone signs in** reads only what needs no session: the stored copy
applied by `startVenueTheme` at start, `/api/theme` (unauthenticated), the image renditions
(served with no session, `packages/media/src/routes.ts:244`), and `/api/till`'s `themeHash` and
`venueName` (unauthenticated), whose `followVenueTheme` brings a newer answer. A signed-out till runs
no poll, so it follows a change at its next start or sign-in, as its colours do (design line 2264).

**D18. A kitchen display or kiosk that falls back to the sign-in screen shows the logo and "Powered
by" there** (review L4, checked by reading). Boot sets `deviceMode = false` before anything else
(`apps/till/src/till-app.ts:4076`) and sets it `true` only after a kitchen display's board has been
read (`:4129`); a failed identity or board read with any code but `device.unauthorized` is caught
and leaves the till on the lock screen (`:4134-4148`; "The lock screen also shows after a boot
failure", `:18716-18717`). That fallback is the ordinary sign-in screen, so it draws the logo and
"Powered by" like any sign-in screen. The kitchen-display and kiosk modes themselves never draw the
lock screen: they run inside the shell (`#shellActive`, `:17647-17653`, with `.kiosk=${this.deviceMode}`,
`:18754`), which draws no bar for them. B8 adds a case for the fallback.

**D19. The library's link** for a `theme_logo` use is `/manage/appearance`, as the design says
(section 8a's "Storage and delivery": "with a link to the Appearance page"), and its words "Logo of
theme {name}" (English), "Logotipo del tema {name}" (Spanish). The guide says to press Edit there.

**D20. Spanish product text** is proposed in the tasks (the design leaves it "to be written with
the strings"); each PR lists every new Spanish string for the owner.

**D21. `VenueThemeAnswer.logo`** becomes `VenueLogoAddresses | null` with `export interface
VenueLogoAddresses { readonly light: string; readonly dark: string | null }`, and
`isVenueThemeAnswer` refuses any other `logo` (slice 7's "Left for later slices"). A stored copy
with a malformed `logo` is then ignored like any malformed copy (`readStored`, `venue-theme.ts:28-37`).

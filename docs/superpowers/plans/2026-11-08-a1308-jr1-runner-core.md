## Global Constraints

- One job runner; a job's name is a stable identifier and never changes once landed (jobs.md §4).
- Jobs stay in the server's one process (jobs.md §1, owner 2026-11-04).
- A job's change-feed listener runs on the writer's call stack after its commit: it only schedules,
  and never throws into the writer (`apps/server/src/live-api.ts:35-49` says why).
- The runner is never built on a restricted or waiting start (CLAUDE.md §5; `boot.ts:1758-1825`).
- Every log line carries a fixed code, never a provider's words or a person's details (CLAUDE.md §3).

  (`menu-activation.ts:9-10`).

## Review Focus

1. **A wake arriving while the job's pass is running.** Exactly one more pass follows, never two
   at once. Task 2's "a wake during a pass gives exactly one more pass".
2. **A job whose pass writes the very table it wakes on** (menu activation writes the release it
   activates). It must settle after one extra pass, not spin. Task 4's re-pointed "is woken once by
   its own activation, which then finds nothing to do" (`menu-activation.test.ts:409`).
3. **A stepdown while a job is mid-pass.** The pass sees its signal aborted at once; no new pass
   starts; `stopJobs` still awaits the running pass. Task 2's stepdown cases.
4. **A job that throws on every pass for hours.** It keeps running, its sleep grows to the back-off
   ceiling, and `/health` still answers 200. Task 2's back-off case and Task 3's "a reported job's
   failures never change the status code".
5. **A shutdown while a job is backing off** (menu activation backs off up to 300 s; the shutdown
   deadline is 8 s, `run-server.ts:31`). `stopJobs` settles at once: every sleep, the back-off
   included, ends at the job's signal. Task 2's "stopJobs during a back-off settles at once".
   (A due time far in the future is covered by "never arms a timer longer than Node honours".)

export const JOB_CATALOGUE = { /* the table below */ } as const satisfies Record<
  string, { readonly kind: "job" | "service"; readonly stepdown: StepdownMark;
            /** The two jobs whose staleness fails /health, through `duties`. */
            readonly failsHealth?: true }>;

export const JOB_NAMES: readonly JobName[];

// job-runner.ts
export interface JobContext { readonly now: Date; readonly signal: AbortSignal }
export interface JobPassResult {
  /** When work is next due; null sleeps the job's ceiling. */
  nextDueAt: Date | null;
  /** The pass did not throw but left due work undone (a skip or a parked run). Counts as a failure
   *  in `consecutiveFailures` (as today's `recordPass`, `health.ts:81-111`), never in
   *  `throwsSinceClean`, and is not backed off. */
  degraded?: boolean;
  /** No further pass, ever (the tamper watch once it has refused trading). */
  finished?: true;
}
export interface JobDefinition {
  readonly name: JobName;            // catalogue kind "job"
  applies(): boolean;                // read before every pass
  pass(ctx: JobContext): Promise<JobPassResult>;
  readonly wakeOn?: readonly string[];   // change-feed resource types
  readonly minSleepMs: number;       // also the shortest gap a wake can make
  readonly maxSleepMs: number;
  readonly backoff: { readonly firstMs: number; readonly maxMs: number };
  readonly firstPassAfterMs?: number;    // default 0
  /** A job whose failures raise their own alert; jr3's job.failing skips it. */
  readonly ownFailureAlert?: string;
  /** Runs once, as soon as the job's loop ends: after its last pass, which for a job marked
   *  { stop: true } is right after the stepdown signal (a pass under way finishes first) — not at
   *  the close. A job that must act the instant its signal aborts, even mid-pass, listens to
   *  ctx.signal itself (jr5's refund resolvers do). */
  onStop?(): Promise<void>;
}
export type JobState = "waiting" | "running" | "not_applicable" | "stopped";
export interface JobView {
  kind: "job" | "service"; state: JobState;
  judged: boolean;             // the catalogue's failsHealth
  lastTurnAt: string | null;   // every loop turn, applying or not
  lastRunAt: string | null; lastOkAt: string | null;
  consecutiveFailures: number; failingSince: string | null;   // throws and degraded passes
  throwsSinceClean: number; throwingSince: string | null;     // throws only, since the last clean pass
  lastErrorCode: string | null;
  nextDueAt: string | null;
  ownFailureAlert: string | null;
}
/** The view without `lastErrorCode` and `ownFailureAlert`: what unauthenticated /health shows
 *  (`health.ts:212-229` serves it to anyone who can reach the port). */
export type PublicJobView = Omit<JobView, "lastErrorCode" | "ownFailureAlert">;
export interface JobRunner {
  add(job: JobDefinition): void;       // starts the job's loop at once
  wake(name: JobName): void;           // a no-op for a name not added
  /** Ends every job's current sleep at once, ignoring minSleepMs and any back-off (a role change
   *  is rare and must not wait out a 60 s floor); jr2 also re-checks services. */
  roleChanged(): void;
  /** Synchronous: aborts the signal of every job the catalogue marks { stop: true }. */
  signalStepdown(): void;
  /** Aborts every job's signal (ending every sleep, back-offs included, at once); each loop ends
   *  after its running pass and runs its onStop; resolves when every loop and onStop has finished.
   *  A second call returns the first call's promise; add() after it throws. */

  views(): Readonly<Record<string, JobView>>;

  monotonicMs?: () => number;                                     // default performance.now

**One job's loop** (the algorithm the tests pin; everything else follows from the interface):

```text
wait firstPassAfterMs (wakeable)
until the job's signal is aborted:
  lastTurnAt = now
  if not applies(): state not_applicable; sleep maxSleepMs (wakeable); continue
  state running; run pass with { now, signal }, contained
    threw   → consecutiveFailures += 1; failingSince ??= now; lastErrorCode = codeOf(error);
              throwsSinceClean += 1; throwingSince ??= now;
              log("error", "job.failed", { job, errorCode, consecutiveFailures });
              throws += 1   (thrown passes in a row; only these grow the back-off)
              sleep min(backoff.maxMs, backoff.firstMs * 2^(throws-1)): ended by the job's signal or
              roleChanged(), never by a change-feed wake
    ok      → lastRunAt = now; throws = 0;
              if degraded: consecutiveFailures += 1, failingSince ??= now
              else lastOkAt = now, consecutiveFailures = 0, failingSince = null, lastErrorCode = null,
                   throwsSinceClean = 0, throwingSince = null;
              if finished: break;
              sleep sleepMsFor(nextDueAt, now, minSleepMs, maxSleepMs) (wakeable)
state stopped; await onStop       (the loop ends here, at the signal, not at the close)
```

Every sleep is cut into pieces of at most `LONGEST_TIMER_MS` and ends at once when the job's signal
aborts. A wakeable sleep is a per-job `createLoopWaker({ minTickMs: job.minSleepMs, delay, monotonicMs })`;
`roleChanged()` does not go through the waker (whose floor would hold it: in a stand-in, a wake 2 s
into a sleep with a 60 s floor ended at 60,073 ms) but aborts a per-job role controller combined
into every sleep's signal (`AbortSignal.any`), replaced after each use. The single change-feed
subscription maps each `change.resources[].type` to the jobs naming it and calls their waker's
`wake()` inside a `queueMicrotask`, wrapped so nothing reaches the writer.

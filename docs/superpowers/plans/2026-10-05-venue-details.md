> venue-wide `locations.order_flow` setting. Quick sales use the zone's `prepay` or

> **For agentic workers:** use `superpowers:executing-plans` for routine inline execution. Start each behavior change with a failing test, observe its intended failure, implement the smallest change, and rerun it. Use `git commit -s` at independently working task boundaries. The driver owns review, commits and landing.

**Goal:** Let you correct the venue's display details on Venue settings, with server-enforced limits that preserve issued documents and historical reporting days.

**Architecture:** A shared server writer owns normalization, change detection, stale-draft checks and post-sale restrictions. A separate Venue details API exposes the stored values and their editing policy; the core dashboard panel uses shared fields and passive live queries. Creation and configuration import remain separate operations, with explicit tests showing that they cannot overwrite an operating venue's details.

**Tech Stack:** TypeScript, Drizzle/SQLite, Hono, Lit, existing `wt-*` fields and form actions, Vitest and real Chromium.

**Spec:** [A261](../specs/2026-10-03-venue-operations-design.md) §§3, 11 step 7, 12; [A254](../specs/2026-10-03-departments-service-styles-hours-design.md) §6; [devices, menus and service zones](../specs/2026-10-04-devices-menus-and-service-zones-design.md), especially §§2, 8–10. ### Precise sale, history, no-op and cache rules proposed

1. **Sale predicate:** `hasSales = EXISTS (SELECT 1 FROM sales LIMIT 1)` in the single-venue database, with no environment, node, tender, fiscal-state, total, void or correction filter. A practice sale, zero-total sale, voided sale, correction, substitute or sale on another retained node counts. A failed/rolled-back sale with no committed `sales` row does not. Check inside the same transaction as the edit. Do not infer sales from invoice counters, AEAT acknowledgements, settled working orders or a dashboard flag.
2. **Additional clock lock:** any row in core `working_orders` or `daily_closes` also locks both clock fields, even before sales. The whole order history matters because C4/C6 and the Orders window can interpret dated rows; an abandoned/settled order is not an empty venue. Open/placed work is included. Read-only FK traces: `packages/db/src/schema/bill-payments.ts:67` through `:71` (payment to order, RESTRICT), `:173` through `:177` (refund to payment, RESTRICT), and `packages/db/src/schema/unpaid-departures.ts:40` through `:44` (departure to order, RESTRICT). Execute those constraints before relying on the inference that retained financial rows retain order history; do not classify a terminal order's financial history as empty. This is deliberately conservative and needs approval. An empty unsaved browser draft does not count, but warn before saving that its later submission uses the new settings. Workforce rows/bookings do not satisfy this core history predicate: retain their stored dates/offsets and warn about civil-now annotations and future recurring schedules.
3. **Manual station overrides before sales:** an otherwise eligible clock edit retains every row. The old/current business-day override can stop applying and a retained row for the new business day can apply. Explain this before submission, displaying the old/new business day and cutover. Do not delete or relabel overrides to make the edit look harmless. Existing schedule/fallback/default precedence stays intact; no existing sent work can pass the order-history lock.
4. **No-op:** authenticate first; reject unknown keys and malformed types; normalize only submitted fields and compare to stored normalized equivalents. Remove equivalent changes before stale-draft and history checks. An empty/equivalent patch returns `{ changed:false }` without an UPDATE, change-feed event, cache reload or snapshot write, including after sales/close/history. `04:00` and `04:00:00`, a recognized time-zone alias, canonical province name/code and allowed surrounding whitespace are equivalent. Retain the existing stored bytes on a no-op. An unchanged locked field alongside a changed allowed name does not block that name. Read-only identity keys in a request are refused even if their values match.
5. **Stale drafts:** for each genuinely changed field, compare its expected original value to the current normalized value. Refuse the whole save on disagreement; never overwrite another editor's address. Ignore concurrently changed fields absent from the patch. A sale committed since the read overrides a previously offered clock/province permission. Whole patch is atomic: a valid name plus refused clock writes neither.
6. **Live behavior:** current location readers already reach the row on each transaction (C4/C6/C8). Keep this path. Move both cached email-zone uses in C8 to per-send reads. Permit pre-sale province edits only when C3's derived values remain equivalent, so the boot-cached display/content policy has no new value to adopt. Preserve a person's chosen language and till browsing/open draft; no forced login, navigation, menu switch or broad till reboot. An already-started email uses its captured setting; the next send uses the committed setting.

The pre-live reset rule is an operator/deployment policy, **not** a bypass on a live UI. `WAITRON_ENV=dev`, practice mode and “no real venue yet” never waive these row-based guards. A reset removes that installation's data through the existing deliberate reset procedure; this editor never offers a reset, clears sales, resets counters or promises to preserve production data. If the owner later wants post-sale clock changes, first commission historical clock versions and reporting/close reconciliation in a separate design.

```ts
type VenueDetailField =
  | "name"
  | "addressLine1"
  | "addressLine2"
  | "postalCode"
  | "city"
  | "province"
  | "timeZone"
  | "dayCutover";
interface VenueDetailValues {
  name: string;
  addressLine1: string | null;
  addressLine2: string | null;
  postalCode: string | null;
  city: string | null;
  province: string | null;
  timeZone: string;
  dayCutover: string; // wire HH:MM; validated storage HH:MM:00
}
type VenueDetailPatch = Partial<VenueDetailValues>;
type DetailReason =
  | "sales"
  | "orders"
  | "daily_close"
  | "geography_context"
  | "current_details_only"
  | "holiday_geography"
  | "clock_effects";
interface VenueDetailsModel {
  details: VenueDetailValues;
  issuer: { country: string; legalName: string; taxId: string };
  hasSales: boolean;
  hasOrderHistory: boolean;
  hasDailyClose: boolean;
  policy: Record<
    VenueDetailField,
    {
      decision: "allow" | "allow_with_warning" | "refuse";
      reasons: DetailReason[];
    }
  >;
  provinces: { code: string; name: string }[];
}
interface VenueDetailWrite {
  changes: VenueDetailPatch;
  expected: VenueDetailValues;
}
// New exported server contracts; route owns the transaction and authorization.
export declare function readVenueDetails(
  tx: Transaction,
  cfg: { locationId: string },
): Promise<VenueDetailsModel>;
export declare function writeVenueDetails(
  tx: Transaction,
  cfg: { locationId: string },
  input: VenueDetailWrite,
): Promise<{ changed: boolean; model: VenueDetailsModel }>;
// Existing apps/server/src/venue-time-zone.ts:5, not a new write helper.
export declare function readVenueTimeZone(
  db: Database,
  input: { locationId: string },
): Promise<string>;
```

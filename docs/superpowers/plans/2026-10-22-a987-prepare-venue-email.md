> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Native inline execution is owner-authorised. Steps use checkbox (`- [ ]`) syntax for tracking. Do not dispatch agents or ask an execution-method question.

**Goal:** Let Prepare and Live use their own SMTP server, keep the unlinked Demo mailbox, and leave Cloud integration dormant until D102 releases its contract and joint tests pass.

**Architecture:** Keep the sealed `email.smtp` credential and resolve delivery immediately before use. Add a structured SMTP diagnostic classifier and bounded transport, preserve existing outbox decisions, and switch Prepare setup and routing together with its working screens. Reserve a delivery-policy boundary for Cloud without creating a provider client, enrolment state or usable Cloud route.

**Tech Stack:** TypeScript, Hono, existing nodemailer, SQLite through `useVenueDb`, Lit/shared `wt-*` controls, Vitest and real Chromium. No new dependencies by default.

**Spec:** [2026-10-22-a987-prepare-venue-email-design.md](../specs/2026-10-22-a987-prepare-venue-email-design.md), especially its 2026-10-22 amendment, then historical §§6.4–6.6. Amendment wins on permissions, stage policy and Cloud.

## Global Constraints

- Cloud is never required. Prepare requires a usable route outside development; until Cloud is released, only SMTP meets that requirement. Linked Demo's eventual Cloud branch remains blocked.
- Required STARTTLS or implicit TLS; certificate checks stay on. No office-CA setting, insecure bypass, migration, backward-data migration or new credential purpose.
- Account sends finish within **30 seconds including transport cleanup**; no automatic retry. A timeout or lost acknowledgement can mean accepted mail. Preserve that uncertainty.
- Public password reset keeps its immediate empty **202**, including unknown addresses and delivery failure. Do not add route, account or enrolment disclosure to public reads.
- Saved relay PUT/DELETE and all another-person sign-in changes stay `person.admin`. Settings read/proposed test stay `system.manage`; tests target the signed-in person's stored address. Captured messages stay admin-only, including direct message reads.
- Preserve invoice and reminder retry/outbox/primary rules. No sale waits for email or Cloud. Fiscal writers, hashes, numbering, immutable records, AEAT, registration, restore and golden code are untouched. Invoice PDF contents are out of scope.
- Sender display is the location's name, not the legal-name session `venueName`. Invoice changes affect only email envelopes, after A739 releases them; no receipt/PDF/body/subject wording changes.
- Live asks again; configuration export keeps no SMTP settings or secrets. Keep runtime remove-without-capture behaviour separate from initial setup requirements.
- No raw provider error/message/response, password, SMTP URL or account-action URL in any log, diagnostic callback or returned refusal. Classify from structured fields only.
- Shared/general code is English-only; ES text belongs in translations/guides. A966 F owns relocation of existing server email wording; no wording move here without recorded handoff.
- Forms use primitives and their native controls, semantic names, `draftScopeFor`, `saveActionState` and its handler early return. Invalid fields explain themselves with one bottom summary; a request refusal alone never disables retry. Successful writes commit the submitted snapshot before close/refresh; reads never erase an action error or a newer draft.
- Every implementation task uses red/green TDD, preserves behavioral assertions, and ends with `git commit -s`. Read the TDD skill before writing code. Commands below are future checks, not checks run by this documentation author.

## Words used in this plan

- **guide** (or **guide page**): one of the three user guides, today `docs/products.md`,
  `docs/modifiers.md` and `docs/content-and-images.md`.
- **twin**: the Spanish version of a guide, the same page in the other language.
- **section id**: the fixed, English, language-independent name of one section of a guide, such as
  `variants`, written in the guide's source as `## Add variants … {#variants}` and used in a link as
  `/help/es/products#variants`. Both languages of a page carry the same ids.
- **the box** (in the dashboard sense of slices 1 and 2): the small popover a help badge opens.
- **the route**: `GET /help/<language>/<page>`.

## Measured while writing this plan

All run 2026-10-18 in this worktree on `main` at `2d5f6211f`.

- **M1, how CI treats a guide's path.** `node --input-type=module -e` importing `scopeForPaths`
  from `scripts/changed-packages.mjs`, with a workspace of `@waitron/server` and
  `@waitron/dashboard`:
  `docs/guide/en/products.md` → `{"kind":"documentation","packages":[],…}`;
  `apps/server/src/guide/en/products.md` → `{"kind":"packages","packages":["@waitron/server"],…}`.
  So a guide under `docs/` gives CI's code jobs and the pre-push hook nothing to run, while the same
  file under `apps/server/src/` runs `apps/server`'s tests.
- **M2, what Hono hands the route.** A throwaway script in `apps/server` (deleted afterwards) with
  `app.get("/help/:lang/:page", …)` on Hono 4.13.13, echoing both parameters. The failing case was
  stated first: if the parameter were used as a path, an encoded `../` would reach the filesystem.
  `/help/en/..%2F..%2Fetc%2Fpasswd` → 200 with `page: "../../etc/passwd"` (decoded);
  `/help/EN/products` → `lang: "EN"`; `/help/en/products.md` → `page: "products.md"`;
  `/help/en/products?x=1` → `page: "products"`; `/help/en/products/` and `/help/en` → 404 (no
  match). So the route must compare both parameters with a fixed list and build the file path only
  from the list's own value.
- **M3, what the guides are written with.** A `grep` survey of the three files (headings, lists,
  tables, fences, quotes, HTML-looking text, links, code spans, emphasis): headings of level 1 and 2
  only; paragraphs hard-wrapped at about 100 characters; one bullet list (`docs/products.md:38-44`,
  with indented continuation lines); `**bold**` (on 153 lines across the three files; six runs of it
  cross a line break, at `docs/products.md:65-66`, `:67-69`, `:82-83`, `:200-201`, `:229-230` and

  nothing else in the three files, measured by the plan review); two code
  spans (`docs/products.md:172`, `docs/content-and-images.md:101`); three links, each to another
  guide (`docs/products.md:207`, `docs/modifiers.md:58`, `docs/content-and-images.md:6`); and
  placeholder text in angle brackets inside bold that must show as written
  (`**<included menu> folder in <including menu>**`, `docs/content-and-images.md:193`, and
  `**<department> receipt logo**`, `:204`). No tables, fences, quotes, images, numbered lists or

## Decisions made in this plan (for the reviewer)

1. **The guides move to `apps/server/src/guide/<language>/<page>.md`, not `docs/guide/` as the
   spec's §4 and §8 say.** This changes where the files sit, not the owner's decision (b).
   Under `docs/`, three pieces of machinery treat a file as documentation that nothing builds:
   - `.dockerignore:17` leaves `docs` out of the image's build context, so the build stage's
     `COPY . .` (`deploy/Dockerfile:25`) would never see a guide (read);
   - `scripts/changed-scope.mjs:126` classifies every `docs/` path as inert, so a guide-only change
     runs no CI code job and no test (M1), and the pre-push hook takes its documentation route;
   - `CLAUDE.md:877` exempts a `docs/`-only change from the pull-request ceremony, so a guide
     shipped in the image could be pushed straight to `main` with nothing run.
   Keeping `docs/guide/` would need a carve-out in each of the three, each in machinery other
   lanes rely on (gating logic, which `CLAUDE.md` says to trace consumer by consumer before
   changing). Under `apps/server/src/`, the guides are `apps/server`'s own files: CI attributes a
   change to the server (M1), its tests read them, and they reach the image exactly as
   `src/assets/` does today: `apps/server/scripts/copy-migrations.mjs:24` copies `src/assets` to
   `dist/assets`, `deploy/Dockerfile:195` copies that to `/app/assets/`, and
   `apps/server/src/invoice-font.ts:4-5` finds it with `new URL("./assets/…", import.meta.url)`,
   which resolves to `src/assets` when run from source and to `/app/assets` from the bundle (read).
   Prettier then formats the guides (`docs/` is in `.prettierignore:11`; `apps/` is not), which is
   harmless for prose. Task 2 adds a dated pointer to the spec's header saying where they went.
2. **Markdown is rendered by a small renderer of our own, at request time, with no new
   dependency.** The guides use a small subset (M3) and the workspace has no markdown library (M4).
   A renderer that knows exactly that subset, escapes everything else, and **refuses** (throws on)
   anything outside it (a table, a fence, a numbered list, a level-3 heading, a link to anything
   but another guide) is about the size of the configuration a library would need to do the same:
   turn off raw HTML, rewrite `.md` links, add fixed section ids. Refusing is the point: a guide
   edit that uses something the renderer does not support fails `apps/server`'s content test in CI
   instead of rendering wrongly on a box. Rendering per request (no cache) keeps it simple and lets
   the dev server show an edit on reload; a page is about 10–18 KB of text. No third-party code is
   added, so the spec's licence-notice condition does not apply; Task 6 still checks the server
   bundle's notices are unchanged.
3. **The route is mounted in the shared part of `bootServer`, beside `mountDiscovery`**
   (`apps/server/src/boot.ts:929-946`, the block commented "Help and certificate downloads precede
   every mode-specific gate and SPA catch-all"), so it serves in **setup mode, the adoption-pending
   boot and every trading boot (primary, read-only mirror, fenced)**, always before the built apps'
   catch-alls (`boot.ts:2278-2291`, read). Why setup too: the image's own smoke test can only reach
   a setup box (`.github/workflows/image-smoke.yml:162` onward checks a blank, unprovisioned box,
   read), so serving it there is what lets CI prove the guides reached the image; the pages hold
   nothing secret. **Not served** by the failed-start recovery page (`recoveryApp`,
   `apps/server/src/recovery-surface.ts:505`, a separate app whose content rules are fixed strings
   and the redacted log; no dashboard or till runs there), nor by the plain-HTTP landing listener
   (`apps/server/src/landing-app.ts`, certificate help only).
4. **The address is checked against fixed lists before anything is read.** Languages `en` and `es`;
   pages `products`, `modifiers` and `content-and-images` (the file names, so the slugs need no
   table). Matching is exact and case-sensitive (`EN` is a 404). The file read is
   `join(root, lang, `${page}.md`)` where `lang` and `page` are the **list's** strings found by
   comparison, never the request's (M2). Anything else answers a 404 page, and that includes
   addresses the `:lang/:page` route does not match at all (`/help`, `/help/en`,
   `/help/en/products/`, `/help/en/a/b`): `mountGuidePages` also registers `app.get("/help/*", …)`
   after the page route, answering the same 404 page. Without it those addresses fall through to
   whatever is mounted later: in setup mode with a built setup app, its redirect middleware sends a
   browser to `/` (`setup-api.ts:1394-1410`); with no setup app, the placeholder answers 200
   (`:1412-1414`); in a trading boot with a till, its catch-all answers an empty 404
   (`spa-api.ts:66-76`, navigation is only under `/tabs`). Measured by the plan review on Hono
   4.13.13 with a throwaway script: `/help/*` registered after `/help/:lang/:page` answered `/help`,
   `/help/`, `/help/en`, `/help/en/products/` and `/help/en/a/b` itself, left `/help/en/products` to
   the page route, and a 404-to-redirect middleware registered after both did not replace its 404.
5. **A page missing in Spanish shows the English page with one line at the top saying so** (spec
   §4). This slice ships all three twins, so on a real box the line never shows today; it is built
   anyway, because the spec makes it the rule for the next guide, and is tested with an injected
   guide folder that holds only the English file. The English file is required: a page in the list
   with no English file is a broken build, answered 500 and logged.
6. **Section ids are written into the source, the same in both languages.** Every level-2 heading
   ends with `{#id}`; the renderer turns each section (its heading and everything up to the next
   one) into `<section id="…">`. A link from the dashboard, and slice 4's sheet, can open
   `/help/es/products#variants` and `/help/en/products#variants` alike. A link between guides is
   written `[text](modifiers.md#lists)` and rendered relative, `href="modifiers#lists"`, so it stays
   in the reader's language. The content test fails if a heading has no id, if two sections share
   one, if a link names a page or id that does not exist, or if a twin's ids differ from the English
   page's.
7. **The page's look.** One self-contained HTML string, no external files, as the certificate
   page is (`apps/server/src/trust-page.ts`, read). Following picture 06: a muted line "Waitron
   guide › Products" ("Guía de Waitron › Productos"), the page's level-1 heading, its sections, a
   reading column about 680 px wide; the section a link opened (`:target`) is drawn on
   `--wt-color-highlight` with a 4 px `--wt-color-primary` bar at its start edge. The page cannot
   load the apps' token files (`apps/server` does not depend on `@waitron/ui-core`), so it declares
   its own copies of the `--wt-*` tokens it reads, each colour as `light-dark(<light>, <dark>)`,
   and every rule reads `var(--wt-…)`. Unlike the certificate page's hand-kept copies, a new root
   guard (Task 5) checks each copy against `packages/ui-core/src/tokens/colors.css` and
   `structure.css`. Sizes in px, never rem or em.
8. **The page follows the theme the person chose in the apps.** The apps save the choice in
   `localStorage` under `waitron-theme` (`packages/ui/src/theme-choice.ts:6`, read), on the same
   origin as the route. A one-line inline script in the page's head, built from `GUIDE_THEME_KEY`
   so the key the guard checks is the key the script reads, reads it and sets
   `data-theme` on `<html>`, which switches `color-scheme`, which `light-dark()` follows; nothing
   saved means the device's own setting. The page answers with a Content-Security-Policy that
   allows that one script by its hash and nothing else to load:
   `default-src 'none'; style-src 'unsafe-inline'; script-src 'sha256-<hash>'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'`.
   `frame-ancestors 'self'` is what lets slice 4 show the page inside the till, same origin, and
   nobody else frame it.
9. **The page's own words** (the "Waitron guide" line, each guide's short name, the missing-twin
   line, the 404 page) live in one `Record<"en" | "es", …>` in the route's module, the way
   `OPERATOR_TEXT` holds the recovery page's (`recovery-surface.ts`, read). Spanish uses _tú_, as
   the dashboard's Spanish strings do (read: 72 strings start "Elige", "Pulsa", "Guarda" or "Añade";
   none "Elija", "Pulse", "Guarde" or "Añada"). Short names: Products / Productos, Modifiers /
   Modificadores (the dashboard's `nav.modifiers`), Languages and photos / Idiomas y fotos.
10. **"Read more in the guide" is drawn by `wt-help-tooltip` itself**, from two new properties,
    `guide-href` and `guide-label` (the screen passes both; a primitive shows no fixed words, spec
    §2). The link is drawn only when both are set, after the text, as a native
    `<a target="_blank" rel="noopener">`, at least `--wt-tap-min` tall. With a link, the box is no
    longer itself `role="tooltip"` (M5): the box holds an inner `role="tooltip"` element with the
    text, which the badge names as its description, and the link beside it, which is the next Tab
    stop after the badge while the box is open. Focus on the link keeps the box open (it is inside
    the element, `onDocumentFocusin`, `wt-help-tooltip.ts:157-159`, read). A click on the link
    closes the box as the new tab opens, so the form underneath is as it was (spec §3.1). The
    dashboard's capture-phase link handler leaves such a link to the browser, both for its
    `target="_blank"` and for a path outside `/manage` (`#onAppLink`,
    `apps/dashboard/src/dashboard-app.ts:1842-1871`, read), so it is not turned into an in-app
    navigation.
    **Without a link the box is drawn exactly as today**, so none of the existing description
    checks change (`wt-help-tooltip.test.ts:67`, `:227`; `wt-help-tooltip.help-mode.test.ts:131`;
    `wt-menu-row.test.ts:259`). The `wt-data-table` column badge and `wt-menu-row` gain no link in
    this slice (no Products part that uses them needs one).
11. **Products links three badges** (the parts the guide says more about than the badge does):
    the price field → `products#selling-unit`, the default course → `products#course`, the Variants
    section → `products#variants`. Not VAT (the guide says no more than the badge does) and not the
    Availability column or Keep (decision 10). Task 2 makes the two sections that do not exist
    yet, by moving existing sentences under their own headings, adding no new claim: "Choose a
    selling unit" (from the introduction, `docs/products.md:8-10`) and "Choose the course"
    (the first two sentences of `docs/products.md:64`, "Use the **Default course** field … It saves
    with the product.", and `:75-78`, today inside "Give the product a main category"). The
    routing sentences at `:64-69` ("Where the dish is made …") stay under the category heading: they
    are what `:61-62`'s "as described below" points to, and they are about stations, not courses.
    **The selling-unit section is thin once moved:** `:8-10` is one sentence, and the price badge's
    own text (`help.products.price`, `apps/dashboard/src/i18n/strings.ts:781`) already says more
    (the till asks how much for a weight or a unit with decimals). A link to a section that says
    less than the badge fails this decision's own test, so Task 3a writes the section out from the
    code (what a unit changes on the price field, at the till, on the receipt), each sentence with
    its receipt; if it cannot, the price badge gets no link and Task 11 drops `products.selling-unit`.
12. **The dashboard builds its links in one place**, `apps/dashboard/src/help-guide.ts`: a fixed
    table of the sections it links to (`"products.selling-unit"` → page `products`, section
    `selling-unit`, and so on) and `guideHref(key)`, which returns
    `/help/<en|es>/<page>#<section>` in the dashboard's current language (`currentLocale()`,
    `@waitron/dashboard-kit`; `es-*` gives `es`, anything else `en`). The till will need the same
    helper in slice 4. A root guard (Task 11) imports that table and the server's guide reader and
    fails when a key names a page or section the server does not serve, in either language; it also
    fails when a dashboard source file other than `help-guide.ts` writes `/help/`.
13. **In development the dashboard's Vite server sends `/help` to the server**, as it does `/api`,
    `/management-api` and `/media` (`apps/dashboard/vite.config.ts:16-20`). The till's proxy is
    left to slice 4, which is the first till code to link a guide. On a box the dashboard is served
    by the server itself at `/manage/` (`boot.ts:2281-2286`, read), so `/help/…` is the same origin.
14. **One pull request.** Fifteen small tasks; the server half and the dashboard half share the
    section-id contract, and reviewing them together is what lets the run-it seat follow a link from
    the badge to the section it lands on.

## What slice 4 (tills) can rely on

- `GET /help/<en|es>/<products|modifiers|content-and-images>` answers 200 with one self-contained
  HTML page (no request to any other address), `Content-Type: text/html; charset=UTF-8`,
  `Cache-Control: no-cache`, and the CSP of decision 8, which permits same-origin framing. Any
  other address under `/help` (including `/help` itself and a trailing slash) answers the guide's
  own 404 page (decision 4).
- It is served in every trading boot and in setup mode, and before the till's own catch-all, so a
  till on the box's origin can load it in an `<iframe>` inside its sheet.
- Section ids are the same in both languages; `#<id>` opens and highlights that section.
- Links inside a page go only to other guide pages, in the same language, so a sheet never leaves
  `/help/`.
- The page follows the saved `waitron-theme` choice the till also writes (same origin, same key).
- `wt-help-tooltip`'s `guide-href` link opens a new tab. Slice 4 must change that on a till (spec
  §3.2: "never a new tab"); this plan adds no hook for it. The obvious one is a cancelable `wt-*`
  event on the link's click that the till handles by opening its sheet.
- The till's Vite proxy does not yet send `/help` to the server (decision 13).

## Global constraints

- No migration, no schema change, no new error code, no new dependency.
- Comments only for an invariant or a non-obvious why; never history.
- Every commit `git commit -s`, plain-English message. Never `--no-verify`. Run `pnpm format:check`

  a guide you changed).

  prints none is no evidence. Before a browser run, check `memory_pressure | grep free`; run beside
  another session's browser run only when free memory is well above 15%. Stop only processes you
  started, by their ids.
- Coverage holds `98/98/98/95` in `apps/server`, `packages/ui` and `apps/dashboard`; never close a
  gap with an ignore comment or an exclude.

  token (guards: `packages/ui/src/no-hardcoded-chrome.test.ts`, `scripts/style-token-names.test.ts`).
  The guide page declares its own copies (decision 7), checked by Task 5's guard.

  translates or corrects is checked against the code, and a Spanish twin uses the Spanish UI labels

- An implementer that passes about 150 tool calls with its task unfinished stops at a passing (or

### Task 1: the renderer

**Files:** create `apps/server/src/guide-markdown.ts` and `apps/server/src/guide-markdown.test.ts`.

**Interface:**

```ts
export interface GuideSection { id: string; heading: string }
export interface RenderedGuide {
  title: string;            // the level-1 heading's text, unescaped (the page shell escapes it)
  html: string;             // the body: <h1>, the opening paragraphs, then one <section> per level-2 heading
  sections: GuideSection[]; // in order
  links: { page: string; id?: string }[]; // every link, as written, for the content test
}
/** Throws `Error` naming the line number and what it found for anything outside the subset. */
export function renderGuide(markdown: string, pages: readonly string[]): RenderedGuide;
```

The subset (M3), and nothing else:

- `# Title` once, as the first non-blank line; `## Heading {#id}` where `id` matches
  `^[a-z][a-z0-9-]*$`. A `##` without `{#id}`, a second `#`, `###` or deeper: refused.
- A paragraph is consecutive non-blank lines, joined with one space before inline parsing (so
  `**Coffee,\nsingle**` is one bold run).
- A bullet list: lines starting `- `; a following line indented by two spaces continues the item.
  `* `, `+ ` and `1. ` at a line's start are refused.
- Inline: `**bold**` → `<strong>`, `_text_` → `<em>` (only when the `_` follows a space, `(` or the
  start, and the closing one precedes a space, punctuation or the end, so `snake_case` stays text),
  `` `code` `` → `<code>`, `[text](page.md)` or `[text](page.md#id)` → `<a href="page">` or
  `<a href="page#id">`, where `page` must be one of `pages`. Any other link target (an `http` URL,
  a path, a `.md` not in the list): refused.
- Refused anywhere: a line starting `|`, ` ``` `, `>`, or four spaces outside a list item; `![`;
  an unclosed `**`, `` ` `` or `[`; a single `*` that is not part of `**` (prettier writes emphasis
  as `_`, M3, so a lone `*` is either a typo or a list marker in the wrong place); a section id
  ending `-heading` (it would collide with another section's heading id).
- Every character of text, attribute and code is HTML-escaped (`&`, `<`, `>`, `"`, `'`), so the
  angle-bracket placeholders of M3 show as written. Bold may contain emphasis and code; the inline
  parser needs no nesting deeper than that.
- Each `## … {#id}` opens `<section id="id" aria-labelledby="id-heading"><h2 id="id-heading">`,
  closed before the next one or at the end. Text before the first `##` goes after the `<h1>`,
  outside any section.

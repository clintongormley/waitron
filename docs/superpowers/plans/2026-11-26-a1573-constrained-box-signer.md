# A1573. Limit what the box’s retained signing key can vouch for

After installing one public certificate, staff can open the till and dashboard at the box’s names and private addresses. The key the box retains can sign new box certificates, and the device refuses a website outside that name limit. [Owner’s ask and phone receipt](../../backlog/setup.md#a1573-a-box-certificate-that-cannot-vouch-for-other-websites-on-android).

**Mint and serve.** In `apps/server/src/self-signed-cert.ts`, reuse the existing certificate builder and permitted names. Make a self-signed root that signs one intermediate, a second certificate carrying the critical DNS and IP limits and a path length of zero. Use distinct subjects and keys. Keep the root key only during minting. `tls/ca.crt` stays the single public root, `tls/issuer.crt` is the intermediate, and `tls/ca.key` matches the intermediate. Keep `server.pem` as the served leaf, followed by the intermediate and the leaf’s private key. `client.crt` likewise carries the client leaf followed by the intermediate. Serve both chains without adding the intermediate to any trusted CA list. RFC 5280 says the self-signed trust anchor “is not included as part of the prospective certification path.” [RFC 5280 §6.1](https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1).

**Keep the chain across changes.** Reuse the durable writes and repair flow in `box-secrets.ts`, `box-tls-install.ts` and `box-tls-repair.ts`. Check the root, intermediate signature and constraints, served chain and matching leaf key. Serving a valid leaf still works with a missing signer key. Repair a damaged leaf under the same valid root and signer. An old one-certificate set takes the existing repair path that asks devices to replace the old trusted root. Preserve the vault key and use the existing recovery lock and restart handling.

**Carry the chain between boxes.** Add `issuer.crt` to `packages/store/src/state-layout.ts`, `packages/handover/src/manifest.ts` and the durable install set, using the existing backup and restore file handling. Use the same chain checks in `backup-verification-secrets.ts`. Add the intermediate certificate to the signed join bundle (`mirror-bundle.ts`, `mirror-bundle-fetch.ts`, `adopt.ts`), validate it against the root and signer key before adoption writes, and keep the root as the existing peer pin. Exercise peer HTTPS and the spare’s mutually authenticated store connection. This changes TLS files and the join bundle, with no database schema change. The B3 preboot recovery listener and custom TLS certificates stay outside this slice.

**Test before changing each path.** Extend `name-constraints.test.ts` to prove a real verifier trusts the root alone, accepts a box name and private IP, and rejects an outside name and public IP. Repeat with an unconstrained test intermediate to prove the rejection comes from the name limit. Use `landing-app.test.ts` for a root-only download, and `box-secrets.test.ts`, `box-tls-repair.test.ts` and `box-tls-install.test.ts` for leaf reissue, old-set replacement and interrupted install. Use `backup-verification-secrets.test.ts` and `boot.restore.test.ts` for a restored chain, and `adopt.test.ts`, `spare-join.e2e.test.ts` and `spare-pipe.test.ts` for the join and client authentication, including a mismatched signer refusal. Update existing fixtures and state-layout expectations with their original assertions intact.

Before landing, run the allowed and refused cases from the product chain, with the unrestricted control, on a second Android phone and on an iPhone. Record device and browser versions and which certificate each device installed. Update the backlog entries and the operator’s certificate instructions. Estimate 300–400 lines of product change and 350–500 lines of tests and fixtures in one pull request.

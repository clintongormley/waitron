# Idle box gateway recovery

**Finish line.** An idle box running the WireGuard companion carries remote staff traffic again within 90 seconds of a gateway replacement at the same Cloud endpoint and key. The replacement starts without the old encrypted session. Lane G owns the outside check of both Cloud routes.

**Cause.** Lane G saw 32-byte keepalives reach the same endpoint while the standby had no handshake. It saw a new exchange at about 142 seconds. Linux WireGuard starts a missing-reply handshake timer after sending data, and excludes empty keepalives from starting it. The 120-second rekey plus a wait for the next 25-second keepalive fits the idle result. With periodic venue traffic, Lane G recovered in 21.841 seconds. Cloud #1325 records both runs in `docs/gateway-reconnection-measurements.md`. See Linux [send.c](https://github.com/torvalds/linux/blob/8dac6df92a2e66e2098bbc69061964cfe7e8375b/drivers/net/wireguard/send.c#L242-L259) and [timers.c](https://github.com/torvalds/linux/blob/8dac6df92a2e66e2098bbc69061964cfe7e8375b/drivers/net/wireguard/timers.c#L145-L154).

In Lane J’s isolated Docker check, the current companion missed 90 seconds with no new handshake. Injecting a one-byte datagram through `wg-cloud` every six seconds brought back the handshake and staff echo in 16 seconds. With the first send delayed to 21 seconds, the handshake and staff echo returned in 37 seconds. Each replacement started with handshake 0, and the box kept its interface.

**Change.** In `deploy/tunnel/peer.sh`, reuse the existing two-second control loop. Send a one-byte UDP datagram on activation and about every 20 seconds while active. This gives the first packet about 20 seconds and WireGuard’s missing-reply timer about 15 more, leaving room in the 90 seconds for gateway readiness and retries. Reuse `socat` with a one-second deadline and bind to the box’s assigned private tunnel address, as the watcher offered at 18:25. Send only to the configured gateway’s private address on UDP port 9. The datagram requires no service or reply. Restart the cadence when the configuration changes. On a failed send, keep forwarding and report the first failure for that configuration.

**Check.** In `scripts/tunnel-container-smoke.sh`, immediately after a verified staff echo and before the gateway’s second address is added, record and require a recent handshake. Recreate its WireGuard interface with the same address, key and port. Require the replacement to start without a session. Until its fresh handshake, read state only, so the check cannot supply the missing traffic. Then require the staff echo and original box interface within 90 seconds. Run this first on the current script and observe a deadline failure. Keep the existing off, input-filter and key-retention checks.

In `scripts/tunnel-container.test.mjs`, distinguish one-shot datagram calls from the TCP forwarder in the existing fake. Use the existing off/reconnect case to check that the send stops and resumes. Add a case that verifies forwarding stays up and reports a send failure. Run the Docker smoke and `pnpm exec vitest run scripts/tunnel-container.test.mjs` after the change.

Update `deploy/tunnel/README.md` for the additional send time and replacement check, and update the existing A951 backlog note in `docs/backlog.md`. Give Lane G the landed revision and the build command `docker build -f deploy/tunnel/Dockerfile -t waitron-tunnel:dev .` for its outside proof.

**Size.** About 15–20 production lines, 45–60 test lines and short operations and backlog updates. Reuse the existing companion, tools and Compose smoke. DNS changes, Cloud election, new privileges and new listeners are outside this change. The overlapping #3808 companion wiring and smoke checks must survive whichever branch lands second.

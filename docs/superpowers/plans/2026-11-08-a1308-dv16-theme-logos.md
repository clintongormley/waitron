`$.logo.dark`) for two columns with foreign keys to `media_images(filename)`, so the database, not
only the app, refuses deleting a photo a theme uses (README R4). Measurement M3 runs first and
decides whether the theme's cached printer dots (`theme.printedLogo`) stay.

## M3: the measurement (Task 1)

**What runs:** time `printedLogoFor` (`apps/server/src/theme-logo.ts:59-63`: decode the image with
sharp and draw both papers' dots) on the largest logo the theme editor accepts, against reading the
cached copy (`readPrintedThemeLogo`, `packages/layouts/src/theme-store.ts:145-157`), 50 runs each,
median and 95th percentile, on the reference micro PC (README U11), or the build machine named if
none is reachable.

**Outcomes** (`tables-devices.md` §8 M3: "If it takes more than about 50 ms per receipt, keep one
cached copy per image (in media). If it is well under, drop both caches."):
- **Above 50 ms** (the design's failing result for dropping): the theme copy stays in the theme JSON
  (§6 item 4: "Until that lands, the theme copy stays"); the figure is written into the menu and
  photos area's backlog entry for a per-image printed copy (or a new line in
  `docs/backlog/printers.md` if that area has none). Task 3 is skipped.
- **Under 10 ms ("well under", a fifth of the bound) on the reference micro PC:** the builder stops
  and the watcher confirms Task 3 (dropping the theme's copy and drawing at print time) before it is
  built (rules §5.4). Dropping `department_receipts.logo_rasters` belongs to its own area (venue and
  box) and is reported, not done here.
- **Between, or measured only on a faster machine:** keep the copy; record the figure as above.

## What it builds

`custom_themes` (`packages/db/src/schema/custom-themes.ts`):

| Column (drizzle) | Type | Rule |
| --- | --- | --- |
| `logo_light_image` (`logoLightImage`) | `label`, null, key to `media_images(filename)`, `onDelete("restrict")` | was `theme.logo.light` |
| `logo_dark_image` (`logoDarkImage`) | `label`, null, same key | was `theme.logo.dark` |

CHECK `custom_themes_logo_ck`: `logo_dark_image is null or logo_light_image is not null` (a dark logo
only with a light one, as the theme document's shape allows today; `packages/layouts/src/theme-configuration.ts:56-62`).
`theme` keeps colours and other look settings and, unless M3 and the watcher say otherwise,
`printedLogo`; it no longer holds `logo`.

- **The store** (`packages/layouts/src/theme-store.ts`): writers (`createCustomTheme` `:159`,
  `saveCustomTheme` `:188`, `prepareThemeSave` `:224`, `documentFor` `:98-112`) split the incoming
  choices' `logo` into the two columns; readers (`choicesOf`, `listCustomThemes` `:114`,
  `readThemeInUse` `:136`, `readPrintedThemeLogo` `:145`, `storedPrintedLogo`) rebuild `logo:
  { light, dark? } | null` from them. The API's `ThemeChoices` keeps its shape: no route, screen or
  wire field changes.
- **Media** (`packages/media/src/images.ts`): `themeLogoName(side)` (`:118-123`) is deleted; its
  three users read the columns: `listImageUsages`' theme rows (`:268-272`), the usage tally
  (`:625-631`), and `image-edits.ts:87`'s `themeMatch` (`= customThemes.logoLightImage`). The app's
  refusal with "where it is used" stays first; the key is the backstop (the owner's call for receipt
  logos and menu photos, `tables-venuebox.md` §1.10, quoted in §1.8).
- **Configuration transfer:** `custom_themes` rows carry the two columns; `theme-configuration.ts`'s
  `checkTheme`/`checkRow` (`:50-75`) read the logo names from the columns and still require each to
  be a carried image (`carried`). Foreign keys are checked at commit during an import
  (`pragma defer_foreign_keys = on`, `packages/provisioning/src/configuration-transfer.ts:710`), so no
  `before` ordering is needed.

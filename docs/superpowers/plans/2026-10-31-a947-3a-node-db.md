# A947 slice 3a — each box's own state moves to `node.db` — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking. Every implementer is dispatched as
> `subagent_type: "implementer"`.

**Goal:** Everything a box must remember about itself — its role, its link to the main box, its
recovery-key check, its membership signing key and the main box's public key it trusts — lives in
that box's own `node.db`, so a box holding a copy of another box's `venue.db` still knows who it is.

**Architecture:** `node.db` is already opened beside `venue.db` and has never held a table. This
slice gives it one migration set, owned by a new package and registered as a module whose set is
applied to the node file; moves the five pieces of per-box state into it; makes every archive and
the sealed state carry a copy of it, and every restore put it back; adds the main box's public key,
the venue's key ring and its certificate authority's private key to the joining bundle; and makes
promotion, a box retiring itself and the main box adding a spare check the membership document
they sign over against keys `node.db` holds.

**Tech Stack:** TypeScript, `node:sqlite` through `@waitron/store`, drizzle-orm / drizzle-kit
0.31.x on the SQLite dialect, Vitest 4, Ed25519 through `@waitron/membership`, AES-256-GCM
through `@waitron/credentials`.

**Spec:** [`docs/superpowers/specs/2026-10-21-a947-two-box-failover-design.md`](../specs/2026-10-21-a947-two-box-failover-design.md)
§11 slice 3a, §4 items 1–2 and the `node.db` paragraph, §6.3 step 2; and where it points, the
[topology design](../specs/2026-09-16-sqlite-litestream-topology-design.md) §2.1, §7.2 and §7.5.

Everything below was read on `main` at `ae4eebe19` (2026-10-31). Line numbers are that commit's.

## Open questions (each has a default the plan builds; the owner may overrule any)

- **OQ1 — where `node.db`'s migration set lives (default: a new package `@waitron/node-db`,
  registered as a mandatory module named `node` whose set says `database: "node"`).** Every root
  guard that checks migrations finds sets by the folder `packages/<pkg>/drizzle` and the module
  list: `migrationSets` (`packages/sync-enrolment/src/testing/migration-sets.ts:20-29`),
  `packageDirOf` (`packages/module/src/module.ts:1792-1800`, which refuses any `from` that is not
  `../<pkg>/drizzle`), and `classification-complete`'s discovery
  (`scripts/classification-complete.test.ts`, `discoverDrizzlePackages`). A second drizzle folder
  inside `packages/db` would be invisible to them; a module of its own is seen by all of them
  unchanged. The alternative — teaching every guard a second folder per package — is more change
  for the same result.
- **OQ2 — backups and restores carry `node.db` (default: yes, as an archive entry `node.dump`,
  required).** Restore needs two things this slice moves out of `venue.db`: the signing key (a
  restored box keeps the dead box's node id and signs the next membership term,
  `apps/server/src/rebuild-first-start.ts:111,128`) and the recovery-key check (read from the
  restored copy at `apps/server/src/restore.ts:328`, `recovery-preparation.ts:137`,
  `recovery-backup-preview.ts:90`, `first-setup-backup-source.ts:102`,
  `first-setup-backup-recovery.ts:138,1153,1339-1343`). Today an archive carries only `db.dump`
  and state files (`apps/server/src/archive-entries.ts:51-70`), and the bucket rebuild gets its
  state files from the `node_sealed_state` row (`restore-stream.ts:247,326`). The topology design
  already said the archive carries `node.db` (§7.2: "The archive also carries `node.db`'s sealed
  secrets"; §7.5 item 2). The alternative — the main box writing the spare's verifier into
  `venue.db` — keeps restores unchanged but still leaves the signing key with nowhere to travel.
- **OQ3 — the certificate authority's private key on the spare (default: stored beside the
  spare's own authority as `tls/venue-ca.key` and `tls/venue-ca.crt`, 0600, and not used by the
  listener until slice 3b).** Swapping the spare's own authority at joining would change the
  certificate the setup browser on the spare sees after the restart; slice 3b names the box
  certificates and the store's TLS, which is where the key is first used (design §11, 3b).
- **OQ4 — a joining box whose vault already holds a sealed row (default: adopt refuses before any
  write, with a new code `mirror.vault_not_empty`, worded in English and Spanish with "Start again"
  as the next step).** Adopt now replaces the spare's key ring with the main box's
  (design §4 item 1); a row sealed under the spare's own ring would then never open again.
  `apps/server/src/setup-api.ts` is among the files that call `putCredential` on a box in setup
  mode (`grep -rln 'putCredential(' apps packages`), so a half-finished setup can leave one.

## Fiscal boundary

Nothing in this plan touches `computeHuella`, the chain or Encadenamiento, invoice-number
allocation, `registros_facturacion`, the alta builders, `registerSif` or `restoreFiscal`
(`packages/fiscal-verifactu/src/restore.ts:3`). So there is no STOP. Three changes sit next to
fiscal code and are called out for the reviewer:

1. **Promotion's point of no return now spans two files** (Task 7, Task 13). Today the role flip,
   the module activation and the new membership document commit in one `venue.db` transaction
   (`apps/server/src/promote.ts:148-161` and `:213-224`). SQLite does not keep a write to two files
   atomic in write-ahead mode: "Transactions involving multiple attached databases are atomic,
   assuming that the main database is not ":memory:" and the journal_mode is not WAL. If … the
   journal_mode is WAL, then transactions continue to be atomic within each individual database
   file" (sqlite.org/lang_attach.html, fetched with `curl` 2026-10-31); the store runs every file
   in WAL (`packages/store/src/index.ts:135-148`) and opens the two files on separate connections
   (`:251-260`). The activation and the document stay in one `venue.db` transaction; the role is
   written to `node.db` only after it commits. A crash between the two leaves the box not selling
   and not filing (role still `mirror`/`secondary`), never filing twice; Task 13 lets a repeated
   promotion finish the flip without activating again. This is a commented decision at the site.
2. **The filing gate reads its role from `node.db`.** Filing runs only while
   `holders.singletonRole.current === "primary"` (`apps/server/src/singleton-pass.ts:5`,
   `boot.ts:2305`), refreshed by `readDeploymentAxes` (`deployment-holders.ts`). Task 7 changes the
   file it reads; not the rule.
3. **Joining's standby establishment stops writing the signing key** (Task 10).
   `establishReservedStandbyIdentity` (`apps/server/src/reserved-identity.ts:36-111`) seals the key,
   writes the `nodes` row and runs each module's `standby.establish` in one venue transaction, and
   uses "a sealed key exists" as its repeat guard (`:58-63`). The key moves to adopt; the repeat
   guard becomes "this standby's `nodes` row exists". The module call is untouched.

## Global Constraints

- **Pre-live: no backwards-compatibility or data-migration code** (CLAUDE.md §3, last bullet). No
  code reads a `membership.node_key` row from `venue.db`, no code copies old `node_roles` rows, and
  an archive without `node.dump` is refused. Development and demo boxes are reset
  (`wa-wt reset demo <name>`); the PR's first line says so.
- **Every `node.db` table is classified `local`, keeps a `node_id` column, and every read and
  write names it** (CLAUDE.md §3, "A `local` table says what ties a row to its node"). The file
  ties the row to the box; the column keeps the rule true when a `node.db` is restored onto new
  hardware.
- **No foreign key into or out of `node.db`.** A column that names a venue row (`origin_node_id`,
  `primary_node_id`) says at the column that nothing establishes the row exists in this file.
- **Lock order: `node.db`'s write lock is always taken OUTSIDE `venue.db`'s, never inside.**
  The two write queues are independent (`packages/store/src/index.ts:73-78`); one path taking them
  in the other order can wait on the first forever.
- **Never use `withTransaction` on the node handle.** It drains `change_log`
  (`packages/db/src/tenancy.ts:30-42`, `change-log.ts:31`), a table `node.db` does not have; use
  `withNodeTransaction` (Task 1).
- **Migration numbers are indicative**: let `drizzle-kit generate` assign them. The node set ships
  exactly ONE migration. CLAUDE.md §3's drizzle rules hold: classification, `migrationOptionsFor`,
  `requires`, journal times strictly increasing, manifest entry, no table rebuild that also adds a
  column, no expression index across a rebuild.
- **Secrets stay sealed or hashed.** The recovery-key verifier is a scrypt hash
  (`apps/server/src/break-glass.ts:40`, `hashSecret`) and stays one; the signing key is sealed
  under the key ring with additional data binding it to the node id; nothing that works as a live
  login is added. `scripts/personal-log-params.test.ts` is not affected: no field holding a
  person's name, email or tax number is added.
- **New error codes** are registered in their package's `errors.ts` and imported by the throwing
  file (`scripts/errors-reachable.test.ts`). They are: `mirror.vault_not_empty` (OQ4, Task 14),
  `node.identity_mismatch` (Task 10) and `membership.held_untrusted` (Task 15). The last two are
  states only a bug or tampering produces. An untrusted held document can only come from a bug or
  tampering; its sites say so in a comment (CLAUDE.md §3, the refusal rule's fault-in-Waitron
  exception), and it shows the screens' existing generic text.
- **Names.** `node.db` tables: `node_mode` (mode, singleton role), `node_mirror_link`,
  `node_recovery_key`, `node_signing_key`, `node_primary_key`. They deliberately do not reuse
  `node_roles` or `mirror_config`, so the old and new tables never share a name while consumers
  move (Tasks 7–12).
- Plain English in comments, commit messages and the PR. Every commit `git commit -s`.
- Run Vitest under `env -u AI_AGENT -u CLAUDECODE` when you need a passing test's output, and read
  the `Tests` count, never only the exit status.

## Review Focus

1. **A spare whose `venue.db` is replaced reads its own identity.** Copy a main box's `venue.db`
   over a spare's: the spare must still read `mode = mirror`, its own signing key and its own
   verifier, and no table in the copy may decide either. Task 16 pins it, with a control.
2. **A crash between the two commits of a promotion.** Venue committed, `node.db` not: the box must
   not sell or file, and a repeated promotion must not activate a second installation. Task 13.
3. **A ring rotation after this slice.** `rotateCredentials` re-seals `tenant_credentials`
   (`packages/credentials/src/store.ts:249-270`); a signing key sealed under the old ring and left
   behind becomes unreadable the day the previous key is dropped. Task 10 adds it to rotation.
4. **An archive or bucket copy restored onto new hardware.** The restored box must carry the dead
   box's signing key and recovery-key check, and the new box's own `node.db` must be set aside, not
   merged. Task 6.
5. **The held document signed by an evicted spare.** After a spare retires itself, the main box's
   held document is signed by the spare (`apps/server/src/boot.ts:1596-1597`, "a retirement chart is
   signed by the node it evicts"). The main box adding the next spare must still accept it. Task 15.

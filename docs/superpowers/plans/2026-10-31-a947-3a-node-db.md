## Questions for the owner — answer before the build starts

### Q1 — When the spare is switched on, the box's role is written a moment after everything else. May it be?

**A worked example.** Friday, 21:40. The main box has died. Marta, the manager, presses «Cambiar al
equipo de reserva» on the bar till and signs in. The spare does what the design's §6.3 step 2
describes: it takes its new installation name, opens its new invoice series, and signs the new
membership chart naming itself the main box. All of that is saved in one step, in `venue.db`, as
today. Then it writes, in its own `node.db`, "I am now the main box". Suppose the spare's power
lead is knocked out in the split second between those two saves.

- **With the recommended default**, the spare starts up again, reads the chart it signed with its
  own key, sees that it names it the main box, and finishes writing its role before it decides
  anything else. Marta sees a restart about as long as the one every switch already causes
  (`apps/server/src/boot.ts:2841-2853` restarts the box after a promotion), then the tills move to
  it. Nothing is filed twice and no second installation name is taken. If Marta's till sends the
  same press again before that restart, the switch runs the same check first and finishes the role
  instead of starting over (Task 13).
- **Without a repair**, the spare would come back still calling itself a spare, holding a new
  installation name it cannot use. Pressing the switch again is refused. That was run in a test
  harness on today's code, which has no repair (the real promotion and fiscal steps, the role set
  back to "spare" by hand; not the HTTP route and not a real box): sending the same request again
  gave `sif.allocation_invalid` `event_mismatch`
  (`packages/fiscal-verifactu/src/hour-selection.ts:372`), a fresh clock comparison 12 minutes
  later gave `minute_in_use`, and one installation stayed open
  (`~/waitron-campaign/a947-plan3a/round3-probes/hour-promotion.round3.test.ts`, re-run for
  revision 3: `Tests 1 passed | 40 skipped`). From that I infer, without having run it, that the
  venue could not sell until the box was restored from a backup.

**Why it has to be two saves.** The role must live in `node.db`, because that is the one file a
stream from the main box cannot overwrite. SQLite does not keep one save across two files whole in
the mode the store uses: "Transactions involving multiple attached databases are atomic, assuming
that the main database is not ":memory:" and the journal_mode is not WAL. If … the journal_mode is
WAL, then transactions continue to be atomic within each individual database file" (sqlite.org
`lang_attach.html`, fetched with `curl` 2026-10-31, copy in `~/waitron-campaign/a947-plan3a/`). The
store runs every file in that mode (`packages/store/src/index.ts:145-154`) and opens the two files
on separate connections, each with its own write queue (`:73-78`, `:251-260`). So no order of writes
and no single transaction can save both files as one. What the default does instead is keep ONE
point of no return: the `venue.db` save, which already holds the fiscal activation and the signed
chart. The role in `node.db` becomes a record that is brought into line with that chart: written
straight after, and checked again at every start before the box decides whether it sells or files.
A repair can only ever move a box towards the main role when the newest chart it holds was signed
with this box's own signing key (kept in its `node.db`, and in backups of this box) and names this
box the main box. Task 16 runs the case of a spare holding the main box's `venue.db`, and of a
chart signed with the spare's real key that names it anything other than the main box: in both the
repair does nothing.

**What it changes that the owner approved.** Spec §6.3 step 2 says "the role flips — one
transaction, the point of no return". With the default, the fiscal half stays one transaction; the
role follows it. Six fiscal test suites change (listed in "Changed test checks", marked
FISCAL — owner rules (Q1)); no fiscal source file changes.

**For your information, no answer needed:** four guards under `scripts/` also change, each only
because a table or check it names is renamed: `write-path-tables`, `schema-constraints`,
`classification-complete` and `two-file-foreign-keys` (their rows are in Group V of "Changed test
checks"). Each keeps its verdict; only the names it lists change.

**Recommended default: yes** — the venue save stays the one point of no return, the role follows
it, and every start, and the switch itself, finishes a role left behind (Task 13).

**The alternative:** keep a role row in `venue.db` as well, saved together with the promotion, and
read `node.db`'s role only when `venue.db` has no row for this box. The promotion stays one save and
the six fiscal suites change less. The cost is that a stale row can decide the role. Say box B was
the main box for a week in March, and box A has been the main box since. Once B rejoins as the
spare under its own id (slice 5d; today a joining box takes a fresh id, `adopt.ts:85`), A's
`venue.db` still holds B's March row saying "main box" (nothing on A ever rewrites another box's
row), and B, reading A's copy, would believe it is the main box — the failure this slice exists to
remove (§4, "nothing the spare needs to remember about itself can live there").

### Q2 — Before the spare receives the venue's keys, should it check that it is really talking to the main box?

**A worked example.** The owner adds the spare in the back office. Today, against a box on the
certificate it makes for itself (every box unless the operator supplies certificate files), the
spare's request fails at the certificate, so joining probably does not work over the venue's
network at all (probed with a stand-in server, not a box; see below). Making it work means trusting
the main box's certificate somehow. Suppose the spare simply trusted whatever certificate answered first, and someone's laptop
on the venue's Wi-Fi answers the name `waitron.local` before the real main box does. The spare would
send the owner's administrator password to that laptop. After this slice the reply also carries the
venue's key ring — which opens the AEAT certificate and the card provider's keys in any copy of
`venue.db` — and the venue certificate authority's private key, which signs certificates every till
trusts (design §4 item 1). A laptop that passes the request on to the real main box would end up
holding all three.

**What the join flow gives the person today.** The connect screen asks for the main box's address,
an administrator's id, password and, when enrolled, an authenticator code — nothing else
(`apps/setup/src/screens/connect-screen.ts:21-24`). The fetch's own comment says: "TRUST BOOTSTRAP:
the admin credential is sent over first-contact TLS with no verification of the primary. Safe only
on a trusted path" (`apps/server/src/mirror-bundle-fetch.ts:91-92`). Nothing shows a fingerprint
and nothing on the main box approves the join; the main box's approval of a joining device
(`pairing-mode.ts`) covers tills and print agents, not a spare. What does exist is a box showing its
authority's fingerprint: the connection page prints «Huella del certificado público» / "Public
certificate fingerprint" (`apps/server/src/connection-bootstrap-strings.ts:38,79`, value
`fingerprint256`, `box-tls-repair.ts:183`). A probe (`~/waitron-campaign/a947-plan3a/fetch-probe.mjs`,
Node v26.11.1) printed `fetch, default trust: refused: DEPTH_ZERO_SELF_SIGNED_CERT` for an HTTPS
server whose certificate no system authority signed, `node:https, ca pinned: 200` when told to trust
exactly that certificate, and `refused` again for a different pinned certificate (the control). A
second probe shaped like a box (`round3-probes/probe.mjs`: a certificate for `waitron.local` and
`localhost` signed by a private authority) printed `fetch default: refused:
UNABLE_TO_VERIFY_LEAF_SIGNATURE`, `200` with that authority pinned, and `refused` with another
authority or with only the box's own certificate pinned. A third (`round3-probes/probe2.mjs`) found a
stand-in server under its own authority received `0` requests from today's default `fetch` POSTing
a password, and `1` once trust was given (the control). The fetch sets no trust of its own
(`mirror-bundle-fetch.ts:93`), and nothing in `apps`, `packages`, `deploy` or `scripts` sets
`NODE_TLS_REJECT_UNAUTHORIZED` or a global dispatcher outside tests, or sets `NODE_EXTRA_CA_CERTS`
(one list passes it through to a child process, `fiscal-certificate-diagnosis-runner.ts:39`;
`git grep`). So
a real join to `https://waitron.local` probably fails at the certificate today — read and probed with
stand-in servers, not measured against a box — and some form of pinning is needed for joining to
work at all.

**Recommended default: yes, by comparing one fingerprint.** Before asking for the password, the
spare fetches the main box's public certificate (the same public download a till uses at pairing),
shows its fingerprint, and asks the person to confirm it matches the fingerprint the main box shows
on the dashboard's Servers screen, opened on a till or phone that is already paired (so that page
arrives over a connection the device already checks). Only then does the spare send the password,
over a connection that trusts that one certificate and nothing else, and it refuses a bundle whose
`boxCaPem` is not that certificate. Cost: one confirmation step on the spare, one line on the
Servers screen, English and Spanish words for both (Task 14b).

**The alternative:** the spare trusts whatever certificate answers first, and accepts it without
asking anyone to compare it. The setup screen and the runbook say plainly that a spare must be
joined only on a network the owner controls, and a backlog item records the check for slice 3b.
Cost: the password and the venue's keys go to whichever machine answers `waitron.local` first.

**Goal:** Everything a box must remember about itself — its role, its link to the main box, its
recovery-key check, its membership signing key and the main box's public key it trusts — lives in
that box's own `node.db`, so a box holding a copy of another box's `venue.db` still knows who it is.

**Architecture:** `node.db` is already opened beside `venue.db` and has never held a table. This
slice gives it one migration set, owned by a new package and registered as a module whose set is
applied to the node file; moves the five pieces of per-box state into it; makes every archive and
the sealed state carry a copy of it, and every restore put it back; adds the main box's public key,
the venue's key ring and its certificate authority's private key to the joining bundle; and makes
promotion, a box retiring itself and the main box adding a spare check the membership document
they sign over against keys `node.db` holds.

**Tech Stack:** TypeScript, `node:sqlite` through `@waitron/store`, drizzle-orm / drizzle-kit
0.31.x on the SQLite dialect, Vitest 4, Stryker 10, Ed25519 through `@waitron/membership`,
AES-256-GCM through `@waitron/credentials`.

**Spec:** [`docs/superpowers/specs/2026-10-21-a947-two-box-failover-design.md`](../specs/2026-10-21-a947-two-box-failover-design.md)
§11 slice 3a, §4 items 1–2 and the `node.db` paragraph, §6.3 step 2; and where it points, the
[topology design](../specs/2026-09-16-sqlite-litestream-topology-design.md) §2.1, §7.2 and §7.5.

## Global Constraints

- **Pre-live: no backwards-compatibility or data-migration code** (CLAUDE.md §3, last bullet). No
  code reads a `membership.node_key` row from `venue.db`, no code copies old `node_roles` rows, and
  an archive without `node.dump` is refused. Development and demo boxes are reset
  (`wa-wt reset demo <name>`); the PR's first line says so.
- **Every `node.db` table is classified `local`, keeps a `node_id` column, and every read and
  write names it** (CLAUDE.md §3).
- **No foreign key into or out of `node.db`.** A column naming a venue row (`origin_node_id`,
  `primary_node_id`) says at the column that nothing establishes the row exists in this file.
- **Lock order: `node.db`'s write lock is always taken OUTSIDE `venue.db`'s, never inside.**
  The write queues are independent (`packages/store/src/index.ts:73-78`).
- **Where one change spans both files, `venue.db` is saved first and `node.db` follows**, inside the
  node lock, and a re-run repairs a `node.db` left behind. Each site states it in a one-line comment
  (CLAUDE.md §3: "Splitting one logical change across transactions is a commented decision"). The
  sites: promotion (Tasks 7a, 13), the recovery-key replacement and its pack record (Task 9a), and
  first setup's key and pack 1 (Task 9c).
- **`withTransaction` refuses the node handle at compile time** (Task 1), because it drains
  `change_log` (`packages/db/src/tenancy.ts:30-42`, `change-log.ts:31`), which `node.db` lacks.
- **Migration numbers are indicative**: let `drizzle-kit generate` assign them. The node set ships
  exactly ONE migration. CLAUDE.md §3's drizzle rules hold.
- **Secrets stay sealed or hashed.** The recovery-key check is a scrypt hash (`break-glass.ts:40`);
  the signing key is sealed under the key ring with additional data binding it to the node id; no
  live login is added. `scripts/personal-log-params.test.ts` is unaffected (no field holding a
  person's name, email or tax number is added).
- **New error codes**, registered in their package's `errors.ts` and imported by the throwing file
  (`scripts/errors-reachable.test.ts`): `mirror.vault_not_empty` (OQ4), `mirror.primary_unconfirmed`
  (Q2 default), `node.identity_mismatch` (Task 10b), `membership.held_untrusted` (Task 15). The last
  two are states only a fault in Waitron produces; each site says so, as CLAUDE.md §3's refusal
  rule allows, and the screens show their generic text.
- **Names.** `node.db` tables: `node_mode`, `node_mirror_link`, `node_recovery_key`,
  `node_signing_key`, `node_primary_key`. They never reuse `node_roles` or `mirror_config`, so old
  and new never share a name while consumers move.
- **Mutation floor 90** for `@waitron/node-db` from its first commit (Task 4).
- Plain English in comments, commit messages and the PR. Every commit `git commit -s`. Run Vitest
  under `env -u AI_AGENT -u CLAUDECODE` when you need a passing test's output, and read the `Tests`
  count, never only the exit status.

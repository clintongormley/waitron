## Goal

A new installation name for setup, restore or promotion is chosen by these rules and nothing else:

1. It is the box's current UTC minute, five symbols (`identity: encodeMinuteIdentity(now)`, `packages/fiscal-verifactu/src/hour-selection.ts:498-504`).
2. Only after a clock on another machine agrees within 30 seconds (unchanged; `packages/fiscal-verifactu/src/hour-clock.test.ts`, "a name needs a second clock within 30 seconds of the box").
3. Setup and restore first wait until a minute start 90 to 150 seconds after the clock check; promotion does not (unchanged; `settles`, `hour-selection.ts:444`).
4. **New:** the minute must not already be in use. "In use" means its name appears in the history the box reads for this choice (Q2 default; what that is on each path is the next section). When it is in use, the box does what it does today for an equal name (measured below): a promotion waits for the next minute that is not in use, up to 150 seconds; a setup or restore whose settle-target minute is in use is refused with "carry on from" the next free minute start, because that start is always more than 150 seconds after the clock reading (the settle target is the first minute start after 90 seconds, `hour-selection.ts:449-451`, so the next is after 150; `apps/server/src/hour-restore-retired-inputs.test.ts:333` "refuses a fresh recovery of the older backup whose settle wait would land on the spent minute" → `allowedFromMs` 12:41, passing today and under the throwaway change).

What goes: "strictly later than every name in the history the box can read" (today's rule 3) and every time floor (the newest invoice record's time, the backup's creation time, a recorded name's own record time). A later name or a later record found is never a refusal and never a reason to pick a later minute. Part 2 flags it. The preproduction throwaway is unchanged (`packages/fiscal-verifactu/src/hour-throwaway-allocation.ts`).

**What stays outside this plan, and still refuses.** A name already in use is refused a second time when it is written: `validateForActivation` refuses `installation_used` when `registro_sif` already holds the same taxpayer, software and installation name, and `series_collision` when `invoice_series` already holds one of the new series codes, in the same transaction as the write (`packages/fiscal-verifactu/src/allocation.ts:101-125`, called from `activate` at `:419`). Setup, restore and promotion all reach it (`allocation-operation.ts:252-281` → `activate`). Receipts: `hour-standby-activation.test.ts:168` "also refuses reuse after the original SIF and every original series are retired" and `allocation.test.ts:496`, both passing under the measurement's throwaway change. So "that minute series doesn't exist in the database already" is already enforced, inside the fiscal boundary, against the database being written. This plan changes only the earlier choice, which today refuses far more.

**Does "already in use" include a name this box's own preparation record already chose?** Measured, two cases:
- The same event retried (a lost reply, a reload of the same attempt): the stored pick is returned again, never a new choice (`intent !== undefined → material(intent)`, `hour-selection.ts:425-438`; "retains exact intent across a boundary and lost reply, without another durable selection", `hour-selection.test.ts:208`). Nothing to decide.
- A different event (a replacement attempt, a new restore event after a page reload): its earlier pick is in `retained-intents`. Today a pick at the same minute makes the new event wait for the next one ("retains abandoned or uncertain intent and demands a later minute for its replacement", `hour-selection.test.ts:228`), and that case still passed under the measurement's throwaway equality-only change. **Default: these names count as in use (Q2).**

### What the 90-second wait now guarantees

The wait stays (owner). Rule 3 protected only names the box could read; the equality check now covers those exactly. What the wait guarantees is unchanged by this plan and is now the only protection for names the box cannot read: a name chosen by an earlier attempt that Start again forgot (A1206), by a box this one never saw, or held in a database a restore replaced. A setup or restore names a minute starting more than 90 seconds after its own clock reading (`hour-selection.ts:449-451`), so if an earlier choice A was made with its box `eA` off the true time and this one is `eB` off, this name is later than A's whenever `eA − eB < 90 s`, which holds whenever both clocks are within 30 seconds of the true time (A1206's argument, pinned by `hour-selection.test.ts:757` "a $action that has forgotten an earlier attempt's name still names a later minute when each clock was within 30 seconds", which passed under the throwaway change; Task 4 reruns it with A1206's deletion control). It does not protect against a name chosen under a clock that was more than about 90 seconds fast, because that name is ahead of true time; rule 3 used to catch the visible ones. See "What the owner accepts".

## What the owner accepts by this (state it in the PR)

- **A later name or later invoices no longer stop a setup, restore or promotion.** The box names its current minute and carries on. Part 2 makes the later ones visible to an administrator; nothing corrects them (separate design, backlog entry in Task 7).
- **Restoring a backup whose invoices are dated after the box's confirmed time now succeeds, and then the box will not take money until a clock confirmation covers it.** This is the existing clock-behind stop (`CLAUDE.md` §5, "More than a minute behind the latest fiscal record, write no record and take/refund no new money unless a clock confirmation covers it"), which A1207 does not change. `clockBehindChain` reads the latest record in every chain, "a restored database may hold only an older chain's records, and a new chain must not start before them" (`packages/fiscal-verifactu/src/clock-behind.ts:145-165`; `clock-behind.test.ts:96` "judges against the latest record in any chain"), and every sale, payment and refund route calls it (`git grep -l refuseWhileClockBehind -- 'apps/server/src/*.ts'`: `bill-payments.ts`, `bill-refunds.ts`, `payments-api.ts`, `tender-refund-api.ts`, `tender-refunds.ts`, `till-sale.ts`, `unpaid-departure.ts`). Activation does not call it, so the restore itself completes. Today rule 3 refuses such a restore until the clock passes the newest record. That the restore completes and then sales stop is reasoning from those call sites, not run end to end; Task 6 pins it with a test. See Q5.
- **A later name held only in a database the restore replaces is forgotten afterwards.** Measured: `apps/server/src/hour-recovery-placement-3.test.ts:217` "refuses an older selected hour before replacing a newer surviving %s destination" turns from a refusal into a placement under the throwaway change; after it the box's own newer name (`0CNSP` in that test) is in no database it reads. If a later setup, restore or promotion happens to run at that very minute in real time, it can repeat that name. The same holds for a later name carried only in a backup's module evidence. Q1's recommended option keeps these names in the flag; see Q6.
- **If a box and the machine confirming its clock are both wrong by the same amount and behind, the name is now taken in the past**, earlier than names the box can read; today the backup's creation time refuses that case ("W: the box and another device wrong together, below the backup's creation", `minute-selection-unknown-name.test.ts:385`, which turns into a selection under the throwaway change). It is refused only if that exact minute is in use.

## Open questions for the owner

Each is built with its default unless it says it waits. The PR lists them.

- **Q1. How are later names and later invoices flagged? (Part 2 waits for this answer; it blocks nothing in Part 1.)** Worked example: a box is restored on 3 November at 10:00 (its clock and the administrator's phone agree). The backup's old box had a clock 2 hours fast for its last evening: it holds the series `A-0CZZW`, `FF-0CZZW`, `R-0CZZW` (named for 3 November 11:40) and 37 invoices dated 3 November 10:05 to 11:58. The restore names `0D…` for 10:02 and finishes.
  - **A (recommended). A recorded alert, on the bell and by email, kept until someone marks it handled.** Code `fiscal.records_later_than_clock` (the fiscal area already claims `fiscal.`), recorded in the same transaction as the restore's or promotion's activation, mailed to administrators like `clock.records_misdated`. The person sees, in their language: "When this box was restored, its records held 37 invoices dated after the time the box confirmed (10:02), from 10:05 to 11:58 on 3 November, in series A-0CZZW, FF-0CZZW and R-0CZZW. They were issued while a clock was wrong. They stay as recorded. Go through them with your tax adviser, then mark this alert as handled." With names but no invoices it reads: "When this box was restored, its records held the invoice series name 0CZZW, for a time after the time the box confirmed (10:02). No invoices were issued under it here." The alert's details keep the later names, so a later choice can treat them as in use (Q6). The box also stops taking money until a clock confirmation (Q5), and today's `clock.behind_chain` alert shows beside it.
  - **B. No new alert: rely on what already shows.** The clock-behind alert appears in the box area while the box's clock is more than a minute behind the newest invoice ("the box's clock is behind its records"), and payments stop until a confirmation. It does not name the series, the count or the range, is not emailed, says nothing when only a later name exists (no invoices), and disappears when the stop lifts. Nothing to build.
  - **C. A line on the Box status page only**, listing the same facts as A, with no bell or email.
  - Sub-question for A: incidents need a `source`; **default: reuse the fiscal module's existing job source, as `clock.records_misdated` does** (`clock-stop-incidents.ts:92`). A new source is a migration.
  - Setup gets no flag under any option: a setup database holds no names (`boot.ts:926-931`).
- **Q2. Which names count as "already in the database"? (Built with the default; blocks nothing.)** **Default: every name the choice reads today** — the database the box will use, plus the box's own record of names it has chosen for other events, earlier abandoned attempts of the same setup, the database a restore replaces, and the backup's own record of names — and only an exact match counts. Alternative: only the database the box will use, the owner's literal words.

## Goal

The owner's rule, in one PR: the choice stops refusing later names and later records (Part 1), and a setup or restore whose minute is already in use waits for the next free one by itself, with an explanation and a countdown, instead of refusing (Part 1b, owner's Q4 answer). The later names and records are not flagged (owner's Q1 answer, 2026-10-30; Part 2 dropped).

A new installation name for setup, restore or promotion is chosen by these rules and nothing else:

1. It is the box's current UTC minute, five symbols (`identity: encodeMinuteIdentity(now)`, `packages/fiscal-verifactu/src/hour-selection.ts:498-504`).
2. Only after a clock on another machine agrees within 30 seconds (unchanged; `packages/fiscal-verifactu/src/hour-clock.test.ts`, "a name needs a second clock within 30 seconds of the box").
3. Setup and restore first wait until a minute start 90 to 150 seconds after the clock check; promotion does not (unchanged; `settles`, `hour-selection.ts:444`).
4. **New:** the minute must not already be in use. "In use" means its name appears in the history the box reads for this choice (Q2 default; what that is on each path is the next section). When it is in use, the box does what it does today for an equal name: it moves on to the next minute not in use, and waits for it if that minute start is at most 150 seconds after the clock reading, or is refused with "carry on from" that minute start if it is further away. After Part 1b that refusal also says when the name will be taken (`remainingMs`) and when the box can wait for it (`recheckInMs`), and the setup and restore pages show one countdown to the name, checking again by themselves at the earlier moment (Part 1b, "Design"); what the box chooses and records is unchanged. What that means on each path:
   - A promotion (no settle wait) waits for the next minute when only the current one is in use (Probe 1, "same minute → waiting 11:41").
   - A setup or restore's **first** select whose settle-target minute is in use is refused, because the next minute start is always more than 150 seconds after the clock reading (the settle target is the first minute start after 90 seconds, `hour-selection.ts:449-451`, so the next is after 150; `apps/server/src/hour-restore-retired-inputs.test.ts:333` "refuses a fresh recovery of the older backup whose settle wait would land on the spent minute" → `allowedFromMs` 12:41, passing today and under the throwaway change; review experiment #5). After Part 1b the page waits instead: one countdown to the name, with a quiet re-check at `allowedFromMs` minus 150 seconds on the box's clock (Part 1b, "Design"; measurement M-b4).
   - A setup or restore that **already recorded a wait**, whose target minute then comes into use, waits for the next minute instead, because by then the next minute start is within 150 seconds. Review experiment #4: first select at 11:40:00 waits for 11:42; a record naming `0CNNY` (11:42) then enters the history; a re-select at 11:41:50 answered `{"status":"waiting","targetMs":"…11:43…"}`, a 70-second wait, on today's code and under the throwaway change alike. Task 4a (iv) pins it.
   - A recorded wait is reused until a minute past its target (`now <= latestWait.targetMs + WAIT_REUSE_MS`, `hour-selection.ts:439-441`), so at exactly that instant the current minute is the one after the target. If that minute is in use, the box waits for the next minute not in use, as today. Round-3 experiment #17: wait recorded for 11:42, `0CNNZ` (11:43) then in the history, re-select at 11:43:00.000 → today's code answered `{"status":"waiting","targetMs":…11:44…,"remainingMs":60000}`. Task 4a (iv) pins it (lead's ruling on round-3 M1).

What goes: "strictly later than every name in the history the box can read" (today's rule 3) and every time floor (the newest invoice record's time, the backup's creation time, a recorded name's own record time). A later name or a later record found is never a refusal and never a reason to pick a later minute. Nothing new reports it (owner, Q1, 2026-10-30): a later name is reported by nothing, and later invoices by the alerts that exist today ("What already shows today"). The preproduction throwaway is unchanged (`packages/fiscal-verifactu/src/hour-throwaway-allocation.ts`).

**Does "already in use" include a name this box's own preparation record already chose?** Measured, two cases:
- The same event retried (a lost reply, a reload of the same attempt): the stored pick is returned again, never a new choice (`intent !== undefined → material(intent)`, `hour-selection.ts:425-438`; "retains exact intent across a boundary and lost reply, without another durable selection", `hour-selection.test.ts:208`). Nothing to decide.
- A different event (a replacement attempt, a new restore event after a page reload): its earlier pick is in `retained-intents`. Today a pick at the same minute makes the new event wait for the next one ("retains abandoned or uncertain intent and demands a later minute for its replacement", `hour-selection.test.ts:228`), and that case still passed under the measurement's throwaway equality-only change. **Default: these names count as in use (Q2).**

### What the 90-second wait now guarantees

The wait stays (owner). Rule 3 protected only names the box could read; the equality check now covers those exactly. What the wait guarantees is unchanged by this plan and is now the only protection for names the box cannot read: a name chosen by an earlier attempt that Start again forgot (A1206), by a box this one never saw, or held in a database a restore replaced. A setup or restore names a minute starting more than 90 seconds after its own clock reading (`hour-selection.ts:449-451`), so if an earlier choice A was made with its box `eA` off the true time and this one is `eB` off, this name is later than A's whenever `eA − eB < 90 s`, which holds whenever both clocks are within 30 seconds of the true time (A1206's argument, pinned by `hour-selection.test.ts:757` "a $action that has forgotten an earlier attempt's name still names a later minute when each clock was within 30 seconds", which passed under the throwaway change; Task 4a reruns it with A1206's deletion control). It does not protect against a name chosen under a clock that was more than about 90 seconds fast, because that name is ahead of true time; rule 3 used to catch the visible ones. See "What the owner accepts".

## What the owner accepts by this (state it in the PR)

- **A later name or later invoices no longer stop a setup, restore or promotion.** The box names its current minute and carries on. Later invoices are already listed by `clock.records_misdated` once a clock confirmation lifts the stop ("What already shows today"). A later name with no invoices under it is reported by nothing; the owner: "A later series with no invoices is not a problem" (Q1, 2026-10-30). Nothing corrects the later invoices (separate design, backlog entry in Task 7).
- **Restoring a backup whose invoices are dated after the box's time now succeeds, and then the box will not take money until a clock confirmation covers it.** On a box that sends records to the tax agency, the box asks the agency for its time about once a minute during the stop, and an answer within a minute of the box's clock lifts it (`apps/server/src/guide/en/box-status.md:177-179`, read, not run); otherwise two tills or handhelds at different addresses, or an administrator's own phone or computer, are needed (`:180-183`). This is the existing clock-behind stop (`CLAUDE.md` §5, "More than a minute behind the latest fiscal record, write no record and take/refund no new money unless a clock confirmation covers it"), which A1207 does not change. `clockBehindChain` reads the latest record in every chain, "a restored database may hold only an older chain's records, and a new chain must not start before them" (`packages/fiscal-verifactu/src/clock-behind.ts:145-165`; `clock-behind.test.ts:96` "judges against the latest record in any chain"), and every sale, payment and refund route calls it (`git grep -l refuseWhileClockBehind -- 'apps/server/src/*.ts'`: `bill-payments.ts`, `bill-refunds.ts`, `payments-api.ts`, `tender-refund-api.ts`, `tender-refunds.ts`, `till-sale.ts`, `unpaid-departure.ts`). Activation does not call it, so the restore itself completes. Today rule 3 refuses such a restore until the clock passes the newest record. That the restore completes and then sales stop is reasoning from those call sites, not run end to end; Task 6 pins it with a test. See Q5.
- **A later name held only in a database the restore replaces is forgotten afterwards.** Measured: `apps/server/src/hour-recovery-placement-3.test.ts:217` "refuses an older selected hour before replacing a newer surviving %s destination" turns from a refusal into a placement under the throwaway change; after it the newer name (`0CNSP` in that test) is in no database the box reads. That test chose `0CNSP` from a separate state folder (`newer-state`, `:222-228`); the case where the same state folder chose the name and runs the restore, so the name may still sit in the record of picks that Q2's default reads, was not run. If a later setup, restore or promotion happens to run at that very minute in real time, it can repeat that name. The same holds for a later name carried only in a backup's module evidence. No flag keeps these names (Part 2 is dropped); see Q6.
- **If a box and the machine confirming its clock are both wrong by the same amount and behind, the name is now taken in the past**, earlier than names the box can read; today the backup's creation time refuses that case ("W: the box and another device wrong together, below the backup's creation", `minute-selection-unknown-name.test.ts:385`, which turns into a selection under the throwaway change). It is refused only if that exact minute is in use.

## Design

**Chosen: the page waits; the box adds two values to its refusal; the page shows one countdown.**

- **Box.** The 150-second refusal (`hour-selection.ts:456-457`) also carries, measured from `now`, the box reading this choice used:
  - `remainingMs = allowedFromMs − now`: time until the name is taken. This is what `remainingMs` already means in the box's `waiting` answer (time until the minute it waits for), so one key means one thing on every answer.
  - `recheckInMs = allowedFromMs − WAIT_BOUND_MS − now`: time until the box can record its ordinary wait for that minute (M-b4: exactly then, and nothing is written before). Above zero by the refusal's own condition (`targetMs − now > WAIT_BOUND_MS`).
  The 150-second rule stays in the box; the page needs no copy of it. Nothing else in the choice changes: which name, when it is taken, what is recorded, and that the refusal records nothing.
- **Page arithmetic.** On that refusal the page shows one "Continues in" figure starting at `remainingMs` and counting down on its own `performance.now()`; once `recheckInMs` has passed it re-checks with the box quietly (a fresh clock comparison, then a select), while the figure keeps counting. The box's answer then sets the figure: an ordinary `waiting` answer restarts it from that answer's `remainingMs` (150 000 when the re-check is on time, so the figure carries on without a jump; less, or a minute more, when the re-check is late, M-b7: the figure follows the box); the same refusal again restarts it from the new `remainingMs` with the new `recheckInMs` (so it repeats while the minute is taken); `selected` ends it.
- **The sentence stays for the whole wait.** The page remembers that it got here through a taken minute (a flag in `ClockWait`), and while the flag is set it draws the taken-minute sentence in place of "Waiting to confirm the time, so no invoice series is ever repeated.", through the refusal phase and the box's ordinary wait that follows. The flag is set by the taken-minute refusal, kept by an automatic re-check's `waiting` answer, and cleared by `selected`, by any other explanation, and when the person presses Make the series (it calls `ClockWait.show()` with nothing first, `first-hour.ts:309`, `recovery-hour.ts:307`) or Check again (`first-hour.ts:288`).
- **How it is drawn (no surprise in 15a/15b).** `createWaitCountdown`'s `start(duration)` becomes `start(duration, checkAfter = duration)` (`setup/wait-countdown.ts:33`): the figure counts `duration` down to zero, and the callback runs once when `checkAfter` has passed. Today's callers pass one value and behave as now. `ClockWait` gains `{ kind: "next-minute"; remainingMs; recheckInMs }`, the flag, and a getter `counting` (true for a `waiting` answer or a `next-minute` explanation; `waiting` stays true for both, so Make the series stays disabled). `ClockWait.renderWait(words)` draws the wait section for both (`data-test="hour-wait"`; the sentence in `role="status"` with `data-test="minute-taken"` when the flag is set; "Nothing to do; keep this page open."; "Continues in" with `data-test="remaining"`). `renderClockProblem` draws nothing for `next-minute`. Each page changes exactly one condition: `result?.status === "waiting"` becomes `this.#wait.counting` (`first-hour.ts:514`, `recovery-hour.ts:417`), so `renderWait` is drawn during the refusal phase too. That is the whole page change in Tasks 15a and 15b.
- Unchanged: a preview refused on load still explains nothing (M-b1), so a page reloaded during the refusal phase shows nothing until Make the series is pressed again (read, not run: nothing is recorded, and `ClockWait.showPreview`, `clock-wait.ts:225-233`, shows only a recorded wait). A promotion still waits by itself up to 150 seconds and is otherwise refused; its caller now also gets the two values.
- The name is taken at `allowedFromMs` (M-b4), the earliest the rules allow, and the same moment option (ii) below would reach.

**Not chosen: (ii) the box answers `waiting` past the 150-second limit.** It would record waits further ahead than the box has ever recorded (M-b5: "Nothing is recorded" is the limit's design), change the decision at `hour-selection.ts:456-457` for setup and restore, and turn the three server cases in M-b5, which check that nothing is written after the refusal, into cases that record a wait. A recorded wait also cannot say why it waits (`Wait`, `hour-selection.ts:50-53`, has no reason), so a page reloaded during it would lose the taken-minute sentence. It reaches the name no sooner (M-b4). The chosen design changes no fiscal state.

**The stored pick: the refusal stays exactly as built** (`hour-selection.ts:408-412`; no `remainingMs`, so the page never counts it down). What was shown:
- A new name inside the same attempt is refused by the record format: one pick per attempt, and a second or changed pick is `history_invalid` (M-b3; `hour-selection.ts:164`, `:307`).
- A new attempt would be safe for the series: the old pick stays in the record of picks and the new attempt skips it (M-b3's control), and the old attempt's input cannot be activated (M-b2's `hour-preparation.test.ts` case, then `installation_used`, `allocation.ts:101-125`).
- But the pages do not start a new attempt by themselves: a setup has one event per attempt (`packages/provisioning/src/first-setup-runtime.ts:158`), and the setup-from-backup restore reuses its stored event (M-b9). Only a Cloud restore reopened gets a new one.
- The refusal mostly shows at activation, where the setup app shows its general message with the code (M-b1).
- How often: no server run reaches it (M-b2); the module reaches it only when a history it reads gains this very minute between the pick and its use. Read, not run: on a setup or restore none of the histories it reads is written by anyone else during the attempt; a promotion's copy of the venue database follows the primary, and a promotion has no page.
- So it is not changed in this PR; Task 16 adds a backlog entry, and "For the owner" explains it.

## For the owner

**One case still stops instead of waiting.** If a setup or restore has already chosen its series name and, before it finishes, that same name turns up in the box's records, the box refuses to finish it. A new name for the same attempt is not possible: the box keeps one name per attempt. A new attempt would be safe, but the pages do not start one by themselves, and the refusal mostly appears at the last step as a general message with a code. Example: a restore picks `0CNNY` (11:42); before the person presses Recover, a record naming `0CNNY` appears; Recover then fails with "The backup could not be staged. Check the file, key and environment. (sif.allocation_invalid)" (that message read from the setup app's code, not run). In the tests this happens only when the records are changed by hand between the choice and the finish, and no server test reaches it. It is left as a backlog entry: start a new attempt by itself and word that message.

**The setup command.** `waitron-provision` shows any refusal as its code and values on one line, so a taken minute will read `sif.allocation_invalid {"reason":"minute_in_use","allowedFromMs":…,"remainingMs":…,"recheckInMs":…}`, with times in milliseconds. You could have it say the page's sentence and when to run it again instead. Default: leave it as it is for this PR.

**The words** (table above) are for your approval, including whether "already has a series" or "is already taken" reads better (the second is true even when the minute was chosen by an attempt that never finished).

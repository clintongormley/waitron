Add `screens/cloud-sign-in-screen.ts` and English and Spanish wording in `i18n/strings.ts`. Admin Next stages the password and PIN in memory and the Live owner claim follows Venue. In `apps/server/src/setup-cloud-sign-in.ts`, keep one short-lived administrator draft in memory across the navigation. Require HTTPS, the configured local origin, an HttpOnly Secure Strict installer cookie and the initiating tab marker on the local POSTs. The first browser to start is the installer authority. Acknowledge draft restoration before erasing it so a lost reply can be retried. Clear it on cancellation or expiry. The ordinary case preserves the draft. A restart asks the installer to re-enter it. Browser storage holds only an opaque tab marker, never passwords, PINs or Cloud codes.

Reuse the signed start, redeem, status and completion in `cloud-client.ts` and `cloud-sign-in.ts`. Reuse the callback page in `cloud-sign-in-callback.ts` with the setup return path, no-store, no referrer and removal of the code from history before the POST. Stop at account-bound on redeem. Skip abandons any pending attempt owned by that tab. Attach only from the authenticated wizard request after successful publication in `setup-api.ts` or `setup-first-fiscal-api.ts`. Read the saved profile through the installed-box reader and keep it with the existing Cloud attempt and its published node identity for retry. Use signed status to recover a lost reply. Only that published venue can resume attachment. Cloud failure leaves local setup usable and the existing Cloud services screen available to finish the connection.

# A789 — Last orders without an offset: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Implementers are dispatched as `subagent_type: "implementer"`.

**Goal:** A period is when its menu can be ordered. The end offset goes (slice 1), the period "Keep
open" goes (slice 2), the server accepts a late send the kitchen agreed to and marks it (slice 3), and
the till warns and asks (slice 4).

**Spec:** `docs/superpowers/specs/2026-10-18-a789-last-orders-design.md` (read it whole; this plan
argues from it). Pictures: `docs/backlog/mockups/a789-last-orders/`.

**The owner's answer to Q39 (2026-10-18), verbatim:** "All recommended, configurable whether
manager's pin required." So choices (a)–(g) are as the design recommends, except (b): whether
confirming a late send needs a manager's PIN is a **setting, off by default**, so "anyone who can
send" stays the default.

**Tech stack:** TypeScript, Hono, drizzle-orm 0.45.4 with drizzle-kit 0.31.11 over `node:sqlite`,
Lit, Vitest 4.1.11 (node and real-Chromium browser projects).

**Words used here.** A **period** is a named stretch of a department's day with its own menu. The
**end offset** is today's per-period number of minutes that moves last orders before or after the
period's end. **Picking** a dish is putting it on an order; **sending** is sending it to the kitchen.
A **clash check** is any check that refuses an hours change because some period's last orders would
run into what follows it.

How claims are marked: **(ran)** means a command was run on 2026-10-21 against `main` at
`8f17dac0b` and the result is quoted; **(read)** means read in the code at that commit, not run.

## Where the manager's-PIN setting lives (decided here, built in slices 3–4)

**Choice: one venue-wide flag on `service_settings`, shown in the dashboard's service settings panel
under its "Changes after sending" heading, beside "Allow changes to items already sent to the
kitchen". Off by default.**

Where ordering-related settings live today (read):

| --- | --- | --- |

| device profiles | what a device may do (actions), zones | `CLAUDE.md` §3 "A device's profile and the signed-in person must both allow…" |

Why `service_settings`: the question is about sending a dish to the kitchen after its period, which
is the same subject as its "Changes after sending" neighbours (`edit_sent_lines` is read by the till
through `apps/server/src/till-api.ts:3858`, read). The department and zone policies are about how an
order starts and is paid, and the period dialog is about one period; a per-period or per-department
PIN rule has no use the owner named. A `flag` column (`packages/db/src/schema/columns.ts:146`, an
integer with no CHECK) added with `.notNull().default(false)` is expected to generate
`ALTER TABLE … ADD` rather than a rebuild (conventions-data.md "A generated table rebuild can copy a
new column out of the old table": an added column with no CHECK, type or key change beside it came
out as `ALTER TABLE … ADD`); slice 3 reads the generated SQL to confirm. `settings.ts:23-25` warns
that adding a CHECK to this table makes drizzle rebuild it.

Proposed column `late_send_needs_manager` (`lateSendNeedsManager`), proposed label "Ask for a
manager's PIN to send a dish after its period". Slice 3 settles the final words with the panel's
other labels in front of it.

## Slice 1 — retire the end offset (one PR, branch `feat/a789-1-retire-end-offset`)

the import check, the dialog's field and its strings, the station guides' "sending" band, and the

its subject survives (a refusal that writes nothing, a holiday-date walk, a clash-list reading), **
rewrite** it to reach the same subject without an offset, and name the new check. Fixture-only edits
(dropping `endOffsetMinutes: 0` or an offset passed but not asserted on) are not changed checks.

# A789 — Last orders without an offset: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Implementers are dispatched as `subagent_type: "implementer"`.

**Goal:** A period is when its menu can be ordered. The end offset goes (slice 1), the period "Keep
open" goes (slice 2), the server accepts a late send the kitchen agreed to and marks it (slice 3), and
the till warns and asks (slice 4).

**Spec:** `docs/superpowers/specs/2026-10-18-a789-last-orders-design.md` (read it whole; this plan
argues from it). Pictures: `docs/backlog/mockups/a789-last-orders/`.

**The owner's answer to Q39 (2026-10-18), verbatim:** "All recommended, configurable whether
manager's pin required." So choices (a)–(g) are as the design recommends, except (b): whether
confirming a late send needs a manager's PIN is a **setting, off by default**, so "anyone who can
send" stays the default.

**Tech stack:** TypeScript, Hono, drizzle-orm 0.45.4 with drizzle-kit 0.31.11 over `node:sqlite`,
Lit, Vitest 4.1.11 (node and real-Chromium browser projects).

**Words used here.** A **period** is a named stretch of a department's day with its own menu. The
**end offset** is today's per-period number of minutes that moves last orders before or after the
period's end. **Picking** a dish is putting it on an order; **sending** is sending it to the kitchen.
A **clash check** is any check that refuses an hours change because some period's last orders would
run into what follows it.

How claims are marked: **(ran)** means a command was run on 2026-10-21 against `main` at
`8f17dac0b` and the result is quoted; **(read)** means read in the code at that commit, not run.

### The offset-at-0 evidence — design §7

Question: which of today's clash checks still refuse something when every offset is 0?

**1. The writers never check at offset 0 today (read).** `endOffsetClash` returns `null` before
reading any schedule when every period of the departments it was given has offset 0
(`menu-timetable.ts:200`), and every writer calls it with `validateZeroOffsets = false`
(`scheduleEndOffsetClash` `:254-256`, `departmentEndOffsetClash` `:259-266`, `assertWeekEndOffsets`
`:701`, `writeMenuPeriod` `:615`). So on a venue whose offsets are all 0 — what every venue
becomes once the offset is gone — the period, week, season, special-day and period-delete writers
refuse nothing through it now.

**2. The time-zone check cannot fire on stored data at offset 0 (read).** `assertPeriodEndOffsets`
(`:268-271`) is the one caller that checks at 0 (`validateZeroOffsets = true`), on a time-zone change
(`apps/server/src/venue-details.ts:261-271`). A time-zone change is refused outright once the clock
holds a start change (`venue-details.ts:243-244`, reason `business_day_history`), so when it runs
the schedule has one changeover. At offset 0 `findEndOffsetClash` refuses only a placement whose
cutoff is at or before its start (`period-end-offset.ts:55`), i.e. an empty or reversed range under
that changeover, and the hours parser refuses exactly those when a range is written
(`service-day.ts:65-66`: `empty` and `order`). No test pins a time-zone refusal (ran:
`grep -rn '"end_offset"' apps/server/src/*.test.ts` finds none).

**3. The import check cannot fire at offset 0 (read).** `validateEndOffsets` uses the bundle's one
changeover (`configuration-transfer.ts:511`), and the import first parses every season range and
special-day paint under that changeover (`configuration-transfer.ts:376-391`, `parseClosedRanges`),
which refuses empty and reversed ranges as above.

**4. `sending_cutoff` is never chosen at offset 0 (ran).** `/tmp/a789-probe/` holds the plan
reviewer's copy of the per-placement reason chain at `business-day-schedule.ts:433-455` (single
placement; it leaves out `cutoffClashes`, which needs `p.offset > 0` at `:422`), beside the same
chain with `sending_cutoff` and the cutoff terms removed. Ran 2026-10-21 with
`node /tmp/a789-probe/control2.mjs`: over 84,049,920 cases (every start and end on the quarter-hour
grid, every pair of quarter-hour changeovers) `sendingAt0: 0` and `differ: 0`; over 2,997,933
random off-grid changeovers `sendingAt0: 0`, `differ: 0`. **Control:** the same grid at offset −15
chose `sending_cutoff` 580,640 times, so the copy can choose it.

**5. Why not a "forced to 0" test run (ran, kept for the record).** Forcing every offset read to 0
in a throwaway worktree and running the suites failed 93 tests — the tests that depend on a nonzero
offset, listed under "Changed test checks" — but a second run with the clash checks also switched
off could not differ from the first for the writers, because the forcing came before the early
return in point 1. That run is evidence for the changed-test list only, not for §7.

The one unit case that refuses at offset 0, `period-end-offset.test.ts` "end offsets for an hours
save after the start moved › judges the weekly ranges under the start in force alone" (`:437-440`),
calls `findSeasonEndOffsetClash` directly with a 22:00–04:30 range under a changeover that moves to
03:00; no writer can store that range (point 2's parser runs under every changeover the schedule
holds, `menu-timetable.ts:730`), and the start-change check refuses the change instead (ran, passing
with the clash checks off: `business-day-schedule.test.ts` "names only the range that crosses the
new start, leaving its day's other range clear", `:418-428`, reason `range`). It goes with the
function.

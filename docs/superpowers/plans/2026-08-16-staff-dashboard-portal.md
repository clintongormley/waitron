# Staff Self-Service Dashboard Portal — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use `- [ ]`.

**Goal:** A **staff self-service portal** inside the existing management dashboard. A `staff`-role person logs into the dashboard (the login infra is already role-blind — see facts), and the shell shows a **staff view** — their own roster, request a shift give-away/cover, accept a swap offered to them, view/request absences — instead of the manager screens. This is the #90 fast-follow ("the staff dashboard portal reuses #90's surface-agnostic verbs/read-models via a management/staff session resolver"), the browser twin of #90's till-PIN-session surface.

**Architecture:** (1) a **whoami** endpoint `GET /management-api/session/me` → `{ personId, role }` (via `resolveManagementSession`, NO `authorizeManager`); (2) a **staff route group** `/management-api/me/schedule/*` mirroring #90's `/api/schedule` but resolving identity from the management session — `requireManagementSession` → `resolveManagementSession` → `personId` → the existing #90 verbs (never `authorizeManager`, never the body for identity); (3) a **role-aware dashboard shell** — the boot probe + post-login use whoami, `staff` → the new staff view, manager/supervisor/admin → the existing manager screens unchanged; (4) a `<dashboard-my-schedule-screen>` + `DashboardApi` methods + i18n.

**No migration.** `management_sessions` already exists and is role-blind; the #90 verbs and workforce tables are unchanged. If a task appears to need a migration, STOP and flag it.

## Global constraints
- **TDD, always; prove guards by deletion.** **The requester identity is ALWAYS the session's `personId`, never the body** (the #90 property) — a real-PG test proves a staff session acts only on its own rows and can't act as another person via a body field, proven by deletion.
- **NEVER call `authorizeManager` on the staff routes.** `staff` has an EMPTY permission set (`permissions.ts:53`), so `authorizeManager` throws for every staff person. The staff routes gate on **session identity only** (`resolveManagementSession` returns `personId` + `role`, role-blind). Guarding the manager routes is unchanged.

## Resolved facts (read before starting)
1. **The management session is ROLE-BLIND end to end.** `startManagementSession` (`management-session.ts:27-36`), `loginManager` (`manager-login.ts:15-41`, a misnomer — no role check), and `resolveManagementSession` (`management-session.ts:43-69`, gates only idle-30min + `person.suspended`, RETURNS `role` but never gates on it) all work for a staff-role person. A staff person with a `password_hash` (manager sets it via the existing `POST /management-api/staff/:id/password`) or a passkey can log in TODAY and get the `waitron_management_session` cookie. The login screen (`login-screen.ts`) already lists ALL active persons and accepts password/TOTP/passkey role-blindly.
2. **The dashboard shell today ASSUMES manager.** `dashboard-app.ts` `#probeSession` calls `api.listStaff()` (gated `person.manage`), so a staff session 403s and drops to login; every nav face is manager-permissioned. **This is the thing to fix** — the shell must learn the role and branch. Login returns only `{ personId }` (`management-api.ts:248`); there is NO whoami endpoint today → add one.
3. **The #90 verbs take a bare `personId` and self-police ownership** (`workforce/src/index.ts:27-47`): `requestSwap`/`acceptSwap`/`createAbsence`/`listShiftsForPerson`/`listSwapsForPerson`/`listAbsencesForPerson`. #90's routes (`apps/server/src/schedule-api.ts`) resolve identity via `requireSession` (till) then pass `personId`; the staff portal swaps ONLY that resolver for `requireManagementSession`+`resolveManagementSession`. Read `schedule-api.ts` and mirror its route bodies + request screens (`request-screens.ts`).
4. **`resolveManagementSession` is exported** (`identity/src/index.ts:11`); `requireManagementSession(c)` (`apps/server/src/management-session.ts:58-62`) extracts the cookie sessionId. Compose them inline (no `authorizeManager`) in an `asStaff` helper = `withTenant`+`asAppUser`, mirroring #90's `asStaff`.

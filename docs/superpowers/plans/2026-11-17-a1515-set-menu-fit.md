# Set menus, piece 3: the fit — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One pure, browser-safe function that, given the set menus on a bill, the set-menu dishes on
it and the set menus offered to it, finds the cheapest mix of set-menu types and where each dish sits,
exactly, within the agreed size bound.

**Architecture:** Three source files in `@waitron/shared`. A placement solver
(`set-menu-placement.ts`) places dishes into set-menu places for a FIXED number of each type, as a
minimum-cost flow, and returns with its cost a lower-bound plane for every other mix. A search
(`set-menu-search.ts`) walks the mixes of types cheapest-bound first, solving a placement only while
some unsolved mix could still beat the best found. The public function (`set-menu-fit.ts`) checks
the input, groups dishes, runs the search, and deals the winning placement out to individual set
menus.

**Tech Stack:** TypeScript 7, Vitest 4, Stryker (shared's mutation floor is 90). No new dependency.

**Spec:** [docs/superpowers/specs/2026-11-17-set-menus-design.md](../specs/2026-11-17-set-menus-design.md),
section 3 "The fit: how the bill decides". Read that section before Task 1.

**Order:** after A1515-REMOVE, as the spec says. The fit's files touch nothing that removal does;
the overlap is `packages/shared/src/index.ts` and `errors.ts`, so it rebases cleanly either way, and
whether to start it early is the watcher's call. Piece 1 can proceed alongside; pieces 2 and 4 call
this piece's `fitSetMenus`.

## Why the method differs from the spec's suggestion

The spec offered "try every split of the unfixed set menus between the types and solve each
placement", leaving the method to the builder provided it is exact and meets the bound (at least 40
set menus, 5 types and 200 set-menu dishes, fast enough to feel instant). A throwaway prototype was
measured on 17 November 2026 on the owner's Mac (Node 26.13.1) over 30 seeded random tables of 5
types, 40 set menus and 200 dishes. Each type listed a random 60% of 40 products, prices were €1
apart, and surcharges went up to €8:

| Method                                                         | Worst fit | Placements solved |
| -------------------------------------------------------------- | --------- | ----------------- |
| Every split, cheapest price first, stop past the best          | 8–12 s    | up to 117,605     |
| Decide each type's count in turn, bound by loosened capacities | 1–7 s     | up to 69,687      |
| Planes from each solved placement (this plan's method)         | 43 ms     | up to 38          |

The third method agreed with an exhaustive search over every mix on 500 small random tables (249 of
them coverable). It also agreed with the second method on 300 more. As a control, the same
comparison with the planes' slopes halved, which makes them overestimate, reported 52 wrong totals
out of 300.

The plan's fresh-context review re-ran the method on 3,000 harder tables against exhaustive search,
with 0 mismatches (its control gave 91). With this plan's tie-break weights added, it measured up to
84 ms at 47 set menus.

Every split remains fast enough for 3 types at 40 set menus (49 ms in the review's run) but not for
5. These figures come from a prototype, not this plan's code: Task 5 measures the real thing.

```ts
// packages/shared/src/set-menu-fit.ts
export interface SetMenuOfferDish {
  readonly productId: string;
  readonly variantId: string | null; // null: a product with no variants
  readonly surchargeCents: number; // 0: included
}
export interface SetMenuOfferLine {
  readonly count: number; // the "N ×"
  readonly courseIds: readonly string[]; // "Mains or Starters": two ids
}
export interface SetMenuOffer {
  readonly id: string; // the set menu's version id recorded on the bill
  readonly priceCents: number;
  readonly dishes: readonly SetMenuOfferDish[];
  readonly lines: readonly SetMenuOfferLine[];
}
export interface SetMenuOnBill {
  readonly id: string; // the set-menu line's id
  readonly fixedOfferId: string | null; // a type the waiter fixed, or the bill froze
}
export interface SetMenuPlace {
  readonly setMenuId: string;
  readonly lineIndex: number;
}
export interface SetMenuDish {
  readonly id: string; // one unit: the spec stores a set-menu dish one unit per line
  readonly productId: string;
  readonly variantId: string | null;
  readonly countsAsCourseId: string;
  readonly pinnedTo: SetMenuPlace | null; // frozen after a payment; its set menu must be fixed
}
export interface SetMenuFitPrevious {
  readonly offerBySetMenu: ReadonlyMap<string, string>;
  readonly placeByDish: ReadonlyMap<string, SetMenuPlace>;
}
export interface SetMenuFitInput {
  readonly offers: readonly SetMenuOffer[];
  readonly setMenus: readonly SetMenuOnBill[];
  readonly dishes: readonly SetMenuDish[];
  readonly previous: SetMenuFitPrevious | null;
}
export type SetMenuFit =
  | {
      readonly kind: "fitted";
      readonly totalCents: number;
      readonly setMenus: readonly { readonly id: string; readonly offerId: string; readonly priceCents: number }[];
      readonly dishes: readonly { readonly id: string; readonly place: SetMenuPlace; readonly surchargeCents: number }[];
    }
  | { readonly kind: "uncovered"; readonly setMenusNeeded: number | null }
  | { readonly kind: "too_large" };

export const MAX_SET_MENU_MIXES = 250_000;
export const MAX_SET_MENU_AMOUNT_CENTS = 1_000_000; // €10,000
export function fitSetMenus(input: SetMenuFitInput): SetMenuFit;
```

**Matching a dish.** An offer lists a dish when one of its entries has the same `productId` and the
same `variantId`; null matches only null. The dish may sit in line `l` of that offer when
`l.courseIds` holds its `countsAsCourseId`. Its price there is the entry's `surchargeCents`.

**The fitted result.**

- `fitted.setMenus` and `fitted.dishes` are sorted by `id`.
- `totalCents` is the sum of every set menu's price and every dish's surcharge, pinned dishes
  included.
- A bill with no set menus and no dishes is `fitted` with total 0.

**The uncovered result.** `uncovered.setMenusNeeded` is a total number of set menus that would cover
every dish: the fixed ones are kept, and the rest are free to take any type. It is the smallest such
number unless a smaller count could not be checked inside the size limit (Task 5).

It is `null` when no number would cover the dishes. That happens when some dish is listed by no
offer with a line accepting its course, or when set menus are on the bill and `offers` is empty.

**The too-large result.** `too_large` means the unfixed set menus can be split between the offers in
more than `MAX_SET_MENU_MIXES` ways (5 offers allow up to 47 unfixed set menus). This limit is **my
call**, chosen to meet the spec's bound. Pieces 2 and 4 decide what the till and the server do with
this result.

**Which outcome wins**, in order:

1. The lowest `totalCents`.
2. The fewest set menus whose offer changes. Only unfixed set menus that are in
   `previous.offerBySetMenu` AND still on the bill count, and only when their previous offer is
   still offered.
3. The fewest dishes whose (offer, line) changes. Only dishes in `previous.placeByDish` that are
   still on the bill count, and the offer is read from `previous.offerBySetMenu`. Entries in
   `previous` naming set menus, offers or dishes no longer present are ignored.
4. The same answer for the same input in any order. Inputs are sorted by `id` first.

Beyond the ranking, dealing out (Task 4) keeps each dish in the same set menu wherever its (offer,
line) did not change.

## Review Focus

1. **A bill with set menus and no dishes, or fewer dishes than places.** Every set menu should be
   charged at the cheapest offer ("fewer than 4 still pays for 4"). Pinned by Task 3, "charges empty
   set menus at the cheapest offer".
2. **Two offers at the same price.** Nothing should reshuffle when nothing changed, and the answer
   should be the same whatever the input order. Pinned by Task 4, "keeps an equal-cost type" and
   "is the same in any order".
3. **A dish whose variant is not listed while its product is** (the bottle of wine on a set menu
   that lists only the glass). It should be uncovered, never matched on the product alone. Pinned by
   Task 3, "matches a dish by product and variant".
4. **A full table of 40 set menus gaining one dish no place can take.** The fit should answer 41,
   never "no number would". Pinned by Task 5, "asks for one more at a full table".
5. **A dish whose type changes for a cheaper mix.** It should stay in its set menu when its own
   (offer, line) did not change. Pinned by Task 4, "the set menu that changes type is the one that
   lost its dish".

### Task 1: The placement solver and its planes

**Files:**

- Create: `packages/shared/src/set-menu-placement.ts`
- Test: `packages/shared/src/set-menu-placement.test.ts`

**Interfaces:**

- Produces:

```ts
export interface PlacementProblem {
  readonly classes: readonly { readonly count: number; readonly arcs: readonly { readonly pair: number; readonly cost: number }[] }[];
  readonly capacities: readonly number[]; // one per pair; may be 0
  readonly uncoveredCost: number; // what leaving one dish unplaced costs; larger than any real total
}
export interface Placement {
  readonly cost: number; // includes uncoveredCost × uncovered
  readonly uncovered: number;
  readonly flows: readonly (readonly { readonly pair: number; readonly count: number }[])[]; // per class
  readonly capacityPrices: readonly number[]; // per pair, ≥ 0
}
export function solvePlacement(problem: PlacementProblem): Placement;
```

A "pair" is one line of one offer. A "class" is a group of interchangeable dishes. Every class can
always send dishes to "uncovered" at `uncoveredCost` each, so the solver never fails.

`capacityPrices[p]` is what one more place on pair `p` would save, at most. For any other
`capacities'`:

```text
solvePlacement({ ...problem, capacities: capacities' }).cost
  ≥ cost − Σ_p capacityPrices[p] × (capacities'[p] − capacities[p])
```

This is the plane Task 2 relies on. It holds because the placement is a linear programme with
whole-number answers (a network), and `capacityPrices` is its dual for the capacity constraints.

  `uncoveredCost: 1000` unless it says otherwise.

    2 dishes with arcs to pair 0 at cost 0 and pair 1 at cost 5. Expect `cost` 5, `uncovered` 0 and
    flows `[{pair:0,count:1},{pair:1,count:1}]`.
  - "trades a cheap place for a dish that has no other": class A (1 dish) has arcs to pair 0 at
    cost 0 and pair 1 at cost 3; class B (1 dish) has one arc, to pair 0 at cost 0; capacities
    `[1, 1]`. Expect `cost` 3, B on pair 0 and A on pair 1.
  - "leaves a dish uncovered when no pair has room": capacities `[0]`, one class of one dish with an
    arc to pair 0. Expect `cost` 1000 and `uncovered` 1.
  - "a class with no arcs is uncovered": `uncovered` equals its count.
  - "prices a full pair a dish wanted": the first case's `capacityPrices` is `[5, 0]`.
  - "its planes never pass above the true cost": a seeded generator (a 10-line linear congruential

    other random capacity vectors `c`. Assert every time that
    `solve(c).cost >= solve(c0).cost - Σ capacityPrices[p] × (c[p] - c0[p])`.

- [ ] **Step 3: Implement `solvePlacement`** as successive shortest paths on a residual graph.
  - Arcs:
    - source → class: capacity `count`, cost 0.
    - class → pair: capacity unlimited, the arc's cost.
    - class → sink: capacity unlimited, cost `uncoveredCost`.
    - pair → sink: capacity `capacities[p]`, cost 0. Add this arc even when its capacity is 0, so
      the pair still gets a price.
  - Find shortest paths with a queue-based Bellman-Ford, because residual arcs can be negative.
    Push the bottleneck along each path.
  - Then the duals. Run the same shortest-path search from every node at once, each starting at
    distance 0, over the final residual graph. That gives potentials `φ`, and
    `capacityPrices[p] = max(0, φ(sink) − φ(pair p))`.
  - Use typed arrays sized once per solve; do not allocate per relaxation.

### Task 2: The search over mixes

**Files:**

- Create: `packages/shared/src/set-menu-search.ts`
- Test: `packages/shared/src/set-menu-search.test.ts`

**Interfaces:**

- Consumes: `solvePlacement`, `PlacementProblem`, `Placement` (Task 1).
- Produces:

```ts
export interface MixSearchProblem {
  readonly offerCount: number;
  readonly unfixed: number; // set menus free to take any offer
  readonly mixCost: (counts: readonly number[]) => number; // exact cost of the mix itself
  readonly capacities: (counts: readonly number[]) => readonly number[]; // per pair
  readonly pairOffer: readonly number[]; // offer index of each pair
  readonly pairPlaces: readonly number[]; // the line's count: capacity per set menu
  readonly placement: Omit<PlacementProblem, "capacities">;
}
export interface MixSearchResult {
  readonly counts: readonly number[];
  readonly placement: Placement;
  readonly cost: number;
}
export function searchMixes(problem: MixSearchProblem): MixSearchResult;
/** Exact when at most MAX_SET_MENU_MIXES, else Infinity. */
export function mixCount(unfixed: number, offerCount: number): number;
```

`MAX_SET_MENU_MIXES` is declared here and re-exported by `set-menu-fit.ts`. `searchMixes` requires
`offerCount ≥ 1`; the caller handles zero offers.

**The search, `searchMixes`:**

1. Enumerate every vector of counts per offer that sums to `unfixed`, in lexicographic order with
   offer 0's count rising from 0. That order decides which of two equal-cost mixes wins.
2. Each vector `v` starts with a bound of `mixCost(v)`.
3. Take the unsolved vector with the lowest bound. On ties, take the first in enumeration order.
4. Stop if that bound is not below the best cost found.
5. Solve the vector's placement. Its total is `mixCost(v) + placement.cost`. Keep it if it is lower
   than the best so far.
6. Raise the bound of every unsolved vector `w` to the following, when that is higher:

   ```text
   mixCost(w) + placement.cost − Σ_p capacityPrices[p] × pairPlaces[p] × (w[offer p] − v[offer p])
   ```

   Precompute the per-offer slope once per solve, so updating one vector costs one pass over the
   offers.
7. Go back to step 3.

Hold the vectors in one flat `Int32Array` and the bounds in a `Float64Array`.

What each reason means:

- `invalid_amount`: a price or surcharge that is not a whole number from 0 to
  `MAX_SET_MENU_AMOUNT_CENTS`.
- `invalid_line`: a count that is not a whole number ≥ 1, or a line with no course ids.
- `pinned_place_invalid`: a line index out of range, a dish its pinned offer does not list, a
  course its pinned line does not accept, or more dishes pinned to a line than its count.
- `duplicate_id`: two offers, set menus or dishes with the same id, or one offer listing the same
  product and variant twice.

`id` names the offending offer, set menu or dish.

**The fit, `fitSetMenus`.** In order:

1. Validate, and throw `set_menu.fit_invalid_input` on the first problem found.
2. Sort offers, set menus and dishes by `id`. Pinned dishes take their place and use up one of that
   line's places; they are not passed to the search.
3. Return `{ kind: "uncovered", setMenusNeeded: null }` when:
   - some unpinned dish is listed with an accepting line by no offer, or
   - there are set menus or unpinned dishes and `offers` is empty.
4. If `mixCount(U, T)` is `Infinity`, return `{ kind: "too_large" }`.
5. Group the unpinned dishes into classes by product, variant and counts-as course. Task 4 also
   splits them by previous (offer, line). Each class gets an arc to every pair that lists and
   accepts it, costing `surcharge × W1`. `W1` is 1 in this task; Task 4 sets it and adds a move
   term.
6. Set `uncoveredCost` to `W1 × (max price × set menus + max surcharge × dishes + 1)`. If
   `uncoveredCost × (dishes + pairs × set menus + 1)` is above `Number.MAX_SAFE_INTEGER`, return
   `too_large`: the search's bounds would no longer be exact. At the size limit (47 set menus, 235
   dishes, 25 pairs) with every amount at the cap, that product is 4.5 × 10¹⁵, inside the safe range
   (9.0 × 10¹⁵). A cap of €100,000 would give 4.5 × 10¹⁶, which is why the cap is €10,000. The guard
   is what catches a bill holding many FIXED set menus, which the mix limit does not count. Test:
   "too many fixed set menus to add up exactly", 1,000 set menus all fixed and 1,000 dishes at the
   cap → `too_large`.
7. Run `searchMixes`. If the best placement leaves any dish uncovered, return `uncovered`. Task 5
   fills in `setMenusNeeded`; until then return `null` and leave its tests as `it.todo`.
8. Deal out the result:
   - Unfixed set menus take offers in sorted order, offer by offer, until each offer's count is
     reached. Task 4 changes this.
   - Then each pair's dishes go, in `id` order, to that offer's set menus in `id` order, each to
     the first with room left in that line.

### Task 4: Staying put — the previous outcome, pinned dishes, and order

**Files:**

- Modify: `packages/shared/src/set-menu-fit.ts`
- Test: `packages/shared/src/set-menu-fit.test.ts`

**Interfaces:**

- Consumes: Task 3's internals and `MixSearchProblem.mixCost`.
- Produces: no new names; `previous` and `pinnedTo` now take effect.

**The ranking as one integer.** "Which outcome wins" becomes one integer per outcome:

```text
totalCents × W1 + offerChanges × W2 + dishMoves
W2 = dishes + 1
W1 = (set menus + 1) × W2
```

- **`offerChanges`** is exact for each mix, and goes into `mixCost`. Let `prev[t]` be the number of
  unfixed set menus whose previous offer `t` is still offered, and P the number of those set menus
  across all offers (both counted after dropping stale entries). Then:

  ```text
  offerChanges = P − Σ_t min(counts[t], prev[t])
  ```

- **`dishMoves`** goes into the arcs. An unpinned dish with a previous place costs 1 more on every
  pair other than its previous (offer, line).
- **Classes** are now also split by previous (offer, line).

**Dealing out, replacing Task 3's step 8:**

1. For each offer `t` with count `c_t`, among the unfixed set menus previously on `t`, keep `t` for
   the `c_t` of them that hold the most dishes the flow left on `t` at their previous line. Break
   ties by `id`.
2. Set menus left over take the remaining offers in sorted order.
3. Put back first, into its previous set menu and line, every dish whose set menu kept its offer and
   whose class the flow left on that pair. Within a class split across pairs, those dishes are the
   ones placed there first.
4. Deal the rest as in Task 3.

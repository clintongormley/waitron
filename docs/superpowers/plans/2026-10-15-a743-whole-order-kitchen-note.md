# A743 Whole-order Kitchen Note Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan inline, task-by-task. Autonomous execution, finish and land are already authorised by the campaign. Do not dispatch subagents or introduce an approval pause.

**Goal:** Let staff tell the kitchen something about the whole order, retain it across ordering paths, and announce subsequent changes.

**Architecture:** Store mutable preparation instructions in one venue-service state table, scoped to a counter working order or a seated party. Resolve a party's note for all its bills and rounds; keep financial rows and existing line-note snapshots untouched. Reuse kitchen ticket generation, polling and acknowledged `changed` notices.

**Tech Stack:** TypeScript, Lit, shared `wt-*` controls, Hono, Drizzle/SQLite, Vitest and real Playwright Chromium, ESC/POS.

**Spec:** [A743 in the backlog](../../backlog.md), [kitchen detail](../../backlog/kitchen.md), [board 1](../../backlog/mockups/a737-a740-till-counter-redesign/1-counter-screen.png), and [approved A669 spec](../specs/2026-10-14-a669-allergy-at-the-table-design.md) for heading placement only. A743 is owner-decided; choices below are implementation choices, not additional owner decisions.

## Global constraints and requirements

- Show the note above the order's dishes on counter, table and handheld; show **+ Note for the kitchen** when empty and a small editor when pressed.
- Show **For the kitchen: {note}** when set, with edit and clear actions; Spanish: **+ Nota para cocina**, **Para cocina: {note}**. Reserve this shared heading region for A669; implement no allergy workflow or data.
- Cover the whole counter order or seated party, including every bill, later round and held group; leave every dish's own note intact.
- Put the effective note above the dishes on every kitchen ticket and on station/pass screens; keep it out of customer receipts, invoices and fiscal inputs.
- Announce edits and removals affecting sent work through existing acknowledged kitchen notices and correction paper, atomically with saving the note.
- Enforce shape, length, session/profile, zone, scope and revision checks; retain frozen commercial data, ticket bytes, historical notices and fiscal immutability.
- Use failing tests first, including browser tests before changing screens. Read the TDD skill before writing implementation or test code; record red and green commands and test counts.
- Change existing tests only for expectations this spec changes, with **Changed test checks** receipts. Do not edit fiscal tests or existing guards. Keep other lanes' changes and migration snapshots.

## Chosen semantics and interfaces

**Ownership:** A counter order uses `{ workingOrderId }`; table orders use `{ partyId }`, shared across bills, people and devices. A counter order merely delivered to a table keeps its own scope until it actually joins a party. A canonical scope is returned with note reads, including a party bill retrieved into the counter basket. A new unseated table draft keeps its note locally and saves it to the party created at seating, before submitting food. A party with no main bill can still save its note without creating a bill.

**Minimal storage:** Add `packages/venue-service/src/schema/order-kitchen-notes.ts`: `order_kitchen_notes` with generated `id`, nullable FKs `working_order_id` and `party_id`, nullable `note`, and `revision` default 0. Exactly one owner must be present; unique indexes on each owner prevent duplicates. A missing row reads `{ note: null, revision: 0 }`; retain a row when cleared so old revisions cannot become valid again. Classify as `state`, exclude from configuration transfer. Core is already a required migration set, so the FKs add no module dependency. Add nullable JSON `order_note_change` (`{ before: string | null; after: string | null }`) to `kitchen_notices`; keep kind `changed`. This avoids a notice-kind CHECK rebuild and adds no column or trigger exception to frozen `working_orders`.

**Interfaces:** In `packages/module/src/module.ts`, define `KitchenNoteScope = { workingOrderId: string } | { partyId: string }`, `KitchenNote = { note: string | null; revision: number }`, `KitchenNoteSnapshot = KitchenNote & { scope: KitchenNoteScope }`, and `KitchenNoteChange = { before: string | null; after: string | null }`. Expose through `VenueServiceContribution`/`service.ts`: `readKitchenNotes(tx, scopes: readonly KitchenNoteScope[]): Promise<ReadonlyMap<string, KitchenNote>>`, `writeKitchenNote(tx, scope, expectedRevision: number, note: string | null): Promise<KitchenNote>`, and `kitchenNoteKey(scope): string` (`order:<id>` / `party:<id>`). Add optional `orderNoteChange` to notice options and `StationNotice`; omit it from wire notices when absent, preserving old bodies. Implement storage/normalisation in new `packages/venue-service/src/order-kitchen-notes.ts`; server orchestration in new `apps/server/src/order-kitchen-note.ts`. Its `readOrderKitchenNotes(tx, orderIds: readonly string[]): Promise<ReadonlyMap<string, KitchenNoteSnapshot>>` resolves party survivors and batch-reads notes once. `HeldOrder` and `TableParty` gain `kitchenNote: KitchenNoteSnapshot`; `StationQueueGroup` and `ExpoOrder` gain `kitchenNote: string | null`. Mirror server wire types in `api/client.ts`.

**Input:** Choose 2,000 characters for this whole-order instruction. Accept string or explicit null; replace runs of C0/C1/DEL controls (including ESC, GS, CR/LF and tabs) with spaces, trim, and turn empty/whitespace/control-only into null. Reject other JSON types and overlength text with registered, translated `kitchen_note.invalid` / `kitchen_note.too_long`; use `kitchen_note.out_of_date` for a stale note revision. Creation omission means no note; update omission is invalid. Equal normalised text changes no revision and sends no notice. Sanitise again at the printer boundary, including historical change text; render screen text through Lit escaping. Leave `screenNote` and line-note limits unchanged.

**Writes:** Add GET/PUT `/api/working-orders/:id/kitchen-note` and `/api/parties/:id/kitchen-note`, mounted from `till-api.ts`. Read returns `{ scope, note, revision }`; PUT carries `submissionId`, `expectedNoteRevision`, `note`, and the captured `expectedPartyRevision` for party scope or `expectedOrderRevision` plus `partyId: null` for counter scope. Order-route reads resolve a party bill to its canonical party; writes cannot silently change scope. Use `runServiceCommand` with kind `kitchen_note.set`, recording the supplied identity/revisions/content in its fingerprint; retries return the original result and enqueue nothing twice. In one write transaction check current session/device (`assertStillSignedIn`), location, `checkZones`, expected ownership and revision, then save and enqueue corrections. Party changes use `checkAndBumpParty`; counter changes advance only the note row's revision, including while a placed/paid order still awaits handover. Refuse closed parties, abandoned/collected counter orders and payment-in-flight writes. Follow existing ordering permission semantics: signed-in admitted operator and profile `take-orders`; no new payment permission. Add route-map rows and refusal cases for all four routes; GETs are passive.

**Movement:** Same-party bill splits/transfers and later main bills keep the shared party note. When a party splits into two parties, copy its note to both. When a bill leaves for the counter/new party, copy the effective source note; a partial departure leaves the source note intact. Counter splits copy the order note. Joining/combining scopes preserves distinct non-empty texts, destination first, joined with `; `; equal complete notes occur once. If the joined value exceeds 2,000 characters, refuse the move atomically with the length error rather than lose instructions. Perform scope adoption before `adoptZone` can fire food. Notify existing work whose effective note changes, including retained paid bills of absorbed parties; do not regenerate their financial rows.

**Kitchen copy:** Tickets read the effective note when enqueued; bytes already queued and old notice payloads stay unchanged. Screens show the latest saved heading. An edit creates `changed` notices with the immutable `orderNoteChange` payload alongside the affected lines' unchanged own notes, using existing per-item station acknowledgement. Target fired, not fully served work and still-held groups with `holdPrintedAt` set; exclude made-here, cancelled, collected and completed work. Held work not printed yet takes the new heading on its next HOLD/FIRE. Do not use `readSentWork` alone as an eligibility filter: its fired query does not exclude served work. Pass screens receive the heading through their existing reads; acknowledgements remain on the existing station notice surfaces. This note is operational metadata, so `editSentLines` does not forbid changing it.

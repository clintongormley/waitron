# A1308 menu and photos, PR mn13: a photo is one row, and its bytes are stored once — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking. Every implementer is dispatched as
> `subagent_type: "implementer"`.

**Goal:** `media_images` takes in `media_image_edits` (framing, revision, replacement picture,
uploaded name) and a new `original_hash`; one table, `media_blobs`, holds every picture's bytes once,
keyed by the bytes' hash, replacing `media_image_data` (by photo id) and `media_image_blobs` (by hash).
A blob no photo names is deleted in the same transaction that stops naming it. The file-name CHECK
stops accepting a name with an embedded NUL. A deleted photo is recorded in `activity_log`.

**Architecture:** Two tables instead of four. `media_images.original_hash` and `source_hash` are keys
to `media_blobs.hash` with `on delete restrict`, so a blob still in use cannot be deleted; a small
`pruneBlobs(tx, hashes)` deletes the given hashes that no photo names after a delete or a replace.
Bytes stay out of `media_images` so metadata reads and change subscriptions never select a payload
(`packages/db/src/schema/media/images.ts:31`). A blob is never changed; a trigger refuses an update.

**Tech Stack:** TypeScript, drizzle on `node:sqlite`, Hono, Vitest, slice 1a's rebuild command and
trigger file.

**Spec:** [design README](../specs/2026-11-02-rationalisation/README.md) §3 R1, R6, "Additions of 6
November 2026" (`media_images` file-name CHECK), §5 U10 ("replaced photo data" pruned);
[tables-menu.md](../specs/2026-11-02-rationalisation/tables-menu.md) §1.22, §1.23, §3 (`photo.deleted`),

## Decisions this plan makes

- **D1. `format` is stored, not read from a name.** A blob may be a photo's original (any of the
  three formats) or a replacement (always WebP, `image-edits.ts:63-64`); no file name belongs to the
  blob itself, so the type is a column (tables-menu.md §1.23).
- **D2. A blob is never updated; it may be deleted.** The A805 follow-up asked for the restriction on
  `media_image_data`. A blob's key is the hash of its bytes, so changing its bytes would break the key's
  meaning; the backup check already treats the bytes tables as immutable
  (`backup-verification.ts:8`). Deletion is the lifetime the owner chose (tables-menu.md §1.23,
  2026-11-04), and the two restrict keys stop a delete while a photo names it. The trigger is the
  refusal; a test pins it and the legitimate delete.
- **D3. One byte lookup.** A photo's file name is the hash of its original bytes plus their type
  (`prepare.ts:23`), and a replacement's name is its hash plus `.webp`, so the hash prefix and the
  extension find either. A request for `<hash>.webp` whose blob is a JPEG answers nothing, as today.
- **D4. The logo reads move with the logo columns, in the slices that make them.** The venue-and-box
  slice that folds `department_receipts` into `departments` adds `departments.receipt_logo_image_id`
  (tables-venuebox.md §1.10; its plan was not written on 2026-11-08), and devices PR dv16 adds the
  theme logo columns ([dv1](2026-11-08-a1308-dv1-devices-row.md), the area table: "dv16 … theme logos as
  keys … needs: menu and photos"). Each replaces the JSON reads in `images.ts` and `image-edits.ts`
  named in item 5 with reads of its own column, in its own pull request, because that is where the
  JSON leaves. This PR keeps those lines byte-identical so either can rebase across it.

- **D5. A backup judges only photos that a live or queued version names.** Today a file name in any
  version's `menu_version_images` row must resolve to a photo's bytes or to `.webp` replacement bytes
  (`reference()`, `backup-verification.ts:138-155`), and
  `packages/media/src/backup-verification.test.ts:232-275` ("checks a blob referenced only by a
  historical menu version") asserts a name with neither is invalid. Once a photo can be deleted
  while an old version still names it (mn10 lets the trigger allow that; this PR then prunes its
  bytes), every backup after the first such delete would fail that check. The photo-in-use trigger
  already defines which versions keep a photo; the backup check follows the same rule. **The test
  changes by design**: that case becomes "ignores a photo named only by a superseded or cancelled
  version" (the old version's release is `superseded`, its photo and bytes are gone, and the check
  passes), plus "refuses a backup whose live version names a photo with no bytes" (the same rows with
  a `live` release, bytes deleted, status `invalid`). The pull request lists both under "assertions
  changed by design" (rules §4, the plan says why).

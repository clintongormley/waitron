# A1574 PR 1 · Open the till when the box is unreachable

After one trusted online visit, opening the installed till without a connection shows “Can't reach the box. Check that this phone is on the venue's WiFi.” The page automatically opens the requested till URL once it is available. This works for `/till/` and saved `/till/tabs/…` URLs. A first-ever offline visit and the bare `/till` alias still use the browser's page. The [second slice](../../backlog/till.md#a1574-a-till-that-cannot-reach-the-box-says-so) covers the till that is already open.

## Build

1. Start with a failing `apps/till/src/offline-navigation.test.ts` case. Use a loopback fixture and an isolated Chromium context in `apps/till/test/offline-navigation.ts`, connected through `apps/till/vitest.config.ts` like `test/native-reload.ts`. Serve a live till, wait for the worker to activate, then cut the connection. Check that the installed entry and a saved tab show the message and that the till does not boot. Restore the box with an upgrade 503 followed by a new live page. Check the notice stays through the 503 and the original URL opens the new page automatically.
2. Add `buildOfflineWorker()` in `apps/till/src/offline-worker.ts` to supply the same script to the fixture and a separate `apps/till/vite.config.ts` plugin. Emit the fixed `/till/offline-worker.js`. Embed one small document with native text scaling and light and dark colour schemes. Use English and Spanish strings from `apps/till/src/i18n/strings.ts`, imported by relative path with no workspace runtime imports. Pick the first supported browser language. About every five seconds, make one bounded, uncached GET of the current URL with HTML accepted and `redirect: "manual"`. Reload on an opaque redirect or other non-5xx answer. Keep trying after network failures or 5xx. Let the browser time the initial network navigation.
3. Use `apps/till/src/register-offline-worker.ts` from `main.ts` after the existing trust probe permits boot. Register at `/till/` in a secure built till without awaiting registration. Unavailable or refused registration leaves boot running. Update promptly with `skipWaiting()` and leave open pages alone. Handle only same-origin GET navigations for the till paths above, including `/till/tabs` itself. Return the network response unchanged, including errors and redirects. Use the embedded page only on a failed fetch. Store no app, asset, API, write or session data. The answering box's normal boot retains `ServerRouter` and `/sw-probe.js` remains 404.
4. Offer the existing **Show me how** route from `trust-instructions.ts` for a phone already on the right WiFi. It opens `http://<hostname>/setup/trust?app=till` outside the worker. A failed fetch cannot identify a certificate error. After a trusted visit, the reconnect page replaces the browser certificate warning and the normal trust screen on a failed till navigation. Keep the normal boot trust probe. Under operator TLS, with landing port 0 or on a spare, the link has no repair page. The lead-in is “Already on the venue's WiFi?” / “¿Ya estás en la red WiFi del local?”, followed by the existing certificate explanation and link. In Spanish the page says “No se puede conectar con el servidor. Comprueba que este teléfono esté conectado a la red WiFi del local.” Open the link in a new tab with `target="_blank" rel="noopener"`. Document the reconnect and trust steps in both languages in `apps/server/src/guide/{en,es}/{till-notices,table-service}.md`.
5. Keep a no-fetch `buildRetiredOfflineWorker()` in the builder. Document in `apps/till/README.md` how a retirement release stops registering and ships that script at the same worker URL for devices returning later. It activates and unregisters without reloading open tills. Leave the open-screen notice in `docs/backlog.md` and `docs/backlog/till.md`.

## Checks and size

- Chromium also checks redirect and refusal pass-through, empty Cache Storage and removal with a controlled page. Import the builder in the browser test. `register-offline-worker.test.ts` covers the helper's skip and rejection cases. Keep `trust-check.test.ts`, `api/server-router.test.ts` and Server's `boot.spa-mount.test.ts` passing.
- Build with `pnpm --filter @waitron/till build`. Run a local, uncommitted Playwright smoke script at `apps/till/test/bundle-smoke.mjs`, following Setup's preview fixture, to prove real registration and continued boot when the worker is refused. Check script MIME and revalidation, look at both languages and themes at phone and desktop widths, and rehearse with an already-installed Android till if available. Keep the physical-phone result distinct from Chromium automation.
- Estimate 95–150 product lines and 100–165 test and support lines, plus docs. No dependency or schema change.

The [Service Workers specification](https://w3c.github.io/ServiceWorker/#handle-fetch) covers response and network-error handling. Chrome's [offline fallback example](https://web.dev/articles/offline-fallback-page) shows the fallback on a rejected navigation fetch. Its [retirement guidance](https://developer.chrome.com/docs/workbox/remove-buggy-service-workers#deploy_a_no-op_service_worker) uses a replacement at the same URL without a fetch handler.

# A841 slice 11 — text set by hand: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Under Advanced on the Look card, a manager sets the theme's typeface ("The device's own"
or "Serif"), each of the four text sizes and each of the three weights by hand. A hand-set size is
the size at 100% and the Text size slider scales it. A size the screens would draw under 12 px
warns, with a one-press fix, counts as hard to read and is listed by the Save dialog; a size drawn
above what Waitron checks the tills at gets a note with its own fix, which is not a warning. Every
bold on a themed screen — the browser's own bold included — follows the Bold weight. The saved card
gains a "Text set by hand" row, and the user guide says all of it in English and Spanish.

**Architecture:** Two pull requests (D1). **11a, the theme:** a `text` part joins the theme
document (absent reads `{}`), checked like every other part; `deriveTheme` writes the typeface and
the three weights beside the four sizes, after it settles the colours; `typefaceStack()` is the one
place a typeface choice becomes CSS; text warnings join the answer's `warnings` with the design's
key-only shape, and every place that words a warning today words them; the two numeric weights on
themed screens read the Bold token and a base-style rule makes `strong`, `b`, `h1`–`h6` and `th`
read it too. **11b, the editor:** the Text rows inside Advanced (until slice 12 folds it into
sections), their warnings, notes and fixes, the Fix all line and Save dialog counting them, the
saved card's row, Advanced's full heading and opening line, and the guides.

`packages/ui`, `apps/dashboard`, `apps/till`), Node test runs for `apps/server` and

## Decisions this plan makes (the design or the brief left them open)

**D1. Two pull requests.** Fifteen tasks, past the brief's twelve. **11a** (Tasks A1a, A1b, A2,
A3, A4a, A4b, A5, visual check A6) stores, checks, derives and serves `text`, words its warnings
wherever a warning is worded today, and makes every bold read the Bold token. **What works after
11a**, for a theme whose text was set through the API or a configuration copy (no editor row sets it
yet): every screen paints it; the Look card's draft compares `text` (`sameDraft` gains `sameText` in
A4a — on main it compares no text, `look-draft.ts:65-82`, so a draft holding text counted as
Waitron's look, review H1's E1), so Use Waitron's look is offered (`look-card.ts:987`) and clears
it, and Save becomes actionable after it; Fix all takes the text fixes and Save becomes actionable
after them; the Fix all line words sizes as sizes (A4b); Save sends the opened `text` back
unchanged (`normaliseChoices(draft.choices)`, `look-card.ts:762`); and a text warning is worded on
the saved card, in the Save and switch dialogs and in Advanced's count. **What does not, until
11b:** no row shows or changes one text setting; Reset all to worked-out leaves `text` alone; the
only way to clear text from the editor is Use Waitron's look, which also clears everything else.
**11b** (Tasks B1-B6, visual check B7) adds the rows and everything the manager sees of them. Before
go-live any venue may be reset, so the window costs nothing a reset does not fix. Every commit of
both PRs typechecks every package it touches (A3 builds the warning functions alone; A4a and A4b
change the dashboard and the shared type in turn, review M2).

**D2. Where `text` lives and what it accepts.** A top-level key of the document, shared by both
versions (design line 1304), required in the type as `textScale` is (`readonly text: ThemeText`,
`WAITRON_CHOICES.text = {}`); an absent `text` reads as `{}` (the recorded rule, `backlog.md:2930-2932`).
`ThemeText` is `{ family?: Typeface; size?: { sm?, md?, lg?, xl? }; weight?: { normal?, medium?, bold? } }`,
holding only what is set by hand. Checked **last**, after `textScale`, so every existing
first-refusal case keeps its answer; inside it in this order, each refusal `theme.invalid` with
`field` and `reason`:

| What is sent | `field` | `reason` |
| --- | --- | --- |
| `text` not an object (`null`, `[]`, `"x"`) | `text` | `bad_value` |
| a key of `text` other than `family`, `size`, `weight` | `text` | `unknown_key` |
| `family` not in `TYPEFACES` (`"system"`, `"serif"`) | `text.family` | `bad_value` |
| `size` not an object | `text.size` | `bad_value` |
| a key of `size` other than `sm`, `md`, `lg`, `xl` | `text.size` | `unknown_key` |
| a size that is not a whole number from 8 to 40 (`7`, `41`, `12.5`, `"12"`, `null`) | `text.size.<key>` | `bad_value` |
| `weight` not an object | `text.weight` | `bad_value` |
| a key of `weight` other than `normal`, `medium`, `bold` | `text.weight` | `unknown_key` |
| a weight not one of 400, 500, 600, 700, 800 (`300`, `900`, `650`, `"600"`) | `text.weight.<key>` | `bad_value` |

(An unknown key names the part holding it, never the key, as `unknownKey` does for every other part,
`document-check.ts:47-57`.) The answer is normalised: an empty `size` or `weight` is dropped, so
`{ size: {} }` reads as `{}`. **The configuration bundle does not move:** the import runs
`readThemeDocument` over each row (`theme-configuration.ts:54`), so a copy without `text` imports as
`{}` and a copy with a bad one is refused as `setup.request_invalid { field: "custom_themes.theme" }`.
Slices 7 and 10 reasoned the same way (slice 10 D2: "every stored theme and every configuration copy
made before this slice stays valid and the bundle format does not move"); it applies unchanged,
because the reason was that reader, and `text` goes through it. A newer box's copy carrying `text`
is refused by an older box as an unknown key; copies go only forward between releases, as for
`logo` and `textScale`.

**D3. The text tokens are written after settling, beside the sizes.** `THEME_TOKENS` becomes the 22
colours, the three radii, the four sizes, then `--wt-font-family`, `--wt-font-weight-normal`,
`--wt-font-weight-medium`, `--wt-font-weight-bold` (appended, so every index already pinned holds).
Both versions carry the same values. `deriveThemeFrom` adds `textTokens(choices.textScale,
choices.text, defaults)` to each mode's settled tokens, as it adds the sizes today, and for the same
reason (slice 10 D3: inside `settleMode` they would be remembered under a `settleKey` that holds no
text choice). Values:
- `--wt-font-family`: `typefaceStack(text.family ?? "system", defaults)` (D4).
- each size: `drawnSize(text.size[key] ?? Waitron's size, textScale)` — the hand-set size is the
  size at 100% and the slider scales it (design lines 957-963); `drawnSize(px, step) =
  Math.floor((px * step + 50) / 100)`, the arithmetic `fontSizes` already uses (`tokens.ts:103`).
- each weight: `text.weight[key] ?? Waitron's weight`, written as its digits. Waitron's weight must
  be `^[1-9]00$`, or `RangeError("not a whole-hundred weight: <name>")`, as the sizes refuse a
  default that is not whole pixels.
With nothing set by hand, every value is Waitron's own, so Waitron's choices still paint exactly
Waitron's tokens (design section 6, lines 1035-1038).

**D4. `typefaceStack(family, defaults)`** in a new `packages/ui-core/src/theme/text.ts`, a `switch`
over `Typeface` with an exhaustive `never` check:
- `"system"` → `defaults.structure["--wt-font-family"]`, which is
  `system-ui, -apple-system, "Segoe UI", sans-serif` (`structure.css:17`);
- `"serif"` → `ui-serif, Georgia, "Times New Roman", serif` (design line 903).
**Departure:** the design writes `typefaceStack(family)`; this takes `defaults` too, so "The
device's own" is Waitron's own value read from the token file, never a second copy of it (design
section 2's anti-goal, "a second, hand-kept copy of Waitron's default colours or type"). Nothing
else maps a choice to a font name (a guard case, Task A2, looks for the serif stack outside
`text.ts`). The uploaded-fonts item adds one value to `TYPEFACES` and one case here.

**Which serif each kind of till draws** (the design asks the plan to list it, line 903). One row
was measured (probe P4); the rest are assumptions, not checked:

| Device and browser | Face drawn for `ui-serif, Georgia, "Times New Roman", serif` | Source |
| --- | --- | --- |
| macOS, Chromium 156 (Playwright 1.64.1) | Georgia — Chromium skips `ui-serif` | Measured, P4 (`CSS.getPlatformFontsForNode`) |
| macOS and iPadOS, Safari | New York (Apple's `ui-serif`) | Assumption: WebKit maps `ui-serif` to the system serif; not measured (Playwright's WebKit is not installed here, design section 12) |
| Windows, Chrome or Edge | Georgia | Assumption: Georgia ships with Windows; not measured |
| Android, Chrome | the system serif (Noto Serif on most devices) | Assumption: no Georgia or Times New Roman on Android, so `serif` decides; not measured |
| ChromeOS, Chrome | Tinos (metric-compatible with Times New Roman) or Noto Serif | Assumption: not measured |
| Linux CI, Playwright's Chromium | whatever `serif` resolves to in the image (DejaVu Serif or Liberation Serif are likely) | Assumption: not measured |

P4's control: in the same page the device's own stack drew `.SF NS` and the code stack Menlo, so
the probe tells faces apart. Width, for the sample "Champiñones al ajillo 0123" at 16 px: Georgia
191.6 px, the system sans 192.7 px — for that string on that Mac, Serif is not wider. Nothing
measured Serif at 130% on a till; B7 shoots it at 1024 × 768 and 1280 × 800, and a cut-off name
there becomes a backlog entry, not more of this slice (review M4).

**D5. The sheet's shapes.** `themeSheet` checks each value by its token: a colour `^#[0-9a-f]{6}$`,
a radius or size `^\d+px$` (today's), a weight `^[1-9]00$`, and the typeface
`^[A-Za-z0-9 ,"-]+$` — letters, digits, spaces, commas, double quotes and hyphens only, so no `;`,
`{`, `}`, `\`, `<` or `'` can end a declaration. The value is never stored text (the document
stores only the choice's key, D2), so this is a second fence, as the colour check is.

**D6. Text warnings.** The design's shape (lines 2043-2046): `{ field: "text.size.<key>", mode: null,
against: [], fix: <whole px>, blockedBy: [] }`. `ThemeWarning` becomes `ColourWarning | TextWarning`
(the colour one exactly today's), with `isTextWarning(w)` (`w.mode === null`). A size warns when its
drawn size is under 12 px (`TEXT_FLOOR_PX`); its fix is the smallest whole size from 8 whose drawn
size at the current step is at least 12 (design lines 966-972). The text warnings come after both
modes' colour warnings, in the order sm, md, lg, xl. A weight or a typeface never warns (design
line 987). Probe P3: at every step a fix exists and draws no more than 16 px, so it never trips the
note, and no size can both warn and get the note.

**D7. The larger-than-checked note is not a warning.** `textNotes(choices, defaults)` in `text.ts`
answers `{ key, drawn, fix }[]` for each size drawn above its limit — Waitron's size times 1.3,
rounded the same way (16, 18, 23, 29 px; design lines 972-976) — with the fix the largest whole
size whose drawn size at the current step is within the limit. It lives in `ui-core` beside the
warning so both share `drawnSize`, but only the browser calls it: the server's answer carries no
note (design line 2045, "worked out by the browser alone").

**D8. Fix all and Fix and save take the text fixes too.** The design says a text warning "is listed
by the Save dialog like a colour's" (line 972); Fix and save applies Fix all, and is offered when
Fix all would leave no warning. So `fixAll` sets each warned size to its fix after the colour rounds,
and `canFixAll` also asks that no text warning is left. The Fix all line above the buttons counts
both: "2 colours are hard to read." while only colours warn (unchanged), "2 text sizes are hard to
read." while only sizes do, and "1 colour and 1 text size are hard to read." for a mix (D21's keys).

**D9. One sentence for a text warning, in every place.** Under the row, in the Save dialog, in the
switch dialog and on the saved card: "{name}: {size} px is smaller than 12 px; text that small is
often hard to read." (design line 606, the row's words). The design gives the dialog's and the
saved card's words for colours only; one sentence keeps the three places saying the same thing. The
drawn size comes from the choices (`drawnTextSize(choices, key, defaults)`), since the warning
carries only keys; so `savedWarningLine` takes the choices, as `saveDialogLine` already does.

**D10. The Bold rule.** In the one base style, `packages/ui-core/src/base-styles.ts` (the brief's
"both base styles": `packages/ui/src/base-styles.ts:2` only re-exports it), after the `:host` rule:
`:where(strong, b, h1, h2, h3, h4, h5, h6, th) { font-weight: var(--wt-font-weight-bold); }`.
**Departure:** the design writes the bare selector list; `:where()` gives it no specificity, so a
component's own rule for one of those elements always wins, whatever order its styles come in
(design-system asks for `baseStyles` first in `static styles`, `design-system.md:4461`, which nothing
enforces). **What changes on Waitron's own look** (probe P1): an element whose component sets no
weight draws Waitron's Bold, 600, where today it draws the browser's 700 — in the signed-in shell 8
of the 9 such elements (the overview's "Today at a glance" `h1` and its five `h2`s, `wt-modal`'s
`h2`s), and on the Look card the name and hard-to-read dialogs' `h2`s and the preview's `h3` and
`h4`s; the settings card's heading already read the token (600 before and after). Setup's screens

# A731 repair-page backup recovery implementation plan

> **For agentic workers:** use `superpowers:executing-plans` inline, under the parent driver. Steps use checkboxes. Execution is already authorised; do not ask for plan approval or dispatch per-task implementers/reviewers. Read the TDD skill before writing implementation or tests.

**Goal:** recover an authenticated archive, bucket copy or supported managed-Cloud copy from the first-setup repair page, retaining the old attempt and every old database independently.

**Architecture:** add a separate authenticated repair service and a version-2 host resolution journal for this handoff. This changes neither the database schema nor the fiscal protocol. Restore into an isolated, initially empty target through existing restore/module-preparation interfaces; select it only after checked completion. Keep V1 resolution, strict readers and restore guards intact.

**Tech stack:** TypeScript, Hono, provisioning's durable host JSON, existing module recovery seats, Lit, Vitest and Chromium.

**Spec:** owner-approved A731 connects the repair page to existing archive, bucket and managed-Cloud recovery with the selected backup's named node recovery key and archive encryption key where applicable. Retained business records are not exposed without their owner proof. See `docs/backlog/fiscal.md` → A731 and the current recovery policy in `docs/operations/hour-recovery.md`. Preserve the original-retention boundaries of `docs/superpowers/plans/2026-10-15-a679-first-setup-repair.md`; its register-based authority is historical. A732 is withdrawn, A733 is shipped, and A1042 waits for A731.

## Global constraints

- Do not change `registerSif`, `restoreFiscal`, fiscal writers, hashes, numbering, alta, SQL, migrations, guards, coverage exclusions or existing behavioral assertions. Do not convert an unknown database into an empty one.
- The selected backup needs its own named node recovery key; an archive also needs its encryption key. Cloud approval and bucket credentials do not replace node authentication. A key that opens a backup does not establish ownership of another database.
- Production naming remains the existing five-symbol UTC-minute selection, independent second clock within 30 seconds, 90–150 second wait and existing history floors. Do not reuse an old consumed or uncertain allocation, introduce a naming fallback, or implement a recovery desk.
- All proof, upload, preview, preparation, Cloud and commit actions require an actual encrypted `TLSSocket`, same-origin checks and `Cache-Control: no-store`. HTTP serves only A733's public connection/bootstrap surface. Never trust URL scheme or forwarded headers as proof of TLS.
- Preserve old databases, sidecars, attempts, preparation histories, malformed remnants and resolution records. Do not reset, prune or run normal boot cleanup against their directories. Separate durable transitions are explicitly authorised; they are not one filesystem/database transaction.
- Browser passwords, node/archive keys and Cloud credentials stay out of URLs, logs, public inspection and browser storage. Repair grants are memory-only, tied to this server boot, inspection, source, event and owner generation. A process restart requires new proof before any further repair write.
- Retain ordinary password recovery, marker repair, empty start-again, interrupted selection and exact publication completion. The new route is not an exemption for the existing global POST guard.
- Parent execution owns signed-off commits, focused validation, finish-branch, CI and any later landing. This plan-only invocation writes this file alone.

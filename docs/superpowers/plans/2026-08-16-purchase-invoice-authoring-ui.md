# Purchase-Invoice Authoring UI — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use `- [ ]`.

**Goal:** A **management-dashboard surface to author received purchase invoices** (supplier, dates, VAT desglose), so the modelo 303 IVA-deducible reporting that #91 landed headless has a data source. The #91 fast-follow; mirrors the #78 catalogue authoring UI.

**Architecture:** (1) a **`purchase.manage` permission** realised in `@waitron/identity` (code-only — no migration); (2) a **`mountPurchasingApi`** management-api route group (`GET/POST/PATCH/DELETE /management-api/purchase-invoices…`) via the catalogue `gated()` pattern (`withTenant`+`asAppUser`+`authorizeManager(purchase.manage)`), calling the #91 `@waitron/purchasing` ops; (3) `DashboardApi` methods + browser-local types; (4) a `<dashboard-purchases-screen>` (load/list/commit/reload/error + `busy` single-flight) + a `<dashboard-purchase-form>` dialog (header scalar fields + an embedded **desglose sub-editor** managing add/remove VAT-rate lines) + a `<dashboard-purchase-list>`; (5) i18n (strings, `purchase.*` code messages, regime/kind domain names).

**No migration.** #91 already shipped the `purchase_invoices`/`purchase_invoice_vat` tables + enums + RLS (migrations 0041/0042). Realising `purchase.manage` is a pure `permissions.ts` edit (roles/permissions are code, no permissions table — `authorize.ts` reads `persons.role` + `roleHasPermission` in code). If a task appears to need a migration, STOP and flag it.

## Resolved facts (read before starting)
1. **#91 ops** (`packages/purchasing/src/operations.ts` + `types.ts`): `createPurchaseInvoice(tx, {header, lines}) → PurchaseInvoice`, `getPurchaseInvoice(tx, id) → PurchaseInvoice|null`, `listPurchaseInvoices(tx, {from?,to?}) → PurchaseInvoice[]`, `updatePurchaseInvoice(tx, id, {header?, lines?}) → void` (lines present ⇒ full replace), `deletePurchaseInvoice(tx, id) → void`. Header: `supplierTaxId, supplierName, supplierInvoiceNumber, issuedOn, receivedOn (YYYY-MM-DD), total, regime ("general"|"equivalence_surcharge"), deductibleProportion (0–100), note`. Line: `rate, base, tax (the cuota — field is **`tax`**, NOT `cuota`), kind ("ordinary"|"capital")`. All take no `tenantId` (run under `withTenant`/`asAppUser`).
2. **Catalogue pattern** (`apps/server/src/catalogue-api.ts`): the `gated(sessionId, fn)` helper = `withTenant`+`asAppUser`+`authorizeManager(CATALOGUE_WRITE_PERMISSION)`; each route `requireManagementSession(c)` → `gated(...)`; request screens throw `management.request_invalid` naming the field; `createErrorBoundary(STATUS, "purchase.failed")`. Mount in `boot.ts` beside `mountCatalogueApi` with `{ db, cfg: { tenantId } }`.
3. **Dashboard UI patterns:** screen = `catalogue-screen.ts` (load/list/edit-dialog/commit/reload/error + `busy` single-flight; `errorKey` localised at the render edge via `codeMessage`). Header dialog = `product-form.ts` (`willUpdate` reseed, dispatch-not-call, `busy` gate, client validation as `role=alert`). **Desglose sub-editor** = mirror `layout-screen.ts`'s repeating add/remove/reorder-rows mechanic over a `@state() lines: LineDraft[]` (a purchase create is NOT idempotent → keep the screen's `busy` single-flight). List = `product-list.ts`. Events bubble+composed, screen `stopPropagation`s. a11y template: `catalogue-screen.a11y.test.ts` + `widgets/test-helpers.ts`.
4. **Client** (`apps/dashboard/src/api/client.ts`): add a `// ── Purchase invoices ──` section of one-liners over `#request`; browser-local `PurchaseInvoice`/`PurchaseInvoiceLine`/input types (Decimal→string, enums local unions). **i18n** (`i18n/{strings,codes,domain}.ts`): `nav.purchases` + `purchase.*` labels (en+es); the three `purchase.*` code messages; `PURCHASE_REGIME_NAMES`/`PURCHASE_VAT_KIND_NAMES` + `regimeName()`/`vatKindName()` resolvers (mirror `vatClassName`).

**Goal.** On a nearly full disk the start deletes the box's spare file (`<state>/spare-space`, 8 MiB) before first-setup resolution, so the box boots normally instead of serving the full-disk page. Straight after that release it writes a small marker, `<state>/spare-space.released`; while the marker exists the full-disk stop holds (the tills save nothing), across restarts, until the spare is written back whole, by a start or by the running box's 60-second free-space watch (which writes it back only while the marker exists, decision 9), which then deletes the marker. The repair page's full-disk words become accurate (the longer reinstall sentence, and the log promise only where a restart really deletes logs).

## Decisions this plan makes that the design does not (each goes in the PR description)

1. **The marker is written inside `releaseSpare`, so every release writes it** — the new start release and slice 1's two (the start's emptying of a discarded recovery, `first-setup-entry.ts:233-235`; the repair host before Start again, `spare-space.ts:121-144`). Design §2 says "straight after a release that deleted bytes". Any release gives the spare's room away, and the rule "the stop holds until the spare is back" is about that room. After the emptying, the same start's top-up (`node-entry.ts:417-428`) writes the spare back and deletes the marker at once when 24 MiB is free; after a Start again the box goes back to first setup, which has no tills, and the next start with room clears it.
2. **The marker is written after the unlink, as the design says, so two windows release the spare and leave no marker:** a power cut between the two, and a marker that cannot be created (ENOSPC on the folder or an inode, or another writer taking the freed room first; logged `storage.spare_marker_write_failed`, Task 2). In both, the stop is held by free space alone: noted at boot only under 16 MiB, lifted at 16 MiB, and not held across a restart, so the Q3 A guarantee is lost for that release. A case-2 release (8 to 16 MiB free after a full-disk failure, Task 3a's rule) gives the boot 16 to 24 MiB, which its own 4 MiB (measured, README:36) brings to 12 to 20 MiB at `noteFullAtStart`, so without the marker the stop may or may not be noted. Writing the marker before the unlink would need room on the full disk it exists to relieve; trying it first and falling back to unlink-then-write is NOT adopted, because whether an empty file can be created on a disk that refuses data blocks is not measured. Both windows are stated in conventions-data.md (Task 13 Step 3) and, as "exceptions in the topic file", in CLAUDE.md (Task 13 Step 4).
3. **The boot learns the spare's folder from `WAITRON_SPARE_SPACE_DIR`, which `runEntry` sets only for a start from a selected backup recovery.** Read: in that case `runEntry` hands `startServer` an environment whose `WAITRON_STATE_DIR` is the recovery's target folder (`node-entry.ts:376-386`, `:488`, `:640`), while the spare lives in the configured state folder (slice 1's rule, `node-entry.ts:419-420`). Unset, the boot uses `config.stateDir`. It is not operator configuration and is not documented as such. A1131c (designed, not built) moves a restored venue to the usual place, which would retire this case.
4. **The real-boot test probes the stop with an unauthenticated `POST /api/working-orders`** (`till-api.ts:1872`, gated: not in `TILL_OPEN_WHILE_DISK_FULL`, `till-api.ts:1245-1265`), which the gate answers 507 before the route authenticates (`disk-full-gate.ts:34-42`; conventions-data.md "A full disk stops the till's writes"). The four sale routes are open on the gate and refused inside (`till-api.ts:1250-1254`, `till-sale.ts:699`), after authentication, so the sale itself is proved in-process (Task 4, `till-sales.disk-full.test.ts`). Design's test list says "a till sale is refused".
5. **The repair page knows whether a restart deletes logs from a new optional param on its 507, `restartDeletesLogs: boolean`, and has THREE outcomes:** `true` → the log promise; `false` → "restarting the box frees no space"; absent → neither (the neutral variant, Task 9b). The server-kit boundary today answers every full disk with `params: {}` (`packages/server-kit/src/error-boundary.ts:34-40`, read), so it changes to keep an `AppError("storage.disk_full")`'s own params. Only the resolution app's GET inspection and its Start-again routes carry the field (Task 9a2); every other route the repair page reads (the backup recovery's routes, mounted at `first-setup-entry.ts:342` and wrapped in the same `createErrorBoundary`, `setup-first-backup-api.ts:16`, read) still answers an engine full disk through the boundary's `params: {}`, and the setup app sends those failures through the same `#describeRepairError` (`apps/setup/src/setup-app.ts:817, 858, 1290, 1360, 1397, 1500, 1507, 1532, 1632, 1726`, read), so from those answers the page cannot tell whether a restart frees space and says nothing about restarting.
6. **The real-disk spare sizes in the new e2e file are 8 MiB (the real size) for the boot-from-zero case and 6 MiB for the restart and write-back cases** (reasons in Task 6). The release thresholds stay the product's constants (8 and 16 MiB) in every test.
7. **A start at the recovery level still releases the spare** when the disk is that full, then serves the recovery page (`runAdmittedEntry`, `node-entry.ts:554`, serves it after resolution). Design §1 accepts a page served after a release; a case pins it.
8. **A second start beside a running server can release that server's spare (accepted, stated).** The start's release runs before any venue lock (Task 3a's rule), unlike the staging clean-up beside it, which skips while another process holds the venue lock fresh (`start-space.ts:92-115`, read); `node-entry.ts:216-219` (read) names "a second copy refused beside a running server". Such a copy deletes the running box's spare and writes the marker; the running server is not stopped by it (its `full()` reads the marker only while a stop is noted, Task 4), and its watch writes the spare back once 24 MiB is free (decision 9). Interleaved with that server's own write-back, it can leave the spare gone and no marker, which waits for the next start with room. Skipping the release while `readVenueHolder` shows a fresh holder was not taken: a holder that dies leaves its file (`packages/store/src/venue-holder.ts:5-9`, read) and reads fresh for 30 s after its last heartbeat (`VENUE_HOLDER_STALE_MS`, `:36`, read), so a start within 30 s of a server that died on a full disk would skip the release and serve the full-disk page instead of booting, the case this slice exists for. Stated in conventions-data.md (Task 13 Step 3).
9. **The running box writes the spare back only while the marker exists** (narrows design §2's "the 60-second free-space watch tops it up"). The boot's `restoreSpare` closure asks `spareReleased` first and calls `topUpSpare` only when it answers true (Task 5). Without this, every booted test server with room would append 8 MiB to its state folder at the watch's first reading (`free-space-watch.ts:82`, `timer(0)`, read; started by every `bootServer`, `boot.ts:2293`, read; 54 test files in `apps/server/src` import `startServer` from `./boot.js` directly, counted there with `/usr/bin/grep -lE 'from "\./boot\.js"' *.test.ts | xargs /usr/bin/grep -l startServer | wc -l`, run), and suites that list a state folder exactly (`recovery-backup-preview.test.ts:268`, `expect(await readdir(stateDir)).toEqual([])`, read) would race it. A boot-harness default of `spareBytes: 0` would not reach those 54 files. Cost: a spare missing with no marker (decision 2's two windows, decision 8's interleave, or a first start without 24 MiB) waits for the next start with room, as today.

# A1127 slice 2: on a full disk the box starts from its spare file, and the tills stay stopped until the spare is back — implementation plan

> **How this plan runs:** the lead builds it INLINE (superpowers:executing-plans), test-first, task by task, committing each with `git commit -s`. Steps use checkbox (`- [ ]`) syntax. Each task is sized well under 100 tool calls; a task that passes about 150 calls unfinished stops at a passing or cleanly red point, commits, and writes a handover (done, left, files, each check's state) in the ledger.

**Goal.** On a nearly full disk the start deletes the box's spare file (`<state>/spare-space`, 8 MiB) before first-setup resolution, so the box boots normally instead of serving the full-disk page. Straight after that release it writes a small marker, `<state>/spare-space.released`; while the marker exists the full-disk stop holds (the tills save nothing), across restarts, until the spare is written back whole, by a start or by the running box's 60-second free-space watch, which then deletes the marker. The repair page's full-disk words become accurate (the longer reinstall sentence, and the log promise only where a restart really deletes logs).

## Decisions this plan makes that the design does not (each goes in the PR description)

1. **The marker is written inside `releaseSpare`, so every release writes it** — the new start release and slice 1's two (the start's emptying of a discarded recovery, `first-setup-entry.ts:233-235`; the repair host before Start again, `spare-space.ts:121-144`). Design §2 says "straight after a release that deleted bytes". Any release gives the spare's room away, and the rule "the stop holds until the spare is back" is about that room. After the emptying, the same start's top-up (`node-entry.ts:417-428`) writes the spare back and deletes the marker at once when 24 MiB is free; after a Start again the box goes back to first setup, which has no tills, and the next start with room clears it.
2. **The marker is written after the unlink, as the design says,** so a power cut between the two leaves the spare gone with no marker: the next boot then lifts at 16 MiB as today. Writing it first would need room on the full disk it exists to relieve. Stated in conventions-data.md (Task 13).
3. **The boot learns the spare's folder from `WAITRON_SPARE_SPACE_DIR`, which `runEntry` sets only for a start from a selected backup recovery.** Read: in that case `runEntry` hands `startServer` an environment whose `WAITRON_STATE_DIR` is the recovery's target folder (`node-entry.ts:376-386`, `:488`, `:640`), while the spare lives in the configured state folder (slice 1's rule, `node-entry.ts:419-420`). Unset, the boot uses `config.stateDir`. It is not operator configuration and is not documented as such. A1131c (designed, not built) moves a restored venue to the usual place, which would retire this case.
4. **The real-boot test probes the stop with an unauthenticated `POST /api/working-orders`** (`till-api.ts:1872`, gated: not in `TILL_OPEN_WHILE_DISK_FULL`, `till-api.ts:1245-1265`), which the gate answers 507 before the route authenticates (`disk-full-gate.ts:34-42`; conventions-data.md "A full disk stops the till's writes"). The four sale routes are open on the gate and refused inside (`till-api.ts:1250-1254`, `till-sale.ts:699`), after authentication, so the sale itself is proved in-process (Task 4, `till-sales.disk-full.test.ts`). Design's test list says "a till sale is refused".
5. **The repair page knows whether a restart deletes logs from a new optional param on its 507, `restartDeletesLogs: boolean`.** The server-kit boundary today answers every full disk with `params: {}` (`packages/server-kit/src/error-boundary.ts:34-40`), so it changes to keep an `AppError("storage.disk_full")`'s own params. Details in Task 9a.
6. **The real-disk spare sizes in the new e2e file are 8 MiB (the real size) for the boot-from-zero case and 5 MiB for the restart and write-back cases** (reasons in Task 6). The release thresholds stay the product's constants (8 and 16 MiB) in every test.
7. **A start at the recovery level still releases the spare** when the disk is that full, then serves the recovery page (`runAdmittedEntry`, `node-entry.ts:554`, serves it after resolution). Design §1 accepts a page served after a release; a case pins it.

# A1308 jr6 — the fiscal drain, payment reconciliation and fiscal reconciliation on the runner — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Owner lands: YES.** This pull request changes when records are sent to AEAT (the fiscal drain wakes
on every newly queued record instead of waiting up to an hour, and no longer waits behind payment
reconciliation), touches the fiscal backend's outbox inserts, and changes how the box's own check
against AEAT is scheduled (rules §6, "AEAT sending"). It is one of two owner-landed pull requests
of this part (jr5 is the other); nothing else rides in it.

**Goal:** Three jobs with a legal or money clock move onto the runner: `fiscal.drain` (R1, with the
restart reset still its first-pass step and its stop signal kept) woken by a notice written with
every queued fiscal record and by the manager's "retry now";
`payments.reconcile` (R2) in its own loop, so a slow reconcile day no longer delays the drain; and
`fiscal.reconciliation` (R20). `/health` judges exactly what it judges today.

**Architecture:** A new `apps/server/src/fiscal-jobs.ts` holds `drainJob` and `reconcileJob`, built
from `runPass`'s two `attempt` bodies (`apps/server/src/pass.ts:79-141`). Each records its own
report into `/health`'s `duties` through today's `recordPass` and `logDegradedDuties`
(`apps/server/src/health.ts:81-131`), so the status code, the budgets (`DUTY_BUDGET_MS`, `:25-28`),
the body's `duties` keys (`fiscal.drain`, `payments.reconcile.stripe`) and `lastPassAt` are unchanged.
AEAT's wait between sends is still enforced by the drain's own gate (`packages/fiscal-verifactu/src/drain.ts:239-260`),
so a wake cannot send early; measure 3 checks it. **The drain keeps its stop signal:** today boot
wires `controller.signal` into `enabledFiscal.drain` (`boot.ts:3616-3630`), and the drain claims no
further batch once it is aborted (`drain.ts:236`); the job hands its own `ctx.signal` through
`resetBeforeFirstDrain` and `runFiscalDrain` to the drain on every pass, so a handed-over box claims
and sends no further batch to AEAT after the stepdown signal.

**What wakes the drain.** Measure 2 is expected to fail: the fiscal-record correction paths append a
record and queue it without touching `sales` (`packages/fiscal-verifactu/src/record-remedy.ts:182-183`,
`record-remedy-absent.ts:125-157`; `record-remedy-absent.test.ts:167` asserts `after.sales` equals
`before.sales`). So this plan builds the design's fallback now (jobs.md §5.2: "an explicit 'record
written' notice from the fiscal backend after commit", never change-feed triggers on
`verifactu_records`): every insert into the submission outbox (`envios`, `verifactu_submissions`
after the fiscal slice) goes through one helper that also writes a change row of type
`fiscal_submission_queued` in the same transaction. `withTransaction` hands change rows to listeners
only after the commit, and a rollback takes the row away with the record (`packages/db/src/change-log.ts:24-47`),
so the notice is "after commit" by construction. The drain wakes on that type alone: it covers every
path that queues a record, the remedies included, and it does not fire on the outbox's own status
updates, which would wake the drain after every reply.

**Spec:** [jobs.md §1 "Waking replaces most polling"; §2 R1, R2, R20; §3 rows "Main background loop", "Fiscal restart reset", "Fiscal filing to AEAT", "Fiscal reconciliation", "Stripe payment reconciliation"; §4 "Data loss" (the 503 rule); §5 measures 2 and 3](../specs/2026-11-02-rationalisation/jobs.md);

## Global Constraints

- The drain always runs with the job's signal; once it is aborted no further batch is claimed,
  and a batch already claimed is still sent (`drain.ts:236`).
- A drain pass is never inline on a sale: a wake only cuts the job's sleep; the sale's request never
  waits for it (CLAUDE.md §5).
- The restart reset runs before the first pass that drains, and is retried until it succeeds
  (`restart-reset.ts:5-13`).
- `/health`'s status code, budgets, `duties` keys and `lastPassAt` behave exactly as today; `jobs`
  never changes the status code.
- A thrown drain or reconcile pass is retried at `timings.minTickMs`, as today (`pass.ts:157-163`
  reports `now`, which the loop floors to `minTickMs`). That is the back-off: `firstMs = maxMs = timings.minTickMs`.
- Every log event today's pass writes (`drain.complete`, `drain.tenant_skipped`,
  `fiscal.awaiting_certificate`, `fiscal.certificate_available`, `reconcile.complete`,
  `reconcile.pair_skipped`, `reconcile.run_failed`, `reconcile.run_parked`, `duty.failed`,
  `duty.degraded`, `fiscal.reconciliation_failed`) is still written in the same case.

## Review Focus

1. **200 sales in a minute.** At most one send while AEAT's wait is running, plus any full batch
   the gate allows. Measure 3.
2. **A fiscal-record correction (a filing case remedy, an absent record's cancellation).** It queues
   a record without touching `sales`; the submission notice wakes the drain anyway. Measure 2's
   remedy cases.
3. **The certificate missing on a box with sales.** The drain's skips keep the duty degraded on
   `/health` and keep `fiscal.awaiting_certificate`; `job.failing` stays quiet, since no pass threw
   (jr3's rule). `fiscal-jobs.test.ts`'s re-pointed "noteAwaitingCert" cases.
4. **A stepdown while the drain holds a claimed batch.** The batch is still sent; no further batch is
   claimed, because the drain reads the job's own signal (`drain.ts:236`,
   `handover-stepdown.test.ts:738`, re-pointed at that signal).
5. **A reconcile day that takes minutes.** The drain keeps running on its own loop meanwhile.
   Task 2's "a slow reconcile does not hold up the drain".

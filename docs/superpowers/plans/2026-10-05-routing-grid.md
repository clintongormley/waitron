## Decisions needed before dependent work

These recommendations make unspecified details executable. They require owner approval, separately from the already accepted row-first rule.

1. **Uncategorised products, A261 §12.2: unresolved.** Recommend the proposed “No category” group at the bottom, with no editable group row or stored synthetic category. Its top-level products get normal product cells and otherwise inherit All categories. The owner must confirm or reject it. While unanswered, plan and test storage/resolution for a null category, retain the visible Unassigned product assignment affordance using the new product-cell writer (source-read receipt: `packages/venue-service/src/dashboard/prep-stations-screen.ts:1394` renders `r.unassigned.products` and `:1405` submits a product assignment), and keep those products/variants selectable in the tester. This is a bounded interim recommendation, not approval to hide them or to build the group. If rejected without an alternative, retain that affordance and park only the final uncategorised presentation; do not invent another grouping. Tasks 6–7 and final acceptance remain conditional.
2. **Collapsed counts and context:** recommend counting distinct hidden top-level product rows and real category rows at all depths, excluding the category itself, variants and the proposed synthetic group. Count rows, not quantities, cells or only immediate children. Show an exceptional deep row once at its tree position, with its category path, without adding otherwise hidden ancestor rows. This keeps “24 more products, 2 more categories” an exact count of rows currently absent. Each summary independently counts absent descendant rows in its own subtree. A hidden row may therefore be counted by both a root and a visible collapsed descendant; never sum summary numbers or count the summary itself as a hidden row. The spec requires hidden exceptions at every depth but leaves this counting/path detail unstated.
3. **Cell result versus timing:** recommend displaying the selected configured station, or No preparation, before the time-dependent fallback walk. Muted text means this coordinate has no saved cell; same-row Every zone is inherited by a zone cell too. An explicit value equal to its inherited result stays normal text. Show a disabled saved station by name with a warning and its fallback outcome; never silently clear it. The tester explains final destination, fallback reasons and origin together. This distinguishes an editable assignment from a temporary closure. The spec's “shows its result” needs approval of this precise presentation.
4. **Catalogue scope:** recommend all categories and active top-level products, including sold-out products and products used only as extras. Categories have no active flag at this base (`packages/db/src/schema/catalogue.ts:25`); do not invent a category activity filter. Put each product under its single effective main category; no variant rows. Retain saved cells for inactive products and show them again on reactivation. Recheck actual catalogue shape at build start before applying this recommendation.
5. **Editing and preview:** recommend retaining the current route-change preview/confirmation for a cell write or clear that changes destinations. Preview uses the existing time-unapplied comparison and names top-level/variant outcomes in active zones; it changes no existing tickets. Zero moves saves directly. Revalidate on save; no promise that a preview reserves the routing state. The default cell uses the existing Make default action and its existing permission, not the new cell endpoint.
6. **Layout and focus:** recommend an app-owned semantic table with sticky row labels and horizontal scrolling at phone width, using shared cell dropdowns. Each label identifies row path, zone, value and set/inherited state. Tab reaches controls, Enter/Space opens, Escape cancels and restores focus; expand/collapse keeps focus on its trigger. Do not add a generic tree-grid primitive or custom arrow-key grid system in this build. New generic UI work would require a separate approved design.

7. **Zone removal versus product deactivation:** recommend preserving the landed zone cleanup policy: removing a zone clears its routing cells, while deactivating a product retains its cells for reactivation. Source-read receipts: `packages/venue-service/src/operations.ts:347` deletes zone exceptions before switching it off; `packages/catalogue/src/operations.ts:1190` switches off a product. This asymmetry is a recommendation, not a consequence of A261’s history-retention sentence. Past sent work keeps its recorded destination; a re-added zone needs routing configured again.
8. **Default permission and repair state:** recommend rendering All categories × Every zone read-only, with a localized explanation, for a routing manager lacking `venue.configure`. Only that permission exposes Make default choices. If no active default exists, show a repair message; an authorized user can choose an active station, while other users see the same read-only explanation. Do not silently create a default or expand permissions.

## Contracts to introduce

Keep these browser-safe in `routing-types.ts`, re-exported through `./routing`. IDs on the wire are validated canonical UUIDs; an unknown/variant subject is refused, never silently rewritten on a write. Normalize caller spellings for service reads as today.

```ts
type RoutingRow =
  | { kind: "all" }
  | { kind: "category"; categoryId: string }
  | { kind: "product"; productId: string };
type CellAddress = { row: RoutingRow; zoneId: string | null }; // null: Every zone
type RoutingCell = CellAddress & { target: RouteTarget };
type RoutingChange = { kind: "cell"; address: CellAddress; target: RouteTarget | null };
// target:null clears the record; {kind:'no_preparation'} is an explicit saved value.
type RoutingDecision = { kind: "cell"; address: CellAddress } | { kind: "default" };
type SelectedCell = { target: RouteTarget | null; decidedBy: RoutingDecision | null };
type GridProduct = { id: string; name: string; categoryId: string | null };
type GridCategory = { id: string; name: string; parentId: string | null };
type GridRow = {
  row: RoutingRow;
  name: string;
  path: string[];
  depth: number;
  hiddenProducts: number;
  hiddenCategories: number;
};
```

type RoutingSelectionRules = Pick<RoutingRules,

## Storage, reset and migration gates

CHECKs forbid simultaneous category/product and the implicit all/null coordinate; target CHECK permits only `(station_id IS NOT NULL AND no_preparation = 0)` or `(station_id IS NULL AND no_preparation = 1)`. Use db column vocabulary. A missing record means unset; no row with a null target is stored.

**Uniqueness recommendation requiring approval:** five partial unique indexes, one per stored row-kind × column-kind: category/product Every zone on `(location_id, subject_id)`, category/product zone on `(location_id, subject_id, zone_id)`, All categories zone on `(location_id, zone_id)`. Each predicate selects its row kind and null/non-null zone class. The sixth all/Every-zone class is forbidden by CHECK, not indexed. Do not rely on a nullable composite unique index, which permits duplicate null coordinates. Use targeted update/insert by validated address, under the caller's transaction; concurrent saves must leave one cell. Avoid an expression-index sentinel and its rebuild trap.

**Words used in this plan.**
- The **outbox** is the Veri\*Factu module's queue of records waiting to reach AEAT: one `envios`
  row per record (`packages/fiscal-verifactu/src/schema/envios.ts`), sent by the **drain**
  (`packages/fiscal-verifactu/src/drain.ts`).
- A **pass** is one run of the drain; the **loop** is the server's background loop that runs a pass,
  then sleeps until the next one is due (`apps/server/src/loop.ts:54-92`).
- The **back-off** is the wait a record is given after a send that did not land, before it is tried
  again: its own `proximo_intento_en`, one minute after the first failure, doubling, at most an hour
  (`backoffMs`, `drain.ts:74-80`). This is what the design calls the "network back-off".
- **AEAT's wait** is the pause AEAT asks for between two sends (Orden HAC/1177/2024 art. 16.2, its
  `t`, sixty seconds until AEAT says otherwise), held in the one-row `envio_flujo` table as
  `proximo_envio_en` (`schema/envio-flujo.ts`). By the same article a **full batch** (1,000
  records, `MAX_REGISTROS_POR_ENVIO`) may go without waiting for it.
- A **held chain** is a chain whose next record the drain stopped sending after the records before
  it were refused three times with one code (`SAME_CODE_REFUSAL_LIMIT`, `drain.ts:62`): that record
  and those after it are `detenido`, and the first is tried again only hourly (`claimProbes`,
  `drain.ts:992-1031`).
- A **seat** is a member of a module contract through which the server reaches a module without
  naming it: here the fiscal contract (`FiscalContribution`,
  `packages/fiscal/src/contribution.ts:110-161`) and the module route seat (`ModuleRoutes`,
  `packages/module/src/module.ts:94-97`).
- The **page** is the dashboard's Box status page (`apps/dashboard/src/screens/box-status-screen.ts`);
  the **Hacienda row** is its "Tax agency" / "Hacienda" row (`box_status.part.tax`).

**Goal:** on the Box status page a manager with `system.manage` sees when the box last saved an
acceptance from AEAT and, while records wait after a failed send, can press **Retry now** /
**Reintentar ahora** so they are tried again at once instead of after their own wait. A press never
lets a send go before AEAT's wait between sends, except a full batch, which AEAT's own rule lets go
at once; and it never releases a chain held after repeated refusals.

**Architecture:** four pieces.
1. **The contracts.** `FiscalContribution` gains an optional `outbox` seat with one function,
   `read` (`packages/fiscal`). The module route seat's context gains an optional `fiscalDrain`
   handle — whether this box files now, and a wake for the loop (`packages/module`).
2. **The module** (`packages/fiscal-verifactu`): `outbox.ts` reads the last acceptance and counts
   the waiting records, and makes them due now; `routes.ts` is its own route,
   `POST /management-api/fiscal-outbox/retry`, mounted through the module route seat; `slot.ts`
   fills the `outbox` seat.
3. **The server** (`apps/server`): a sleep the loop can be woken from (`loop-wake.ts`); boot hands
   the module route its `fiscalDrain` handle and the loop the waker's sleep; the page's read
   (`GET /api/box/health`) carries `outbox`.
4. **The dashboard**: the Hacienda row's detail line and the Retry now button with its help
   tooltip, refusal and answer; the guides in English and Spanish.

**Tech stack:** TypeScript, Hono, `node:sqlite` behind drizzle, Lit, Vitest 4.1.12 (Node for
`packages/*` and `apps/server`; real headless Chromium for `apps/dashboard`).

## Decided departures from the design and from picture 4

1. **The press also wakes the loop.** The design says the press "clears the network back-off … so
   the next pass sends them". M2 shows the next pass can be an hour away, so the press ends the
   loop's sleep as well (decision 5). Without it the button would do nothing visible for up to an
   hour.
2. **It clears the wait after an unreadable answer too, not only after a network failure.** The
   design says "network back-off". The only other back-off is the one `awaitReadableAnswer` sets
   when AEAT answered but the answer for a record could not be read or trusted (M8). Both lead to
   the same resend (M12), the table cannot tell them apart without reading the incidents, and the
   press only makes that resend sooner (decision 3).
3. **The module's own route, through the module route seat, whose context gains a host handle.**
   The design says "It is the Veri\*Factu module's own route". The module route seat exists
   (`ModuleRoutes`, `packages/module/src/module.ts:94-97`; boot mounts every enabled module's routes
   at `boot.ts:2016`, as bookings does, `packages/bookings/src/routes.ts:113`), so the route lives in
   `packages/fiscal-verifactu/src/routes.ts`. Its context has no way to ask whether this box files
   or to wake the loop (`ModuleRouteContext`, `module.ts:81-92`), so it gains an optional
   `fiscalDrain` handle (decision 4): a cross-package change to `packages/module`.
4. **"los envíos fallan desde 17:31" is not drawn, and neither is a next-try time.** The row's
   detail shows the last accepted time only (decision 11). No column says when sends started
   failing. A next-try time was dropped because the earliest wait in the outbox is not when the
   drain next tries (round-1 R2: a later record's earlier wait cannot go before the first record's;
   claim check X1: the loop may sleep past every wait).
5. **Records behind a held record are not counted or cleared** (decision 2). The design is silent;
   M4 shows such a record is held, not sent.
6. **The button is drawn only on a box that files** (decision 10). A demo or prepare box, and a
   pre-production box without test submissions, never run the drain
   (`fiscalDrainEnabled`, `apps/server/src/onboarding-policy.ts:11-16`).
7. **The button can act only while the row shows the unsent-records notice** (decision 12), so a
   healthy box whose latest sale has not gone yet does not offer a retry.

## Decisions this plan makes that the spec does not

Each is a DEFAULT to build; the owner or the plan review may overrule any.

1. **The read is an optional `outbox` seat on `FiscalContribution`, not on `FiscalBackend`.** The
   contribution already carries the submission side — `drain` and `resetInFlight`
   (`contribution.ts:126-131`) — while `FiscalBackend` is the sale-path backend
   (`contribution.ts:123-125`, "it records locally and never contacts an authority"). It also keeps
   this slice out of `packages/fiscal/src/backend.ts`, which PR #2025 changes. Shape:
   ```ts
   /** What the outbox holds, as the Box status page shows it. */
   export interface FiscalOutboxState {
     /** The box's time when it last saved an acceptance from the authority, with or without
      * errors; null if it never has. */
     readonly lastAcceptedAt: string | null;
     /** Records the next tries will try: every unsent record not behind a record held after
      * repeated refusals on its own chain. */
     readonly waiting: number;
   }
   export interface FiscalOutboxSeat {
     /** Select-only; the host calls it in a write-lock turn with no change-log drain. */
     read(tx: Transaction, now: Date): Promise<FiscalOutboxState>;
   }
   // on FiscalContribution:
   readonly outbox?: FiscalOutboxSeat;
   ```
   No word in it is on `packages/fiscal`'s forbidden list (`no-regime-vocabulary.test.ts:55-71`; the
   claim check pasted revision 1's types and the guard passed, and failed on a control word).
   `fiscal-none` fills nothing; the server then reads no outbox.
2. **"Waiting" is every `pendiente` record that is not behind a `detenido` record of its own chain**
   (an earlier `secuencia` on the same `sif_id`). That is the coordinator's ruling 1: the count
   says every unsent record the next tries will try, including the records queued behind a
   backed-off one (M9), which go with it, and records already due that the loop has not yet tried
   (M10, M11). Not counted: `enviando` (being sent), `detenido` and the records behind it (M4),
   `retenido` (set aside for a filing case), and every final state. One SQL fragment,
   `waitingRecords()`, is the set; the read counts it and the press counts it before clearing.
   Known edges, accepted: a record of another deployment environment is counted, though the drain
   refuses it with an incident (`claimBatch`'s guard, `drain.ts:658-683`) — such a record exists
   only after a misconfigured `WAITRON_ENV`; a cancellation waiting for its original is counted,
   though it is tried only after the original is answered (`drain.ts:600-611`); and a record at its
   first claim (`intentos` 0 before the claim) that follows a run of same-code refusals on its chain
   is counted, though the drain holds it at that claim rather than sending it
   (`haltOpenChainClaims`, `sameCodeRunBefore`, `drain.ts:812-819`) — the drain's own rule, and rare.
3. **What the press changes: the future waits inside that set, set to `now`; nothing else.** It
   writes `proximo_intento_en = now.toISOString()` on the records of the set whose
   `proximo_intento_en` is later than `now` — the only per-record back-off there is (M8) — in the
   column's one spelling, as `requeueClaims` does (`drain.ts:515`; CLAUDE.md §3, a time compared as
   text). It leaves `envio_flujo` (AEAT's wait; M3); every row outside the set, including
   `detenido` rows and their `enviado_en`, from which the hourly retry is counted (M4); and, on the
   rows it changes, `intentos`, `incidencia` and `technical_incidence`. Keeping `intentos` means a
   retry that fails again waits as long as before, and keeps `haltOpenChainClaims`'s first-claim
   test (`own.intentos = 1`, `drain.ts:819`) meaning what it means. Keeping `technical_incidence`
   keeps the next send marked as following a technical incident, as art. 16.4 asks (M14). The
   press returns `{ waiting, cleared }`: `waiting` counted before the clear, `cleared` the rows it
   changed. `cleared` is used only by the log line (decision 13).
4. **The module route's context gains `fiscalDrain`.** In `packages/module/src/module.ts`'s
   `ModuleRouteContext`:
   ```ts
   /** The host's fiscal submission loop: whether this box files records now, whether its last pass
    * with work was skipped for a missing tax-agency certificate, and a wake that ends the loop's
    * sleep. Absent on a host that runs no submission loop. */
   fiscalDrain?: { filing(): boolean; awaitingCertificate(): boolean; wake(): void };
   ```
   Optional, so no other module and no existing context builder changes (M13). The Veri\*Factu
   route mounts nothing when it is absent; Task 7's boot test proves boot passes it.
5. **A press wakes the loop; the route never runs a pass itself.** A new `createLoopWaker`
   (`apps/server/src/loop-wake.ts`) gives the fiscal loop its `sleep` and boot's `fiscalDrain` its
   `wake`. A wake ends the sleep under way, or the next one if a pass is running, but never sooner
   than `minTickMs` (5 s by default, `config.ts:135`) after that sleep began, so presses cannot run
   passes back to back. One wake is spent by one sleep; two wakes during one sleep end it once.
   Shutdown still ends any sleep at once. The shape follows the content-suggestion runner's wake
   (`apps/server/src/content-suggestion-runner.ts:182-231`: `AbortSignal.any` over the shutdown and
   a wake signal, and a flag for a wake that arrives while no sleep is under way). Why not run a
   pass in the request: the drain would then have two callers in one process, the request would
   wait on AEAT, and the pass's own containment (`attempt`, `apps/server/src/pass.ts:161-190`)
   would be bypassed. A woken pass also runs the card reconciliation duty early; it runs only what
   is due (`runDue`, `boot.ts:2678-2694`), so this is accepted. **What a press does when the loop is
   asleep past every wait** (M2, M11): it changes no wait, because they have passed, and it ends the
   loop's sleep, so the waiting records are tried at the pass that follows — no sooner than
   `minTickMs` after that sleep began — and not up to an hour later. It does not change when the
   loop sleeps after that pass (Task 14 files that).
6. **The route is `POST /management-api/fiscal-outbox/retry`, `system.manage`, in

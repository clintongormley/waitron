# Automatic remote access on a paired box

**Goal.** After the normal box install or upgrade, pair with Cloud and open the assigned staff address from a phone on mobile data. The **Remote access** switch disconnects it and can bring it back without pairing again. Lane J's BOX-REMOTE-ACCESS-AUTOMATIC queue item records the ask. The trial used a separate Docker bridge and verified the assigned staff address and off/on from a phone. [Trial receipt recorded by Lane K, 18 November 2026.]

**Approach.** Keep the existing signed provisioning, certificate, staff-listener and WireGuard code. Compose starts the key-watching companion at box boot. The companion starts the WireGuard interface and forwarding only when the paired box writes `peer.json`, and removes both, including existing connections, when the off switch removes that file. This is the proposed meaning of starting and stopping remote access. The helper itself waits for the next change. Custom domains, public customer routes, Cloud-side work and expansion of the current pre-production staff admission are outside this change.

## 1. Use the private bridge on the normal install

- [ ] In `scripts/tunnel-container-smoke.sh`, first make the unmodified Compose model fail for its missing default tunnel and private staff bind. Extend the real TCP smoke to use the Compose bridge gateway as upstream, with a host listener bound to that address. Verify the gateway can reach it over WireGuard, the box's ordinary host address cannot connect on 8443, and removing peer configuration closes the held connection and permits reconnection with the same key.
- [ ] In `deploy/compose.yml`, enable the companion by default. Give its dedicated bridge a small reserved subnet and gateway. Use the same gateway for the peer's host alias and the app's `WAITRON_STAFF_HOST` at port 8443. Keep the app on host networking and the peer's existing network permissions and separate key volume. Reuse `deploy/tunnel/peer.sh` and the cloud refresh. Run the smoke and `pnpm exec vitest run scripts/tunnel-container.test.mjs`, then focused server `cloud-tunnel.test.ts` and `boot.staff-name-switch.test.ts`.

## 2. Deliver the companion over the existing image paths

- [ ] First extend `scripts/ci-workflow.test.mjs` and `scripts/waitron-sh.test.mjs` to check companion publication under the normal gate and matching main, release and source-ref image selection. In `.github/workflows/ci.yml`, publish `deploy/tunnel/Dockerfile` beside the app and print-agent, under their SHA, release and guarded main tags. Use the existing licence files in `/app/third-party/system/` and verify them in the image smoke.
- [ ] Add the companion to `deploy/waitron.sh` and `scripts/box/upgrades/host.mjs` via the existing candidate image map. In `scripts/box/upgrades/host.test.mjs`, prove an old optional local tunnel rolls back with its original image, and the new Compose gets the new candidate image even if the old tunnel was absent. Carry the new default image through the offline recipe in `deploy/box/build.sh`, `deploy/box/start-dev.sh` and `bench/box-installer/`. Prove the staged image inventory with the existing installed-start checks. Run the changed root test files and the real Compose smoke.
- [ ] Update `deploy/tunnel/README.md` and the A951-S entries in `docs/backlog.md` and `docs/backlog/replication-cloud.md`. Book the pre-production box with Lane K after a candidate exists. Use the ordinary upgrade with the current venue preserved. On mobile data, open the assigned Staff address, switch access off and verify it closes, then turn it on and open it again. Record the candidate SHA, local dashboard check and the phone result before landing.

**Expected size.** About 160–230 deployment lines, 120–170 test and smoke lines, and 25 documentation lines. A production-eligible pair or a physically stopped helper would need a separate decision.

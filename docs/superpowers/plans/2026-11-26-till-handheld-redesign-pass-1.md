## PR 1. Find and switch bills from the bottom of the screen

On a narrow till or handheld, tap the bill at the top of an open table to see a full-width list rising from the bottom. Scroll to any bill or **+ New bill**, even in a short landscape window. The closed selector shows the bill, its balance or status, and its position among the visible bills. This ships on the current table screen using the approved dropdown in picture `j` (middle and right).

1. **Place the list.** In `packages/ui/src/components/wt-row-actions.ts`, add a reflected `bottomSheet` Boolean (`bottom-sheet`, default `false`). Reuse the native popover and its selection, Escape, outside dismissal and focus handling. Pin the sheet to the visible bottom edge, with a scrim, token styling, safe-area padding and internal scrolling. Use the keyboard inset tokens and respect reduced motion. Clear inline anchor offsets and height when docking and reposition when the property changes. In `apps/till/src/screens/till-table-order-screen.ts`, use `MediaQueryController` with `(width < 800px)` and pass its match to `billSwitcher` as `bottomSheet` through the shared render for both table mounts. At 800 px and above, use the existing anchored menu.
2. **Keep one bill list and one way to switch.** In `apps/till/src/screens/table-bill-controls.ts`, give the menu a visible, localized heading using the table display name already on `party`. Keep `shownBills`, `billRowContent`, the checked row, unsent marks and `newBillBusy`. Show `Bill 1 · €73.20 · 1 of 4` for several bills using the one-based position in `shownBills`. After Bill 2 leaves, Bill 3 is `2 of 2`. Keep the bill name when set, the short single-bill label, and the existing Paid, Deferred payment, left-unpaid and overpaid wording. Put EN/ES strings in `apps/till/src/i18n/strings.ts`. Keep the `#leavingActions` callbacks that send `switch-bill` and `new-bill`. `TillApp.#switchToBill` already waits for the draft save and verifies the visit before changing bills.
3. **Pin the behavior before changing it.** Add the placement and label assertions first and watch them fail on the anchored list and old label. Run the named browser suites after the change.

## Where the app already draws the boundaries

- **Tabs and home.** `apps/till/src/built-in-screens.ts` feeds the shell and `TillApp` home, URL resolution, tab events and table opens. `packages/venue-service/src/device-zone-selection.ts` intersects the saved device choices with current profile zones and returns a usable start. The client `state/device-zones.ts` currently puts every selected handheld zone on Floor. `#enterSignedIn` can read default profile offers, which may be for the table's zone or outside the saved subset. Before enabling Counter, select the effective counter zone explicitly and verify both sale modes, a saved table start, a saved counter start, an unsaved handheld URL or first Floor zone, a failed read, and a profile change. Keep default or failed scope from opening an unrestricted Counter. Check existing handheld Floor access to tables in counter zones before moving those entries. `till-app-device-zones.test.ts` pins the current behavior.
- **Visibility, permission and work in flight.** `TillApp.#affordances` and `#allowsDestination` gate staff destinations. Station also has a till demo/prepare exception today. `#kitchenBody` gates the dedicated display with `act-as-kds` and that display uses device-authorized routes. Keep its boot and session flow separate. Selling and payment still use the server's profile, person and zone checks (`apps/server/src/device-session.ts`, `till-api.profile-actions.test.ts`, `till-api.profile-zones.test.ts`). Follow `#onTabSelect` and `#requestLeave` for draft flush and browser Back. `#reconcileSavedDeviceZones` defers applying a scope that would displace work in progress, and `#deviceZoneAllows` checks new picks against the pending scope. Keep visit and session checks, stale-read protection, and the live connection and polling fallback in `till-app-live-connection.test.ts`.
- **Work queues.** The singular `till-tab=order` on a handheld represents one open table and has no table ID to restore on reload. `state/bar-tables.ts` already finds the signed-in person's unsent tables from floor data. Parked and Waiting use `#loadList` and existing Counter retrieval and collection handlers. The initial reads and shell entry points are currently till-only. Transfers has its own `DepartmentTransferMonitor`, payment permission and session checks. Keep those reads and actions through their existing entry points until their replacements work. The table screen's current-order groups and the kitchen boards serve different work.
- **Tips today.** `TillApp.#applyVenueSetup` reads `tipsEnabled`. `widgets/bill-pay-dialog.ts` already sends `addedTip` for card and previews cash change with none, some or all left as a tip. `widgets/tender-pay.ts` already accepts an entered tip for a connected-reader counter sale. Presented bills go through `#onPresentedPay` and `#payPresentedOnReader` with a separate whole-payment flow that carries no guest tip choice today. `packages/orders-sales/src/bill-allocation.ts` computes bill, tip and cash change separately and detects a changed allocation before taking payment. Use those paths when adding the guest question and prove the presented and cash paths explicitly. A793's attribution, distribution, reporting and payroll remain open.

### Decisions to carry into those plans

- **Orders.** The recommended bridge is a distinct `orders` destination for signed-in staff, including profiles with no selling tab. Link to the four existing work areas with their current access checks. This delivers the entry point now and leaves §9's unified list design open. Keeping the existing queue buttons until pass 2 would preserve today's access but postpone the approved Orders entry. A unified list now would require new row, ordering, refresh and transfer decisions that §9 reserves. Reusing `order` would collide with the open-table route and its Back and reload behavior. Keep the dedicated KDS path separate from this staff tab map.
- **Counter and home.** The spec says Counter has no Send step before paying, while selected counter zones can be `ticket_then_pay`. The plan keeps that configured flow and its Waiting queue. The switch from an unsaved handheld's Floor home to a profile start, and the eventual home for tables currently shown in counter zones, deserve explicit treatment in PR 2. Keep today's Floor fallback and table reachability until each has a working destination.
- **Payments.** The drawer rule needs reconciliation. §§7.5 and 7.8 say a phone opens no drawer, yet the server checks the profile's `open-cash-drawer` and §7.3 includes a permitted drawer selector. Keep today's authority while the visual work proceeds. For §7.1, check the existing printed-bill projection for customer snapshots. The staff-facing `TabLine.name` in `api/kitchen-api.ts` cannot supply them. Use distinct staff, customer and kitchen fixture names. Confirm the drawn percentages as fixed first-pass copy or settle different values in that slice. Keep custom totals exact to cents, apply a tip once, and clear or recheck it on bill, balance, tender or payment-way changes. Pay special attention to presented bills, splits and Other card machine, where existing tender paths differ. A793's sharing rules and venue-configurable percentages stay open.

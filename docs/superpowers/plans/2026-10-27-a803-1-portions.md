- **D1** Table-service writers only; walk-ups, `openTab` with lines and parked counter orders are

- **D2** A portion is allocated when a working line is written, never at draft save; draft lines
  keep a quantity (`orderDraftLines.quantity`, `apps/server/src/order-drafts.ts:1753`). A lost-send
  replay writes no line, so it allocates nothing. **One exception:** raising a recalled line writes
  working lines at draft save today (`apps/server/src/draft-recall.ts:129-149`), so the added
  portions are written there too (D6, Task 16).
- **D3** Expansion splits the priced rows before they are inserted (a pure `expandPortionRows`),
  then `registerPortions` writes the registry and bindings in the same transaction. This departs
  from the master plan's proposed `expandPortions(tx, orderId, lines, soldByUnitLineIds)`, which
  splits inserted lines: before the insert no ticket item, context or allergy tick exists yet, and

- **D4** The first portion keeps the priced row's id, so `priceOrderLines`' identities
  (`working-order.ts:1044-1049`) stay real line ids for `issuancePass`
  (`apps/server/src/issuance-pass.ts:30-35`, contexts by line id).
- **D5** Only dish lines are bound. An extra belongs to its dish's portion through
  `parent_line_id`; bindings are unique by line and by portion.
- **D6** A pricing cohort is the set of portions expanded from one priced request line. A rise
  that today raises the stored row in place (`applyLineEdits` action `"free"`,
  `working-order.ts:5976-5987`; `saveRecalledLine`, `draft-recall.ts:129-149`) adds portions to the
  same cohort, copying the stored row, so the filed row equals today's raised row. A rise that
  today inserts a separately priced row (`"raise"`, `"change"`, adjusted lines,
  `working-order.ts:5720-5722, 5750-5771`) starts a new cohort. Whether a rise expands follows the
  **line**: a bound line always rises by new portions, whichever order it is on (D30).
- **D7** Readers group bound dish lines by cohort plus every `LockedLine` field except `quantity`
  and `parentLineNo`, plus product id, classification and list price; their extras must be equal

  position; its identity id is that member's line id, and it carries every member's line id and
  portion id.

- **D31 — the till names the row; the server never widens one line into its row** (owner answer
  of 2026-10-28, finding 6). A "row" here means what the till shows as one "3 × Croquetas" line:
  identical portions grouped by `state/portion-groups.ts` (Task 10). An adjustment request and a
  cancel-item request may carry `lineIds`: every portion line of that row (2 or more, distinct,
  `lineId` among them), plus the optional whole `quantity` they already take, which now counts
  portions ("cancel 2 of the 3"). A request with `lineId` alone keeps meaning exactly that one line
  — one portion once Task 26 lands — as it does today; nothing on the server looks for a line's
  siblings. Why the till names them rather than the server finding them: only the till knows what
  it drew as one row. Its key (kitchen state, served, cancelled, paid, release group, made-here,
  late mark…) is not the filing key (D7, which adds the ordering cohort), so a server that widened
  `lineId` to "its identical portions" could comp a served portion the waiter saw on another row, or
  miss half of a row that spans two sends. Naming members is also what Tasks 11 and 12 already do
  (serve, Transfer items, Split bill, the kitchen's grouped tap), and slice 4's picker can then
  send *some* portions by naming only those, with no new field. The server checks the members:
  each is a top-level dish line of this bill bound to a whole, unmeasured portion — or, D34, an
  extra line whose dish is one. **Unbound lines are never members** (third version, after the
  round-3 claim check's I2 and I3, reversing the second version's acceptance of unbound one-unit
  lines): the till groups only bound portions — the server's line read gains a `portion` fact and
  the till's `wholePortion` (`apps/till/src/state/portion-groups.ts:36-42`), which today does not
  look at bindings, requires it (Task 25d). Why the conservative choice: unbound one-unit lines
  (a counter order's lines moved to a table, or lines written before the release) have no cohort,
  so D33's approval history and D7's filing group have nothing to hold them together, and a
  discount spread over several of them files one row per line, each with its own VAT base — the
  round-3 check ran the real `baseFromGross` at 10%: 10% off three €12.00 lines filed apart gives
  base 29.46 against 29.45 for one line of three. Kept apart, as today, each is shown and acted on
  alone and its money is exactly today's; all share D7's grouping key **without** the cohort
  (product, names, variant, options, note, course, unit and list price — equal list and price read
  as none, as Task 3's fix does — and the same extras), read by comparing the groups
  `readLockedLines` forms for them, as Task 6 does (review M7: no second copy of the key); and none
  is held by another device's draft (the recalled-draft check `planAdjustment` already runs,
  `adjustments-apply.ts:650-675`, over every member rather than the one line). Anything else is
  refused `management.request_invalid` with `field: "lineIds"` (an existing code and wording: no
  new Spanish string). Only a fault in Waitron reaches those refusals — the till sends only rows it
  grouped — so each says so in a one-line comment at its site (CLAUDE.md §3: a refusal that only a
  bug can produce is identified at the site as a fault in Waitron). The server does not check
  kitchen or service state across members: the till's row already holds one state. **One
  deliberate exception** (review M3): Discard of a draft (Task 25b-2) groups the recalled portions
  of one row on the server, because it names no row — it cancels everything the draft holds.
- **D32 — a row acts exactly as today's one line of the same count.** The server builds one
